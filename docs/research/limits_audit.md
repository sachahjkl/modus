# Audit of the limits of modus

This audit lists the capacities, bounds and limits of the sources (`src/`, `tools/modustool`) and puts each one in one class. The goal is a system for real use: a limit that refuses a legitimate real use is a defect to fix now.

The rules that decide the classes:

- [`docs/PROPERTIES.md`](../PROPERTIES.md), "14. Memory is supplied by the caller": data with no known bound is held in arenas of the budget, and a refused growth is `No_Budget`, a value.
- [`docs/PROPERTIES.md`](../PROPERTIES.md), "20. No ambient access: the other holes to close", line 16: each resource is a handle with a limit, and a process divides its limit among its children. A limit is a budget that a parent or the principal sets, not a constant.
- [`docs/PROPERTIES.md`](../PROPERTIES.md), "22. General mechanisms, and a plain expression for each frequent task": no frequent task needs knowledge of a number of the implementation.
- [`docs/PROPERTIES.md`](../PROPERTIES.md), "13. Data-oriented kernel internals": kernel tables have a fixed size, and "a table that grows needs a reserve of address space".
- [`src/md/features/memory_without_a_bound.md`](../../src/md/features/memory_without_a_bound.md): the growable arena exists (`system.arena_*`).

## The classes

| Class | Meaning | Verdict |
|---|---|---|
| A | Contract layout: a record size, a ring entry, a wire field, a value fixed by an outside standard (QUIC, TLS, virtio, UEFI, ELF, Unicode) | Keep |
| B | Protection of memory or time for one unit of work: a frame, a head, a hang bound, a call region, a step | Keep, because the whole passes in pieces |
| B-flag | A unit bound where the whole cannot pass in pieces | A defect, as C |
| C | An arbitrary cap that refuses a legitimate real use | A defect |
| D | A budget that the principal or the plan sets | Keep when it is set there |
| D-const | A budget written as a constant in the code | A defect |
| Done | A defect that is fixed: the column Fix gives its new bound | Fixed |

## Method

- A grep of the sources found 2 497 named constants with a name of a limit (`*_CAPACITY`, `*_LIMIT`, `MAX_*`, `*_BYTES`, `*_COUNT`, `*_SIZE`), and about 550 more with `*_MOST`, `*_PAGES`, `*_LEAST` and `MAX_*` forms. Test files and fuzz targets are out, except where a limit exists only there.
- The constants of a pure layout (offsets, record sizes, magic numbers, key and hash sizes of cryptography) are class A. The tables group them by file.
- For each other limit, the audit read the code around it: what the limit bounds, and whether a larger whole passes in pieces (a page of a list, ranges of an object, a second call, a stream).
- The impact score is 1 to 5. A score of 5 means that a person or a program hits the limit on the first day of normal use.
- The demonstrations (`src/modules/demonstrations`) show one property each. Their limits are listed only when a real use depends on them (the browser, paint, the notes).

## The order of the fixes

Each batch adds one capability to a system that works, and each batch ends with its machine test. The order follows the dependencies: the arenas of a process need a budget past 64 MiB, and each saved size needs storage that holds it.

1. **Storage that grows with its disk.** The storage service reads the size of the block device and uses all of it; its free map pages. The stores of a disk are a B+ tree of their own, not 60 cells of the root block. A name of an entry has up to 255 bytes, as in the other file systems, with a key of variable length in a node. The store `module_files` and the store of a disk process get a quota from the plan of the principal, not 16 MiB. Defects 1, 8, 9 and the store part of 10. One format change; no migration (nothing is kept for compatibility before 1.0).
2. **Memory and process counts from budgets.** The plan of the principal and the machine memory set the largest budget; the table `budget_exceptions` leaves the code and becomes rows of the plan. The kernel sizes its process, memory object, thread and budget tables at the start from the memory of the machine, in a reserve of addresses that grows (property 13). The per-process tables (handles, mappings, threads, waited words, module records) grow in pages that the budget of the process pays (property 14). The root service, the compositor and the start list hold their tables in arenas. Defects 2, 3 and 18, and the module part of 10.
3. **Text with no size.** The text model becomes a piece table in an arena; it reads and writes the object by ranges, which the storage service already serves (`docs/STORAGE.md`, "Ranges"). The line editor grows in an arena: a line of the console has the size of its text, and the parser reads it whole (the declaration parser already reads 64 KiB). The history is an object that grows by ranges. The clipboard gives a memory object of the size of the content at a paste. The assistant keeps its conversation in an arena and its requests and replies in text models. The evaluation of Lex takes its calls, list items and hashes from an arena of the line. Defects 4, 5, 6, 14 and 16.
4. **Every character.** The glyph cache keys by code point (the Swiss table of `modus:hash_table` exists), and the outline of a character comes from its font at its first use. The fallback chain gets General Punctuation, the arrows, the common symbols and Latin Extended-B. A script with no font in the image shows the replacement glyph only because its font is absent, not because of the size of a table. Defect 7.
5. **Lists that page.** One cursor form for each list that crosses a border. The document picker and the powerbox read pages of the storage service with a search. A content tree is a tree of tree nodes (as the trees of git), so a folder has any count of entries. The history of a store pages its snapshots. The store exchange between machines sends pages of entries and streams each object in frames, as the object cache does after its fix. The palette pages its candidates. A table of the console scrolls over its records. Defects 11, 12 and 15.
6. **Programs of any size.** The root service reads a module file by ranges into an object that the budget pays. The C compiler, the assembler and a project bundle read their sources into an arena. Recipes keep their objects in the store and move them through the object cache. The rest of defect 10 and the rows of the recipes.
7. **Remote and network.** The connection and client tables of the remote services are budgets. The screen of a viewer is the screen in force, sent in the screen pieces that exist. The network service holds its endpoints in a table of its budget and reads its prefix from the network. TCP gets window scaling (RFC 7323). Defect 13 and the rows of the network.
8. **Pictures, guests and the browser.** Paint holds a picture in tiles of an arena. Image decode checks the pixels against a budget, not each side against 4 096. A surface is bounded by the screen. A guest gets its memory, its processors and its disk from the plan, and its disk image streams. The browser builds its DOM in an arena, as [`src/md/features/memory_without_a_bound.md`](../../src/md/features/memory_without_a_bound.md) already designs. Defects 19, 20 and the browser.

Batches 4 and 8 depend on no other batch. They can run in parallel with batch 1.

- [`src/md/features/memory_without_a_bound.md`](../../src/md/features/memory_without_a_bound.md), "The decision points": "The largest budget of the root service is 16384 pages (64 MiB)". Batch 2 decides it.
