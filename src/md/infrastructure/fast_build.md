# Fast iteration build and test mode

A fast iteration workflow compiles only the modules needed by the requested boot volume without full optimization, reuses unchanged module outputs across worktrees from an opt-in content-addressed host cache, and skips screenshot captures when iterating on machine scenarios, while keeping full optimization, full module builds, clean reproducibility checks and full screenshot verification for default builds, checks, measures and releases.

## Purpose

While iterating on a bug or a machine test, compiling all 179 modules with `-o:speed` and `llc -O3`, building all 28 boot volumes, rebuilding identical modules across worktrees or branch switches, and capturing dozens of QMP screenshots slows every edit-test cycle. A developer who works on one part of the system needs a fast loop that keeps the same module contract, sound content-addressed caching and clean shipping builds.

## Constraints

- Every shipping build (`build`, `test`, `check`, `screenshots`, `measure`, `release`, `ship`, and `nix flake check`) must continue to use `-o:speed` and `llc -O3`, build all modules and all required boot volumes, run without the shared host cache, and capture all scenario screenshots.
- Switching between fast iteration mode and default speed mode must never mix outputs of one mode with outputs of the other.
- Every module of a fast iteration build must still obey the module contract: no thread-local storage, no undeclared external symbols, valid log fact tables and valid library segments.
- The kernel must keep fixed-size stack frames that pass `kernel_stack_check` and `kernel_has_no_vector_instruction`, and stay within the 16-page kernel stack and 2-page interrupt stacks ([kernel_stack_depth.md](kernel_stack_depth.md)).
- The boot program must link cleanly with `lld-link /nodefaultlib` without undefined symbols.
- The shared host cache must be safe under concurrent processes across worktrees, must verify every restored file against its recorded BLAKE3 hash before use, and must treat any missing, malformed or corrupt cache entry as a cache miss rather than failing a build.

## The chosen form

- **Closed optimization mode enum (`Optimization_Mode`).** `tools/modustool/build/modules.odin` defines `Optimization_Mode :: enum { Speed, None }` with explicit border conversions (`"speed"`, `"none"`). No boolean or integer flag carries optimization state. The mode passes explicitly on the command line of every `module` and `volume` child process, and every command that checks, repeats, measures or ships forces `.Speed`.
- **User modules in `.None` mode (`--fast`).** A non-kernel, non-library module compiles with `odin build -o:none -use-single-module -no-thread-local`, runs `opt -O1 -S` on the single LLVM IR file before `facts_reached`, and runs `llc -O1` to emit the object.
  - `-use-single-module` keeps one LLVM IR file per module: Odin defaults to `-use-separate-modules` under `-o:none`.
  - `-no-thread-local` prevents `base:runtime`'s uncalled `default_random_generator_proc` from emitting `@thread_local` (`__tls_get_addr`) in unoptimized IR; modus modules never use thread-local storage.
  - `opt -O1 -S` performs light interprocedural constant propagation and dead-code elimination so dead calls into `text_rendering` foreign imports (from `bootscreen` in modules such as `root` that do not import `text_rendering`) and unreached support-package `log_fact` immediates are removed before `facts_reached` and `ld.lld`.
  - `llc -O1` performs stack slot coloring over the `alloca`s inlined by `opt -O1`: measured on `root::root_loop_pass`, `llc -O0` emitted a 169,608-byte stack frame that overflowed the 256 KiB (`STACK_PAGES = 64`) stack at boot, whereas `llc -O1` shrinks `root::root_loop_pass` to 13,304 bytes in 12.7 s.
- **The kernel and library modules always compile with `.Speed`.** `module_effective_optimization` returns `.Speed` for any row with `build.kernel == true` or `build.library == true`. Measured on `src/modulus`: under `-o:none` and `llc -O0`, LLVM emits dynamic stack alignment (`andq $-0x40, %rsp`) and frame-pointer restores (`movq %rbp, %rsp`) that `kernel_stack_check` refuses, and unoptimized frames risk exceeding the fixed 16-page kernel stack and 2-page interrupt stacks. Measured on `text_rendering` and `drawing`: under `-o:none`, Odin retains read-only relocation tables (relro rebases) that library modules cannot carry because each importer maps the shared library at a different address. Only three modules are kernels and three are library modules, and incremental builds keep them unchanged whenever their sources do not change.
- **The boot program always compiles with `.Speed`.** `src/boot` compiles directly with `odin build -target:freestanding_amd64_win64 -build-mode:obj` and links with `lld-link /nodefaultlib`, with no separate `opt` pass. Measured on `src/boot`: under both `-o:none` and `-o:minimal`, uneliminated dead branches in `bootscreen` -> `text_rendering` leave undefined references (`line_shape`, `line_widths`, `line_fit`, `glyph_find`) that fail `lld-link`. Compiling `src/boot` with `-o:speed` takes about 2.5 s once for a single volume; skipping the other 27 boot volumes saves over a minute.
- **Explicit optimization mode in every build record.** `Build_Record` (`build record, form 2`) stores an `optimization <speed|none>` line alongside `key`, `output`, `source` and `load`, and the optimization mode and exact `odin`, `opt` and `llc` commands are also hashed in `Build_Key_Inputs`. A record whose `optimization` line is absent, malformed or different from the requested mode is refused (`"the optimization mode changed"`), forcing a clean rebuild.
- **Shared content-addressed host module build cache (`MODUS_BUILD_CACHE` / `--cache <dir>`).** `tools/modustool/build/module_cache.odin` stores finished module artifacts across worktrees and branch switches under `<cache_dir>`:
  - All repository paths inside `Build_Key_Inputs` are canonicalized relative to the repository root while external Nix store paths stay absolute, so two worktrees at different host paths compute the exact same BLAKE3 keys.
  - `manifests/<base_key_hex>/<manifest_hash_hex>.manifest` records canonical `(source_files, load_files)` lists for each pre-compile base key (module name, tool identity, host programs, flags, optimization mode and assembly files), allowing a fresh worktree with an empty `build/` folder to discover candidate dependency lists without invoking Odin. Multiple manifests under one base key coexist across branches.
  - `entries/<module_key_hex>/` stores the deterministic conversion outputs (`module.bin`, `sources.list`, `reached_facts.list`, `module.debug` when debug information is enabled, and `kernel_stack.measure` for kernels) keyed by the combined canonical compile key and conversion inputs (including current hashes of imported and child `.module` files and `start_grant_sets.odin`), followed by `build.record` written last via unique temp file and atomic rename.
  - On restore, the tool reads every cached output file into memory, verifies its BLAKE3 hash against `build.record`, and writes it to `build/modules/` via temp file and atomic rename (skipping the write when the destination file already matches the verified hash). Any missing, unreadable or hash-mismatched entry is treated as a cache miss.
  - Cache writes run only when `build_key(..., inputs_must_be_unchanged = true)` succeeds, so files modified during the build never enter the shared cache.
  - `build whole`, `modustool check`, `modustool repeat`, `modustool release`, and `modustool ship` always disable the shared cache (ignoring `MODUS_BUILD_CACHE`); passing `--cache` explicitly with `build whole` or `test <part> from <folder>` is refused.
- **Minimal per-volume module filtering in `--fast`.** `tools/modustool/build/volume_modules.odin` computes `modules_needed_for_volumes`: when `modustool build --fast <volume>` or `modustool test --fast <part>` requests specific boot volume(s), the build compiles only the modules belonging to those volume(s)' boot images, their kernels, their transitive `imports` and `children`, and any part-declared extra modules (such as disk modules for `disk_processes` and `start_policy`).
  - Only the boot images referenced by the requested volume(s) are encoded. Direct builders for `BOOT_IMAGE_CONSOLE` (13 console modules plus transitive imports and `kernel`) and `BOOT_IMAGE_RELEASE` (shipped modules only, zero test modules) produce byte-for-byte identical boot images without building `BOOT_IMAGE` or unused test modules.
  - Post-build consumers (`debug_image_write`, `fact_catalog_of_build`, `kernel_test_texts_check`, `library_modules_measure_print`, `build_manual_pages`) respect the active module filter. Default `build`, `build whole`, `test` without `--fast`, `check`, `repeat`, `release`, `ship`, and `nix flake check` leave the filter unset and build all modules and all boot images.
- **Optional screenshot skip (`--no-shots`) on `modustool test`.** `modustool test [--fast] [--no-shots] [--cache <dir>] [<part> ...]` sets `skip_shots = true` on `Test_Part_Run`. During `.Shot` steps, `picture_name_claim` still runs to catch duplicate screenshot names, while QMP `screendump`, screen settle waits and PNG encoding are skipped. `--no-shots` is refused with `from <folder>` and is never enabled by default `modustool test`, `modustool check`, `modustool screenshots` or `nix flake check`.
- **Single-volume and single-part commands.**
  - `modustool build [whole] [--fast] [--cache <dir>] [volume_name] [host_processes]` builds all boot volumes when no volume name is given, or only the named boot volume (for example `modustool build --fast console` or `modustool build --fast main`), skipping the other 27 volumes. Unknown volume names, unknown flags and invalid flag combinations are refused before any build starts.
  - `modustool test [--fast] [--no-shots] [--cache <dir>] [--snapshot <dir>] <part> [steps ...]` builds only the boot volumes declared for `<part>` and runs `<part>`. `test --fast` requires a part name, and `--fast`, `--no-shots`, `--cache` and `--snapshot` are refused with `from <folder>` (which takes positional `snapshot <dir>`).
  - `modustool film [--fast] [<name>]` compiles user modules in `.None` mode and filters to the main boot volume's modules when `--fast` is passed (before or after `<name>`), keeping `-o:speed` when `--fast` is omitted.
- **Usable-boot QMP VM snapshot (`bootSnapshot`) and 10 parallel `main_*` shard derivations.**
  - `tools/modustool/machine/main_shards.odin` partitions `main_scenario.odin` by exact unique markers into 10 balanced logical shards (`main_console_and_desktop` through `main_settings_editor_and_builders`), keeps the shared `MAIN_BOOT_PRELUDE` in the core tool (verified step-for-step against `scenario[:prelude_end]` by host test), and pairs each shard with minimal self-contained setup steps so every shard passes `scenario_check_before_start` independently and covers all screenshots with zero duplicates.
  - `modustool boot-snapshot <target> [from <test-inputs>]` (`tools/modustool/machine/qmp_snapshot.odin`) converts `OVMF_VARS` and creates sparse `qcow2` images for the data and scratch disks, attaches the boot volume read-only, boots through `MAIN_BOOT_PRELUDE`, pauses the guest, saves a QMP internal snapshot (`savevm usable_boot-<16-hex>`), quits QEMU with zero post-snapshot guest execution, and writes `ovmf_vars.qcow2`, `data_disk.qcow2`, `scratch_disk.qcow2`, `boot_log.txt`, and `snapshot.meta` (tag, full 64-hex BLAKE3 boot-image hash, `guest_clock_unix`, and `prelude_steps`).
  - `flake.nix` builds `bootSnapshotToolBinary` from `toolCoreSources` alone (so scenario edits never invalidate `bootSnapshot`), builds `bootSnapshot` once per `testInputs`, and invokes `modustool test <part> from ${testInputs} snapshot ${bootSnapshot}` for all 10 `main_*` shard derivations. Each restoring shard validates `snapshot.meta` against `build/boot.image`, stages writable `qcow2` copies, seeds its serial log from `boot_log.txt` with QEMU `-chardev file,...,append=on`, starts QEMU paused (`-S`), runs QMP `loadvm` and `cont`, adjusts `clock_offset_seconds` from `guest_clock_unix` (keeping `date_check` valid even across Nix store cache hits days later), skips `MAIN_BOOT_PRELUDE`, and runs its setup, body, and epilogue.
  - `main_console_and_desktop` writes `build/test_output.txt` (preserving boot lines and `log_measures.txt`); the other nine shards write distinct `build/test_output_main_<shard>.txt` logs, and `checks/measure_record.odin` reads `vector_glyphs` from `test_output_main_notes_editor_inspect_and_ui.txt` and `output_wiring` from `test_output_main_log_and_streams.txt`.

## The refused forms

- **Plain `-o:none` and `llc -O0` on all modules without `opt -O1` or `-no-thread-local`.** Refused by measurement: `root` retained `__tls_get_addr` (violating the no-TLS module rule) and undefined `text_rendering` symbols (`glyph_find`, `line_fit`, `line_shape`, `line_widths`), and `kernel` emitted `andq $-0x40, %rsp` and `movq %rbp, %rsp` that `kernel_stack_check` refuses.
- **`-o:none` or `-o:minimal` on `src/boot`.** Refused by measurement: `lld-link /nodefaultlib` fails with undefined `text_rendering` symbols (`line_shape`, `line_widths`, `line_fit`, `glyph_find`).
- **Separate build folders (`build/fast/`) for fast builds.** A second folder duplicates every module, boot image and 64 MiB boot volume on disk and complicates commands that read `build/`. Recording `optimization` in the build record keeps one build folder and guarantees clean invalidation when switching modes.
- **Caching `linked.elf` across worktrees.** `linked.elf` holds absolute DWARF `DW_AT_comp_dir` paths from the originating worktree, which `debug_source_file_hashes` would fail to open if that worktree was removed. Caching the host-path-free conversion outputs (`.module`, `.debug`, `sources.list`, `reached_facts.list`, `kernel_stack.measure`) avoids stale DWARF paths and keeps the cache compact.
- **Hard-linking cached files directly into `build/modules/`.** Subsequent writes via `os.write_entire_file` truncate files in place (`O_TRUNC`), which would corrupt shared cache entries, and hard-linking creates a TOCTOU window after BLAKE3 verification. Copying the already-verified in-memory bytes via temp file and atomic rename eliminates both failure modes while staying under 1 ms per module.
- **A boolean flag `fast_build := false` instead of `Optimization_Mode`.** A boolean hides a closed choice and does not scale cleanly at the CLI and record borders.
- **Allowing `modustool test --fast` with no part or with `from <folder>`.** Running all test parts in unoptimized mode is not an iteration loop, and `from <folder>` runs no build.
- **Capturing `bootSnapshot` with the whole tool binary or with `snapshot=on` raw boot volumes.** Using the whole tool binary would rebuild `bootSnapshot` and all 10 `main_*` shards on any unrelated scenario edit (breaking `part_cache`); using `snapshot=on` temporary overlays loses the boot-drive snapshot on QEMU exit, whereas `readonly=on` on `boot` keeps `savevm` and `loadvm` self-contained inside the three `qcow2` images.
- **Running `main_*` shards without per-shard setup or keeping monolithic `main` beside the 10 shards.** Later shards depend on processes (`monitor`, `life`, `remote`, `rings`, `time_page`, `threads`, `workers`, `tally`) started in earlier sections, and keeping monolithic `main` beside the shards duplicates every screenshot name and doubles execution time.

## Subtle points

- Kernel modules record their effective mode (`.Speed`) in their build records and cache entries, so switching between `--fast` and default mode rebuilds or restores user modules without recompiling unchanged kernels.
- Boot volumes record the requested `Optimization_Mode` (`.Speed` or `.None`) even though `src/boot` compiles at `-o:speed`, so volume records also invalidate explicitly across mode switches alongside their boot image hashes.
- `modustool check`, `modustool repeat`, `modustool release image`, `modustool screenshots` and `nix flake check` always force `Optimization_Mode.Speed`, disable the shared cache, build all modules, and keep full screenshot verification.
- In `test --fast <part>`, `host_modules` (which validates descriptions of every module) and `release_image` (which compares `BOOT_VOLUME_SECURE_BOOT` against `BOOT_IMAGE`) run without module filtering so their cross-image invariants remain complete.
- Restoring a `bootSnapshot` captured earlier adjusts `machine.clock_offset_seconds` from `snapshot.meta`'s `guest_clock_unix`, so `Date`, `Appearance_Auto`, `Bar_Local_Time`, and `date.now()` checks remain valid even when Nix restores `bootSnapshot` from a prior day's store entry.

## State
