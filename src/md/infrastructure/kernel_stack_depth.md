# The deepest stack of the kernel

Each processor has one kernel stack of 16 pages (`op.KERNEL_STACK_PAGES`), between guard pages. A chain of calls that is deeper than the stack stops the machine at the guard page. The build measures the frame of each procedure of the kernel and the deepest chain of calls from each place where the kernel starts on that stack. It prints the measure at each build, and it fails when less than a named margin stays free. The guide is [`docs/TOOLS.md`](../../../docs/TOOLS.md), "The deepest stack of the kernel".

## Purpose

The source does not show the size of a frame. The compiler inlines procedures into their callers, and a frame holds the locals of every branch that it inlined: `execute` is one large frame. A command with a table of error details runs its operation under two frames of `execute` ([features/kernel_error_details.md](../features/kernel_error_details.md)). Without a measure, the room that is left on the stack is not known, and a change that adds a deep chain is found only when a machine stops at the guard page.

## Constraints

- **The measure reads what the processor runs.** The frames are those of the code that `llc` made, after the inlining, not an estimate from the source.
- **No chain is left out in silence.** A procedure that a chain reaches and whose frame is not known, a call whose target is not known, and a recursion with no stated bound stop the build. A stated rule names each exception, with its reason.
- **The tool only.** No other process reads the kernel: the tool reads the files that the build makes, with the Odin standard library.
- **No cost in the kernel.** The measure changes no byte of the module file of the kernel.

## The chosen form

- **The frame of a compiled procedure.** `llc` writes the section `.stack_sizes` with `-stack-size-section` (the kernel only): for each procedure, its address and the bytes of its frame. The frame holds the saved frame pointer, the saved registers, the locals and the argument area of each call that it makes; it does not hold the return address that its caller pushed. The link keeps the section and writes the address of each procedure in it, so the tool reads it from the linked file. The section is not in a segment: the module file does not change.
- **The frame of a procedure of assembly.** `nasm` writes no frame. The tool has one table of the assembly procedures that compiled code calls (`assembly_frames` of `kernel_stack_rules`, in `tools/modustool/build/kernel_stack.odin`): the bytes that each one pushes, read from its source. A procedure that a chain reaches and that has no frame from `llc` and no row stops the build.
- **The calls.** The tool reads the listing of the linked kernel that the check of the vector instructions already makes (`llvm-objdump -d`). A `call` to the start of a procedure is a call: the frame of the caller and a return address stay under the callee. A jump to the start of another procedure is a tail call: the callee takes the place of the frame of the caller. A jump inside a procedure is not a call. A call to an address where no procedure starts stops the build.
- **The labels of assembly.** A label `procedure.label` of `nasm` is a symbol, so the listing shows it as the start of a procedure. A name with a dot and no frame from `llc`, after a procedure of assembly (no frame from `llc` either), is a label inside that procedure. The name before the dot is not compared with the name of the procedure: the listing gives one name to an address, and it can be another name of the procedure (`memcpy`, whose labels are `copy_bytes_without_overlap.over16`). A compiled procedure with a dot in its name (`kernel::self_test.overflow-11736`) has a frame from `llc`, so it is never a label. Two names at one address are one procedure.
- **The scan of the stack pointer.** The tool follows the stack pointer through each compiled procedure, from its first instruction, along each path of its jumps: a `push` adds 8 bytes, a `pop` removes 8, a `sub` or an `add` of a constant to `%rsp` adds or removes the constant. Where two paths meet, the scan keeps the larger count. A call to a procedure that never returns (no `ret`, no jump through a register, no tail call to a procedure that returns) ends its path, so the pushes before it do not flow into the next block. Inside the body of a procedure the count equals its frame from `llc`, because the prologue pushes the saved registers and subtracts the rest of the frame. The scan gives two facts that the frame does not hold:
  - **A push outside the frame.** `llc` passes the arguments of some calls with `push` instructions just before the call, and removes them with an `add` after it (in the kernel: `execute` pushes 32 bytes before `thread_create`). These bytes are not in the frame from `llc`. The count at a call, less the frame, is the bytes pushed outside the frame, and the edge of that call holds them: they stay under the callee with the frame and the return address.
  - **A jump through a register.** At a count of 0 the frame is gone: the jump is a tail call to a procedure that the listing does not name, and it stops the build unless the table `indirect_calls` names the procedure with its targets. Above 0 it is a branch of a table of a `switch`, inside the procedure: each block after an instruction that ends a path, and that no path reached, is a branch of such a table and starts with the count of the jump.
  The scan also proves its own reading: each `ret` and each tail call must find a count of 0. A `ret` or a tail call with bytes on the stack, a `pop` under the entry, another write of `%rsp` (`mov`, `lea`, `and`), a jump to an address that is in no procedure, and a call that no path reaches each stop the build with the procedure and the instruction. The procedures of assembly are not scanned: the row of each one holds what it pushes, and `stack_switch` jumps through a register to the start of a fresh stack, which is an entry.
- **The indirect calls.** The listing shows a call through a register (`callq *%rax`) with no target. A procedure that a chain reaches and that has an indirect call or an indirect tail call stops the build, unless the table `indirect_calls` names it with the procedures that the call or the jump can reach. The kernel has one row: the self test calls the code of a process, to prove that the processor refuses it. The call reaches no procedure of the kernel: the processor faults at its first instruction. The kernel has no indirect tail call: each of its jumps through a register is a branch of a table.
- **The calls into data.** The self test also calls `test_code`, an array of the kernel data, to prove that the processor refuses to run data. `llc` makes that call direct, to an address where no procedure starts. A row of the table `data_calls` names the caller and the data symbol. The row holds only when the listing names the symbol at no offset and no procedure of the listing has that name.
- **The recursion.** A cycle of calls has no depth. Only a procedure that calls itself, with a row of the table `recursions`, is allowed: the row gives the most levels of it on one chain, and the depth is the levels times the frame and a return address, then the deepest callee. The rows:
  - `execute`: two levels. Its default branch runs the operation of a command with a table of error details once more, and that run has no table bit.
  - `tables_free` of the IOMMU: one call for each level of the tables of a domain, at most `iommu.DOMAIN_TABLE_LEVELS_MOST` (4).
  - `walk` of `mappings_report`: one call for each level of a page table of the processor, `info.PAGE_TABLE_LEVELS` (4).
  - The overflow of the self test calls itself until the guard page, on purpose: its row has no level, and the measure leaves out the calls into it.
- **A cycle break.** A cycle through several procedures that a state of the kernel cuts has a row of the table `cycle_breaks`: a procedure, and a procedure that no chain below it runs. The measure takes the depth of the first with the second left out, and checks that no cycle stays below it. The kernel has three:
  - `lock_order_broken` logs, and the log takes a lock, but `lock_order_broken` calls `fault_report_begin` first. From then the log writes the serial port only and takes no lock (`log_take`), and `machine_stop` takes none. So no chain below `lock_order_broken` runs `lock_take`.
  - `queue_ready` logs only when a thread enters a queue outside its placement (a check of the test build), after `fault_report_begin`. From then `log_record` returns before it wakes the readers of the log. That log is the one way from `queue_ready` to `word_wake`, which can make a thread ready again.
  - `process_stop` marks its process Stopped before it finishes its threads and cleans it up. `thread_finish` stops the process of its thread only while that process is not Stopped, and each thread that `process_stop` and `process_cleanup` finish is of that process. So no chain below `process_stop` runs `process_stop`.
  The listing of the kernel has no other cycle through several procedures. Any new cycle stops the build with its procedures.
- **The entries.** The kernel starts on the kernel stack at these places, each with the bytes that are on the stack before its first instruction (the table `entries`):
  - `kernel_interrupt` from a process (a `syscall`, an interrupt or an exception of a process): the frame of 22 values that the entry pushes from the top, and a return address.
  - `kernel_interrupt` after a return that the processor refused: the fault of the `iretq` of `resume` pushes its frame under the five values of the return, 48 bytes under the top after the alignment to 16 bytes.
  - `first_run`, `schedule_from_the_top` and `processor_entry`: `stack_switch` or the start code pushes a null return address at the top.
  The procedure `entry` runs on the stack of the boot program, not on a kernel stack. Its chains are not measured; what it reaches counts as reached.
- **An interrupt over the kernel.** The kernel runs with interrupts off, except in `idle_wait` and in `interrupt_window`, the window after each byte of the drain of the serial port in the idle loop ([log_side_channels.md](../features/log_side_channels.md)). Both are procedures of assembly with no frame, named in the rules of the measure (`idle_wait` and `interrupt_windows`). So one interrupt of the machine can come over a chain of the kernel: at the deepest chain to either of them, the processor aligns the stack (8 bytes at most), pushes the frame of the interrupt, and runs `kernel_interrupt`. A handler of an interrupt of the kernel returns with no wait, so there is no second level. The measure takes the deepest chain of `kernel_interrupt` as a bound of that handler.
- **The measure and the check.** The measure is the largest of the entries and of the interrupt at the idle wait. The build fails when less than a quarter of the stack stays free (`STACK_LEAST_FREE_PART`): 4 pages of the 16. The measure counts each push and each tail call that the listing shows, so the margin holds only for the bound of the graph: a chain of the graph that no input runs, and a change of the code between two builds. The line names the deepest chain, with the bytes that a caller pushed outside its frame for a call of it.
- **Each procedure is reached.** A compiled procedure that no entry and no `entry` reaches is an entry that the tables do not know (a new procedure of `stack_switch`), or code of the compiler that no code calls. The first stops the build; the second has a row of the table `not_run`, with its reason.
- **Where it runs.** The compile step of each kernel module runs the check after the link, beside the check of the vector instructions, and writes the measure lines in `build/modules/<name>/kernel_stack.measure`, an output of the step. Each build prints them, also for a kept kernel.

## Refused forms

- **The call graph from the relocations of the objects.** A call between two procedures of one section has no relocation (the assembly), and a call through a register has none. The listing shows both, and the build makes it already.
- **The call graph from the LLVM IR.** `llc` adds calls that the IR does not have (the copies of records become calls of `memcpy`), and the IR does not have the frames.
- **The frame from the prologue in the listing.** A prologue has several forms (`push`, `sub`, a probe of the stack); `llc` knows the frame and writes it. The scan of the stack pointer does not replace the frame: it adds only the count above the frame at a call, and it checks itself at each `ret`.
- **A fixed bound for each push sequence.** A bound such as "at most 6 pushed arguments" is a guess that a new call breaks in silence. The scan reads the bytes of each call.
- **A jump through a register always as a branch, or always as a tail call.** The first misses a tail call; the second asks a row for each jump of a table of `switch` in the kernel, more than 20. The count at the jump tells the two apart, because a tail call leaves no frame.
- **The smaller count where two paths meet.** It can hide a push. Two paths of compiled code meet with the same count; where they do not (a call that the scan takes as one that returns), the larger count only makes the bound larger, and a `ret` with bytes on the stack shows the fault.
- **A measure on a machine** (fill the stack with a pattern, read the deepest written byte after a test). It measures the chains that a test runs, not the deepest one, and a machine test is not a build.
- **One kernel stack per thread, or a larger stack, before a measure.** The size of a stack is chosen from a measure, not before it.
- **Every fault of the kernel in the check.** An exception of the kernel stops the machine, so the line prints the bound of a fault over the deepest chain and does not check it. If that report passes the guard page, the processor reports a double fault on its own stack.
- **A sentence in place of a number for the refusal of a register trial.** "Far from the deepest chain" is a claim with no measure. The measure computes that chain (below).

## Subtle points

- **The return address.** The frame of `llc` does not hold the return address that the call pushed: each call on a chain adds 8 bytes. A tail call adds none, and the frame of its caller is gone.
- **The frame pointer.** Every module keeps frame pointers (`--frame-pointer=all`), so no prologue of the kernel is empty: a branch of a table is never at a count of 0, and a jump through a register at 0 is always a tail call.
- **A recursion with pushes.** Each level of a procedure that calls itself adds its frame, the bytes that it pushed for that call, and a return address.
- **Lines of the listing that are not whole instructions.** `llvm-objdump` writes a prefix (`lock`, `rep`) on its own line, at its own address, and a jump can go to that address. The line stays an instruction that moves no stack pointer. A far return (`lretq`, the return of `gdt_load` that loads the code selector) is a return: without it, `gdt_load` would never return, and the scan would read nothing after a call of it. A procedure of assembly can run on into a global label, which the listing shows as the next procedure (`model_specific_register_trial_read` into `model_specific_register_trial_read_instruction`, which holds the `ret`): a procedure whose last instruction that is not padding goes on returns when the next procedure of the listing returns.
- **Shrink wrapping.** `llc` can put the prologue after a first test, so a path returns before any push. The scan follows each path from the first instruction, so that `ret` finds 0 too.
- **The bound is above the real depth.** A chain of the graph can be a chain that no input runs. The deepest chain of `kernel_interrupt` is the bound of each handler, also of a handler of an interrupt of the kernel, which runs a short part of it.
- **A frame that is not fixed.** `llc` writes no frame for a procedure with an `alloca` of a variable size. Such a procedure has no frame from `llc`, so the build stops when a chain reaches it.
- **The interrupt stacks.** The gates of four vectors name an interrupt stack (`src/kernel/processor.odin`): the double fault (4 pages), the debug exception, the non-maskable interrupt and the machine check (2 pages each). The timer and the devices run on the kernel stack. The whole graph of `kernel_interrupt` is not the bound there: its deepest chain is the command path of `execute`, which runs only after an entry from a process, on the kernel stack. On the stacks of the double fault, of the non-maskable interrupt and of the machine check, `kernel_interrupt` stops the machine, from a process or from the kernel: it calls `fault_report_begin`, writes one line (with `fault_reason`, and the name of the vector at a checked index), and calls `machine_stop`. The table `report_callees` names these callees, and the build stops when `kernel_interrupt` does not call one of them. Under the report, `log_take` takes no lock and `log_record` returns before its wake, so the measure leaves out `lock_take` and `word_wake` (`report_never_reaches`). A fault inside the report pushes its frame on the same stack: the measure adds one more `kernel_interrupt` that runs `fault_report_begin`, which ends that second report with one line. A third level cannot come: `fault_report_begin` stops the machine at the second report. On the stack of the debug exception only the stub runs, so its use is the frame of the stub. Each interrupt stack keeps a quarter of its bytes free, as the kernel stack does, or the build fails.
- **The refusal of a register trial.** It is the one protection fault of the kernel that returns ([features/processor_counters.md](../features/processor_counters.md)). The fault pushes its frame on the stack of the trial, and `kernel_interrupt` returns at once through `register_trial_refusal_address`. So the measure adds, to the deepest chain from an entry to a trial (the table `register_trials`), the alignment, the frame of the fault, a return address, the frame of `kernel_interrupt` alone and the chain of that callee, and prints the sum as its own line. The chain is part of the deepest chain, so the margin checks it. The trial of the first processor runs on the stack of the boot program, which the measure does not cover; another processor and the self test run it on the kernel stack.
- **Two kernels.** `kernel` and `kernel_without_return_check` are measured each.
- **Names.** Odin gives a nested procedure a number (`kernel::self_test.overflow-11736`) that changes with the source. A row names it without the number: a row matches a symbol that is its name, or its name, `-` and digits.

## State

Changed: the pushes outside the frame and the indirect tail calls are now counted; before, the margin was their room. Left: nothing of the listing; the bound stays a bound of the graph.
