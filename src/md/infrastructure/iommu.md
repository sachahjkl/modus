# The IOMMU

A device reads and writes memory by itself (direct memory access). Without an IOMMU, a device service with a fault, or a service that a device obeys, makes its device write any page of the machine. The IOMMU translates each address that a device gives, through tables that the kernel writes. With it, a device reaches only the memory that its service declared, and a device service with a fault damages no other program. Property 5 names it as a requirement on real hardware ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "5. Kernel off the data path"); property 7 keeps the code of each device out of the kernel.

The terms are in the glossary: [`docs/GLOSSARY.md`](../../../docs/GLOSSARY.md), "IOMMU"; [`docs/GLOSSARY.md`](../../../docs/GLOSSARY.md), "Remapping unit"; [`docs/GLOSSARY.md`](../../../docs/GLOSSARY.md), "Device domain"; [`docs/GLOSSARY.md`](../../../docs/GLOSSARY.md), "Device address"; [`docs/GLOSSARY.md`](../../../docs/GLOSSARY.md), "Reserved memory range". The guide is [`docs/ARCHITECTURE.md`](../../../docs/ARCHITECTURE.md), "K5. Device grant and interrupts".

## The irreducible constraints

1. **The IOMMU names a device by its requester identifier**: the bus, the device and the function of PCI. The kernel must know which requester a service drives, or it cannot build the tables of that device.
2. **A device service already asks the kernel for each address that it gives to its device** (`Memory_Physical`). No other path gives such an address to a program. So that call is the declaration: no new kernel operation is needed.
3. **A page must leave the tables of a device before the page is free again**, and the unit must have forgotten its cached translation (the IOTLB) before then.
4. **A fault of a device must stop nothing.** The device service is a program; its device is its part. A DMA fault is a line of the log and a count.
5. **The kernel holds no driver.** It writes the tables of one standard unit, and it holds no code of a device class.
6. **A real machine has several units.** An Intel machine has one unit for its graphics device and one that covers every other device (the flag `INCLUDE_PCI_ALL`), and devices behind bridges on buses other than 0. A form that only the test machine has would leave the IOMMU off on the first real machine.

## The hardware

The first form is Intel VT-d, which the test machine emulates: QEMU with `-device intel-iommu`, which needs the machine type q35. The part `iommu` of the test adds `-device intel-iommu,intremap=off` first among the devices, and `iommu_platform=on` on each virtio device: without that property, the virtio devices of QEMU do not send their accesses through the IOMMU. It puts the disk of the measures behind a bridge of PCI Express (`-device pcie-root-port`), on bus 1.

The firmware lists the remapping units in the ACPI table DMAR. The kernel programs at most 4 units of segment 0 (`iommu.UNIT_CAPACITY`). A unit lists device scopes: an endpoint, or a bridge and every bus behind it. Each scope names its device by a start bus and a path, one pair of a device and a function for each bridge down to the device. The kernel resolves each path at the start: it reads the secondary bus of each bridge on the path. The unit of a device is the first unit with a scope that names it (an endpoint with its requester, or a bridge whose buses hold its bus); else the unit of segment 0 with `INCLUDE_PCI_ALL`. The unit of a device is chosen once, at `Device_Create`, and its domain, its invalidations and its faults are on that unit.

A function that no unit covers gives its accesses past every unit: the kernel gives its registers no requester, so it has no domain, and its service declares nothing. Such a device reaches every page, the tables of the units and the kernel too, so its service can end the isolation of every other device: the start writes one line on the log for it, and so does `Device_Create` of its registers. Refusing that `Device_Create` was weighed: the machine would lose a device that it has with no IOMMU, and the root service already chooses which service drives which device.

The IOMMU stays off, with one line that says why, and the machine runs as a machine with no IOMMU, for:

- **a table that the kernel cannot hold**: more than 4 units, more than 8 reserved memory ranges, more than 64 device scopes, a path of more than 4 pairs, a unit or a range of a segment other than 0, more than 8 devices that the reserved ranges name;
- **a unit that the firmware left in a mode**: translation, the queue of invalidations or interrupt remapping already on (the global status). The kernel does not take over a unit that it does not know: its register invalidations do not work with the queue on, and with remapping on each interrupt needs an entry that does not exist;
- **registers or a configuration memory that are not device memory**: the registers of each unit (64 KiB) and the configuration memory of the buses that the table MCFG gives (1 MiB for each bus) must be ranges that the firmware gave as reserved, never memory that it gave as free or loaded, so a table that lies cannot make the kernel write a frame;
- **a unit with no drain of reads and writes** at an invalidation (see "The end of a grant"), with too few domain identifiers (41 or more: 32 slots of devices and 8 reserved devices), or with no table form of 39 or 48 bits.

Each unit is checked before any unit is turned on: one bad unit leaves all of them off. A machine with one unit on and one off would have a part of its devices isolated and the other part able to write the tables of the first. A unit that does not take its root table or does not turn translation on turns each unit before it off again; a unit that does not turn off in one second writes one line, and stays on with its standing domains only. The configuration memory past the direct map is not read: a device on such a bus gets no domain.

While the IOMMU is in use, `Device_Create` refuses a range that meets the registers of a unit, the configuration memory, or a reserved memory range: the kernel owns the first two, and the root service could otherwise turn translation off; the third is memory of the firmware that a device of the firmware writes.

AMD-Vi (the table IVRS) is left. It has the same parts (a device table by requester, page tables, a log of faults), so the kernel side of this design holds; the formats and the registers differ.

## Bridges

The kernel walks the buses at the start and at each `Device_Create` of the kind `Memory`: bus 0, then the secondary bus of each bridge that it finds, at most once for each bus. A bridge is a function whose header has the type 1; the kernel reads its secondary and its subordinate bus.

- **A bridge of PCI Express** (a root port, or a port of a switch: the capability of PCI Express with the port type 4, 5 or 6) passes the requester of each device behind it unchanged. Each such device has its own domain, with a context table for its bus.
- **A conventional bridge** (a bridge from PCI Express to PCI, or a bridge with no capability of PCI Express) gives the accesses of each device behind it the requester of the bridge, or of its secondary bus. Every device behind it then shares one requester. A domain of that requester would let each device behind the bridge reach what the service of any other one declared: the isolation between those devices would end with no line that says so. So the kernel gives a device behind a conventional bridge no requester, writes one line at its `Device_Create`, and its accesses are refused. Refused: one domain for the bridge, owned by the first service that declares. It is a correct form only when one service drives every device behind the bridge, and the kernel cannot know that.
- **The context tables** are made at the start, one for each bus that the walk found and that a unit covers, from memory of the kernel, as the root tables: no budget pays for them, and they live as long as the machine. A device on a bus that the walk at the start did not find (a bus that the root service numbered later) gets no requester, with one line.
- **One root bus.** The walk starts at bus 0 only. A server has other root buses (one for each root complex, such as 0x80), which no bridge of bus 0 reaches. A device there gets no requester, and its accesses are refused, with one line at its `Device_Create`; a reserved range of a device there is not mapped, with one line at the start. Isolation holds; the device does not work. A walk from each root bus is left.
- **The functions that the walk does not find.** A virtual function of SR-IOV reads the vendor 0xFFFF in its configuration, and an ARI function can sit behind a place whose function 0 is absent. Such a function gets no requester, and its accesses are refused.
- **The cost of the walk.** Each `Device_Create` of the kind `Memory` walks the buses again: 32 reads for each bus, 8 for each function and 64 for each bridge, each a possible exit to the hypervisor. It is a few thousand reads at a rare call; a measure on real hardware is left.
- **A function that no unit covers** gets one line at the start, also when no service ever gets its registers: the firmware can have started its DMA. Refused: a context table made at `Device_Create`, paid by the budget of the root service. A context table serves the devices of several services, so no service can pay for it, and memory of the kernel taken after the start breaks the sum of the frames.

The kernel trusts the root service with the bus: the root service holds the ports of the configuration, and could move a register or number a bus again after the start. A handle would then name a device that is not its requester. The root service is trusted with the bus, as with the choice of the device of each service.

## Mechanism in the kernel, policy outside

The kernel owns the root table of each unit, the context tables of the buses and the second-level tables of each device. The policy (which device a service drives, which memory a client lends) stays outside: the root service gives a service its device, and a service declares what it gives to its device.

- **The requester of a handle.** When the IOMMU is in use, `Device_Create` of the kind `Memory` walks the buses through the configuration memory (the ACPI table MCFG). A function whose memory register starts at the first page of the range is the requester of the new memory object. The kernel reads the bus; it finds no device and starts none: the root service does that.
- **The service of a device** is a program that holds a handle to a memory object with a requester. That is the program to which the root service gave the registers.
- **The declaration.** `Memory_Physical` from a service gives the device address of the object (see "Device addresses"), and maps each page of the object in the domain of each device whose registers the caller holds by a handle. A call from a program that holds no such handle declares nothing. Device memory (registers, the framebuffer) is never declared: a device reaches the memory of programs only, not the registers of another device. Either each device of the call gets the object, or none that did not have it before.
- **The rights of the handle.** The device writes a page while the service holds a handle with Write to its object; else it only reads it. The kernel creates no right that the handle does not carry (property 2). A declaration through a handle with Write adds the write bit. The close or the revocation of the last handle with Write of the service takes the write bit out of each page in each domain of the service, while a handle with Read keeps the pages; a declaration through a Read handle when the service holds no handle with Write does the same. Example: a client attaches an object with Write, then attaches it again with Read only; the block service declares the new handle and closes the old one, and the device then only reads the object.
- **The record of a declaration.** Each memory object keeps one bit for each slot of a device whose domain maps it, and one bit for the write. There is no table of declarations: a table of fixed size, shared by all services, would let one service fill it and refuse every other one. The cost of a declaration is then paid by the budget of the service alone: the object, and the tables of its domain.
- **The bounds of a service.** A service declares to at most 4 devices whose registers it holds; one more gives `No_Slot`. The kernel has 32 slots of devices, and a slot is free again when its domain ends. The count of the faults of a device is apart from its slot: 256 counts by the function of bus 0, and one count for the other buses, so it outlives the service.
- **The refused binding.** A third value of `Device_Create`, the requester that the root service read, would bind a handle to a device with no read of the bus in the kernel. It is a change of the contract for a value that the kernel can read itself, and the root service could then name a wrong device: the read of the registers was chosen.
- **The domain.** A device with a declared page has a context entry that names its tables, with the domain identifier of its slot. A device with no service, or whose service has declared nothing, has no context entry: its empty domain. Each of its accesses is refused and recorded. A device that a reserved memory range names is the one exception (see "Reserved memory ranges").
- **One owner for each domain.** The first program whose declaration to a device succeeds owns its domain. The domain ends when that program stops, or when it holds neither a handle nor a mapping of the registers of that device: its pages, its context entry, the invalidation, its tables, its slot. A device that the root service gives to another service then reaches nothing of the first. The declaration of another program for the same device gives `Bad_State` while the domain lives: the root service gives one device to one service, and the budget of the owner pays for the tables. A device whose first declaration fails gets no owner; a device of the same call whose declaration succeeded keeps its domain and its owner. A failed call leaves each device with no page of that object, and takes back a write that the call added.
- **A mapping of the registers is a hold of the domain.** A service that closes its handle of the registers and keeps the mapping can still drive the device. Before, its domain ended at the close: the root service could then give the device to a second service, whose declarations the first service could make the device write through its old mapping. Now the domain ends only when the last handle and the last mapping of the registers of that device in the owner end: while the first service maps the registers, a declaration of the second gives `Bad_State`. The root service still revokes the registers handle before it gives the device to another service: a revocation ends the mappings that came from the handle.
- **Only the holder maps the registers.** While the IOMMU is in use, `Memory_Map` of the registers of a device with a domain into another program than the caller gives `Bad_Operation`. Else the owner could map them into a program that it controls, close its own handle and mapping, and so end its domain while that program still drives the device. Refused: a mapping in any program as a hold of the domain. The kernel would then search the mappings of every program at each close and each unmap of registers, and a domain would outlive its owner, paid by a budget that no longer drives the device. No program of the system maps registers into another program: the root service gives the handle, and the service maps it. The rule holds because the root service gives the registers with Read and Write and never with Give: a service with Give could copy its handle to a program that it controls, and that program would map it as its own. A grant of the registers with Give is refused for this reason.
- **The address width.** The kernel takes 4 levels when the unit has 48 bits (the field SAGAW), else 3 levels for 39 bits. The levels belong to the unit, and a domain takes the levels of the unit of its device. A unit also blocks each request above its maximum address width (the field MGAW), whatever its tables map. A unit of fewer than 39 bits gives no device windows, with one line at the start: its devices get contiguous objects only, and a contiguous object must end below its width, else `Bad_Operation`.

## Device addresses

The device address of a declared object is the address that `Memory_Physical` gives, and that the device uses for its first page.

- **A contiguous object** has its physical address as its device address (an identity mapping). A service gives its device the same address with and without the IOMMU. Such an object must end below 2^38 (256 GiB), else `Bad_Operation`. On a machine with more than 256 GiB of memory, a contiguous object that the frame allocator places above that limit cannot be declared: a device service can then fail by the place of its object. The windows are fixed at 2^38 so that a domain of 3 levels holds them all; a placement above the memory for a unit of 4 levels is left.
- **An object that is not contiguous** has a device window when the IOMMU is in use: the kernel maps its pages, in their order, at consecutive device addresses from `iommu.WINDOW_BASE` (2^38) plus its slot in the table of memory objects times `iommu.WINDOW_SIZE` (128 MiB). The device sees one run, and the service gives one address, as for a contiguous object. The declaration first gives each page its frame, and the frames of the object do not move until it ends. An object of more than 128 MiB, or an `Uncommitted` object (a decommit would take a frame from under the device), gives `Bad_Operation`. With no IOMMU, or from a program that declares to no device, such an object gives `Bad_Operation`, as before: its frames are anywhere.

What changed: before, every declared object had an identity mapping, and `Memory_Physical` refused an object that is not contiguous. A contiguous object of 512 KiB for each endpoint of the network ([network_data_path.md](network_data_path.md), "The send with no copy") can fail on a machine with fragmented memory, and the root service then cannot start the program. With a window, the root service makes the datagram region with no `Contiguous` flag when the network device has windows.

Why these forms:

- **The window is a function of the slot of the object.** One object has one device address in every domain, so one call gives one address for each device of the service. The kernel keeps no allocator of device addresses and no field in the object: the slot is free again only after the object left every domain. 2048 slots times 128 MiB is 256 GiB, the upper half of a domain of 39 bits.
- **Identity stays for a contiguous object.** A device that gives only 32 bits of address works with a contiguous object in low memory, as on a machine with no IOMMU. A window above 2^38 needs a device with at least 39 bits of address, which every virtio device and every device of PCI Express with 64 bits of address has. A service of a device with fewer bits keeps `Contiguous` objects. The kernel does not know the width of a device, and does not enforce that rule: a service that gives a window to a device of 32 bits sees an address of 2^38 or more, and a device that cuts it reaches another place of its own domain, or faults. The damage stays in the memory of that service.
- **The root service learns the facts of each device.** `Device_Create` of the kind `Memory` gives, in its second result, whether the device has a domain and whether its unit gives windows (`op.Device_Memory_Facts`). The root service makes the datagram region not contiguous only when the network device has windows. Refused: a count of the units in the boot report as that fact. A machine can have an IOMMU and a network device that no unit covers, whose service then cannot declare a window.
- **Refused: a window for every object**, contiguous or not. One form is less code, but a device of 32 bits would lose the memory that it has today.
- **Refused: an allocator of device addresses** with a field in each object. It packs the windows, and costs a table of the free ranges under the frame lock for no gain: the space of the windows is fixed and large.
- **Refused: a second result of `Memory_Physical`**, the device address beside the physical address. The service needs only the address that its device uses.

The cost of a domain: a table of the last level maps 2 MiB, so a window of a small object costs one table, and the identity pages of a device spread over the physical memory take more tables than pages packed at low addresses. The tables of one device are paid by the budget of the owner.

## Reserved memory ranges

The table DMAR lists reserved memory ranges (RMRR): memory that the firmware keeps for a device, which the device keeps using after the start (the emulation of a USB keyboard by the firmware, the stolen memory of a graphics device). Before, any reserved range left the IOMMU off.

- **A standing domain.** At the start, before translation is on, each device that a reserved range names (at most 8 devices) gets a domain of its own, with each of its ranges mapped at the same address, readable and writable. The kernel pays its tables, as the context tables, and its domain identifier is above the 32 slots. The device then keeps doing what the firmware does with translation on.
- **A service takes the device.** At the first declaration of its service, the domain of the service maps the reserved ranges of that device too, paid by the service, and the context entry moves from the standing domain to the domain of the service: the entry is cleared, both domains are invalidated, then the new entry is written. When the domain of the service ends, the context entry moves back to the standing domain. Refused: the pages of the service in the standing domain. Its tables would then hold pages of two payers, and the end of the domain could not give the tables back to one budget.
- **The range is never given to a program.** `Device_Create` refuses a range that meets a reserved range, and a declaration never maps one: it is memory of the firmware, and a program with it could write what the device of the firmware reads.
- **A range that the kernel does not map**, with one line at the start: a range that meets memory that the firmware gave as free or loaded (a table that lies would give a device a frame of a program), a range that ends at or above 2^38 (the windows), a range of more than 1 GiB, a scope that is a bridge, or a device on a bus with no context table (another root bus, or behind a conventional bridge). A device that no unit covers needs no mapping: its accesses pass the units. Its device then faults on that range, and the IOMMU stays on: a fault is a line, a range of free memory given to a device is a breach.

## The end of a grant

- **The service closes or loses its last handle** (`handle_close`, which a revocation also reaches): the device of the service reaches what the service holds, so the kernel clears the pages of the object in each domain that the service owns, and invalidates, before the close returns. The object can live on in its client, which then uses it for its own data: every gift can be taken back (property 2). The block service closes the region before when a client attaches a new one, and the device then loses the old one. A mapping of an object does not keep its declaration: the handle does. The close of a handle of an object that is neither declared nor registers costs two loads.
- **The memory object ends** (`region_release`): under the frame lock, before its frames return, the kernel clears the entries of its pages in each domain, and invalidates.
- **The service stops** (`program_cleanup`): before its handles close, the kernel clears the context entry of each device that it owns, clears its bits in each memory object (one pass over the table of the objects), invalidates, gives the pages of the tables back to its budget, and frees the slots.
- **The invalidation** is register-based, on the unit of the device, for its domain only: one write of the context command register for that domain identifier when a context entry changed, one write of the IOTLB register for that domain identifier with the drains of reads and writes, and a wait until the unit is done. A service pays for its own domain, and drops no translation of another device. The kernel refuses a unit that does not offer both drains: without them, a write that the unit translated before the invalidation can still reach a page after it, and the specification gives no other way to wait for it. After each command, the granularity that the unit made (CAIG, IAIG) must not be 0; a unit can make a wider one, which is correct. A context entry that becomes present on a unit with the caching mode is invalidated with the domain identifier 0, which such a unit gives to the entries that are not present. The start invalidates each unit globally, once. A queue of invalidations, and an invalidation of one page, are left: an end of a grant is rare.
- **The invalidation runs only when a domain changed**: a clear, a write bit added or taken, an undo, or a new entry on a unit with the caching mode (a unit without it keeps no entry that is not present) or on a unit that asks for a flush of its write buffer (the flush comes first in the invalidation). A service that calls `Memory_Physical` again for an object that it declared costs no wait on the unit.
- **The wait** is bounded by one second of the cycle counter for each command, not by a count of reads; an invalidation has at most three commands (the write buffer, the context cache, the IOTLB), so the frame lock is held at most three seconds before the machine stops: each read of a register can be an exit to the hypervisor. The waiter answers `processor_sync` at each turn, as a waiter for a lock does. A unit that does not end a command, or ends it with no invalidation made, stops the machine, as a machine check: a page that a device can still reach must not become free.

The entries change under the frame lock, which already orders the frames of a memory object and the pages of the budgets: no new kind of lock. The lock order is program, then frame: a declaration, a close and an unmap hold the program lock first. A declaration gives the frames of an object that is not contiguous before it takes the frame lock (the region lock comes before the frame lock). A change walks one table of the last level for each 2 MiB, not the upper levels for each page, so the time under the lock is one pass over the entries of the object. A declaration while the frame lock is held reads no memory of a program.

## A DMA fault

Each unit records each refused access in its fault recording registers, and sends the fault event, a message interrupt to the vector `VECTOR_IOMMU_FAULT` of the first processor. The kernel reads the records of each unit (the requester, the page, read or write, the reason), clears each one, adds 1 to the count of the device, and writes one line on the log:

`kernel: a DMA fault of the device at bus 1, device 0, function 0 (service iommu_device): a write of 000000003f2a5000; reason 0000000000000006; faults of this device: 1`

The kernel stops nothing. A virtio device of QEMU that cannot translate a buffer sets its status "needs a reset" and does no more requests: its service sees that, and the other programs go on.

- **A storm of faults.** A service can make its device fault in a loop. The kernel writes the line of each of the first 4 faults of a device, then one line of the count when the count is a power of two (8, 16, 32...), and counts every fault: the log keeps the first faults whole, and the first processor writes about one line for each doubling. Refused: the bit FPD of the context entry after a count, which needs a change of the entry from the handler and hides the faults that follow.
- **No lost event.** While a record holds a fault, a unit sends no new fault event. The handler reads the fault status of each unit again after each pass over its records, and passes again while a record is pending, at most twice in one call: with interrupts off, a call reads at most 2 passes of the records of each unit (512 records for the largest unit, 3 reads each), so with 4 units at most 4 times that many reads. A record that is still pending after the second pass is read at the next tick of the first processor, which reads one word when no record was left: the reports go on under a storm. The handler reads the word with the bit F of a record first, then the other words, so the line names the fault that set it.
- **The name of the service** in the line is read with no lock: in a race with the end of the service, the line can name the program of the slot before or after. It is a line of the log, not a record that a program reads.

The count is in the kernel, and in the line. A report of the devices for a program (a kind of `Inspect` with a row for each device, and its count of faults) is a contract change that is not made: the line of the log is the record until a program needs the count.

## A machine with no IOMMU

One line at the start: `kernel: no IOMMU: the firmware lists no DMA remapping table; each device reaches all memory`. The machine runs as before, and `Boot_Report.iommu_units` is 0. The status of property 5 says that the isolation of a device is not held on such a machine ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "5. Kernel off the data path").

## Interrupt remapping

Left. With the bit IRE off, a unit passes a message interrupt (an address of 0xFEEx_xxxx) as before, and the machine q35 with `intel-iommu,intremap=off` needs no remapping. A device service writes the table of the message interrupts through the root service only, so a service cannot send another vector today. A device that writes to the interrupt addresses as a DMA write can still send any vector of the first processor: that is the hazard that remapping removes.

## The proof

The part `iommu` of the test runs the whole system on the machine with the IOMMU: the storage service on the data disk and the network service run with translation on, so each page that a service gives to its device is declared. The disk of the measures is behind a root port of PCI Express, on bus 1. The program `iommu`, a client of that disk, makes the root service start the test device service `iommu_device` for it in place of the block service. The test device service:

1. declares its queue and a data object of two pages, writes a block from the first page and reads it into the second: the bytes arrive, through the context table of bus 1;
2. declares a new page with a known pattern, notes its address, then closes its handle and keeps its mapping: the kernel takes the page out of the domain at the close;
3. puts the address of that page in a descriptor of a read;
4. waits for the condition "the device needs a reset" or "the device used the request", with the hang bound, and checks that the page keeps its pattern.

The kernel writes the line of the DMA fault with the device at bus 1 and the address, and the client then gets an answer from the service: the machine goes on.

Then `net` runs its cases. Its datagram region is not contiguous: the root service reads that the IOMMU is in use. The network device reads the data of each datagram from the window of that region, which the frame service declared through a handle with Read only ([network_data_path.md](network_data_path.md), "The send with no copy"). The echo of its datagram comes back, and the step fails on a DMA fault of the network device.

The step 2 is the means of the test, and the rule of the close at the same time: a page that the service can read after the write, at an address that it no longer holds by a handle. A real fault gives the device a wrong address by a wrong computation; the result is the same refusal. A close of the handles of the registers would not serve: it ends the whole domain, and the device would then fault on its own queue.

QEMU emulates one unit, with no reserved range. The host tests of `src/library/contract/iommu` read a table with two units (one for a graphics device, one with `INCLUDE_PCI_ALL`) and with reserved ranges, resolve the paths of the scopes through bridges, and check the unit that each device gets.

The main test does not move to the machine with the IOMMU yet. Its risks: every virtio device of the main test then goes through the emulated unit (a cost in time for each access of the disk and of the network, which is a measure, not a check), and a page that a service forgets to declare stops a part of the main test with a DMA fault, which is the purpose. The part `iommu` finds such a page first.

Left: AMD-Vi; interrupt remapping; a queue of invalidations, and an invalidation of one page; a segment other than 0; one domain for the devices behind a conventional bridge; a bus that the root service numbers after the start; a root bus other than 0; the virtual functions of SR-IOV and the functions of ARI; a refusal of a window for a device of 32 bits; windows above the memory on a unit of 4 levels, for a machine of more than 256 GiB; a count of the faults for each device outside bus 0; a report of the devices for a program; the main test on the machine with the IOMMU.
