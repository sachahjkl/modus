# The IOMMU

A device reads and writes memory by itself (direct memory access). Without an IOMMU, a device service with a fault, or a service that a device obeys, makes its device write any page of the machine. The IOMMU translates each address that a device gives, through tables that the kernel writes. With it, a device reaches only the memory that its service declared, and a device service with a fault damages no other process. Property 5 names it as a requirement on real hardware ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "5. Kernel off the data path"); property 7 keeps the code of each device out of the kernel.

A message interrupt is a write of the device too: a write of 4 bytes to the interrupt addresses (0xFEEx_xxxx). Without interrupt remapping, a device can write any vector of any processor there, so a device service can make its device interrupt the kernel or the service of another device. The unit checks each such write against a table that the kernel writes, so a device sends only the interrupts that its service was given.

The terms are in the glossary: [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "IOMMU"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Remapping unit"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Device domain"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Shared requester"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Device address"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Reserved memory range"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Interrupt remapping"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Queue of invalidations"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Device table"; [`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Event log". The guide is [`docs/ARCHITECTURE.md`](../../../docs/ARCHITECTURE.md), "K5. Device grant and interrupts".

## The irreducible constraints

1. **The IOMMU names a device by its requester identifier**: the bus, the device and the function of PCI. The kernel must know which requester a service drives, or it cannot build the tables of that device.
2. **A device service already asks the kernel for each address that it gives to its device** (`Memory_Physical`). No other path gives such an address to a process. So that call is the declaration: no new kernel operation is needed.
3. **A page must leave the tables of a device before the page is free again**, and the unit must have forgotten its cached translation (the IOTLB) before then.
4. **A fault of a device must stop nothing.** The device service is a process; its device is its part. A DMA fault is a line of the log and a count.
5. **The kernel holds no driver.** It writes the tables of one standard unit, and it holds no code of a device class.
6. **A real machine has several units.** An Intel machine has one unit for its graphics device and one that covers every other device (the flag `INCLUDE_PCI_ALL`), and devices behind bridges on buses other than 0. A form that only the test machine has would leave the IOMMU off on the first real machine.
7. **An interrupt entry names its device.** The unit knows the requester of each message write. An entry of the interrupt table that does not name its device lets every device send that vector. So the kernel must know the device of each message interrupt that `Device_Create` makes.
8. **Two vendors, one kernel side.** An AMD machine has AMD-Vi, with other tables and other registers but the same parts. The domains, the declarations and the end of a grant must not exist twice.

## The hardware

The first form is Intel VT-d, which the test machine emulates: QEMU with `-device intel-iommu`, which needs the machine type q35. The part `iommu` of the test adds `-device intel-iommu,intremap=on` first among the devices, with `-machine q35,kernel-irqchip=split` (QEMU refuses interrupt remapping with the interrupt controllers of KVM whole in the host kernel), and `iommu_platform=on` on each virtio device: without that property, the virtio devices of QEMU do not send their accesses through the IOMMU. It puts the disk of the measures behind a bridge of PCI Express (`-device pcie-root-port`), on bus 1. The part `iommu_amd` runs the same system on the unit of AMD (see "Two vendors behind one kernel side").

The firmware lists the remapping units in the ACPI table DMAR. The kernel processes at most 4 units of segment 0 (`iommu.UNIT_CAPACITY`). A unit lists device scopes: an endpoint, or a bridge and every bus behind it. Each scope names its device by a start bus and a path, one pair of a device and a function for each bridge down to the device. The kernel resolves each path at the start: it reads the secondary bus of each bridge on the path. The unit of a device is the first unit with a scope that names it (an endpoint with its requester, or a bridge whose buses hold its bus); else the unit of segment 0 with `INCLUDE_PCI_ALL`. The unit of a device is chosen once, at `Device_Create`, and its domain, its invalidations and its faults are on that unit.

A function that no unit covers gives its accesses past every unit: the kernel gives its registers no requester, so it has no domain, and its service declares nothing. Such a device reaches every page, the tables of the units and the kernel too, so its service can end the isolation of every other device: the start writes one line on the log for it, and so does `Device_Create` of its registers. Refusing that `Device_Create` was weighed: the machine would lose a device that it has with no IOMMU, and the root service already chooses which service drives which device.

The IOMMU stays off, with one line that says why, and the machine runs as a machine with no IOMMU, for:

- **a table that the kernel cannot hold**: more than 4 units, more than 8 reserved memory ranges, more than 64 device scopes, a path of more than 4 pairs, a unit or a range of a segment other than 0, more than 8 devices that the reserved ranges name;
- **a unit that the firmware left in a mode**: translation, the queue of invalidations or interrupt remapping already on (the global status). The kernel does not take over a unit that it does not know: a queue of the firmware can hold descriptors that the kernel did not write, and with remapping on each interrupt needs an entry that does not exist;
- **registers or a configuration memory that are not device memory**: the registers of each unit (64 KiB) and the configuration memory of the buses that the table MCFG gives (1 MiB for each bus) must be ranges that the firmware gave as reserved, never memory that it gave as free or loaded, so a table that lies cannot make the kernel write a frame;
- **a unit with no queue of invalidations** (the field QI of the extended capability), **no drain of reads and writes** at an invalidation (see "The end of a grant"), too few domain identifiers (41 or more: 32 slots of devices and 8 reserved devices), or no table form of 39 or 48 bits. The specification makes each unit that offers interrupt remapping offer the queue too, because the queue is the only way to invalidate an interrupt entry.

Each unit is checked before any unit is turned on: one bad unit leaves all of them off. A machine with one unit on and one off would have a part of its devices isolated and the other part able to write the tables of the first. A unit that does not take its root table or does not turn translation on turns each unit before it off again; a unit that does not turn off in one second writes one line, and stays on with its standing domains only. The configuration memory past the direct map is not read: a device on such a bus gets no domain.

While the IOMMU is in use, `Device_Create` refuses a range that meets the registers of a unit, the configuration memory, or a reserved memory range: the kernel owns the first two, and the root service could otherwise turn translation off; the third is memory of the firmware that a device of the firmware writes.

## Two vendors behind one kernel side

AMD-Vi has the same parts as VT-d, in other formats. The kernel keeps one side that does not know the vendor, and a small set of procedures for each vendor.

**The side of the kernel that does not know the vendor**: the walk of the buses and the requester of a handle, the slots of the devices and their owners, the declaration (`Memory_Physical`), the bits `declared` and `declared_writable` of a memory object, the device windows, the end of a grant, the counts of the faults and the lines of the log, the message interrupts that `Device_Create` makes. Every rule of this file that is not in the table below holds for both vendors.

**The procedures of a vendor**, one switch on the vendor that the start found, in each of these places. The vendor is the table of the firmware: DMAR for VT-d, else IVRS for AMD-Vi. The code of AMD-Vi is in its own file of the kernel (`iommu_amd_vi.odin`) and of the kernel part `iommu` (`amd_vi.odin`). The rule of a bridge, which the root service reads too, is the contract package `bridge_requester`.

| Place | VT-d | AMD-Vi |
|---|---|---|
| The start: the table of the firmware, the check of each unit, the tables of the units, translation on | DMAR; a root table, a context table for each bus; the global command | IVRS; one device table for all requesters of the buses of the configuration memory; the control register |
| The entry of a device: present with the tables of its domain, or cleared | a context entry with the domain identifier | a device table entry with the domain identifier |
| The entry of a page and of a table | the second-level format: read and write in bits 0 and 1 | the AMD format: present in bit 0, the next level in bits 11:9, read and write in bits 61 and 62 |
| The invalidation of one domain, of an entry, of an interrupt entry, and the wait for it | the queue of invalidations, with a wait descriptor | the queue of invalidations of AMD, a ring of commands, with the command `COMPLETION_WAIT` |
| The faults | the fault recording registers and the fault event | the event log and the message interrupt of the function of the unit |
| The interrupt entry of a message, and the address and the value that the device writes | one table for the machine, the remappable format | one table for each device with a message interrupt, the value is the index |

Why a switch and not a table of procedure values: two vendors are a closed set, and a switch reads in one place, with no indirect call on the path of a declaration. Refused: one build for each vendor. The machine says its vendor at the start, and one boot image runs on both.

The form of AMD-Vi:

- **The table IVRS** lists each unit (a block IVHD of the kind 0x10, 0x11 or 0x40) with the base of its registers, its own requester (a unit of AMD is a function of PCI), and the device entries that it covers: one device, a range, all, an alias of a device to another requester. A firmware can describe one unit by blocks of several kinds (QEMU 10 gives a block 0x10 and a block 0x11 for its one unit): the kernel reads the blocks of the highest kind that it knows and skips the others, as the specification asks, else it would process one unit twice. The entries become ranges of requesters, and adjacent entries of one unit are one range: a firmware names each device of bus 0 by one entry, so the bound is `iommu.AMD_REQUESTER_RANGE_CAPACITY` (256) ranges, not the 64 scopes of VT-d. Two units that name one requester leave the IOMMU off, with one line. What changed: the last range held, so the order of the blocks chose the unit; an entry "every device" in the block of a second unit would then send the invalidations of the devices of the first unit to the second, and the first would keep its translations after the end of a grant. VT-d has an order that does not depend on the blocks (a scope wins over `INCLUDE_PCI_ALL`); the table IVRS has none, so the kernel refuses the table. An alias makes two requesters one, and the kernel keeps the target of each alias with its range. An alias that a conventional bridge explains, whose target is the shared requester that the walk of the bus finds for its source, is the domain of that bridge (see "Bridges"): QEMU 10 names the buses behind such a bridge by one alias range to it. That holds only when every alias that targets the shared requester has its sources on buses behind that bridge; an alias to it from a device outside, which the check of the group never counts, gives the group no domain. Another alias gives no domain to its source or to its target; so does an alias of a device behind a conventional bridge to another requester, as the table and the bus then disagree on what the unit sees. What changed: only the source was refused, so a service of the target would have its declarations reached by the source too; then every alias was refused, so a device behind a conventional bridge had no domain on AMD-Vi. The byte 3 of each entry (its settings) is kept with its range; a special entry (an IOAPIC, a timer) is a range of its own requester. A block IVMD of one device (0x21) is a reserved memory range, as RMRR, with the bounds and the refusals of VT-d. A block IVMD of every device or of a range of devices (0x20, 0x22) leaves the IOMMU off, with one line: the kernel would map the range for each device of the walk, and a bound of 8 standing domains does not hold that. The bounds of `iommu.UNIT_CAPACITY` and `RESERVED_RANGE_CAPACITY` hold, with the same refusal.
- **The unit at the start.** The kernel refuses a unit that the firmware left on (a bit of the control that turns on the unit, its event log or its queue of invalidations), a unit with no translation through host tables (the field HATS of the extended features is 3), a unit whose function has no message interrupt in the configuration memory, and a unit whose function is not of the class of an IOMMU (0x0806): the kernel turns on the message interrupt and the bus master bit of that function, and a table that lies must not make it turn on a device of a service. Each unit takes 4 levels (48 bits): every value of HATS that the kernel accepts allows them. Before a unit is on, the kernel writes 0 in its exclusion range (the base with ExEn and ExAllow, the limit) and in the 12 registers of its 4 apertures of memory access routing: a range that the firmware left in either passes the devices past the tables, whatever their entry holds. On a unit with no apertures those registers are reserved, and a write of 0 leaves them as they are. The registers that the kernel owns are 16 KiB from the base; a unit with performance counters has registers up to 512 KiB, and those do not turn translation off.
- **The device table** has an entry of 32 bytes for each requester: the domain identifier, the top of the tables, their levels, and the bits of the interrupt table. One table of 2 MiB serves every unit, with an entry for each of the 65536 requesters, whatever buses the table MCFG gives: a requester on a bus that the root service numbers later, or past the buses of MCFG, has an entry that refuses it too. What changed: the table covered the buses of MCFG only, and QEMU 10 reads the entry of a requester past the table from the frames that follow it. Its subtle point: **an entry of zeros passes every access with no translation**, the opposite of a context entry of VT-d. So the kernel writes each entry of the table at the start as valid with translation on, the 4 levels, the top of one empty table of the kernel, and neither read nor write: the empty domain refuses every access, as on Intel. What changed: the design wrote the mode 0 (no table) in the empty entry. The specification gives the mode 0 the rights of the entry only, but QEMU 10 gives a device whose entry has the mode 0 all memory, with no check. An entry with the levels and an empty table refuses on both.
- **The order of the words of an entry.** The unit can read an entry between two stores of the kernel. A domain is made by its domain identifier first, then the word with its tables and its rights; it is cleared by the word of the empty table first, then the identifier 0. Each mixed entry that the unit reads in one read of the entry then refuses every access. A unit that reads the two words in two reads could still walk the tables of a domain under the identifier 0, which each refusing entry carries: each change of an entry also makes the unit forget the domain 0, in the same batch, before the tables or the frames return. The words of translation change under the frame lock, as the domains do; the word of the interrupts changes under the control lock, as the message interrupts do. Each is a store of 8 bytes, so they never mix.
- **The page tables** have the levels of VT-d with other bits: present in bit 0, the level of the table that an entry names in the bits 11:9 (0 for a page), read and write in the bits 61 and 62. The unit takes the rights of each level together, so an entry that names a table has both. `pages_change`, `leaf_table` and `tables_free` take the format of the vendor and keep their walk.
- **The queue of invalidations of AMD** is a ring of one page of commands of 16 bytes. `INVALIDATE_DEVTAB_ENTRY` for an entry, `INVALIDATE_IOMMU_PAGES` with the domain identifier and the address of all pages for a domain, `INVALIDATE_INTERRUPT_TABLE` for the interrupt table of a device, then `COMPLETION_WAIT` that writes a word in memory, as the wait descriptor of VT-d. The wait has the same bound of one second, and the same stop of the machine; a unit that refuses a command stops its queue, which the wait reads in the status. The completion wait comes after the requests that the unit translated before it, so no drain flag is needed, as on VT-d. A unit of AMD keeps the device entries that it read, also one that refused: each new device entry is invalidated. It keeps a page that was not present only with the flag NpCache (bit 26) of its capability header, at the place that its block of the table gives, which QEMU 10 sets: the kernel reads it, and invalidates a new page of a domain only with it, as VT-d does only with the caching mode. A header at no valid place, or of another kind, counts as NpCache. The start makes each unit forget every cached entry (`INVALIDATE_IOMMU_ALL`, when the unit offers it).
- **The entry of each requester at the start.** After the units are on, each unit invalidates the entry of each of the 65536 requesters, in batches of 7 commands for each wait: about 9400 waits for each unit, at the start only. QEMU 10 switches a device to translation only when its entry is invalidated: until then it passes each access of the device with no check, whatever the entry holds. What changed: the kernel invalidated only the functions that the walk found, so on QEMU a function that the walk does not find (a virtual function, a function behind a bus numbered later) passed every access. Now such a function is refused on QEMU too, as on a real unit, which reads the entry for each request.
- **The address of an event on QEMU.** QEMU 10.2 writes the address of an event with `amdvi_setevent_bits(evt, addr, 64, 64)`, whose mask `MAKE_64BIT_MASK(64, 64)` is empty: each record of the test machine has the address 0, and the line of a DMA fault says "of 0000000000000000". QEMU also sets no write flag, so the line says "a read". The kernel reads the address at bytes 8 to 15 of the record, as the specification of AMD puts it; on a real unit the line names the page.
- **The event log** is a ring of one page of records of 16 bytes that the unit writes, with the message interrupt of the function of the unit. The kernel writes that message interrupt in the configuration of the function: the vector of the fault event, the first processor, one message, the mask bits at 0 when the capability has them (a mask that the firmware left set would stop each event interrupt, and the log would fill with no line), and the right to write memory. The function of a unit is of the kernel, as its registers: the root service starts no service for it. The kernel does not hold the configuration of that function: the root service holds the ports of the configuration, and is trusted with the bus. The kernel reads each record of the kind `IO_PAGE_FAULT` (the requester, the address, the access, the flag I of an interrupt request) and writes the line of a DMA fault or of a refused interrupt with the same counts; a record with the flag I is a refused interrupt only when its address is one of the interrupt addresses. Each other record is a line with a count for each of the 16 kinds, by the rule of the lines of a DMA fault: a storm of a kind that a device causes (a request that the device table does not allow) does not hide the line of an error of the unit. The kernel clears the interrupt bit of the status before it reads the tail, so a record that comes after the read sends a new interrupt; it reads at most one log of each unit in one call, and the tick reads again while a record came during the last read. A unit can move its tail before the record is in memory: the kernel reads a record of the kind 0 as not written yet, reads it again 64 times, then leaves it, with the head on it, to the next tick. It writes 0 in each record that it read, so a record of the last lap of the ring is never read again. A full log stops the records of every device: a storm of one device can then hide the line of the first DMA fault of another device, whose access the unit still refuses. The kernel stops the log, clears the overflow, empties the log, starts it again, and counts it on the log. The stop of the log waits at most one second, in the handler of the fault event with interrupts off, and answers `processor_sync` at each turn, as the waits of the queue do.
- **Interrupt remapping** is a table for each device with a message interrupt: the entry of the device table names it, and the value that the device writes is the index of the entry. A device can then name only the entries of its own table, so the check of the requester is the table itself. Each table has 16 entries of 4 bytes, one for each message interrupt of `op.MESSAGE_CAPACITY`, at its index. A device has a table while it has at least one message interrupt, so `op.MESSAGE_CAPACITY` tables are enough: they are one page of the kernel, made at the start, 128 bytes apart. What changed: the design made a table for each device; a table for each function of the bus would cost memory for each function that never has a message interrupt. The entry of each device with no table is valid with the control that refuses each message, so a device that has no message interrupt sends none. The end of the last message interrupt of a device frees its table, and its entry refuses again. The kernel turns remapping on when the table IVRS names an IOAPIC, as Linux does: a firmware gives that entry only on a platform that remaps.
- **The pass bits.** With remapping, the third word of an entry also decides the messages of the kinds INIT, ExtINT, NMI, LINT0 and LINT1, which do not go through the interrupt table. On an AMD platform the processor has no pin for the 8259 or the NMI: a device of the chipset sends the virtual wire of the 8259 (ExtINT, LINT0) and the NMI as such messages, and the firmware gives that device the settings that pass them (often 0xD7). The kernel writes, in the entry of each requester that a range names, the pass bits of the settings of each range that names it, and keeps them at each change of the interrupt table; with no pass bit, a unit refuses those messages. What changed: no pass bit was written, so a real AMD machine with remapping on would lose the 16 lines of the 8259 and the NMI. QEMU does not send these messages through its unit, and the test does not reach them. The bits SysMgt (the messages of system management) stay 0: those messages are refused.
- **On QEMU 10** (10.2 was read): `-device amd-iommu,dma-remap=on,intremap=on`, with `kernel-irqchip=split`. Without `dma-remap=on`, QEMU translates no access of an emulated device. The facts of QEMU that the kernel and the test meet:
  - QEMU records no event for an interrupt that it refuses, and it gives a write of a device to the interrupt addresses the requester of the IOAPIC (0:14.0), not the requester of the device. So the test of a forged interrupt runs on the unit of Intel only. The test of AMD-Vi shows the message interrupt of a device that arrives through its table: with no valid entry, the unit would refuse it.
  - QEMU records the device of an `IO_PAGE_FAULT` by its device and its function only, with no bus: the line names the device only on bus 0. The part `iommu_amd` puts the disk of the measures behind a conventional bridge at the place 28 of bus 0, whose requester the disk gives.
  - QEMU sets the flag I on each page fault, and gives the access in the flags 0 and 1, not in the flag RW. The kernel reads the specification, so the line of a DMA fault on QEMU names each access a read; the reason field holds the flags as the unit wrote them.
  - A virtio device of QEMU whose read of its queue the unit refuses keeps its request: it neither ends it nor sets the state "needs a reset". A refused write into a buffer ends the request with the status 0, and the bytes do not reach memory. A read of 4096 bytes into a page that the unit refuses makes about 256 page faults, which can fill the event log.
  - QEMU does not check the index of a message against the length of the interrupt table: on QEMU, a message of a device with an index past its table reads the next table. The message of a device carries the value that the root service wrote in its table of message interrupts, which the device service does not reach, and a write of the device to the interrupt addresses carries the requester of the IOAPIC, whose entry has no table. A real unit refuses an index past the table.

## Bridges

The kernel walks the buses at the start and at each `Device_Create` of the kind `Memory`: bus 0, then the secondary bus of each bridge that it finds, at most once for each bus. A bridge is a function whose header has the type 1; the kernel reads its secondary and its subordinate bus.

- **A bridge of PCI Express** (a root port, or a port of a switch: the capability of PCI Express with the port type 4, 5 or 6) passes the requester of each device behind it unchanged. Each such device has its own domain, with a context table for its bus.
- **A conventional bridge** (a bridge from PCI Express to PCI, or a bridge with no capability of PCI Express) makes the requests of each device behind it with one requester: the shared requester ([`docs/glossary/devices.md`](../../../docs/glossary/devices.md), "Shared requester"). A bridge from PCI Express to PCI gives its secondary bus with the device 0 and the function 0; another conventional bridge gives its own requester. Behind several conventional bridges, the one nearest to bus 0 decides: it makes the request on PCI Express. QEMU 10 and Linux take the same rule. The unit cannot tell those devices apart, so they have one domain, of the shared requester: what one of them can reach, each of them can reach. See "The domain of a conventional bridge".
- **The context tables** are made at the start, one for each bus that the walk found and that a unit covers, and one for the bus of each shared requester of the form secondary bus, device 0, function 0, from memory of the kernel, as the root tables: no budget pays for them, and they live as long as the machine. A device on a bus that the walk at the start did not find (a bus that the root service numbered later) gets no requester, with one line.
- **One root bus.** The walk starts at bus 0 only. A server has other root buses (one for each root complex, such as 0x80), which no bridge of bus 0 reaches. A device there gets no requester, and its accesses are refused, with one line at its `Device_Create`; a reserved range of a device there is not mapped, with one line at the start. Isolation holds; the device does not work. A walk from each root bus is left.
- **The functions that the walk does not find.** A virtual function of SR-IOV reads the vendor 0xFFFF in its configuration, and an ARI function can sit behind a place whose function 0 is absent. Such a function gets no requester, and its accesses are refused: on VT-d it has no context entry, and on AMD-Vi its entry refuses, also on QEMU 10, because the start invalidates the entry of each requester.
- **The cost of the walk.** Each `Device_Create` of the kind `Memory` walks the buses again: 32 reads for each bus, 8 for each function and 64 for each bridge, each a possible exit to the hypervisor. It is a few thousand reads at a rare call; a measure on real hardware is left.
- **A function that no unit covers** gets one line at the start, also when no service ever gets its registers: the firmware can have started its DMA. Refused: a context table made at `Device_Create`, paid by the budget of the root service. A context table serves the devices of several services, so no service can pay for it, and memory of the kernel taken after the start breaks the sum of the frames.

The kernel trusts the root service with the bus: the root service holds the ports of the configuration, and could move a register or number a bus again after the start. A handle would then name a device that is not its requester. The root service is trusted with the bus, as with the choice of the device of each service.

### The domain of a conventional bridge

The hazard: the devices behind a conventional bridge share one domain. If two services drove two of them, the device of the second would reach what the first declared, with no line: the isolation between the two services would end.

**The chosen form: one service holds them all, and the kernel checks it.**

- **The memory object of the registers.** `Device_Create` of the kind `Memory` over the registers of a device behind a conventional bridge gives the object the shared requester as its requester, and keeps the requester of the function itself apart (`bridge_function` of the object). The declarations, the domain, the faults and the interrupt entries of the device are those of the shared requester. The group counts as one device in the bound of 4 devices of a service.
- **The check at the first declaration.** Before the first declaration of the domain of a shared requester, the kernel walks the bus and finds each function that shares it: each function on the buses behind the bridge, except a bridge, which makes no request of its own. The caller must hold a handle or a mapping of the registers of each of them. A function with no memory base address register cannot be held so, and it can still reach memory, through its ports: its group then gets no domain. A declaration that misses one gives `Bad_State`, with one line that names the function that the caller does not hold; that line is not written again while the same function is missed, by any service. The first declaration that passes writes one line with the count of the functions.
- **A bridge that the walk cannot follow.** In the walk of the check, a bridge behind the conventional bridge whose secondary bus is not above its own bus, is past the last bus of the configuration memory, or was already reached by another bridge, can route devices that the walk does not count. The group then gets no domain, with one line that names that bridge.
- **The control lock.** The making and the end of the domain of a shared requester run under the control lock: the declaration that makes it asks for that lock, and so do the close of a handle and the unmap of a mapping of the registers of a function behind a conventional bridge. Under that lock no hold of a function of a group ends, and no domain of a shared requester is made or ends, while another path reads them; a hold can still be added (a service maps its own handle), which only makes a check true that was true. The interrupt entries of the group follow the domain (see "The interrupts"). A path of the kernel that ends such a hold with no control lock is a fault of the kernel: the machine stops, with one line.
- **The end of the domain.** Each function counts apart: the domain ends when its owner no longer holds one of them, as a domain of one device ends at the end of its last hold. Else the root service could take one device back from the service and give it to another service, whose device would reach what the first declared.
- **A function that appears later.** A process gets the registers of a function only through `Device_Create`. When `Device_Create` of the kind `Memory` names a function of a group whose domain lives, and the owner of the domain does not hold that function, the kernel ends the domain: the new function was not counted by the check, and it would reach what the owner declared. The next declaration of the owner walks the bus again. Refused: a refusal of that `Device_Create`. The root service makes the handles of a device before it gives them; a refusal would also stop a root service that gives the whole group again to one service, and the end of the domain holds the rule with no new state.
- **The policy outside.** The root service gives every device behind a conventional bridge to the service of the first of them that it starts: the first page of the registers of the first memory BAR of each other device, in the grants after its own BARs. The root service reads the address of that BAR and does not size it: a size turns the memory of the device off, and another party can use it at that time ([whole_frame.md](whole_frame.md)) (`pci.GRANT_BRIDGE_DEVICE`, at most `pci.BRIDGE_DEVICE_COUNT`). It starts no other service for a device there. The service does not have to drive them: it holds them, so no other service can drive them.
- **The interrupts.** A message interrupt of such a device is bound to the shared requester: on VT-d its entry checks that requester, on AMD-Vi it is in the interrupt table of that requester. Each device of the group can send the message interrupts of the others, so the entries get the rule of the domain: an entry of a shared requester is present only while a domain of that requester lives, which the check made, and while the owner of that domain is the process that holds the interrupt. `Device_Create` of the kind `Message` records the binding, and writes the entry only when that holds; the first declaration of the domain writes the entries of the message interrupts of the group that its owner holds, the end of the domain clears them, and so does a change of the process that holds an interrupt. A declaration that runs with the control lock updates the entries whatever its status: a call that fails after it made the domain keeps it, and its interrupts come with it. A device whose service let one device of the group go then sends no interrupt of the group, also when another service takes the group and keeps none of the interrupts of the first. Refused: a check at `Device_Create` of the kind `Message`. The root service makes the message interrupt before the service exists and holds the registers, so the holder at that time proves nothing about the service.
- **The cost.** The walk of the check runs at the first declaration of a domain only, a few thousand reads of the configuration. A declaration to a domain that the caller owns reads no bus.

Why this form: the hardware makes those devices one party for the IOMMU, and the kernel makes them one party for the system. The trust is the one of a single device: the root service gives one device to one service, and the kernel checks what it can at a rare call.

Refused:

- **One domain owned by the first service that declares, with no check.** A second service that holds another device behind the bridge would get `Bad_State` at its declaration, and its device could still reach the declarations of the first, with no line. The kernel can know the group: it walks the bus.
- **No domain for those devices**, the form before. Isolation held, and every access of such a device was refused: a machine with an older bridge lost its devices with the IOMMU on.
- **A domain for the requester of each device.** The unit never sees that requester: every access would be refused.
- **The policy of the root service as the only guard.** A fault of that policy would end the isolation with no line, and the check costs a walk at a rare call.
- **A check at each declaration.** A walk of the bus at each `Memory_Physical` of the block service; the end of the domain at the end of any one hold keeps the check true after the first declaration.

The subtle points:

- **A device of PCI-X** behind a bridge from PCI Express to PCI-X can make its request with its own requester and not the shared one. The kernel maps the shared requester only, so the accesses of such a device are refused: isolation holds, and the device does not work. Linux maps each possible requester of a device; that is left.
- **The firmware of AMD-Vi** names the devices behind the bridge by an alias range to the shared requester. The kernel accepts the alias only when its target is the shared requester that the walk found, and when every alias that targets that requester has its sources behind that bridge: the walk at the start keeps the shared requester of each bus. An alias from a device outside the group to the shared requester would make the unit translate the accesses of that device with the domain of the group, which the check never counts (see "Two vendors behind one kernel side").
- **A function with the header of a bridge** is not counted, as a bridge makes no request of its own. A bridge that makes requests with bus master on is rare; a CardBus bridge (the header type 2) is counted, has no memory base address register, and so leaves its group with no domain.
- **A reserved memory range** of a device behind a conventional bridge is not mapped: it names the requester of the device, which the unit never sees.

## Mechanism in the kernel, policy outside

The kernel owns the root table of each unit, the context tables of the buses and the second-level tables of each device. The policy (which device a service drives, which memory a client lends) stays outside: the root service gives a service its device, and a service declares what it gives to its device.

- **The requester of a handle.** When the IOMMU is in use, `Device_Create` of the kind `Memory` walks the buses through the configuration memory (the ACPI table MCFG). A function whose memory register starts at the first page of the range is the requester of the new memory object. The kernel reads the bus; it finds no device and starts none: the root service does that.
- **The service of a device** is a process that holds a handle to a memory object with a requester. That is the process to which the root service gave the registers.
- **The declaration.** `Memory_Physical` from a service gives the device address of the object (see "Device addresses"), and maps each page of the object in the domain of each device whose registers the caller holds by a handle. A call from a process that holds no such handle declares nothing. Device memory (registers, the framebuffer) is never declared: a device reaches the memory of processes only, not the registers of another device. Either each device of the call gets the object, or none that did not have it before.
- **The rights of the handle.** The device writes a page while the service holds a handle with Write to its object; else it only reads it. The kernel creates no right that the handle does not carry (property 2). A declaration through a handle with Write adds the write bit. The close or the revocation of the last handle with Write of the service takes the write bit out of each page in each domain of the service, while a handle with Read keeps the pages; a declaration through a Read handle when the service holds no handle with Write does the same. Example: a client attaches an object with Write, then attaches it again with Read only; the block service declares the new handle and closes the old one, and the device then only reads the object.
- **The record of a declaration.** Each memory object keeps one bit for each slot of a device whose domain maps it, and one bit for the write. There is no table of declarations: a table of fixed size, shared by all services, would let one service fill it and refuse every other one. The cost of a declaration is then paid by the budget of the service alone: the object, and the tables of its domain.
- **The bounds of a service.** A service declares to at most 4 devices whose registers it holds; one more gives `No_Slot`. The kernel has 32 slots of devices, and a slot is free again when its domain ends. The count of the faults of a device is apart from its slot: 256 counts by the function of bus 0, and one count for the other buses, so it outlives the service.
- **The refused binding.** A third value of `Device_Create`, the requester that the root service read, would bind a handle to a device with no read of the bus in the kernel. It is a change of the contract for a value that the kernel can read itself, and the root service could then name a wrong device: the read of the registers was chosen.
- **The domain.** A device with a declared page has a context entry that names its tables, with the domain identifier of its slot. A device with no service, or whose service has declared nothing, has no context entry: its empty domain. Each of its accesses is refused and recorded. A device that a reserved memory range names is the one exception (see "Reserved memory ranges").
- **One owner for each domain.** The first process whose declaration to a device succeeds owns its domain. The domain ends when that process stops, or when it holds neither a handle nor a mapping of the registers of that device: its pages, its context entry, the invalidation, its tables, its slot. A device that the root service gives to another service then reaches nothing of the first. The declaration of another process for the same device gives `Bad_State` while the domain lives: the root service gives one device to one service, and the budget of the owner pays for the tables. A device whose first declaration fails gets no owner; a device of the same call whose declaration succeeded keeps its domain and its owner. A failed call leaves each device with no page of that object, and takes back a write that the call added.
- **A mapping of the registers is a hold of the domain.** A service that closes its handle of the registers and keeps the mapping can still drive the device. Before, its domain ended at the close: the root service could then give the device to a second service, whose declarations the first service could make the device write through its old mapping. Now the domain ends only when the last handle and the last mapping of the registers of that device in the owner end: while the first service maps the registers, a declaration of the second gives `Bad_State`. The root service still revokes the registers handle before it gives the device to another service: a revocation ends the mappings that came from the handle.
- **Only the holder maps the registers.** While the IOMMU is in use, `Memory_Map` of the registers of a device with a domain into another process than the caller gives `Bad_Operation`. Else the owner could map them into a process that it controls, close its own handle and mapping, and so end its domain while that process still drives the device. Refused: a mapping in any process as a hold of the domain. The kernel would then search the mappings of every process at each close and each unmap of registers, and a domain would outlive its owner, paid by a budget that no longer drives the device. No process of the system maps registers into another process: the root service gives the handle, and the service maps it. The rule holds because the root service gives the registers with Read and Write and never with Give: a service with Give could copy its handle to a process that it controls, and that process would map it as its own. A grant of the registers with Give is refused for this reason.
- **The address width.** The kernel takes 4 levels when the unit has 48 bits (the field SAGAW), else 3 levels for 39 bits. The levels belong to the unit, and a domain takes the levels of the unit of its device. A unit also blocks each request above its maximum address width (the field MGAW), whatever its tables map. A unit of fewer than 39 bits gives no device windows, with one line at the start: its devices get contiguous objects only, and a contiguous object must end below its width, else `Bad_Operation`.

## Device addresses

The device address of a declared object is the address that `Memory_Physical` gives, and that the device uses for its first page.

- **A contiguous object** has its physical address as its device address (an identity mapping). A service gives its device the same address with and without the IOMMU. Such an object must end below 2^38 (256 GiB), else `Bad_Operation`. On a machine with more than 256 GiB of memory, a contiguous object that the frame allocator places above that limit cannot be declared: a device service can then fail by the place of its object. The windows are fixed at 2^38 so that a domain of 3 levels holds them all; a placement above the memory for a unit of 4 levels is left.
- **An object that is not contiguous** has a device window when the IOMMU is in use: the kernel maps its pages, in their order, at consecutive device addresses from `iommu.WINDOW_BASE` (2^38) plus its slot in the table of memory objects times `iommu.WINDOW_SIZE` (128 MiB). The device sees one run, and the service gives one address, as for a contiguous object. The declaration first gives each page its frame, and the frames of the object do not move until it ends. An object of more than 128 MiB, or an `Uncommitted` object (a decommit would take a frame from under the device), gives `Bad_Operation`. With no IOMMU, or from a process that declares to no device, such an object gives `Bad_Operation`, as before: its frames are anywhere.

What changed: before, every declared object had an identity mapping, and `Memory_Physical` refused an object that is not contiguous. A contiguous object of 512 KiB for each endpoint of the network ([network_data_path.md](network_data_path.md), "The send with no copy") can fail on a machine with fragmented memory, and the root service then cannot start the process. With a window, the root service makes the datagram region with no `Contiguous` flag when the network device has windows.

Why these forms:

- **The window is a function of the slot of the object.** One object has one device address in every domain, so one call gives one address for each device of the service. The kernel keeps no allocator of device addresses and no field in the object: the slot is free again only after the object left every domain. 2048 slots times 128 MiB is 256 GiB, the upper half of a domain of 39 bits.
- **Identity stays for a contiguous object.** A device that gives only 32 bits of address works with a contiguous object in low memory, as on a machine with no IOMMU. A window above 2^38 needs a device with at least 39 bits of address, which every virtio device and every device of PCI Express with 64 bits of address has. A service of a device with fewer bits keeps `Contiguous` objects. The kernel does not know the width of a device, and does not enforce that rule: a service that gives a window to a device of 32 bits sees an address of 2^38 or more, and a device that cuts it reaches another place of its own domain, or faults. The damage stays in the memory of that service.
- **The root service learns the facts of each device.** `Device_Create` of the kind `Memory` gives, in its second result, whether the device has a domain and whether its unit gives windows (`op.Device_Memory_Facts`). The root service makes the datagram region not contiguous only when the network device has windows. Refused: a count of the units in the boot report as that fact. A machine can have an IOMMU and a network device that no unit covers, whose service then cannot declare a window.
- **Refused: a window for every object**, contiguous or not. One form is less code, but a device of 32 bits would lose the memory that it has today.
- **Refused: an allocator of device addresses** with a field in each object. It packs the windows, and costs a table of the free ranges under the frame lock for no gain: the space of the windows is fixed and large.
- **Refused: a second result of `Memory_Physical`**, the device address beside the physical address. The service needs only the address that its device uses.

The cost of a domain: a table of the last level maps 2 MiB, so a window of a small object costs one table, and the identity pages of a device spread over the physical memory take more tables than pages packed at low addresses. The tables of one device are paid by the budget of the owner.

## Reserved memory ranges

The table DMAR lists reserved memory ranges (RMRR): memory that the firmware keeps for a device, which the device keeps using after the start (the emulation of a USB keyboard by the firmware, the stolen memory of a graphics device). Before, any reserved range left the IOMMU off.

- **A standing domain.** At the start, before translation is on, each device that a reserved range names (at most 8 devices) gets a domain of its own, with each of its ranges mapped at the same address, readable and writable. The kernel pays its tables, as the context tables, and its domain identifier is above the 32 slots. The device then keeps doing what the firmware does with translation on.
- **A service takes the device.** At the first declaration of its service, the domain of the service maps the reserved ranges of that device too, paid by the service, and the context entry moves from the standing domain to the domain of the service: the entry is cleared, both domains are invalidated, then the new entry is written. When the domain of the service ends, the context entry moves back to the standing domain. Refused: the pages of the service in the standing domain. Its tables would then hold pages of two payers, and the end of the domain could not give the tables back to one budget.
- **The range is never given to a process.** `Device_Create` refuses a range that meets a reserved range, and a declaration never maps one: it is memory of the firmware, and a process with it could write what the device of the firmware reads.
- **A range that the kernel does not map**, with one line at the start: a range that meets memory that the firmware gave as free or loaded (a table that lies would give a device a frame of a process), a range that ends at or above 2^38 (the windows), a range of more than 1 GiB, a scope that is a bridge, or a device on a bus with no context table (another root bus, or behind a conventional bridge). A device that no unit covers needs no mapping: its accesses pass the units. Its device then faults on that range, and the IOMMU stays on: a fault is a line, a range of free memory given to a device is a breach.

## The end of a grant

- **The service closes or loses its last handle** (`handle_close`, which a revocation also reaches): the device of the service reaches what the service holds, so the kernel clears the pages of the object in each domain that the service owns, and invalidates, before the close returns. The object can live on in its client, which then uses it for its own data: every gift can be taken back (property 2). The block service closes the region before when a client attaches a new one, and the device then loses the old one. A mapping of an object does not keep its declaration: the handle does. The close of a handle of an object that is neither declared nor registers costs two loads.
- **The memory object ends** (`region_release`): under the frame lock, before its frames return, the kernel clears the entries of its pages in each domain, and invalidates.
- **The service stops** (`process_cleanup`): before its handles close, the kernel clears the context entry of each device that it owns, clears its bits in each memory object (one pass over the table of the objects), invalidates, gives the pages of the tables back to its budget, and frees the slots.
- **The invalidation** goes through the queue of invalidations of the unit of the device, for its domain only: a descriptor of the context cache for that domain identifier when a context entry changed, a descriptor of the IOTLB for that domain identifier with the drains of reads and writes, then a wait descriptor that writes a number in a word of the kernel. The kernel moves the tail of the queue, and waits until the word holds that number. A service pays for its own domain, and drops no translation of another device. The kernel refuses a unit that does not offer both drains: without them, a write that the unit translated before the invalidation can still reach a page after it, and the specification gives no other way to wait for it. A context entry that becomes present on a unit with the caching mode is invalidated with the domain identifier 0, which such a unit gives to the entries that are not present. The start invalidates each unit globally, once. An invalidation of one page is left: an end of a grant is rare.
- **Why the queue, and not the registers.** Interrupt remapping needs the queue: an interrupt entry is invalidated by a descriptor only, and a unit with the queue on refuses the invalidation by its registers. One path for every invalidation was chosen over two (the registers while remapping is off, the queue while it is on): the queue works on each unit that the kernel takes, and a second path would be code that one machine of the test never runs. What changed: before, the kernel wrote the context command register and the IOTLB register, and read the granularity that the unit made.
- **One queue for each unit, under the frame lock.** The queue is one page of 256 descriptors of 16 bytes, memory of the kernel. Each invalidation writes at most five descriptors and waits until the unit has read them all, so the queue never holds more than one invalidation and never fills. Every writer holds the frame lock, or runs at the start: no new lock. The start writes one measure line with the cycles and the nanoseconds of one round trip of the queue of the first unit, the time that a holder of the frame lock waits for at each invalidation. If a measure of the waits for the frame lock ever shows the queue, the queue gets a lock of its own, after the frame lock in the lock order.
- **The errors that the firmware left.** The start clears the error bits of the fault status (IQE, ICE, ITE, with the overflow) in one write before the queue is on. A firmware that used a queue and turned it off can leave IQE set, and the first wait of the kernel would read it as its own error and stop the machine.
- **The invalidation runs only when a domain changed**: a clear, a write bit added or taken, an undo, or a new entry on a unit with the caching mode (a unit without it keeps no entry that is not present) or on a unit that asks for a flush of its write buffer (the flush comes first in the invalidation, by its register, which the queue does not replace). A service that calls `Memory_Physical` again for an object that it declared costs no wait on the unit.
- **The wait** is bounded by one second of the cycle counter, not by a count of reads: each read of a register can be an exit to the hypervisor. The flush of the write buffer has its own second, so the frame lock is held at most two seconds for one unit before the machine stops; the invalidation of an interrupt entry, on each unit, at most two seconds for each unit. The waiter answers `processor_sync` at each turn, as a waiter for a lock does. A unit that does not reach the wait descriptor, or that sets the error of the queue (IQE, a descriptor that it refuses), stops the machine, as a machine check: a page that a device can still reach must not become free.

The entries change under the frame lock, which already orders the frames of a memory object and the pages of the budgets: no new kind of lock. The lock order is process, then frame: a declaration, a close and an unmap hold the process lock first. A declaration gives the frames of an object that is not contiguous before it takes the frame lock (the region lock comes before the frame lock). A change walks one table of the last level for each 2 MiB, not the upper levels for each page, so the time under the lock is one pass over the entries of the object. A declaration while the frame lock is held reads no memory of a process.

## A DMA fault

Each unit records each refused access in its fault recording registers, and sends the fault event, a message interrupt to the vector `VECTOR_IOMMU_FAULT` of the first processor. The kernel reads the records of each unit (the requester, the page, read or write, the reason), clears each one, adds 1 to the count of the device, and writes one line on the log:

`kernel: a DMA fault of the device at bus 1, device 0, function 0 (service iommu_device): a write of 000000003f2a5000; reason 0000000000000006; faults of this device: 1`

The kernel stops nothing. A virtio device of QEMU that cannot translate a buffer sets its status "needs a reset" and does no more requests: its service sees that, and the other processes go on.

- **A storm of faults.** A service can make its device fault in a loop. The kernel writes the line of each of the first 4 faults of a device, then one line of the count when the count is a power of two (8, 16, 32...), and counts every fault: the log keeps the first faults whole, and the first processor writes about one line for each doubling. Refused: the bit FPD of the context entry after a count, which needs a change of the entry from the handler and hides the faults that follow.
- **No lost event.** While a record holds a fault, a unit sends no new fault event. The handler reads the fault status of each unit again after each pass over its records, and passes again while a record is pending, at most twice in one call: with interrupts off, a call reads at most 2 passes of the records of each unit (512 records for the largest unit, 3 reads each), so with 4 units at most 4 times that many reads. A record that is still pending after the second pass is read at the next tick of the first processor, which reads one word when no record was left: the reports go on under a storm. The handler reads the word with the bit F of a record first, then the other words, so the line names the fault that set it.
- **The name of the service** in the line is read with no lock: in a race with the end of the service, the line can name the process of the slot before or after. It is a line of the log, not a record that a process reads.

A refused interrupt comes in the same records, with a reason from 0x20 to 0x2F and the index of the entry in the place of the address. The kernel writes its own line for it, with its own count (see "Interrupt remapping"): a storm of forged interrupts does not hide the first DMA fault of the same device.

A unit of AMD writes its refused accesses as records of its event log, with its message interrupt to the same vector, and the kernel writes the same lines with the same counts (see "Two vendors behind one kernel side"). The flags of the record are the reason of the line.

The count is in the kernel, and in the line. A report of the devices for a process (a kind of `Inspect` with a row for each device, and its count of faults) is a contract change that is not made: the line of the log is the record until a process needs the count.

## A machine with no IOMMU

One line at the start: `kernel: no IOMMU: the firmware lists no DMA remapping table and no I/O virtualization table; each device reaches all memory`. The machine runs as before, and `Boot_Report.iommu_units` is 0. The status of property 5 says that the isolation of a device is not held on such a machine ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "5. Kernel off the data path").

## Interrupt remapping

The hazard: the root service writes the table of the message interrupts of a device (MSI-X), and the service does not get that memory, so a service cannot change it. But a message interrupt is only a write of 4 bytes to 0xFEEx_xxxx: a device service that gives that address to its device as a buffer makes the device write any vector of any processor. That is an interrupt of the kernel at a vector of its own (the timer, the fault event of the IOMMU), or the interrupt of another device service.

**The chosen form on VT-d.** The kernel turns interrupt remapping on in each unit after translation, when the table DMAR allows it (its flag INTR_REMAP) and every unit offers it (the field IR of the extended capability). A firmware clears the flag on a platform whose remapping has a fault, even when each unit offers it: the kernel then leaves remapping off, with one line that names the table. One interrupt table serves every unit: one entry for each message interrupt of `op.MESSAGE_CAPACITY`, at the index of the message interrupt. An entry is present while a handle names its message interrupt. It holds:

- the vector of that message interrupt (`VECTOR_MESSAGE_BASE` plus its index), fixed delivery, the first processor in the physical mode;
- the requester of its device, with the check of all 16 bits (SVT 1, SQ 0): the unit refuses the entry to every other requester.

`Device_Create` of the kind `Message` takes, in `a`, the physical address where a memory base address register of the device starts: the same identification as the kind `Memory`, by the same walk of the buses. The root service gives the base of the register that holds the table of the message interrupts. It gets the address in the remappable form (the index in the bits 19:5 and the bit 2, the bit 4 set, no subhandle) and the value 0. With no remapping in use, `a` is not read, and the address and the value are the compatible form, as before.

**What happens to a forged interrupt.** The unit refuses each message write that names no present entry, an entry past the table, an entry of another requester, or the compatible form (the kernel never sets the bit CFI, so the unit blocks every message in the compatible form). It records the refusal in a fault record, as a DMA fault, with a reason from 0x20 to 0x2F (the specification defines 0x20 to 0x27 for interrupt remapping, and the kernel takes the whole group) and the index of the entry. The kernel writes one line, and counts it in a count of the refused interrupts of the device, apart from its DMA faults:

`kernel: an interrupt of the device at bus 255, device 31, function 7 (service no service) is refused: entry 30720; reason 0000000000000021; refused interrupts of this device: 1`

That line is the line of the test on QEMU (see "QEMU" below); on a real machine it names the requester of the device.

The rule of the lines of a storm is the rule of the DMA faults. The interrupt does not arrive, and nothing stops.

**The end of an entry.** When the last handle of a message interrupt closes, the kernel clears its entry and invalidates it on each unit, before the slot can be given again. Each unit, because one table serves all: a unit that kept the old entry would let the old device send the vector of the next owner. The entry changes under the control lock, which `Device_Create` and the close of an interrupt handle already hold, and its invalidation takes the frame lock, which orders the queue.

**The lines of the 8259, and the IOAPIC.** The kernel keeps the 16 device lines on the 8259, on the pin LINT0 of the first processor in the mode ExtINT (the virtual wire through the local interrupt controller), and it processes no IOAPIC. A line of the 8259 reaches the processor as that wire, not as a write to 0xFEEx_xxxx, so the units do not remap it, and the keyboard and the other lines keep working with remapping on. A pin of the IOAPIC that the firmware left on sends a message in the compatible form: the units refuse it (the bit CFI stays 0), and the log has the line of a refused interrupt with the requester of the IOAPIC, often bus 0, device 31, function 0. The kernel never wanted that message; the rule of the lines of a storm bounds the log. A board whose firmware carries the 8259 through the pin 0 of the IOAPIC (the virtual wire through the IOAPIC) and not to LINT0 loses those lines; the kernel sets LINT0 for the 8259, so such a board is rare. On an AMD platform the virtual wire of the 8259 and the NMI arrive as messages of a device of the chipset, which the unit of AMD-Vi passes only with the pass bits of the entry of that device (see "Two vendors behind one kernel side").

**A device with no requester.** A device that the walk does not find, a device that no unit covers, or a device on a bus with no context table: `Device_Create` gives the compatible form. A device behind a conventional bridge has the shared requester (see "The domain of a conventional bridge"). A unit that covers the device refuses it, as it refuses each of its DMA accesses; a device that no unit covers sends it past the units, which is the one form that works for it. Refused: `Bad_Address` for such a device. The machine would lose the interrupt of a device that it can use with no isolation, as for its memory.

**Refused forms.**

- **The requester as an argument.** The root service reads the bus and could give the requester in `a`. The kernel then trusts a value that it can read itself, and a wrong value gives the vector of one device to another. The base address register is the identity that the kind `Memory` already uses.
- **One table for each unit.** One table for all needs an invalidation on each unit at the end of an entry; one table for each unit needs the unit of the device at `Device_Create` and a table for each. A message interrupt ends rarely, and four units are four descriptors.
- **The subhandle form.** The value would carry the index, and the address a base. A device service does not see the value (the root service writes the table), so it gives no isolation, and one form is less to test.
- **Remapping only on the units that offer it.** A device of a unit with no remapping sends any vector, so the isolation of the interrupts would hold for a part of the devices only, with no line that names them. The kernel turns remapping on in every unit or in none, with one line that says why.
- **The extended interrupt mode (x2APIC, EIME).** The first processor has an identifier below 256, which the start checks already. The 32 bits of the destination wait for a processor with a larger identifier.

**QEMU.** QEMU 10 passes a message in the compatible form even with remapping on (it does not emulate the bit CFI), and it checks the requester only for a message that a device sends by its own interrupt path, not for a DMA write to the interrupt addresses: such a write has no requester, and its fault record has the requester 0xFFFF. So the test forges a message that names an entry past the table, which QEMU refuses with the reason 0x21, and the line names the device 255:31.7. On a real machine the unit knows the requester of each write, and it refuses the compatible form too.

## The proof

The part `iommu` of the test runs the whole system on the machine with the IOMMU: the storage service on the data disk and the network service run with translation and interrupt remapping on, so each page that a service gives to its device is declared, and each interrupt of a device comes through its entry. The disk of the measures is behind a root port of PCI Express, on bus 1. The process `iommu`, a client of that disk, makes the root service start the test device service `iommu_device` for it in place of the block service. The test device service:

1. declares its queue and a data object of two pages, writes a block from the first page and reads it into the second: the bytes arrive, through the context table of bus 1, and its message interrupt arrived through its entry (its count is not 0);
2. writes a block of zeros, then reads it into the interrupt addresses at 0xFEEF_0000: each write of the device in the remappable form names an entry past the table, and the unit refuses it; each write in the compatible form names the processor 0xF0, which does not exist, so no processor gets it on QEMU, which passes that form;
3. declares a new page with a known pattern, notes its address, then closes its handle and keeps its mapping: the kernel takes the page out of the domain at the close;
4. puts the address of that page in a descriptor of a read;
5. waits for the condition "the device needs a reset" or "the device used the request", with the hang bound, and checks that the page keeps its pattern.

The kernel writes the line of the refused interrupt after step 2 and the line of the DMA fault with the device at bus 1 and the address after step 4, and the client then gets an answer from the service: the machine goes on. The forged interrupts come before the DMA fault: a virtio device of QEMU that needs a reset does no more requests.

Then `net` runs its cases. Its datagram region is not contiguous: the root service reads that the IOMMU is in use. The network device reads the data of each datagram from the window of that region, which the frame service declared through a handle with Read only ([network_data_path.md](network_data_path.md), "The send with no copy"). The echo of its datagram comes back, and the step fails on a DMA fault of the network device.

The step 2 is the means of the test, and the rule of the close at the same time: a page that the service can read after the write, at an address that it no longer holds by a handle. A real fault gives the device a wrong address by a wrong computation; the result is the same refusal. A close of the handles of the registers would not serve: it ends the whole domain, and the device would then fault on its own queue.

The part `iommu_amd` runs the same system on the unit of AMD, with translation and interrupt remapping on, and the same steps of `iommu_device`. Its disk of the measures and an entropy device of virtio are behind a conventional bridge with no capability of PCI Express (`-device i82801b11-bridge`) at the place 28 of bus 0, at the places 0 and 1 of bus 1: both give the requester of the bridge, 0:1C.0, on bus 0, where QEMU names the device of an event (the facts of QEMU 10 in "Two vendors behind one kernel side"). The root service gives `iommu_device` the disk and the registers of the entropy device, and the kernel writes the line of their one domain at the first declaration. The message interrupt of step 1 arrives through the interrupt table of the requester of the bridge. The read of step 2 ends, and no line is waited for: QEMU records no event for the messages that it refuses. The line of the DMA fault of step 4 comes from the event log, and names the device at bus 0, device 28. Then a sixth step: the service starts its device again while its domain lives, closes the registers of the entropy device, and its domain ends. Its next declaration gives `Bad_State`, with the line of the kernel that names the entropy device at bus 1, device 1. A read of the disk into a page that the service declared before then does not end: QEMU 10 neither ends the request nor says that the device needs a reset when the unit refuses the read of its queue; it keeps the request. The count of the faults of 0:1C.0 is then past the lines that the kernel writes whole (the refused read of step 4 alone makes about 256 faults and fills the event log), and the records of step 4 that the kernel reads after the end of the domain name no service: neither the state of the device nor a line of a fault can bound the wait. The tool bounds it. The disk has no ioevent file (`ioeventfd=off`), so QEMU took or refused the request before the notify returned; after the line of the service, the tool stops the machine, which ends each read that QEMU took, gives the disk a new size and starts it again. The service waits for the new size in the configuration of the device, then checks that the request did not end, that the page keeps its bytes, and that no interrupt arrived: the configuration interrupt of the new size is refused too, as the end of the domain cleared the interrupt entries of the group. The disk of the measures of that machine is made new at each run, so the new size always differs. Then `net` runs its cases through the windows, as in the part `iommu`.

QEMU emulates one unit, with no reserved range. The host tests of `src/kernel/iommu` read a table DMAR with two units (one for a graphics device, one with `INCLUDE_PCI_ALL`) and with reserved ranges, resolve the paths of the scopes through bridges, check the unit that each device gets, and give the shared requester of each kind of conventional bridge. For AMD-Vi, they read the table IVRS of QEMU 10 (a unit described by two blocks), its alias range behind a conventional bridge, and the same table with an alias to the shared requester from a device outside the bridge, which gives no domain, two units with an alias whose source and target are both aliased, the target that each alias names, two units that name one device in either order, the settings of an entry and its pass bits, the reserved ranges of one and of several devices, and the tables that the kernel refuses; they check the class, the flag NpCache and the mask register of the function of a unit, and they check the bits of the device entry, the page entries, the commands, the records of the event log and the interrupt entry against the bits that QEMU 10 checks.

The main test does not move to the machine with the IOMMU yet. Its risks: every virtio device of the main test then goes through the emulated unit (a cost in time for each access of the disk and of the network, which is a measure, not a check), and a page that a service forgets to declare stops a part of the main test with a DMA fault, which is the purpose. The part `iommu` finds such a page first.
