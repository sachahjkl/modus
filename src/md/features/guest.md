# A guest

A process runs another system on the processor, with the virtualization support of the processor. The kernel holds the mechanism: the nested page table, the state of the guest processor, the entry and the exit. The process holds the policy: the memory that the guest gets, and the answer to each exit. The terms are in [`docs/glossary/access.md`](../../../docs/glossary/access.md), "Guest". The guide is [`docs/ARCHITECTURE.md`](../../../docs/ARCHITECTURE.md), "A guest". Why a foreign system runs whole in a guest is in [foreign_systems.md](foreign_systems.md).

## Constraints

- **The kernel holds mechanism only** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "1. Small kernel with a small, counted interface"). No device model, no emulation of an instruction, no firmware is in the kernel.
- **A guest holds only what its process was granted** (property 2, and "Objective"). It reaches the memory objects that its process mapped into it, and nothing else of the machine.
- **Each new kernel operation has its reason.** The bound of [foreign_systems.md](foreign_systems.md) is three to five new operations for the whole of the guest support. The guest support uses one: `Guest_Run`. Each later capability is a field of its record, an argument, or a flag of an existing operation.
- **The test host is an AMD processor.** Nested virtualization of KVM gives a test machine the form of the host processor only: on this host, the AMD form (SVM). The form of Intel (VMX) cannot be tested here.

## The chosen form

### A guest is a process whose page table is the nested page table

A guest is a process that `Process_Create` made and that no thread ever ran. Its page table becomes the nested page table of the guest: a guest physical address is an address of that process. `Memory_Map` with the process handle puts a memory object at a guest physical address; `Memory_Unmap` removes it; `Handle_Revoke` of the memory handle ends the mapping, as in any process. A page on first use gets its frame when the guest first touches it.

Two forms of `Memory_Map` exist for guest memory only, into another process that no thread ran:

- `At_Address_Zero` puts the mapping at the address 0, the guest physical address 0. The address argument 0 keeps its meaning "the kernel chooses".
- `Write` with `Execute` and `No_Access` makes a switching mapping: each of its pages has `Write` or `Execute`, never both, and the kernel switches one page at the nested page fault that asks for the other access ("The switch of a page"). `Memory_Protect` with the process handle gives the whole mapping one access, or `No_Access`. No page table entry is ever writable and executable.

`Process_Start` refuses a process that holds such a mapping (`Bad_State`): a thread there would run with no fault at the address 0, or on pages that it writes and then executes.

The reasons:

- One page table structure of the kernel serves a process, a guest and, later, a device. The format of the long mode page table is the format of the nested page table: each entry of a process has the bit User, which a nested walk needs.
- The mapping, the revocation, the budget of the page tables, the origin tree and the shoot-down exist and are tested. A second address space object would copy each of them.
- The guest is visible as a process in each report: its name, its mapped pages, its stop.

The first run makes the process a guest, under its process lock: the kernel removes the time page and clears the kernel half of the top table. After it, `Process_Start` of that process gives `Bad_State`: a thread with the page table of a guest would run with no kernel half. The first run of each guest processor takes two pages from the budget of the process: its control block and its extended state.

### One operation: `Guest_Run`

`Guest_Run(process, registers, processor)` runs one guest processor of a process on the calling thread until an exit that the kernel does not handle itself. The completion record of the operation is the exit: a record on the kernel ring of the thread. The reason for a new operation: the instructions that enter a guest are privileged, and no existing operation runs code of another address space on the calling thread.

- `registers` is a `Guest_Registers` record in the memory of the caller (240 bytes): the general registers, `rip`, `rflags`, `cr0`, `cr3`, `cr4` and `efer` of the guest processor, its 64-bit system state: `star`, `lstar`, `sfmask`, `fs_base`, `gs_base` and `kernel_gs_base`, its interrupt shadow (`interrupt_shadow`), and `event_pending`, which the kernel writes: 1 when the guest processor holds an event that an exit interrupted. The kernel copies it before the entry and writes it back after the exit. The process answers an exit by a change of the record: the value of a port read in `rax`, the next instruction in `rip`, the new value of a write of `EFER` in `efer`, of `LSTAR` in `lstar`.
- `processor` is the index of the guest processor, from 0 to `GUEST_PROCESSOR_CAPACITY - 1` (32 guest processors).
- The segments, the descriptor tables and the extended state of the guest processor stay in the kernel between two runs.
- A guest processor starts in 16-bit real mode, with each segment at base 0.

The record holds two requests of one run. The kernel serves each one before the first entry of the operation, and clears it in the record that it writes back:

- `mode_load` (`Guest_Mode_Load`): `Real_16`, `Protected_32` or `Long_64` loads the segments of that mode and the privilege level 0, with the selectors of the record. `Keep` (0) loads nothing. A process starts a system in long mode with one run, then passes back the record that it got.
- The event (`inject_kind`, `inject_vector`, `inject_error_code_valid`, `inject_error_code`): an external interrupt (a vector from 32), the non-maskable interrupt, an exception or a software interrupt, which the processor delivers through the interrupt table of the guest at the entry (AMD `EVENTINJ`). The kernel serves an external interrupt only when the record says that the guest takes interrupts; else it opens the interrupt window, and the request stays in the record ("The interrupt window").

The run is an operation of the calling thread, not a thread state of its own. The thread is the guest processor while the operation runs; its process pays the time, as for any instruction of the thread. A process that wants several guest processors runs several threads, each with its own index.

### The exits

The kernel handles two exits itself: a nested page fault on a page on first use of a mapping that allows the access, and a nested page fault that asks a page of a switching mapping for the access that it does not have. It gives the page its frame, or switches it, and enters the guest again.

Each other exit ends the operation with an exit record (`Guest_Exit_Kind`):

| Exit | What the process gets |
|---|---|
| `Port_Write`, `Port_Read` | The port, the size, the value of a write, the address of the next instruction |
| `Halt` | The address of the next instruction |
| `Cpuid` | The registers hold the leaf; the process writes the answer |
| `Memory` | The guest physical address and the access: no mapping there, or a mapping that refuses the access |
| `Interrupted` | An interrupt of the machine ended the run: nothing to answer, run again |
| `Writes_Own_Page` | An instruction writes the page of a switching mapping that holds it: `a` the guest physical address that it writes, `b` 1 for 64-bit code. The instruction never completes |
| `Interrupt_Window` | The guest takes interrupts again: the external interrupt of the record is delivered at the next run |
| `Shutdown` | The guest processor stopped on a triple fault |
| `Refused_State` | The processor refused the state of the guest |
| `Other` | Another intercepted instruction or exception, with the exit code of the processor; for `rdmsr`, `wrmsr`, `rdtsc` and `rdtscp`, the address of the next instruction too |

The guest intercepts each port, each model-specific register, `rdpmc`, `rdtsc`, `rdtscp`, `cpuid`, `hlt`, the instructions of virtualization, `xsetbv`, `invd`, `wbinvd`, `monitor`, `mwait` and each access to a debug register. Each of these touches a state that the guest processor shares with the kernel or with other processes (`rdpmc` reads the performance counters of the machine), or a device of the machine: the kernel does not run it on behalf of a guest.

`rdtsc` and `rdtscp` exit as `Other`, with the exit codes 0x6E and 0x87 (the intercepts: bit 14 of the word at 0x00C, bit 7 of the word at 0x010 of the control block, the AMD manual, volume 2, table B-1). The process answers each one from its own clock: the count in `rdx:rax`, for `rdtscp` the processor number in `rcx`, and the next instruction in `rip`. A guest then reads no time of the machine, and no processor number through `rdtscp`. The processor checks `CR4.TSD` and the privilege level before the intercept: the fault of a read that the guest forbade itself never reaches the process.

The guest also intercepts two exceptions of its own: the debug exception (`#DB`, exit code 0x41) and the alignment check (`#AC`, 0x51). A guest that owns its interrupt table and its stack can make the delivery of one of them raise it again: the processor then loops inside the delivery, takes no interrupt, never exits, and each processor that waits for it stops too. Each arrives as an exit `Other`, with no kind of its own. The process gives the exception back to the guest with an event of the kind `Exception` at the next run: a guest that needs single steps or the alignment check keeps them, and a loop in the delivery still exits at each step. The instruction `int1` (icebp) raises a debug exception that the exception intercept does not cover: it has an intercept of its own, which the kernel sets, and arrives as an exit `Other` with the exit code 0x88; `guest_demo` checks it.

A nested page fault with the reserved bit set ends the run with the exit `Memory` and one line of the log; it does not stop the machine. A guest may cause it with an address past the width of the nested table, and no exit that a guest can cause stops the machine.

### The interrupt window

The processor delivers an injected event with no check of the interrupt flag of the guest or of its interrupt shadow. An interrupt of a device that a guest receives with its interrupt flag clear breaks the guest: it runs a handler in a section that `cli` protects. So the kernel checks the record before it injects an `External_Interrupt`: with the interrupt flag set in `rflags` and `interrupt_shadow` 0, it writes `EVENTINJ`; else it opens the interrupt window of the guest processor and writes no event.

The window is the virtual interrupt of SVM: the kernel sets `V_IRQ` (bit 8 of the word at 0x060 of the control block) with the priority 15 (`V_INTR_PRIO`, bits 16 to 19) and `V_IGN_TPR` (bit 20), and intercepts `VINTR` (bit 4 of the word at 0x00C). With `V_INTR_MASKING`, which the kernel always sets, the guest takes the virtual interrupt when its own interrupt flag is set and it is out of its shadow; the processor then exits with the exit code 0x64 before the guest receives anything. The run ends with `Interrupt_Window`. The request is still in the record: the process runs again with it, and the kernel now injects it. Each run writes the window again, open or closed, so a window of an earlier run never ends a later one.

An injected interrupt that an exit interrupts before the guest received it comes back in `EXITINTINFO` ("Subtle points"): the kernel delivers it at the next entry, and writes `event_pending` 1 in the record, after the last entry of each run. A request of the process waits behind it. An `External_Interrupt` that waits behind such an event opens the window too: the held event goes first, then the run ends when the guest takes interrupts again, not at the next interrupt of the machine. So no interrupt is lost between the process and the guest.

The process of a Linux guest (`guest_os.linux_machine`) asks for the vector of the line that waits as soon as one waits. With the guest taking no interrupt, the request only opens the window: no line goes into service, and the exit `Interrupt_Window` acknowledges the line and asks for its vector. It asks for no vector below 32: before the guest programs its interrupt controllers, their base is 0.

The pure part (the bits of the window, the choice between the injection, the wait and the window) is in `guest_rules` (`interrupt_window_write`, `event_service`), with host tests.

### The switch of a page

A page of a switching mapping is writable or executable, never both ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "11. Reproducible system": the rule for the memory of a guest says that an entry of the nested page table is never writable and executable at once, and that the process that runs the guest maps its memory with no Execute; the rule is for each entry). A system writes its code and runs it in the same memory: a kernel that loads a module, a program that the system loads, a decompressor. So the access follows the guest page by page:

- A nested page fault of a write on a page that is executable, or of a fetch on a page that is writable, makes the kernel write that one entry of the nested page table with the other access. A page on first use gets the access of its fault (a read gets the access of the mapping). The run goes on with no exit to the process.
- The access of a page lives in its entry of the nested page table only. `Memory_Protect` of the whole mapping with `Write`, `Execute` or `No_Access` gives each present page that access again. A read-only protection and a protection of a part are refused (`Bad_Operation`): the next fault would switch the page whatever they said.
- The bound: each switch counts as a page given, so `GUEST_PAGES_IN_ONE_RUN` (64) switches and first uses end one run with `Interrupted`, and the process runs again.
- The cost: one nested page fault and one write of an entry for each switch, with no exit to the process. A switch takes away an access: the kernel sends its interrupt to each other processor that runs a guest processor of the same guest (`processors_with_table`), as an unmap does, and that run ends. The processor that switched needs no flush of its own: each entry flushes the translations of the guest address space identifier ("Subtle points"). A flush of the one page (`invlpga`) would add an instruction to each switch and remove no flush.
- The kernel counts the switches of each guest and the exits `Writes_Own_Page`, and writes both in one line of the log when the guest ends: a measure, not a bound.

**An instruction that writes its own page.** An instruction fetched from page P that writes P needs both accesses at once: the fetch switches P to `Execute`, the write to `Write`, and the instruction never completes. The kernel watches each guest processor: when the same page switches with the other access at the same `rip` twice in a row and then faults on a write, the run ends with the exit `Writes_Own_Page`, with the address that the instruction writes.

The process does that one write for the guest: Linux reaches it at its start, when it patches its own text with `memcpy` (`text_poke_early`), and `memcpy` has sites to patch in its own page. The loop is found at a write, so the exit gives the address that the instruction writes. The machine of `guest_os` decodes the instruction with the decode of a device access (a `mov` to memory), writes its bytes through the mapping of the memory in the process, and moves `rip` past it; the page of the guest keeps the access that the kernel gave it. It decodes only 64-bit code (`b` of the exit is 1), and does the write only when the linear address of the operand, through the page table of the guest, is the address of the exit. It refuses each other instruction (a string store with `rep`, as `rep movsb`, or a `lock`), an address of 32 bits, an operand at another address, and a write that crosses a page: the guest then stops with a line. Linux reaches it with the `mov` of `memcpy`; a `rep movs` that writes its own page would stop Linux, which the machine test would show. The forms refused for it:

- An emulator of the write in the kernel: a decoder of the stores of x86 in the kernel, which the properties forbid ("Constraints"), for code that the process can answer.
- A step of the instruction with the page writable and executable: the entry would be both for one instruction, which property 11 ("Reproducible system") forbids.
- A stop of the guest with no write: every boot of Linux stops at its first patch of its text.

### The run, step by step

1. Under the lock of the caller: the handle with **Control**, the copy of the registers record. Then the checks of the record (`guest_registers_check`) and of the index of the guest processor, with no lock.
2. Under the lock of the guest process: its state (`Created`, no thread), the setup of the first run of the process and of the guest processor, the flag `running` of the guest processor, and one hold of the process, as a thread on a processor holds its process.
3. With no lock, once: the mode load, and the event or the interrupt window in the control block. The flag `running` gives the run its guest processor alone.
4. With no lock: the save of the extended state of the thread, the restore of the extended state of the guest, the entry, the exit, the save of the guest and the restore of the thread. Interrupts of the machine are on during the guest, so that a timer tick, a wake and a shoot-down end the run at once.
5. A nested page fault on a page on first use, or one that asks a page of a switching mapping for the other access: the kernel gives or switches the page under the guest lock, and goes back to step 4. A page that writes itself ends the run ("The switch of a page").
6. The served requests leave the record. Under the guest lock, the flag `running` clears. The hold ends: a stop of the guest process during the run cleans the process up here, as the last processor of a stopped process does.
7. Under the lock of the caller: the copy of the registers back, and the exit in the completion record.

### A machine with no support

A processor with no SVM, no nested paging, SVM turned off by the firmware, or fewer than two address space identifiers gives `Bad_Operation` with the error kind `Unsupported` for each `Guest_Run`. A process learns it from its first run. The log of the boot says which.

## Refused forms

- **Intel VMX first.** It cannot run on the test host: KVM on AMD gives a guest SVM only. A form that no test runs is not built first. VMX is the next form, with the same operation and the same records.
- **A hypervisor in the kernel with device models** (the form of KVM with its emulated devices, or of a type-1 hypervisor). It puts the code of the devices, which a guest drives with hostile values, in the kernel. Property 7 forbids drivers in the kernel; a device model is a driver of the other side.
- **A type-2 hypervisor in a process with no kernel help.** A process cannot run the privileged instructions of virtualization; the only form left is an emulator of the instructions, two orders of magnitude slower, which the processor support makes needless.
- **A Guest object kind with its own handle.** A second kind of address space would copy the mapping, the revocation and the reports of a process. The process is the address space; the guest processor is its state.
- **One operation to create a guest.** The first run makes the guest. A creation operation would add a kernel operation for one setup that has no other argument.
- **The exits on a ring of their own.** The completion record of the operation is already a record of a ring, and the thread that runs the guest waits for nothing else while it runs.
- **The guest processor as a thread state that the scheduler runs.** It puts the entry of a guest on the path of the scheduler, and a second kind of thread in each strategy. The thread that calls `Guest_Run` is the guest processor; the scheduler sees one thread.
- **A mode that each run loads.** A field of the mode that the kernel applies at each run writes the segments again at each run, over the segments that the guest loaded itself: a guest in real mode changes `ds` all the time, and a guest in protected mode has segments that the kernel cannot read from its descriptor table. The load is a request of one run; `Keep` is its zero.
- **The 64-bit system state that stays in the kernel only.** Each access to a model-specific register exits, so a guest that writes `LSTAR` or `FS_BASE` waits for its process, and the process had no way to put the value in the guest processor: a Linux guest could not make a system call. A new operation to write one register would add an operation for a state of six words; the record carries the six words, at a cost of 48 bytes. `CSTAR` (the entry of `syscall` from 32-bit code) and the three `SYSENTER` registers are not in the record: a guest of 64 bits does not enter through them, and the process keeps the values that the guest writes.
- **The control registers that stay in the kernel only.** The guest writes them itself, but the process must answer a write of `EFER`, which exits, and must start a guest in long mode. A record that carries them in and out does both with no new operation; the cost is 48 bytes of record.
- **Pages that are writable and executable for a guest.** Property 11 ("Reproducible system") says that an entry of the nested page table of a guest is never writable and executable at once. Each page of a switching mapping gets one access at a time ("The switch of a page"). The process that runs the guest writes the memory of the guest through its own mapping, which has no Execute: it is the machine of the guest, and the property allows it.
- **A switch of the whole mapping by the process.** A guest mapping switched between `Write` and `Execute` as a whole, with `Memory_Protect` at each exit `Memory`. An instruction that writes data in the mapping that holds its code then never completes: each fetch gives the mapping `Execute` and each write `Write`. The decompressor of a bzImage of Linux does it at its first instructions, in a region of 2 MiB; with mappings of one page, a process runs out of mappings at 128. The switch of one page by the kernel costs no exit.
- **The address of `Memory_Map` with one more meaning.** The address 0 means "the kernel chooses" for each process. A flag, `At_Address_Zero`, names the address 0 with no change of that meaning.
- **An offset of the time stamp counter** (`TSC_OFFSET`, at 0x050 of the control block). The guest still reads the counter of the machine, moved by a constant: it still measures the time of the machine, and two runs of one build read different values. The intercept costs one exit at each read; a guest that reads the counter often (a calibration loop) pays it.
- **The kernel that answers `rdtsc` itself**, from a clock of the guest in the kernel. The clock of a guest is a policy of its process (a build wants a virtual clock that moves at each exit, another guest the time of the machine); the kernel holds no clock of a guest.
- **An exit kind for `rdtsc`.** The exit `Other` already carries the exit code, and the next instruction is a result of the operation: a new kind adds a word of the contract for no new fact.
- **The process that checks the interrupt flag alone.** The process injected only after an exit with the interrupt flag set and no shadow. A guest that ran `cli` and then a long loop with no exit kept its interrupt until the next tick of the machine: a delay that the guest cannot bound. The window costs one exit, at the instruction where the guest takes interrupts again.
- **The kernel that keeps the external interrupt across runs.** The kernel could hold the request and inject it at the window with no exit to the process. It then holds a queue of events of a device that the process models, which is policy: the process may want to deliver a higher vector that came meanwhile. The request stays in the record, and the process decides at each run.
- **A field of its own for the interrupt window.** A flag of the record could ask for the window with no event. The window has no use without the event that it waits for: the request of an `External_Interrupt` is the flag.
- **An external interrupt at any vector.** The vectors 0 to 31 are the exceptions of the processor: a guest that took an interrupt there would run the handler of an exception with no error code on its stack. The refusal excludes a guest in real mode that keeps the base of the controllers of the PC (8 for the primary, 0x70 for the secondary): the primary there gives 8 to 15. A guest of the system runs in protected mode or long mode and programs its controllers first, as Linux does; a guest in real mode that needs interrupts is not supported.
- **A refusal of the external interrupt in the shadow.** The kernel refused the record before the window. A process then had to read the shadow and wait for another exit; the window does it with no rule for the process.
- **An operation for each new capability** (an operation to inject, one to load a mode, one to make a guest processor). Each is a field of the record or an argument of `Guest_Run`: the operation count does not change.

## Subtle points

- **The extended state.** The kernel has no vector instruction, and the registers of a thread stay live through each kernel entry. A guest changes them. So the run saves the thread and restores the guest before the entry, and the reverse after the exit, with the three procedures that may name those registers. The save of the guest uses `xsave`, not `xsaveopt`: the guest can run `xrstor` at any address, and `xsaveopt` trusts the address of the last `xrstor`.
- **The state that the exit does not restore.** The exit gives back the control registers, the segment table and the stack, not `fs`, `gs`, the task register, the system call registers and the debug registers. `vmsave` and `vmload` keep the first four: `guest_enter` saves the state of the kernel with `vmsave` to the host page of the processor, loads the state of the guest from its control block with `vmload` before `vmrun`, saves it there with `vmsave` after the exit, and loads the state of the kernel again; the guest cannot write a debug register (each access exits), and the kernel writes the debug control register again after the exit, with the breakpoints of the thread when it has some.
- **The shoot-down.** A processor that runs a guest uses the nested page table of the guest process, not the table in its `cr3`. The kernel writes that table in a word of the processor before the entry, and `processors_with_table` reads it: an unmap in the guest process sends its interrupt to the processor that runs the guest, whose run ends at once. Each entry flushes the translations of the guest address space identifier, so no translation outlives an unmap.
- **One address space identifier.** Nested KVM gives 8 identifiers; the kernel uses one for every guest and flushes it at each entry. The cost is a cold translation cache after each exit. A generation of the nested table would keep it (not built: no measure asks for it yet).
- **The stop of a guest process.** `Process_Stop` of a guest process keeps the contract of a stop: when it returns, no instruction of the guest runs. `process_stop` adds each processor whose word of the running nested table names the table of the process to the processors that run its threads: each one gets the wake interrupt, which ends the run at once, and the stop waits for the hold of the run, as for a thread on a processor. A run that writes its word after the stop read it sees the state `Stopped` before its entry, and does not enter: each side writes, then reads the word of the other side.
- **An event that an exit interrupts.** An exit can come while the guest delivers an event: a page on first use of its interrupt table or of its stack, or an interrupt of the machine during the delivery. The processor gives that event in `EXITINTINFO`; the kernel copies it to `EVENTINJ` after each exit, and the next entry delivers it, in the same run or in the next `Guest_Run`. An event of an instruction (`int n`, `int3`, `into`) is not copied: the guest is still at that instruction, which runs again.
- **What a guest still sees of the machine.** `rdpid` gives the processor number that the kernel wrote in `TSC_AUX`: a guest learns on which processor it runs, as a process does. `rdtscp` exits, so it gives the number that the process chooses. A guest can turn on protection keys in its own `cr4` and write `PKRU`; the kernel does not save `PKRU` (it is not in `XCR0`), so the next guest on that processor can read it: a channel of 32 bits between two guests of one processor. A process has no such channel, because the kernel never turns protection keys on for a process. A clear of `PKRU` at each exit would close it (not built).
- **Long mode.** Each write of a model-specific register exits as `Other` (exit code 0x7C). The process answers a write of `EFER` with the new value in `efer` of the record and the next instruction in `rip`; the guest then turns paging on itself, and the processor sets LMA. A process that starts a system in long mode at once gives a record with `mode_load` `Long_64` and the control registers of long mode. The kernel always sets SVME in `EFER` and the extension type in `cr0`: the processor refuses a guest without them.
- **The checks of the record.** `guest_registers_check` refuses a bit that no processor defines in `cr0`, `cr3`, `cr4` and `efer`, an inconsistent long mode (LMA without LME, PG and PAE; LME and PG without LMA), a non-canonical `rip` in long mode, a non-canonical `lstar`, `fs_base`, `gs_base` or `kernel_gs_base` in any mode, and a bit of `sfmask` from 32. The processor checks the rest at its entry, and refuses it with `Refused_State`: the kernel checks first only what gives a clearer refusal. The record that the kernel writes back is masked to the same bits, so that a process can always pass it back.
- **The 64-bit system state in the control block.** The kernel writes the six words of the record at each entry and reads them back at each exit, at the offsets of the save area (the AMD manual, volume 2, table B-2): the base of `fs` at 0x448 and of `gs` at 0x458 (the bases of their segment records at 0x440 and 0x450), `STAR` at 0x600, `LSTAR` at 0x608, `SFMASK` at 0x618 and `KernelGsBase` at 0x620; `CSTAR` at 0x610 stays 0. `vmrun` does not load them: `vmload` does. `guest_rules` holds the offsets and the two procedures, so a host test checks each byte. The record wins over a mode load: a mode load writes the segments of `fs` and `gs` with base 0, and the entry then writes the bases of the record. A process that loads real mode with a data selector other than 0 writes the selector times 16 in `fs_base` and `gs_base` itself. The read back puts each address in its canonical form and clears the reserved bits of `SFMASK`, so a process can always pass the record back.
- **An injected event that an exit interrupts.** A nested page fault on the interrupt table or the stack of the guest can interrupt the delivery of an injected event. The guest processor keeps the injected word and the address of the injection (`Pending_Injection`) until the guest has received it. After each exit, an event in `EXITINTINFO` with the type and the vector of that word, with the guest still at that address, goes to the next entry again, whatever its type. The same event from an `int n`, `int3` or `into` of the guest is not delivered again: the guest is at that instruction, which runs again.
- **The return address of an injected software interrupt.** With NRIPS, the delivery of a software interrupt, `int3` or `into` pushes the address in `CONTROL_NEXT_INSTRUCTION`, which each exit overwrites. Before each entry that delivers such an injected event, the kernel writes the address of the injection there, so that the guest returns to `rip` of the record. Without NRIPS, the processor pushes `rip`.
- **An event waits behind an interrupted event.** After an exit that interrupted a delivery, the control block holds that event for the next entry. A request of the process then waits: the kernel enters with the interrupted event, and leaves the request in the record. After `Refused_State`, the kernel drops the event that it wrote, and the request stays in the record too.
- **The kernel checks the record, not the control block.** The kernel decides between the injection and the window from `rflags` and `interrupt_shadow` of the record, which it writes into the control block before the entry: the guest enters with that state. A process that changes the interrupt flag of the record changes what the guest runs with, so the choice follows it. An exception and a software interrupt do not wait for the window: an instruction raises them whatever the interrupt flag.
- **The interrupt shadow.** After `sti` or `mov ss`, the processor takes no interrupt and no non-maskable interrupt until the next instruction completes. The kernel reads bit 0 of the word at 0x068 of the control block (`INTERRUPT_SHADOW`, the AMD manual, volume 2, table B-1) into `interrupt_shadow` after each exit, and writes the field there before each entry; bit 1 of that word is read only, and the kernel writes it 0. The rules of the record: `interrupt_shadow` is 0 or 1, `event_pending` is 0 or 1, the two bytes after them are 0, and an event of the kind `Non_Maskable_Interrupt` with `interrupt_shadow` 1 is refused (`Inject_In_Interrupt_Shadow`): the processor would deliver it one instruction early. An `External_Interrupt` in the shadow waits for the interrupt window. An exception and a software interrupt stay allowed: an instruction in the shadow can raise one. A process that completes the instruction of the exit (it moves `rip` past it) clears `interrupt_shadow`, as the processor does: that instruction ended the shadow. With `sti; hlt`, the exit of `hlt` comes in the shadow; the process that answers it moves `rip`, clears the shadow, and can inject at once.
- **The injection of a machine check.** `Guest_Inject_Kind.Exception` refuses the vector 18: the kernel takes a machine check of a guest as a fault of the machine and stops it, and an event of the process must not do that.
- **Several guest processors.** Each one has its control block and its extended state, and its flag `running` under the lock of the guest process: one thread runs it at a time, and other threads run the other guest processors of the same guest at once. They share the nested page table and the address space identifier, which each entry flushes on its processor: two guest processors on two processors keep no translation that an unmap left. A stop and an unmap reach each processor whose word of the running nested table names the table of the guest, so they reach each running guest processor. A guest processor that a process never ran costs nothing. An interrupt between guest processors (an IPI of the guest) is a write that exits to the process, which injects the event in the other guest processor.
- **The memory of 32 guest processors.** The kernel keeps one record `Guest` for each process slot, with a record of 72 bytes for each of the 32 guest processors: 2 328 bytes for each slot, 146 KiB for the 64 slots of today and 582 KiB for 256 slots (measured with `size_of` of the kernel types and their parts). The memory that grows with use, the control block and the extended state of a guest processor (two pages), comes from the budget of the process at the first run of that processor and goes back to it at the end of the guest. Refused: the records of a guest in pages that the budget of its owner pays at its first run. It adds an allocation and a failure to the first Guest_Run of each guest to save 2.3 KiB of each slot. The end of a guest, under the process lock, reads the 32 records and gives back at most 64 pages: a fixed bound, whatever the guest did.
- **A switch while another guest processor runs.** A switch that takes `Write` away sends its interrupt to each processor that runs a guest processor of the guest, and `processor_sync` waits until each one left its run before the switching processor enters again. In that time, a third guest processor can enter: its entry flushes the translations, so it sees the new entry, and can execute the page while the second one still writes it through its old translation, until its interrupt comes. The window is the delivery of one interrupt. Keeping each guest processor out until the sync ends would need a lock of the guest on each entry; not built.
- **Two guest processors that fault one page in opposite directions.** One writes the page while the other executes it: each fault switches the page and ends the run of the other. Nothing but the order of the entries bounds this: the switching processor enters again first, after the sync, and its instruction then completes before the other faults again, as a rule; no count stops the exchange. A system whose processors write and execute one page at once is rare (a JIT that patches code that another processor runs); the watch of `Writes_Own_Page` is of one guest processor, and does not see it.
- **What the watch counts.** A switch counts toward `Writes_Own_Page` only when the fault is the access of the instruction: a fault while the processor walks the page table of the guest (bit 33 of the first exit information) or while it delivers an event (`EXITINTINFO` valid) ends the row. The row is of one page, one `rip` and one `cr3`.
- **The rule of property 11 for the process.** The process that runs a guest maps the memory of the guest with no `Execute` ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "11. Reproducible system"). The guest builder and `linux` do it; the kernel does not refuse it yet, and the gap is wider: no check stops one memory object mapped with `Write` in one mapping and with `Execute` in another, in one process or across processes. The check that closes it counts, for each memory object, its live mappings that write and those that execute (or switch), and refuses a map that would give it both, as the counts of the cache types of device memory do; a guest mapping that switches counts as both, so the process that runs the guest can map its memory with `Write` and never with `Execute`. Planned (`ROADMAP.md`).
- **The check of the build.** `vmrun`, `vmload` and `vmsave` start with `v`, like the vector instructions that the check of the kernel refuses (`tools/modustool/build/vector_check.odin`). The check lets them through by the name of the procedure: in `guest_enter` only, and refuses them anywhere else.
- **No page is writable and executable.** The rule of a process holds in a guest, page by page. The kernel writes an entry of a switching mapping with `Write` and no execute, or with execute and no `Write`, and with nothing else: `guest_rules.switched_entry_bits` gives the bits, and refuses a fault that asks for both. The memory object of a guest stays writable in the process that runs the guest: that process is not the guest, and its own pages of the object are not executable.
- **Page 0 of a guest.** `Memory_Map` with `At_Address_Zero` maps at the guest physical address 0. `guest_demo` still starts at 0x1000.
- **Guest memory before the first run.** The two forms of guest memory need a process that no thread ran, not a process that is a guest already: a process loads the memory of its guest before the first run. `Process_Start` refuses a process with such a mapping, so a process with guest memory never gets a thread.
