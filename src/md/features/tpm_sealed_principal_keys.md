# The keys of a named principal sealed by the TPM, and their recovery key

## Purpose

The keys of a named principal were sealed under a key that Argon2id derives from its passphrase, and nothing else. A copy of the disk then allows tries of passphrases without limit, at the cost of one derivation each. A principal who loses the passphrase loses the principal: no administrator can reset it (property 21).

This design seals the keys by the TPM, to the measure of the system and to the passphrase together. A copy of the disk then allows no try away from the TPM of the machine. The TPM counts each wrong passphrase, and after too many it limits the rate of the tries; this holds only while the lockout hierarchy of the TPM has an authorization value that the attacker does not know, so the TPM service sets a random one, which nobody keeps, when it finds an empty one (see "The count holds only with a lockout authorization value"). A recovery key, shown one time at the creation, opens a copy of the keys when the TPM refuses or when the passphrase is lost.

The guide is [`docs/PRINCIPALS.md`](../../../docs/PRINCIPALS.md), "The keys sealed by the TPM". The terms are in [`docs/glossary/trusted_boot.md`](../../../docs/glossary/trusted_boot.md): "Authorization value", "TPM secret", "Recovery key". The design of the seal itself (the TPM service, the proof of the creation, who may seal) is [tpm_sealed_machine_key.md](tpm_sealed_machine_key.md); this file states only what differs.

## Constraints

- **The TPM and the passphrase together.** A seal by the TPM beside a seal under the passphrase, each enough alone, is refused for the machine key ([tpm_sealed_machine_key.md](tpm_sealed_machine_key.md), "Refused forms"): an attacker with the disk tries passphrases against the second one. The same holds here.
- **The tries must be counted where the attacker cannot copy them.** Only the TPM can count: a count on the disk is reset by a copy of the disk.
- **The count of the TPM is set by its lockout hierarchy.** `TPM2_DictionaryAttackParameters` and `TPM2_DictionaryAttackLockReset` need only the lockout authorization value, not the PCRs. A new or cleared TPM has an empty one.
- **The system has no orderly stop.** A machine stops at once; no process sends `TPM2_Shutdown`. A TPM counts one failure at each start that follows a use of an object that it protects, with no `TPM2_Shutdown` between them.
- **No new kernel operation, no new grant.** `unlock` already holds the ring of the TPM service.
- **The tests run on one software TPM (libtpms)**: three tries, then a lockout of 1000 seconds of the time of the TPM, which runs only while a machine runs.

## The chosen form

### What the TPM seals

The TPM seals a TPM secret: 32 random bytes. The file keeps the two secret keys sealed with ChaCha20-Poly1305 under the seal key: keyed BLAKE2b of the TPM secret over the key of the passphrase. The key of the passphrase is Argon2id of the passphrase and the salt of the file, as before.

The sealed object has an authorization value: keyed BLAKE2b of the key of the passphrase over a text of its own. Its policy is `TPM2_PolicyPCR` with PCR 7 and PCR 11, then `TPM2_PolicyPassword`. Its attribute `noDA` is clear: each wrong value is a failure that the TPM counts.

So the keys need three things: the TPM of this machine, the measure of this system, and the passphrase. Why the passphrase enters twice:

- **As the authorization value**, so that the TPM checks it and counts each wrong one.
- **In the seal key**, so that a reader of the TPM secret still runs Argon2id for each guess. The secret crosses the bus of the TPM in clear at each seal and unseal (no encrypted session is built), and a TPM can leak.

### Why `TPM2_PolicyPassword` and not `TPM2_PolicyAuthValue`

`TPM2_PolicyAuthValue` sends an HMAC keyed with the value, and the TPM service would compute and check HMACs. `TPM2_PolicyPassword` sends the value in clear. Both extend the policy with the same code, so the object is the same. A reader of the bus gains nothing more from the value in clear: the session has no salt and no bind, so an HMAC with the known nonces is the same test of a guess. Each guess still costs one Argon2id. The encrypted session, when it is built, covers both.

### The order of the checks of the TPM

The TPM checks the lockout, then the policy (the PCRs), then the value. So:

- On another system, the TPM answers `TPM_RC_POLICY_FAIL` and counts nothing: the passphrase is not checked there. A changed system asks for the recovery key, whatever the passphrase typed.
- On this system, a wrong value answers `TPM_RC_AUTH_FAIL` and counts one failure. The TPM answers `TPM_RC_BAD_AUTH` for a failure that it does not count; the service never sees it, as it checks that `noDA` is clear before the unseal.
- After too many failures, the TPM answers `TPM_RC_LOCKOUT` on each system, even before it checks the PCRs. The window then asks for the recovery key, or the principal waits.

### The count holds only with a lockout authorization value

The count limits a rate, not a number. After the lockout, the TPM forgives one failure at each recovery time. On the test TPM (libtpms, with no setup) that is three tries, then one try for each 1000 seconds of the time of the TPM: about 86 tries a day while the machine runs. A hardware TPM has the limits that its owner or its firmware set.

The count is worth only as much as the lockout authorization value. With an empty one, an attacker with the machine starts another system (Secure Boot off, or any signed loader), sends `TPM2_DictionaryAttackParameters` with a recovery time of 0, or a large count of tries, or `TPM2_DictionaryAttackLockReset`, then starts this system again. The PCRs match the seal, and the attacker types guesses in the window of `unlock` with no limit of the TPM: each guess then costs one derivation of Argon2id, as for the form `PRINCIPL`. So the form `PRINCIPT` is never weaker than `PRINCIPL`, and it limits the rate of the tries only on a TPM whose lockout authorization value the attacker does not know.

### The lockout authorization value

The TPM service reads two groups of properties of the TPM with `TPM2_GetCapability` (`TPM_CAP_TPM_PROPERTIES`):

- At each start, before it serves its ring: `TPM_PT_LOCKOUT_COUNTER`, `TPM_PT_MAX_AUTH_FAIL`, `TPM_PT_LOCKOUT_INTERVAL` and `TPM_PT_LOCKOUT_RECOVERY`, the count limits. It writes them on one line of the log, and a warning when the interval is 0: such a TPM limits no rate. This read changes nothing.
- Just before the first `Seal` or `Unseal` that carries an authorization value: `TPM_PT_PERMANENT`, whose bit `lockoutAuthSet` says if the lockout hierarchy has an authorization value. The check ends for the run only once the TPM answered that read. A read that fails, or a change whose answer the interface lost, leaves the check to the next such request, so one silent read never leaves the hierarchy unchecked for the run.

The value matters only for an object whose wrong values the TPM counts, that is, the keys of a named principal and the machine key under a machine passphrase ([tpm_sealed_machine_passphrase.md](tpm_sealed_machine_passphrase.md)). So a boot that never seals or unseals such keys (a trial boot, a machine with the machine key sealed by the TPM alone, a system with Secure Boot off that never seals) leaves the lockout hierarchy as it found it. The first guess of an attacker in `unlock` is such a request, so the check comes before it in each case.

When the bit is clear, the service draws 32 bytes from the generator of its process, with the strength that a key needs, and sends `TPM2_HierarchyChangeAuth(TPM_RH_LOCKOUT)` with the empty value in a password session. Then it erases the bytes. From then on, `TPM2_DictionaryAttackLockReset`, `TPM2_DictionaryAttackParameters` and `TPM2_Clear` by the lockout hierarchy need a value that nobody knows. When the bit is set, the service writes one line and changes nothing.

**Where the value lives: nowhere.** No process, no file and no store keeps it. The reasons:

- **Nothing in the system may use it.** Its uses are the reset of the count, the change of its limits and the clear of the TPM. A reset by this system is a refused form (see "Refused forms"): a process that can ask for it makes the count worthless. A value that the system keeps only waits for a command that must not exist.
- **A kept value joins two principals.** The machine key has a copy under the recovery key of the machine. With a lockout value sealed under the machine key, the holder of that recovery key gets a reset of the count, and so tries without limit against the passphrase of a named principal: the keys of alice then fall to the recovery key of principal 0 and Argon2id alone.
- **A kept value needs a new grant.** The TPM service holds no store. A store for one value, which no command reads, gives a process a right for nothing.

"Nobody keeps it" means after the draw: the root service chose the seed of the TPM service, as it chooses its code and its grants, and erased the seed that it served.

The cost is stated. A principal locked out by the count waits for the recovery time of the TPM, or types the recovery key: the storage key is exempt from the count, so the recovery and the new seal work during a lockout. The count limits stay those of the TPM: modus cannot change them later. A clear of the TPM then needs the platform hierarchy: the menu of the firmware, or the physical presence interface, each of which needs presence at the machine. A clear destroys the storage key and each seal; the recovery keys cover that case, and the first use of a passphrase after it sets a new lockout value.

**A value that this service did not set.** The bit says only that a value exists, not who set it: the service keeps no copy to compare, and the TPM gives no owner. The service cannot take the value over (a change needs the old value) and does not try. It writes one line: an earlier start of this system set it, or another system did. Then the count holds against each party that does not know the value, and not against the system that set it. A machine that starts another system that set the lockout value (a second operating system on the machine, or an attacker who reached the TPM before the first use of a passphrase in modus) has the trust of that system. Only a clear from the firmware gives the hierarchy back to modus.

### `TPM2_Shutdown` after each use of the passphrase

The TPM marks in its memory that an object with `noDA` clear was used. At the next start it counts one failure, unless `TPM2_Shutdown` came first. The system never sends it at a stop, so each start after an unlock would count one failure; the third start would lock the TPM.

So the TPM service sends `TPM2_Shutdown(CLEAR)` after each unseal with an authorization value that the TPM answered, before it gives the completion, except after a counted failure (`TPM_RC_AUTH_FAIL`). It says only that no try is in progress. An attacker who cuts the power during a try still gets one failure counted at the next start, as the TPM marked the use before the check.

**No shutdown after a counted failure.** The reference code writes a failure to its non-volatile memory before it answers, when that memory is available; a hardware TPM can defer or rate-limit that write, and keep the failure in its RAM. A shutdown then makes the state orderly, and a cut of the power loses the failure: "guess, then cut the power" would count nothing. With no shutdown, the mark of the use stays, and the next start counts one failure at least. The cost: a principal who mistyped and then stops the machine pays one more failure at the next start; a right passphrase later in the same run sends the shutdown and clears it. After every other answer, a policy failure included, the shutdown is sent: the TPM marks the use before it checks the policy. The TPM goes on to take commands after `TPM2_Shutdown`; a later command that changes state makes the state not orderly again, which counts nothing when no object of this kind was used.

A TPM that follows the reference code answers `TPM_RC_RETRY` at the first use of such an object after a start. The service sends the unseal again, three times at most. libtpms does not ask.

### The file

`unlock` keeps one file of a named principal, the object `principal`, in one of two forms by its first 8 bytes: `PRINCIPL` (under the passphrase alone) or `PRINCIPT` (sealed by the TPM). Both forms use format 3 (formats 1 and 2 are refused as older formats). The form `PRINCIPT` keeps the first 180 bytes of `PRINCIPL` (the magic, format, name, public keys, principal identifier, Argon2id parameters, salt, and 24-byte `Unlock_Hints` block), then the PCRs, the four parts of the sealed object in the form of the record of the machine key, the keys under the seal key, and the keys under the key of the recovery key.

The additional data of the seal under the seal key covers every byte before the nonce (`PRINCIPL`) or before the PCRs (`PRINCIPT`), which includes the 24-byte `Unlock_Hints` block: tampering with the keyboard layout, assistive flags, or language breaks ChaCha20-Poly1305 verification. The additional data of the recovery seal stops before the salt, so a new passphrase or an authenticated update of `Unlock_Hints` keeps the copy under the recovery key valid.

The opened keys must give the public keys of the file: that check takes the place of the key check of the machine key.

### The life of the file

**The creation.** With the TPM service and Secure Boot on, `principal_create("alice")` gives the form `PRINCIPT`. The passphrase is typed two times. `unlock` makes the keys, the recovery key and the TPM secret, seals the copy under the recovery key, has the TPM seal the secret with the value, and seals the keys in a file that waits in memory. Its window then shows the recovery key until Enter. Only after Enter does `unlock` write the file, give the record to the root service, and start the session. So a stop before Enter (a close of the window, a fault, a cut of the power) leaves no principal: nobody saw a recovery key that a file holds. The write at Enter reads the file back when the store does not answer it, as a change does (see "The write at Enter, and its read back"). With no TPM service, or with Secure Boot off, the form is `PRINCIPL`, with a line of the log that says why: it has no recovery key, so the file is written and the session starts after the second passphrase.

**The unlock.** The passphrase gives the value; the TPM gives the secret; the two give the seal key. A wrong passphrase: the window says that the TPM counts it.

**A lost passphrase.** The prompt of the passphrase of an unlock has an item of its action bar, Ctrl+R "recovery key", that asks for the recovery key at once, as the prompt of the machine passphrase does ([tpm_sealed_machine_passphrase.md](tpm_sealed_machine_passphrase.md), "The life of the record"). A principal who lost the passphrase then types no wrong try: each one would count in the TPM, against the machine passphrase and each other principal too, and nothing in the system resets the count. No request reaches the TPM. The item shows only for the form `PRINCIPT` while the TPM service runs: the form `PRINCIPL` has no copy under a recovery key, and with no TPM service the window asks for the recovery key already. Enter with nothing at the recovery key goes back to the passphrase, as after a refusal.

**A refusal of the TPM.** Another system, another machine, a lockout, a record that the TPM did not make, or no TPM service: the window asks for the recovery key. Enter with nothing goes back to the passphrase while the TPM service runs.

**The recovery.** The recovery key opens the copy. With the TPM service and Secure Boot on, the window asks for a passphrase two times, and the TPM seals the keys again to it and to the system that runs: the file gets a new salt, a new TPM secret and new parts. So the recovery is also the change of a lost passphrase. With Secure Boot off, nothing is sealed again, for the reason of the machine key. The session starts in each case.

### A change of the passphrase, and a new recovery key

**Who asks.** The principal, in its session. A console that the desktop starts during the session acts for the principal; its `passphrase_change()` or `recovery_key_change()` sends the command `Principal_Change` of the root ring, with values[4] the change. The root service takes it only from a caller that holds the grant `acts_for_principal`, whose principal is a named principal with an unlocked session, and while no `unlock` runs. It then starts `unlock` in the mode `Unlock_Mode.Change_Passphrase` or `Unlock_Mode.New_Recovery_Key`. No new grant: the console holds `Root_Ring` and `acts_for_principal` already, and `unlock` is still the one process that holds the passphrase and the keys. The console of principal 0 does not act for the named principal, so it cannot ask: a change needs the session of the principal, not the machine.

**The proof.** The window asks for the current passphrase first. It opens the keys as an unlock does: in the form `PRINCIPT` the TPM releases the TPM secret only to its authorization value and counts each wrong one, so a change gives no try that an unlock does not give. A refusal of the TPM (a lockout, another system) changes nothing: the window says it, and Enter with nothing ends the change. A session that runs is no proof: a process of the session, or anyone at the keyboard of an unlocked desktop, can ask for a change, and the passphrase decides.

**A new passphrase.** After the proof the window asks for the new passphrase two times. In the form `PRINCIPT` the TPM seals the keys again, as after a recovery: a new salt, a new TPM secret, new parts. The copy under the recovery key stays, as its additional data stops before the salt. In the form `PRINCIPL` the keys are sealed again under the new passphrase alone, with a new salt and a new nonce. The session goes on; nothing is sent to the root service, as the keys and the tag of the disk grant table do not change.

**A new recovery key.** After the proof `unlock` makes a new recovery key and a new nonce, and seals the copy of the keys under it in a file that waits in memory. The window shows the new key first; the file is written only after Enter, when the principal wrote the key down. So a stop, a lock or a cut of the power before Enter leaves the old key the key of the file, and a key that nobody saw never becomes it. The passphrase and the seal by the TPM stay. Only the form `PRINCIPT` has a copy: in the form `PRINCIPL`, `unlock` refuses before its window opens.

**The end of a change.** Each change ends on a screen of the window with its sentence and "enter: done": what changed, or why nothing changed. A change never ends with a silent close: a principal who believes a passphrase changed that did not would type it at the next lock, and the TPM would count it. `unlock` also gives the end to the root service (`Principal_Change_End`), which holds the completion of `Principal_Change` until then, so the line of the console gives the end too, and the cause of a refusal that the window cannot show on one line. The console waits with no time limit, as a principal types at its own pace; Escape ends its wait, and the window goes on. When `unlock` stops before the end (a lock, a close, a fault), the root service gives the end "unlock stopped before the end: the old or the new secret opens": a stop between the write and the end leaves the new file on the disk, so the end must not say that nothing changed.

**A write whose answer failed.** The store can keep a write and fail its answer. `unlock` then reads the file back and compares it: the window says that the new secret is kept, that nothing changed, or, when the read fails too, that the old or the new secret opens the keys.

**What stays true of an old copy of the file.** The keys of the principal never change: they are the principal (its public key, the tag of its disk grant table). So a change replaces the file, and does not revoke an old copy of it:

- A file written after the change opens with the new passphrase or the new recovery key only. The old recovery key opens nothing in it, and the old passphrase gives a wrong authorization value, which the TPM counts.
- The write of the new file makes the file from before a version. Right after the write, `unlock` asks the store to erase the versions of the file: the store ends them and writes zeros over each block that no other state names ([version_erase.md](version_erase.md)). Only `unlock` holds the grant for it, `Versions_Erase`. Each unlock whose current file opens the keys asks again, so a stop between the write and the erase leaves the old file on the disk only until the next unlock.
- After the erase, a thief of the machine who knows the old passphrase or the old recovery key opens nothing that the storage service reads on this disk, under the limits of the erase ([version_erase.md](version_erase.md), "Limits"): a copy of the disk made before the change; a copy that the device or the host keeps under the logical blocks (a flash remap, a snapshot of the image); old bytes in free blocks after a loss of power during the zeros, or after a failed second root or write of zeros; a damaged version that the erase ended with no zeros; and a clone or a restore of the version that a process acting for principal 0 made before the erase. Each of them still opens with the old secret: the old recovery key anywhere, the old passphrase on this TPM and system, as its sealed object stays valid.
- A writer of the disk who kept the old file can put it back. On a machine with the TPM service, the pin of the file refuses it (see "The pin of the file").

### No window of `unlock` outlives a lock

A lock stops each process of the session. `unlock` belongs to principal 0, as it reads the store of `unlock`, so the lock does not stop it as a process of the session. The root service stops the `unlock` that runs at a lock, whatever its mode: a change, a machine passphrase that is set, a machine key that the TPM seals. Anyone at the keyboard of a locked machine then sees no recovery key and sets no machine passphrase: a console of the session started that window, and the lock ends what the session asked. The `unlock` of the lock starts after the reap, by the rule below.

A stop at any point must lose no recovery key that nobody wrote down. So each window that shows a new recovery key writes nothing before Enter: the creation of a principal, the new recovery key of a change, the machine passphrase sealed by the TPM, and the machine key sealed by the TPM alone. The file or the record waits in memory with the secret that the session or the root service needs after the write; the root service receives no key before the write. A stop before Enter leaves the disk as it was: no principal, the old recovery key, or no record of the machine key. The owner asks again. A window with no recovery key (a machine passphrase alone, a change of the passphrase) writes after the second passphrase; a stop before it changes nothing, and a stop during the write leaves the old or the new record, as a cut of the power does.

**The write at Enter, and its read back.** The store can keep a write and fail its answer: a storage service that stops after its commit and before its answer, for one. So each write at Enter reads the object back when the store does not answer `Ok`, and compares it, as the write of a change does. Three outcomes:

- **Kept**: the file or the record is the one that the window showed the recovery key of. `unlock` goes on: the key of the table, or the record and the session.
- **Not kept**: the store holds the object of before, or none. The window says "the store did not keep it: nothing is set; ask again" until Enter. The recovery key opens nothing.
- **Not known**: the read back failed too. The object can be on the disk, so the window never says that nothing is set: it keeps the recovery key on the screen, says "the record may be on the disk: keep this recovery key" (or "the file may be on the disk: keep this recovery key"), and ends at the next Enter. The root service receives no key and no record in this run; the next start of `unlock` reads what the disk holds. A screen that said "nothing is set" here would have the owner throw away the only recovery key of a record on the disk: the fault that this design is for.

**A creation never meets a lock while the system holds one named principal.** `principal_create` needs the record of principal 1 absent, and `PRINCIPAL_CAPACITY` is 2: so no session runs during a creation, and no lock is possible. The root service asserts that capacity at compile time. With several named principals, a creation can run during the session of another one, and its lock then stops the creation: nothing is written before Enter, so that case stays safe, but a stop between the write of the file and the record leaves a file with no record in the root service until the next start of `unlock`.

**What a stop leaves in memory.** A stop by the root service runs no code of `unlock`: the keys of a new principal, the new machine key and the text of the recovery key stay in the frames of the stopped process. The kernel zeroes a frame when a memory object takes it, not when it is freed, so no process reads them; a reader of the physical memory (a cold boot, a device with no IOMMU, a dump) reads them until the next take. The keys of a change waited the same way before; the wait now lasts until Enter.

**A seal that nobody writes.** The TPM keeps no copy of a sealed object: it is bytes in the memory of `unlock`, so a stop before Enter leaves nothing in the TPM, and adds nothing to its count. One exception: on a TPM whose lockout authorization value is empty, the first seal with a passphrase sets that value (see "The lockout authorization value"), and the value stays even when the window closes before Enter. The lockout hierarchy is then taken with no object of modus that the TPM counts, the outcome that the refused form "a lockout authorization value set at each start" avoids. It is accepted here: the owner asked for a seal with a passphrase, and the next ask sets nothing more. A design that sets the value at the first unseal, or at the write, would remove it.

**A locked principal always has a window.** After each reap, the root service starts `unlock` when a named principal is locked and no `unlock` runs. One rule covers a lock, a close of the window of `unlock`, a stop of a change, and a start that failed, where a flag for each path left a principal locked with no way in until a restart. Each stop of `unlock` that the root service did not ask, while a principal is locked, counts against `UNLOCK_RESTART_LIMIT` (3) until the next lock or session, whatever its stop outcome: an `unlock` that stops at once with `Done` (a store that lost the file of a locked principal) loops as surely as a fault. A stop that the root service asked (a close of the window, a stop at a lock) never counts, so closes by mistake never reach the bound; the root service sets a flag at each of its two calls of `Process_Stop` on `unlock`. A failed start counts, except a full table: a slot comes free only with a stop, which is an event, so the next pass tries again with no hot loop. Past the bound, the log says it, and only a restart of the machine gives the window back.

### The machine passphrase

The machine passphrase on a machine with the TPM service and Secure Boot on has the same form, in the record `MACHINEP`: the TPM seals a TPM secret with an authorization value from the machine passphrase, with a text of its own for each key ([tpm_sealed_machine_passphrase.md](tpm_sealed_machine_passphrase.md)). The two share the count of the TPM. A machine key sealed by the TPM with no passphrase keeps the form `MACHINET`, which needs no typing.

### The pin of the file

A copy of the disk keeps an older file of a named principal, and the older passphrase opens it on this TPM and system: the old sealed object stays valid. On a machine with the TPM service, the TPM pins the current file, as it pins the record of the machine key ([tpm_sealed_machine_key.md](tpm_sealed_machine_key.md), "The pin of the record"): the same commands `Pin_Read` and `Pin_Write`, the same policy of the index, the same announce and settle around each write, the same first pin, and the same limit against code with the TPM.

**The index** of the principal n is `0x01806E00` + n, n from 1 to 64 (`tpm2.pin_index_of`).

**The payload** (format 4, 152 bytes): the magic `MODUSPFP`, the format (`4`), the state (`Principal_Pin_State`: `Active = 0` or `Free = 1`), the number of the principal, a generation of 64 bits, the 32-byte principal identifier, SHA-256 of the whole file, SHA-256 of the announced file (zeros when none is), and SHA-256 of a text of its own and the bytes before it. Principal 0 is refused: the machine has no principal file. SHA-256 and not BLAKE2b: the contract of the TPM has SHA-256 only, as each digest of the TPM.

**The rules** (`principal_file_pin_advance`, `principal_file_pin_check`, `principal_file_pin_free`, `principal_file_pin_create` in `modus:contract/tpm_attestation`, `principal_file_pin_verdict` in `modus:contract/tpm_service`):

- an `Active` pin carries a non-zero principal identifier, a non-zero file digest, and a generation above 0;
- a `Free` pin carries `"free, generation g"`: all-zero identifier, all-zero file digest, all-zero announced digest, and a generation above 0;
- valid transitions are `Absent -> Active(A, g >= 1)`, `Active(A, g) -> Active(A, g' > g)`, `Active(A, g) -> Free(g' > g)` (during principal removal only), and `Free(g) -> Active(B, g' > g)` (creation of a new principal in a freed slot after reboot);
- `Absent -> Free`, `Active(A) -> Active(B)`, `Free -> Free`, and any `g' <= g` are refused;
- when the pin is `Active`, the file on disk must match the pinned identifier and either the file digest or the announced digest;
- when the pin is `Free`, no principal file may exist on disk for that slot (if a writer puts an old file back, the `Free` pin refuses it), and a new principal creation is allowed from `generation + 1`.

**The check** comes after `unlock` gives the record to the root service, which gives the number of the principal, and before any passphrase is asked. A file that the pin does not name is refused: `unlock` writes "the file of principal 1 is not the file that the TPM pins", with the rule that failed, and no window of the principal opens in this run. The root service keeps the record, so the principal stays locked; the machine key opens as before. A change of the passphrase or of the recovery key on such a file is refused the same way.

**A removed file versus an intentional removal.** If the store gives no file and an `Active` pin names one, a writer of the disk removed it: `unlock` refuses it, no window opens, and `principal_create` is refused. Only a deliberate removal (`Principal_Remove`) advances the pin from `Active(A, g)` to `Free(g + 1)`, after erasing the principal's stores and deleting the file. A `Free` pin allows `principal_create` on a later run to reuse the slot at `generation + 1`, while still blocking rollback of any older file from `g` or earlier.

**The creation** writes the file before the root service gives its number, so the pin comes after the record: a stop between the write and the pin leaves a file with no pin, which the next start pins. A pin of that number that appears between the check at the start of the creation and the pin is not moved: the new file stays unpinned, and the next start refuses it.

## Refused forms

- **The keys sealed by the TPM alone, with no passphrase in the seal key.** A reader of the bus at one unseal gets the secret, and then the keys, with no guess.
- **The authorization value as the passphrase itself, or as a fast hash of it.** The value crosses the bus in clear: a reader would test guesses at the speed of a hash.
- **A count of the tries in the file, or in the store.** A copy of the disk resets it.
- **A lockout in `unlock`, with a delay after each wrong try.** A restart of the process, or of the machine, resets it.
- **`TPM2_DictionaryAttackLockReset` from the service.** A process of this system that can ask for it makes the count worthless. No command of the service resets it, and the service keeps no lockout authorization value that a command could use (see "The lockout authorization value").
- **The lockout authorization value sealed under the machine key, or sealed by the TPM to PCR 7 and PCR 11.** The holder of the recovery key of the machine, or any process of this system that reaches the sealed value, then resets the count of a named principal. Nothing of the system has a use for the value.
- **The lockout authorization value in a store of the TPM service.** A new grant for a value that no command reads, and a copy on the disk for a reader of the disk.
- **A lockout authorization value that a principal types, or that the window shows.** It is a second secret to keep for a use that the system refuses, and a weak one when it is typed.
- **The lockout authorization value set at each start of the service.** Only a clear undoes the change, and it takes the reset of the shared count from each other system on the machine. At a start, no object of modus that the TPM counts may exist: a trial boot, or a machine with the machine key only, then takes the hierarchy from another system for no gain. The security is the same at the first request with an authorization value: an attacker who resets the count before modus starts does so in both forms, and the first guess in `unlock` is such a request.
- **A change of a lockout authorization value that another system set.** The change needs the old value. A try of a wrong value closes the lockout hierarchy for its recovery time, and gains nothing.
- **`TPM2_Shutdown` at the stop of the machine only.** The machine has no orderly stop, and a stop by the power is a stop too.
- **No `TPM2_Shutdown`.** Three starts after three unlocks would lock the TPM, with no wrong passphrase.
- **The recovery key under Argon2id, or chosen by the principal.** As for the machine key: 160 random bits need no slow derivation.
- **A recovery that keeps the old passphrase.** The passphrase that was typed before a refusal of the policy was never checked; and a lost passphrase is the case that the recovery is for.
- **A recovery copy for the form `PRINCIPL`, now.** It is the same work on the other form; it is a roadmap entry.
- **A change in the session with no proof of the passphrase.** A session is not the principal: a process that acts for it, or anyone at an unlocked desktop, would take the principal with a passphrase of its own.
- **The recovery key as the proof of a change.** The recovery key already sets a new passphrase when the TPM refuses; a change while the TPM opens the keys asks for the passphrase, which the TPM counts. A lost passphrase goes through the recovery. So the prompt of the current passphrase of a change has no Ctrl+R: a principal who lost the passphrase locks the session, and Ctrl+R at the prompt of the unlock asks for the recovery key.
- **The change typed in the console.** The console keeps each line in its history and its store: the passphrase is typed in the window of `unlock` only.
- **The completion of `Principal_Change` at the start of `unlock`.** The console then said nothing of the end: a change that failed looked like one that succeeded.
- **The file written before the new recovery key is shown.** A stop between the write and the display leaves a file whose only recovery key nobody saw.
- **A window of `unlock` that runs to its end after a lock.** A console of the session asks for the machine passphrase or the seal of the machine key; after the lock, anyone at the keyboard reads the recovery key, or types the machine passphrase, and so holds the disk grants of principal 0.
- **A stop at the lock with the record written before the recovery key shows.** The stop then leaves a record whose only recovery key nobody wrote down: a machine key or a principal with no way back after a refusal of the TPM.
- **A window that hides at the lock and shows again after the unlock.** The keys and the recovery key then wait in memory across a lock for anyone who unlocks, and the root service holds a window of a session that ended. A stop and a new request cost one more passphrase, and keep one rule: a lock ends what the session asked.
- **The stop by the mode of `unlock`, a list of the modes that a lock ends.** Each new mode would need its place in the list. Each `unlock` that runs during a session was asked by it, so the rule names no mode.
- **A flag for each path that must start the `unlock` of a lock.** Each new path (a close, a failed start) needed its own flag; the rule after each reap covers them all.
- **New keys at a change.** New keys are a new principal: another public key, another tag of the disk grant table, and the grants that the old keys signed lost. An old copy of the file would still hold the old keys.
- **A change of the form of the file.** A change keeps the form. From `PRINCIPT` to `PRINCIPL` weakens the file. From `PRINCIPL` to `PRINCIPT` makes an old copy under the passphrase alone a file with the same keys: a writer of the disk then puts it back, and the keys fall to guesses against Argon2id alone. Today no file `PRINCIPL` holds the keys of a principal that the TPM seals.

## Subtle points

- **A wrong passphrase on another system is not counted, and not known as wrong.** The policy fails first. The window then asks for the recovery key: a principal who mistyped on an updated system needs the recovery key anyway.
- **The lockout comes before the policy.** A locked TPM refuses the right passphrase on this system too; the recovery key opens the keys, and the new seal works during the lockout: the storage key is exempt from the count.
- **The keys after a recovery wait in `unlock`** until the new passphrase is typed two times. They are erased at the end of the seal, whatever its result, and the window then ends: it cannot ask again for a passphrase that it has no keys to seal.
- **A new passphrase does not revoke the old one.** After a recovery or a change, the old sealed object stays valid on this system: its parent is the storage key that the TPM derives again at each use, and its policy still holds. A writer of the disk who kept the old file puts it back; the pin of the file refuses it (see "The pin of the file"). This matters when the old passphrase leaked, not when it was lost. Code with the TPM can remove the pin, and the old file then opens with the old passphrase.
- **A new recovery key does not revoke the old one either.** A new seal keeps the copy under the recovery key; only `recovery_key_change()` replaces it. The old recovery key then opens no file written after. The store erases the version from before, but each other copy of the old file still opens with the old recovery key, with no TPM: a copy of the disk, or a copy that the device kept. Who holds the old recovery key and such a copy holds the principal.
- **The proof of a change comes before each new secret.** `unlock` draws the new salt, TPM secret or recovery key only after the current passphrase opened the keys, and keeps the opened keys only until the new seal, as after a recovery. Enter with nothing at the new passphrase erases them and ends the change: opened keys do not wait for anyone at the keyboard. A change that fails keeps the file as it was.
- **A stop during a request to the TPM** can leave an authorization value or a TPM secret in the region of the TPM service, and a lock stops `unlock` at any point of a window that a session asked. The next `unlock` erases both fields of the region when it maps it.
- **The change of the passphrase of the form `PRINCIPT` needs Secure Boot on**, as each seal does. With Secure Boot off, `unlock` writes why and stops before its window opens; a new recovery key needs no seal by the TPM, and stays allowed.
- **The creation writes the file before the record goes to the root service, and both after Enter.** A root service that does not take the record leaves the file, whose copy under the recovery key the principal wrote down: the next start of `unlock` reads it. The secret keys wait in memory from the seal to Enter, as after a recovery, because the session needs the key of the disk grant table; they are erased at Enter, whatever the result. A stop before Enter erases nothing (see "What a stop leaves in memory").
- **The `unlock` that a lock stops can be in a request to the TPM.** The TPM service ends the request alone, and the next `unlock` erases the region (see "A stop during a request to the TPM"). A seal that the TPM made for a record that nobody writes leaves nothing in the TPM, but for the lockout authorization value of a first seal (see "A seal that nobody writes").
- **The lockout value crosses the bus in clear, once.** `TPM2_HierarchyChangeAuth` sends it with no encrypted session. A reader of the bus of a hardware TPM at that first use learns it; the encrypted session, when it is built, covers it.
- **The first use decides.** The value protects the count from the first request with an authorization value on a TPM with an empty value. A party that sets its own value before it keeps the reset; the service only writes that a value exists.
- **The count is one for all the systems of the machine.** The TPM counts the failures of each object with `noDA` clear, of each system: the failures of another system count against alice, and a lockout of alice locks the objects of that system too. The first system that sets the lockout value owns the reset of that count for all. After modus sets it, another system can no longer reset its own lockout or set the count limits, and can propose a clear of the TPM. A clear that another system asks for (through the physical presence interface, "Clear TPM" in Windows) destroys each seal of modus; the recovery keys open the keys, and the next use of a passphrase sets a new value. An update that resets a firmware TPM is a clear.
- **The bit `lockoutAuthSet` is read before the change, in the same run of the service.** No other process reaches the TPM between the read and the change: the service is its one driver after the start.
- **No Secure Boot check for the change.** A seal needs Secure Boot on, as it trusts the boot program. A lockout value trusts nothing: it only takes the reset away from each party. The service sets it on each system where a passphrase is used with the TPM.
- **A refused change is not fatal.** A TPM whose lockout hierarchy waits after a wrong value of another party answers `TPM_RC_LOCKOUT`. The service writes the code on the log and serves the request; the next start tries again at its first use of a passphrase.
- **The test of the lockout depends on libtpms**: three tries, and no other failure counted. That is why the service sends `TPM2_Shutdown`: without it, each start of a machine of the test would count one more failure. Each machine of the test that types a wrong passphrase types the right one, or reaches the lockout, after it in the same run, so no start counts a failure of a stop.
