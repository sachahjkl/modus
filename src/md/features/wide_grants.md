# Grants of wide authority, for agents first

An agent that drives the machine for the principal needs much authority at once: lines of the console, the screen, the keys and the pointer, the start and the stop of processes, the log, the stores. The powerbox ([powerbox.md](powerbox.md)) gives one object at a time and refuses such a request at its border. A wide grant is the other path: a set of wide scopes, each with its bounds, given to one agent on a screen of its own, after a proof of the principal, with a mark that shows while it holds, a record of each act, and one revocation that ends it all.

The first user is the roadmap entry "An agent drives a machine through `remote`": a bridge on the host that holds a client key ([remote_client_keys.md](remote_client_keys.md)).

## Purpose

- The principal gives an agent exactly the authority that a task needs, from one screen that says in plain words what the agent can see and do.
- The principal bounds the grant in time and in place, and keeps some acts asking at the moment they happen.
- Nobody at the machine can miss that an agent holds wide authority, and one press revokes it.
- The principal reads afterwards each act that the agent did under the grant.

## Constraints

- **A principal is the one source of new grants** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "21. Principals: who acts, without users"): a human, an agent and a remote caller are the same thing, a process tree with handles; the system tells them apart only by what they hold.
- **A broad grant is rare, visible and revocable** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "20. No ambient access: the other holes to close", the cost of the processes that manage the system).
- **A viewer with input already acts as the principal at the machine** ([remote_display.md](remote_display.md), "The constraints"): through the key super it reaches the palette, so the console. A wide grant must say so and bound it, not hide it.
- **The trusted path is a role** ([powerbox.md](powerbox.md), "The trusted display"). Each screen and mark below is a record of that contract; a replacement compositor fills it.
- **No act without its record, and no writer of the system that waits on a reader** ([module_outputs.md](module_outputs.md); the loop of the trusted display waits for no process).

## The chosen form

### The holder of a wide grant

A wide grant is given to one agent, named by what proves it:

- **A client key of `remote`** today: the agent runs outside the machine and proves the key in the QUIC handshake. The wide grant is a state of the row of that key in the client table, beside its uses (`Calls`, `View`, `Input`), with its own serial.
- **The hash of a module**, later: an agent that runs on modus as a disk process.

One holder has one wide grant at most. A new grant replaces it whole.

### The wide scopes

A wide scope is a member of the enum `Wide_Scope` of the contract, with a boundary that one mechanism of the system enforces.

| Scope | What the agent can do | What enforces the boundary | Its place bound |
|---|---|---|---|
| `Console_Lines` | Run lines of Lex in an agent console: a console that the root service starts for the grant, in the session of the principal, in place of the read-only agent console of the key, and which reaches only what the other kept scopes give; the agent sends its lines in agent steps ([agent_code_mode.md](agent_code_mode.md)) | The start grant set of the agent console: its start grants are the union of the kept scopes, never the start grant set of the console of the principal | None: the other scopes bound what the lines reach |
| `Screen_View` | See the screen, as a viewer with `View` | The use `View` of the row, and the session in front ([remote_display.md](remote_display.md), "The authority") | None |
| `Input` | Send keys and the pointer, as a viewer with `Input`; needs `Screen_View` | The input face of the trusted display, which drops each record for a window outside the bound | The windows of chosen processes; or every window, which includes the palette and the window of each console |
| `Processes` | Start and stop the processes of the session | The root commands `Start` and `Stop` in the sender table of the agent console, for the processes of its own session | The names or nicknames chosen; or each one |
| `Log_Read` | Read the log of the session of the principal | A connection to the log service that acts for the principal and reads only | None |
| `Stores` | Read, or read and change, stores of the principal | Shares of the chosen stores, each read-only unless the principal kept `Change` for it; "every store" is a connection to the storage service that acts for the principal, read-only unless `Change` is kept | The stores chosen, with the rights of each |

No scope gives:

- a change of a grant: `allow`, `disallow`, `remote_allow`, a client key, `Apply` of a difference that adds a grant ("Acts that still ask");
- a command of the principals: a creation, a lock, a passphrase, the machine key, a start policy;
- `Replace`, the debug access, a right over the machine or a device;
- the answer to a grant dialog or to a wide grant screen.

The agent console has no sender of these commands in the table of the root ring, so a line that asks for one is refused with `No_Grant` before it runs.

**Which scopes go with ordinary items.** None. Each wide scope reaches a set of objects that the principal cannot read as one row: the whole screen, each window, each store, each process. The border of the grant request refuses an item whose kind is a wide scope with `Reserved`. An ordinary item that reaches as far (a connection to `storage` that acts for the principal, a connection to `remote` or to the log of the session) is not a kind of the powerbox at all.

**Why `Input` on every window is said in full.** Input to the palette is input to the console of the principal. The screen says it in words: "with every window, it can type in a console and do what you can do". A bound to chosen windows removes the palette, the console and every other window from the reach of the agent.

### The screen of a wide grant

The screen of a wide grant is a record of the contract of the trusted display, `Show_Wide_Grant`, never the ordinary dialog.

**Who asks.** The agent, through `remote`: a typed record of the scopes and the bounds that it proposes, with no text, which `remote` passes to the root service for its key. Or the principal, from its console: `agent_allow(key, scopes, minutes)`. Both show the same screen; the principal changes what the agent proposed.

**The ask of an agent.** A stream of `remote` whose first word is the request kind `Wide_Grant_Ask` carries `remote.Wide_Grant_Ask_Request`: the kind, a reserved word of 0, the word of the scopes and the duration in milliseconds, 24 bytes. `remote.wide_grant_ask_check` refuses a stream of another length, a reserved word that is not 0, a word of scopes that names no scope or names `Send_Input` alone, and a duration of 0 or past `MAX_WIDE_GRANT_DURATION_MS`, each with the field in the error record. `remote` sends `Wide_Grant_Agent_Ask` to the root service with the key that the client proved in its handshake, never a key of the request, so an agent asks only for its own key, and the root service takes the principal from the row of that key: an agent never names a principal. Only a process with the start grant `Remote_Clients` sends it. The answer is an `Answer` whose value is the number of the screen, or a refusal with its error record; the steps after it are the steps of an ask of a console. The agent bridge sends it with the method `ask_wide_grant` ([agent_bridge.md](agent_bridge.md)).

**What it states**, in plain words from the table of the display texts of the scopes, with no word of the agent:

- the agent: the hash prefix of its client key, and the head of the whole key; the hash of its module when the holder is a module; the principal for whom it will act;
- what the agent can see: "the screen", "the log of your session", "the stores: notes, mail";
- what it can do: "type and press in the windows of edit and notes", "start and stop edit", "change the store notes";
- what it can do without asking, and what still asks: each scope with its mode, "at any time" or "asks each time";
- for how long, and how to end it: "until 15:42", "until the lock", "until you revoke it or the machine stops", and "the mark in the bar ends it";
- what it never does: "it cannot grant, change your passphrase or apply a plan that grants".

**The tuning on the same screen.**

- Each scope has a tick, set for each scope that the agent proposed.
- The time bound: one hour (the default), this session (to the lock; for principal 0, until the machine stops), or until revoked. Each one ends at the latest when the machine stops: no wide grant is written on the disk.
- The place bounds: the picker of the powerbox gives the candidates (the stores of the principal, the processes of the session, the windows), and the principal picks. `Stores` and `Processes` start with no pick: "every store" and "every process" are explicit choices.
- The mode of each scope: "asks each time" or "at any time". It starts at "asks each time" for `Processes` and for each store with `Change`.

### The deliberate act: the proof of the principal

The act that gives a wide grant is the passphrase of the principal, typed in the window of `unlock`, with the keys of the machine only.

- After the tuning, the root service fixes the terms: it keeps the hash of the record of the screen, and starts `unlock` in a mode that proves the passphrase and opens no session, as the proof before a change of the passphrase does ([`docs/PRINCIPALS.md`](../../../docs/PRINCIPALS.md), "A change of the passphrase"). For principal 0, the proof is the machine passphrase.
- The trusted display gives that window the keys of the input service only: the input face of the remote display never reaches it, as it never reaches a trusted surface. The root service marks the window so in the record `Client_Add` of `unlock`.
- The root service makes the grant only when `unlock` says that the passphrase opened the keys, for the terms whose hash the screen showed. A change of the terms after the proof is refused.
- **A principal with no passphrase gives no wide grant at the keyboard.** Principal 0 with no machine passphrase, or with only the machine key that the TPM releases with no typing, is refused with one line that says to set a machine passphrase.
- **A machine with no person**, such as a test machine, proves the principal with a signature in place of the passphrase: a signing key of the principal, kept on the host and never on the machine, signs the hash of the terms. The root service checks the signature with the public key of the principal before it makes the grant, as for the passphrase, and a change of the terms after the signature is refused. The signature reaches the root service through `remote`, never through the input of the remote display. The key on the host is the principal for this act: whoever holds it gives the grant.

**The proof record is keyed.** The record of a proof, `Wide_Grant_Proof`, holds its kind, its origin, the principal, a proof serial, its time, the hash of the terms and the hash of the verifier, then `proof_tag`: the keyed BLAKE3 hash (`blake3.keyed_hash`) of all of them under the authority key. Only the unlock authority, which makes the proof, and the collector, which checks it, hold that key. The unlock authority is the root service: it fixes the terms and makes the grant only when `unlock` says that the passphrase opened the keys, so it is the one party that can say that a proof holds; `unlock` proves the passphrase and holds no key that a later run of it could leak.

**The authority key at the start.** Right after it seeds its random generator, the root service draws 32 bytes for a key (`random.fill_for_a_key` with the least strength `Processor`, `wide_grants.AUTHORITY_KEY_LEAST_ENTROPY`), in `wide_grants.Wide_Grant_Authority`: the key of the run. A seed that is only the jitter of the cycle counter makes no key: the state is `Refused_Weak_Entropy`, one fact says so, and the collector gets four zero values, so it refuses each wide grant. **One key for each principal.** From the key of the run, the root service makes the authority key of each slot of a principal (`authority_init_for_principal`: the keyed BLAKE3 hash, under the key of the run, of a domain text and the slot), then erases the key of the run. The key of the run signs nothing and never goes to a collector (`Authority_Scope.Run`); the key of a principal signs the terms of that principal only (`authority_mint_proof` refuses other terms) and goes to the collector of that principal only. So the collector of one principal makes no proof that the collector of another principal accepts. A slot is never used again in a run of the machine ([several_principals.md](several_principals.md), "The identity: three names"), so one key for a slot in a run names one principal. At the start of the collector, the root service writes the key of its principal in the values 5 to 8 of its context (`GRANT_VALUE_WIDE_GRANT_AUTHORITY_KEY`) beside its principal in the value 4, and erases its copies of the values after the start. The collector reads the four values once and writes zeros over them. The root service mints each proof with `authority_mint_proof`, whose proof serial grows by one at each proof of that principal and never at a refusal: one sequence for each principal, so a collector learns no count of the proofs of another one. Refused: **one key for every collector**: the collector of one principal could then make a proof that the collector of another principal accepts; **a key from `unlock`**: `unlock` runs again at each lock and for each change of a passphrase, so the key would cross a ring at each run; **a key on the disk or sealed by the TPM**: a grant never outlives a start, so the key needs not either; **a key from a weak seed**: a key that the cycle counter alone gave can be guessed, and a guessed key forges each proof. So:

- a record that a process computes without the key is refused, and a change of one field (the origin, the principal, the serial, the terms and so their windows) breaks the tag;
- the origin is a field of the record that the tag covers (`Proof_Origin`): `Local_Unlock_Dialog` for a passphrase, `Local_Host_Key` for a host signature. `Remote_Display_Input` is refused for each kind, even with a right tag;
- the all-zero key is refused where a proof is made and where it is checked: a key that everybody knows authenticates nothing. A collector that the start gave no key refuses each wide grant, and its act store still serves its reader;
- the collector refuses a proof serial that is not past the last one it accepted, so one proof gives one grant.

Refused: **an unkeyed hash as the tag**, the first form: any process could compute it, so it proved nothing; **booleans of the record that say "verified by the local unlock" and "not from the remote display"**, the first form too: the sender of the record set them.

**Why the passphrase.** A wide grant hands over the authority of the principal; the act must prove the principal, not only a person at the keyboard. A hold of a key or a typed word proves a press, and an agent that holds `Input` from an earlier grant, or a person who passes by the machine, can give it. The passphrase exists already, is typed in one window only, and is never a text of the console. The cost: a wrong passphrase counts in the TPM, as each wrong passphrase does ([`docs/PRINCIPALS.md`](../../../docs/PRINCIPALS.md), "The keys sealed by the TPM").

Refused: **a hold of a key for some seconds**: it proves no principal, and a stuck key gives it; **typing a word that the screen shows**: an agent with `Screen_View` reads it, and only the rule of the local keys stops it; **a second device**: the system has no pairing of a device yet; **a wide grant with no proof on a machine with no person**: the agent then gives itself the authority of the principal.

**A wide grant ends at each restart, for now.** The grant is never on the disk, so each run needs a fresh proof, and a stolen agent key gets no grant after a restart. An agent that works each night from a schedule needs a grant that a restart keeps, which needs a key that the TPM releases with no person. That form is reopened when a scheduled agent exists.

### Acts that still ask

- **The mode "asks each time".** Each act of that scope waits for the answer of the principal: a grant dialog of the powerbox whose asker is the agent console, with one row, "stop edit" or "open notes to change it". The same merge, arm time and bounds hold, so a burst of acts gives one screen.
- **Acts that always ask, whatever the grant.** While a wide grant holds in a session, each `Apply` whose difference adds a grant, from any console of that session, needs the proof of the principal on the screen of the difference ([powerbox.md](powerbox.md), "The relation to the other paths"). The root service cannot know which line an agent typed into which window, so the rule holds for each asker of the session while the grant holds.
- **The grants of a process that the agent started.** Such a process asks through its own window; its dialog names the agent console as the process that started it. The agent cannot answer it.

### The mark

While a wide grant holds, the trusted display shows a mark of wide authority on the place that no process covers: the word "agent", the hash prefix of the key, and the time left. The contract fixes it ([powerbox.md](powerbox.md), "The trusted display"): the holder draws it from the record `Mark` of the root service, whatever any other process says. One press on the mark shows what the grant holds (the scopes, the bounds, the time left, the count of acts so far), with the button revoke; one press there ends the grant at once. Input from the remote display never presses it.

The mark of a viewer ([remote_display.md](remote_display.md), "The authority") stays: it says that a screen is seen. The mark of wide authority says that an agent acts.

### The record of each act

Each act under the grant is an act record, written before the act runs, on a record output of the party that does the act ([module_outputs.md](module_outputs.md)):

| Writer | Act records |
|---|---|
| The root service | The grant, its terms, each start and stop, each share and connection made, each answer of "asks each time", the revocation and the end |
| The agent console | Each line, whole, and the kind of its result |
| `remote` | Each call outside the agent console |
| The trusted display | Each change of the window that receives the input of the agent, with the count of the keys and of the presses since the last change; the open and the close of the view |

The reader of each act record output is the collector ([module_outputs.md](module_outputs.md), the roadmap entry "The collector and the audit"), wired by the root service at the grant, into a space of the principal that the agent cannot read or erase. The collector is the first reader of the act records, and it is built before the first layer of this file: no wide grant exists before its act records have a reader.

**The form of an act record on a ring.** Each of the four writers declares the record output `acts` of the record `wide_grants.Act_Stream_Record`: the grant serial, the principal, the time, the writer (`Act_Producer`), the act kind (`Act_Kind`), the target window and two words of detail, 64 bytes with no padding. The collector keeps each writer in its own audit space, the source the name of the writer (`root`, `remote`, `compositor`) and the output `acts`, with the terms `act_audit_space_terms`: `Audit`, the bound of `Act_Space_Plan`, no forward. The space of `console` opens with the agent console of the layer `Console_Lines`: an empty space would take a window of memory from the audits of the servers.

**The record of the input of a viewer.** The trusted display writes one record for each change of the window that takes the input of a viewer: `Target_Window_Changed`, with the window, and the count of the keys and of the presses that the window before it took. It writes it before the first act on the new window, so each act has a record of its window before it runs. A viewer with `Send_Input` on the window of a console leaves key records of that window only: its lines are no act record of this layer, as "The lines of a console are no act of this layer" says. The open and the close of a view are a record `Frame_Read` each; a view whose record did not leave does not open. A view that is open when a grant starts gets its record of the open at the start of the grant, from which the agent may read the screen through it; a view whose record does not leave then ends. The counts of keys and presses of the last window leave in a record `Input_Counted`: each `INPUT_COUNTS_INTERVAL_MILLISECONDS` while the grant holds, and at the end of the grant, before the mark clears, with the time of the last act that it counts, so the collector keeps it as a record of before the end.

### The size of the act records

Each space of a writer holds `Act_Space_Plan.bound_records` records in the private store, in a ring of segment slots, and its newest `SPACE_RECORDS_MOST` in memory. A reader of the audit reads it whole: `records_read` reads the records before the memory window from the segments, checks each segment and its chain from the segment before it, then reads the window. A slot map object for each space names the segment of each slot, so a start reads the index, one map for each space and the segments of the window, a few objects whatever the count of records; the measure is in the line of the start of the collector. The map takes the slot of a new segment before the segment is written: a stop between the two writes leaves a map that names a segment that its slot does not hold yet, and the records end before it.

**The memory of the spaces.** No count of the store is fixed: the budget of the collector bounds each part. The window of a space, its records in memory and its slot map (`Space_Window`, about 22 KB, `SPACE_WINDOW_PAGES` pages), is memory that the collector commits when the space opens and decommits when it closes. The table of the places and the buffer of the index grow in arenas of the collector as places are needed, and never move. The store reaches all three through a port (`Space_Memory_Port`), as it reaches the private store; a host test binds it to the heap. Before a window opens, the store asks the port how many windows the budget still pays (`Budget_Read` on a machine); a window that it cannot pay refuses the space with `Memory_Refused`, and so does a commit that the kernel refuses.

**The starter pays for the audits.** The stated budget of the collector is an integer literal, as the tool reads it (`src/md/features/module_budget_request.md`): its tables and the windows of the three act spaces. The root service reads the start list that it chose, counts its wiring rows with audit terms, and widens the budget of the collector of principal 0 by `SPACE_AUDIT_PAGES` for each: a window, a place and its row of the index. An image with 20 audited servers gives a collector that pays 23 windows. `modustool` refuses a start list whose audits would widen the collector past the largest budget of one process. The wirings of the audits and the ends that the collector holds are paid the same way, by budgets and tables, with no count (`src/md/features/module_outputs.md`, "The bounds of the wirings").

**The links grow too.** The collector keeps one link for each ring of its sources, in a table that grows in an arena of its budget (`Source_Links_Port`, `link_tables.odin`), with the lists of tags that a pass fills, one entry for each place of the table of the ends of the process (`system.stream_end_places`). A link that the budget does not pay refuses its source with `Memory_Refused`. 20 audited servers and a wide grant are 23 links.

**Only the grant opens an act space.** The export `space_open` refuses the pair of the output `acts` of a wired writer with `Act_Space`, even to the principal: a caller that opened it with another record size would close the audit of the grant. Only `act_wiring_attach` opens it.

**The act places are reserved.** The three act spaces of a wide grant (`ACT_SPACES_RESERVED`) keep their windows: a space that is not an act space is refused with `Memory_Refused` when the budget would then pay fewer windows than the act spaces that are not open yet. A server audit never takes the room of a wide grant, and a wide grant never closes a server audit. An act space is a space of the output `acts` of a wired writer (`space_is_act`).

**A record size that changes.** The pair of a source and an output keeps one space for one record size. When a module changes the size of its record, the pair opens a new space, and the old one closes: an audit space gives back its window, keeps its place and its records in the store, and its row of the index says `Closed`, with its next serial and its last link, so a reader reads it whole and `space_verify` checks it; `record_append` refuses it with `Space_Closed`. A space `Keep` holds its records in memory only, so it frees its place whole. The order is the one that makes a refusal change nothing: the new space takes its window, the index is written with the new space and the old one closed, and only then the old space gives back its window. A window that is not paid, or an index that is not written, leaves the old space open with its ring and its records, `Keep` too. So the change needs one window more for a moment.

**The end of a closed audit space.** A closed audit space is kept for the retention of audit records, then removed: its segments, its slot map, and then its place. The retention is `CLOSED_AUDIT_RETENTION_DEFAULT_MILLISECONDS`, 90 days, until a plan states it: a principal reads or copies the audit of a module in the quarter after its update, and the storage service keeps the versions of the removed objects by its own retention after that. It counts on the date (`modus:contract/date`), from the first pass of the collector that knows a date after the close; a date that goes back removes nothing. The removal takes out each slot of the place, the slots of the segments that rotated out too, which a rotation leaves in their slot, then the slot map: a new space in the place finds no slot taken. The removal has two steps in the index: the row says `Removing` and is written before the first object is removed, so a stop in the middle goes on at the next start; once each object is removed the row says `Removed`, and the place is free for a new space. A reader of a space that is `Removing` or `Removed` gets `Space_Removed`, not a part of an audit.

**A grant that fills its space.** Past the room of its space, a few thousand records of each writer, each act of the grant is refused to its end. `remote` refuses each call with the kind `Full` of the unit `Act_Records`, which names the cause; the card of the mark counts the acts refused with no room for their record apart from the input out of the picked windows.

Refused: **reading the newest 64 records only**: an audit that cannot be read whole is no audit; **reading each slot at a start**: a start of 256 slots read 256 objects for each space; **a room of records shared by all spaces**: a room of 256 records left place for one audit of a server beside the act spaces, while the memory is one window for each space whatever its bound; **a fixed table of 8 windows in the memory of the collector**: it paid 8 windows whatever the image held, and refused a ninth space that the budget could pay; **a count of spaces that the tool writes for the collector to read**: the budget already says what the collector can pay; **a budget of the collector that the tool computes for each image**: one module file serves each image, and the tool reads only integer literals, so the starter, which pays the budget of each process, widens it; **a fixed table of 32 places, a fixed count of 16 windows and a fixed bound of 13 audits**: an image with more audited servers would get a collector that refuses them; **a close before the new window and the index**: a refused commit or write left the old space closed with nothing in its place; **a new space in the place of a closed audit space**: it would write its segments over the records of the old one; **one bound of 32 records for each writer**: input stopped after 32 events, and the space of the root service refused the 17th grant; **a record for each key and each press**: a minute of typing filled any bound, and the count of the keys says the same; **a separate space for each grant**: 8 spaces of a collector would hold 2 grants; **deleting the segments that rotate out**: the port of the private store writes and reads only, and a slot that a later segment takes needs no delete.

**The router of the grant.** `wide_grants.Grant_Act_Router` is the state of the act spaces of the grant in the collector, a closed state machine `Unwired`, `Wired`, `Ended`. At the creation of a grant, `act_wiring_attach` opens the four spaces and writes `Grant_Started` in the space of the root service, or refuses the grant whole: a collector with no store, or a store that cannot hold the spaces, gives no wide grant. A grant that replaces another ends the wiring of the other first, with its record `Grant_Revoked` and the reason `Replaced_By_Newer_Grant`. Each record that comes on a ring of `acts` passes `act_wiring_accepts_stream_record` before the space keeps it: a writer word that is not the writer of the space, a grant serial or a principal that is not the grant in force, a lifecycle act from a writer other than the root service, a time before the last record of that writer or before the start of the grant, and any record with no grant or with a time after the end close the ring of that source. A ring that ends or that the collector closes while its grant holds ends the grant: the collector revokes it with the reason `Audit_Ring_Closed` and tells the root service with `Grant_Ended`. A revocation and an expiry write their record in the space of the root service and end the router, even when that space is full, so an agent cannot hold its grant by filling its audit; the router then says that the end record is missing. `act_wiring_rows_build` gives the rows of a wiring list from the running writers to `collector.sources`, with the pace `Always_Holds_Writer`, and refuses a writer twice, an end that is not `Started` or `Connected`, and one process at two ends.

**No act without its record.** A writer runs an act only when its record left (`wide_grants.act_emit`): a ring that is full, and also one with no reader or that ended, refuses the act, since no one keeps its record. A writer that starts while a grant holds has no reader until the root service wires it, and refuses each act until then. The agent console answers its line `Busy`; the root service refuses the command `Busy`; the trusted display drops the input of the agent, and counts it. The principal reads the acts with the console, as each record output: `acts(key)`.

Refused: **log facts as the record**: the log is lossy by design, and a wide grant must lose no act; **the act record after the act**: an act that ran with its record lost leaves no trace.

### The revocation

A press on revoke, `agent_disallow(key)`, the end of the time bound, the lock of the session, or the stop of the machine ends the grant. The root service, in one pass:

1. gives the row of the key a new wide grant serial and clears its wide grant, so `remote` and `remote_display` end each connection of the key with the code `Revoked`, as for a revoked client key ([`docs/PRINCIPALS.md`](../../../docs/PRINCIPALS.md), "The client keys of remote");
2. revokes with `Handle_Revoke` each handle that came from the grant: the shares, the connections, the log connection;
3. stops the agent console;
4. writes the act record of the end, with its cause, and ends the wirings of the act records with their end record;
5. tells the trusted display, which removes the mark.

**What the agent sees.** Its QUIC connection ends with the application code `Revoked`. The root service gives the row of the key a new serial when it clears a wide grant that the row held: `remote` and `remote_display` see a serial that is not the serial of the connection, and close it, as at a lock. A flow that ends before the grant holds (a refused screen, a proof not given) leaves the row and its connections as they were. A new handshake of its key holds only the uses of its row outside the wide grant, `Calls` if the principal gave it with `remote_allow`; a call of the agent console is refused with the error record `No_Grant`, unit `Wide_Grant`, and the cause: revoked, time bound, lock.

### The path of a grant, end to end

One grant at a time crosses the machine, in this order. Each step is a state of `wide_grant_flow` (`src/library/internal/root/wide_grant_flow`), a pure part of the root service with host tests: `Idle`, `Screen_Shown`, `Proving`, `Creating`, `Wiring`, `Active`, `Ending`. A word that comes in a state that does not wait for it, or with another tag or another flow, is refused with its `Flow_Refusal` and changes nothing. An end before the collector holds anything goes back to `Idle` at once; an end after it waits in `Ending` ("The end of a grant in the root service"), and a new ask is `Busy` until then.

1. **The ask.** A console that acts for the principal sends `Wide_Grant_Ask` (`agent_allow(key, scopes, minutes)`): the client key of the agent, the scopes that it proposes and a duration. The root service refuses a key with no row of that principal in the client table, a word of scopes that names no scope or `Send_Input` without `View_Screen`, a duration of 0 or past `MAX_WIDE_GRANT_DURATION_MS`, a flow that is not `Idle`, a key within its 10 minutes after a refused screen, a key after 3 refused screens of it in one run, and a principal after 3 proofs not given since its unlock ("The pauses of an ask").
2. **The screen.** The root service sends `Wide_Grant_Screen_Show` on the control ring of the trusted display. The compositor draws the screen above every window, with a tick for each scope, the duration (one hour, or until the lock), and the windows that the input may reach, from the windows that show, 4 at most. A window is offered when it shows, is not minimized and is not marked local; its id is the id that the display gave it when it opened ("The screen and the windows"), and the window in front is ticked. Up, Down and Tab move between the lines, Space or a press changes a line, Enter gives and Escape refuses; a give with no scope or no window is not sent. The screen takes the keys and the pointer of the input service only: while it shows, each key and each pointer record of the remote display is dropped. It answers `Wide_Grant_Screen_Answer`: the serial of the flow, give or refuse, the scopes, the duration, and the windows in two words of two ids of 32 bits.
3. **The terms.** The root service reads the answer through `flow_screen_answer`, which refuses a serial of another flow, a word of a decision or of scopes that names no member, a scope that the ask did not propose, a duration past the ask, no window, a window of 0 or twice. It seals the terms (`wide_grant_terms_seal`), keeps their hash, and starts `unlock` in the mode `Prove_Wide_Grant` for the principal. A refused screen starts the 10 minutes.
4. **The proof.** `unlock` asks for the passphrase of the principal (for principal 0, the machine passphrase) in its window, which the compositor marks local: while that window is open, no key and no pointer of the remote display reaches the desktop. A principal with no passphrase that proves it here gets `Refused` at once: no record, or a machine key that the TPM alone seals. The proof offers no recovery key: a refusal of the TPM ends it. It opens the keys, and sends `Wide_Grant_Proof` with the principal and the outcome `Proved`, `Cancelled` or `Refused`. Only the holder of `Principals` sends it, and only the run that the flow started is taken: `flow_proved` refuses another principal and a proof in a state other than `Proving`. `unlock` holds no authority key and sees no terms: it proves that the principal is at the keyboard, and the root service binds that to the terms that the screen showed.
5. **The grant.** The root service mints the proof (`authority_mint_proof`, the verifier the hash of the public key of the principal, and for principal 0 the hash of its measure) and sends `Create_Grant` on the ring of the collector of the principal, which it starts when none runs, with its region at the handles 10 and 11. The collector checks the proof, opens the four act spaces, and answers the grant serial, or refuses the grant whole.
6. **The wiring.** The root service wires the record output `acts` of `remote` and of the trusted display to `collector.sources`, one `Wire` of one row at a time through the wiring service, with the rows of `act_wiring_rows_build`. The collector is the asker of these wirings, and pays their rings from its budget: the audit is its own. The root service names each writer with the fact `audit_wired_by_root`, which only the core writes in the request, and which the wiring service takes only with the collector as the reader and the asker. A wiring that fails ends the grant: no grant holds before its act records have a reader.
7. **Active.** The root service writes the grant serial in the row of the key in the client table, which `remote` reads, and sends `Wide_Grant_Mark` to the trusted display with the grant serial, the principal and the end time. The trusted display draws the mark and keeps the windows of the answer as the bound of the input of a viewer: a key goes to the window in front only, never to the palette or the clipboard, and a key or a pointer of a viewer to another window, to the bar or to the desktop is dropped and counted. A mark of another screen than the last answer bounds the input to no window. The mark shows the minutes left; a press opens a card with the scopes, the minutes left, the count of the acts recorded and revoke. Control, Shift and Escape on the keys of the machine revoke in one press. The mark has one writer, the root service: the export `compositor.wide_grant_indicator`, which a caller that acts for the principal could call, is removed.
8. **The end.** `agent_disallow(key)` (`Wide_Grant_End`), a press on the mark (`Wide_Grant_Revoke_Pressed`), the end time, and the lock of the session of the principal each end the grant: the root service sends `Revoke_Grant` with its reason to the collector, ends the wirings of the collector as an asker (`Revoke_Asker`), clears the row and the mark, and goes back to `Idle`. A clear of the mark also closes a screen that still shows. A stop of the collector, of the trusted display or of a writer ends the grant too, and a row of the key that leaves, locks or becomes contested ends it at the next pass. The reasons `Session_Locked` and `Time_Bound` join `Revocation_Reason`.

**What the root service records itself.** The root service is no process that the wiring service knows, and it never waits for a reader: its act records of the grant, its terms and its end are written by the collector, in the space `root.acts`, when it opens and ends the grant. The record output `acts` of the root service is removed.

**Each call of `remote` under a grant.** `remote` reads the grant serial of the row of each connection. Before it runs a call of a key whose row holds a grant, it writes an act record `Call_Made` (the first 8 bytes of the hash of the service, the length of the request) with no wait; a record that finds no room refuses the call with the kind `Full` of the unit `Act_Records`, so no call runs without its record.

**The lines of a console are no act of this layer.** The scopes of this layer are `Screen_View` and `Input`: the agent types in a window, and the trusted display records each key. The writer of the lines is the agent console of the scope `Console_Lines`, which the second step of the order of the work builds. The console of the principal writes no act record: it is not the agent, and a record of its lines would mix the acts of the principal with the acts of the agent. Its record output `acts` is removed until the agent console exists. The command `agent_allow` only asks for the screen; the principal gives the grant on the screen and in `unlock`, never with a line of the console.

**The proof with no person** (a signature of a key of the principal on the host) is not in this path yet.

Refused: **the key in `unlock`**: `unlock` runs at each lock and change of a passphrase, so the key would cross a ring at each run; **the terms through `unlock`**: `unlock` has no need of them, and a terms hash that `unlock` echoes proves nothing that the flow state does not; **the root service as the asker of the audit wirings**: it is no process of the wiring service and has no budget of its own to pay rings from; **one `Wire` of several rows**: a `Wire` carries one row, and a wiring list with a child needs a `Start`; **a grant suspended at a second connection, which the principal resumes**: a resumed grant would hold again with no proof that the key is back in the hands of its agent, and a resume would need the proof, which is the cost of a new grant; **a key in the ask of an agent**: an agent would ask for a key that it does not hold.

**The end of a grant in the collector.** `act_link_keep` is the one step of a record of a ring of act records: a record that does not decode, of another writer, of no grant, of another grant or of a time after the end closes its link with no pending record, and its space keeps nothing. At each pass, `act_links_close_ended` closes each link of an act space whose grant ended and that holds a pending record, which its full space will never keep. A writer fills only its own space; the space of the root service is written by the collector only, so the record of the end lands while that space has room, and the grant ends when it has none.

**The end of a grant in the root service.** The flow has the stage `Ending`, between an end and `Idle`: it holds the work that the end waits for. The root service sends `Revoke_Grant` again after a full ring, reads its answer by its tag, asks the end of the wirings of the collector only after that answer (so the record of the end has its reason, not the close of a ring), and asks it again after a refusal of the wiring service. A Create_Grant whose answer comes after an end names a grant that the end then revokes. A bound of `END_BOUND_MILLISECONDS` ends the wait when the collector or the wiring service does not answer. At a lock, the collector of the principal stops only when the end settled, after its record of the end. The grant has one end time, which the root service fixes when the proof is given and gives to the collector in `Create_Grant`. A mark that the control ring did not take ends the grant with `Mark_Not_Shown`: no grant holds without its mark.

**The screen and the windows.** A window has an id that the trusted display gives it when it opens and never gives again in one run, 32 bits; a window that closes leaves the bound of the grant and the lines of the screen, so a window that opens later in the same place gets no input of a viewer. The screen names a window by the name that the root service gave its process in `Client_Add`, never by a title that the process chose. One trusted dialog shows at a time: a screen that comes over another dialog waits for it, and the other dialogs refuse with `Busy` while a screen shows or waits. The input of a viewer goes by the hit test of a press (`window_position_at`): under a grant, only to the surface of a window of the bound with nothing over it, never to its frame, the bar, the desktop, the palette, a menu or a card; and only with `Send_Input` in the mark.

**The pauses of an ask.** A refused screen pauses its key for 10 minutes, and 3 refused screens bar that key for the run, each key on its own, in a table of 16 keys. When each row holds a key barred for the run, the keys with no row share one more row: their refusals count together, so a new key never asks with no pause. A proof not given counts for its principal; after 3, the keys of that principal get no screen until the principal unlocks its session again.

## Security

- **An agent that asks for wider authority step by step.** A wide grant is replaced whole, never extended: each new screen shows the whole set, marks what is new, and needs the proof again. After a refused screen the key gets no screen for 10 minutes on the clock of the system, and after 3 refused screens of that key in one run, none until the machine starts again; after 3 proofs not given, the principal gets no screen until it unlocks its session again. The ordinary requests of the processes that the agent starts each show a dialog that names the agent console, and the agent cannot answer them.
- **An agent that drives the very dialog that grants it.** The input face of the remote display never reaches a trusted surface: no dialog, no screen of a wide grant, no mark, no window of `unlock` in its proof mode. The proof needs the passphrase from the keys of the machine. An agent with `Screen_View` sees the screen and can act on nothing that it sees there.
- **A prompt-injected agent that acts against the principal.** The system cannot read the intent of an agent. It bounds what a turned agent can do: the scopes that the principal kept, the places picked, "asks each time" on the acts that destroy or change, no change of a grant, a time bound of one hour by default, the mark that shows the count of the acts, and the act records that tell the principal after what happened.
- **An agent key stolen from the host.** The thief holds the key and acts with each use of its row, the wide grant too, while the grant holds. It ends with the time bound, at the lock, at the stop of the machine, and at a revocation; it is never on the disk, so a stolen key gets no wide grant after a restart without a new proof. A second connection of the key while the row holds the grant ends the grant with the reason `Duplicate_Connection`: `remote` closes both connections with `Revoked` at once, before any call of the second one, and sends `Wide_Grant_Second_Connection`; the root service ends the grant as for any other end. An agent that reconnects before `remote` ends its old connection at the idle bound makes a second connection too, so a lost connection ends the grant unless the agent waits out that bound. Only `remote` counts connections: a viewer of `remote_display` with the same key is a connection of another service and ends nothing. The principal gives it again with a new screen and a new proof. The act records show each act of the thief.

## The prior art

- **macOS 27.3**, beta 2 of 16 November 2026 ([the announcement](https://developer.apple.com/news/?id=oqng0zjk); [the support article](https://support.apple.com/en-us/149699)). Device Control and Data Access splits into System & App Protection Override and Accessibility. The person chooses the apps or the folders that an app reaches in place of the whole Mac, each app with "Ask First" or "At Any Time". A screen lists in words what the app will be able to do, a confirmation for each line ("Control Your Mac, Apps, and Settings", "Monitor Everything You Do"), then asks for the password. An indicator in the menu bar shows while an app controls another app. Taken: the place bounds by picked objects, the mode "asks each time", the list in plain words, the password at the end, the indicator. Refused: a confirmation for each line, which trains the reader to press with no reading; a grant that lasts for ever; the grants of before kept as they were by an update.
- **Accessibility, Screen Recording and Automation of macOS.** Accessibility gives the control of each app at once, and Screen Recording each window: taken as the honest statement that `Input` on every window and `Screen_View` reach everything, refused as switches with no bound. Automation is one switch for each pair of apps, which the system asks for at the first use and then never again: the pair is the form of the place bound of `Input` by window, taken; the question with no end time is refused.
- **OAuth 2.0 scopes** ([powerbox.md](powerbox.md), "The prior art"): a scope with a name and a boundary, and an answer that says which scopes were given.

## The order of the work

1. **The scopes `Screen_View` and `Input` with the mark and the screen.** The wide grant on the row of a client key, the screen of the contract, the proof in `unlock`, the time bounds, the place bound of `Input` by window, the mark with its revoke, the end at a second connection, and the act records of the trusted display and of the root service. It needs the first layer of the powerbox and the collector as the reader of the act records.
2. **`Console_Lines`, `Processes` and `Log_Read`**: the agent console with its start grant set from the kept scopes, the act records of the console, and the rule that an `Apply` that adds a grant needs the proof while a grant holds.
3. **`Stores`**, with the picker of the powerbox and the shares.
4. **"Asks each time"**, through the grant dialog of the powerbox.
5. **A wide grant to the hash of a module**, for an agent that runs on modus.

Why this order: the roadmap entry of the agent needs the screen and the input first; the scopes that reach the console and the stores add authority, so they come after the mark, the proof and the act records that bound them.
