# Log facts: typed records in place of formatted lines

## Purpose

A line of the log that matters becomes a log fact: a record type of the source, whose values the record carries with no text. The module file describes the type and gives its fact template, and the reader writes the sentence. Today a log record carries a formatted text and value runs: a reader knows that a part is a number, not that it is the `block` of a bad block. The writer formats each line, the formatting is inlined at each call site ([library_modules.md](../api/library_modules.md)), and a test compares sentences. With log facts, a reader filters by a field (`block = 12`), a machine test waits for a fact and its fields, and the tool refuses a test that names a field that no fact type has, before the machine runs.

The guide is [`docs/TOOLS.md`](../../../docs/TOOLS.md), "The log". The log scope does not change: [log_reader_scope.md](log_reader_scope.md).

## Constraints

- **No text between processes** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "19. A command is a function: no text between processes"). A reader parses no text of a writer.
- **No contract depends on a feature of one language** (property 19). The record of a log fact and its description are bytes and flat tables, not the types of Odin.
- **The kernel holds no text parser** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "1. Small kernel with a small, counted interface"). Its check of a log record is a filter of bytes, and it gets no new operation.
- **Module metadata is flat tables, read through functions** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "12. Module metadata in flat tables, read through functions").
- **The hash of a module is its identity** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "11. Reproducible system"). A module file cannot hold its own hash.
- **A library module holds no address that the loader rebases into a read-only segment** ([library_modules.md](../api/library_modules.md)).
- **A process sees no other process** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "20. No ambient access: the other holes to close", row 1). The log scope stays the one border of the reader.
- **A log record has 256 bytes**, and the whole log and each own log ring keep records of that one size ([own_log_ring.md](own_log_ring.md)).
- **One general mechanism, and a plain expression for each frequent task** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "22. General mechanisms, and a plain expression for each frequent task"). See "The frequent tasks".
- **The kernel log is lossy by design.** The whole log and the own log ring evict, the budget of each second refuses, and the serial port loses the lines of a flood ([log_side_channels.md](log_side_channels.md)).
- **No backward compatibility.** The record changes in place, and the old path leaves.

## The chosen form

### What the log is, and what it is not

The log is diagnostics for a person, a test or an operator. Its readers accept loss: a ring evicts, a budget refuses, the serial port drops lines and counts them. A record has no order that the work of its writer promises, and a reader reaches it through the log service and its log scope.

The work of a module, for another program, goes through a record output of the module, which the other program reads as a record input: the answer of the system to the refused `stdin` and `stdout` of property 19. A record output loses no record, has flow control, is reached through a handle that someone gave, and is part of the contract of its module. Its design is [module_outputs.md](module_outputs.md).

The two share one part: a record type of the source, extracted into the module file as a record description (`docs/glossary/communication.md`, "Record description"). That part is generic. The table `Records` of the module file holds the description of each record that the module names: the records of its exports, of its log facts, of its record outputs and of its record inputs. Nothing in it is a log thing. The kernel log and the record outputs share nothing else: not the path, not the guarantees, not the rights.

**The record output `log`.** Each process has one record output that no module declares: `log`, which carries its own log records, its text lines and its log facts. Its starter can wire it at the start of the process, for an audit. The kernel log stays as it is, lossy diagnostics; a wired `log` has the guarantees of a record output: no record is lost, and the writer waits for its reader. So a process can keep the log of a child whole, which the kernel log never promises. See "The record output `log`" below.

### The fact type in the source

A fact type is a record type with one fact template. The template is an attribute of the type, and the call names the value only: no string is at the call.

```odin
// A block whose check is not the check that its pointer names.
@(log_fact = "storage: the block {block} has a wrong check {check}, expected {expected}")
Bad_Block :: struct {
	block:    u64,
	check:    value_kinds.Hexadecimal_32,
	expected: value_kinds.Hexadecimal_32,
}

system.log_fact(.Warning, Bad_Block{block = number, check = found, expected = wanted})
```

- **The attribute.** `log_fact` is a custom attribute: the build gives the compiler `-custom-attribute:log_fact`, which accepts it on a declaration and ignores it. Without the option the compiler refuses the attribute ("Unknown attribute element name"). The tool reads the attribute and its literal from the syntax tree.
- **The fact key is the typeid of the record type.** `system.log_fact(level, value: $T)` writes `transmute(u64)typeid_of(T)`. See "The fact key: why the typeid".
- **The compiler holds two refusals.** The procedure has the clause `where !intrinsics.type_struct_has_implicit_padding(T) && size_of(T) <= op.LOG_FACT_VALUE_CAPACITY`, so a record with padding or too large fails at the compile of the call, before the tool runs.
- **The tool holds the rest.** It refuses a call whose value is not a composite literal of a named type, because it has no type checker. It refuses the named type of a call when that type has no attribute `log_fact`. And it refuses the attribute on a declaration that is not a record type of the package scope.
- **One fact type for one record type.** The template is on the type, so a record type has one template. The fact name for a reader is the package name and the type name: `storage.Bad_Block`.
- **The kinds of the fields** come from the distinct types of `modus:contract/value_kinds`, as for an export ([console_value_colors.md](console_value_colors.md)). This design adds the kinds that the log uses and a record description lacked, as the field kind (`value_kinds.Field_Kind`): see "Field kinds". [console_value_colors.md](console_value_colors.md) holds the form in the description, the borders and the colors.
- **A fact type can have no field.** `Usable :: struct {}` is a record of 0 bytes, and its sentence is its template: a line with no value is a fact as each other line is, so a reader finds it by its fact type. The kernel takes a fact of 0 value bytes: the body is the head of 48 bytes, the least length that `Log` of the form `Fact` takes. A fact of no field given a value byte is refused by the render (`Value_Count`), as each count that is not the size of the record. A record of an export, of a result or of a table keeps its field: a call carries values, and the tool refuses a record with none there.
- **A fact type can be a distinct type of a record type**, of its package or of a package of the library: `Request_Refused :: distinct errors.Error_Record_Fact_Fields`. Its fields are those of the record type, its name and its template its own, so a shape that several modules share is declared once and each module keeps its own fact type, since a fact type is of its package. The call writes it with a composite literal or with a conversion of one value, `Request_Refused(errors.error_record_fact_fields(record))`: the tool reads the named type of the conversion as it reads the type of a literal. See "The error record as fields".
- **No padding.** The compiler and the tool refuse a fact type with a byte that no field covers. Such a byte carries memory of the writer that no field names.
- **No Handle field.** A handle number means nothing to a reader of the log. The tool refuses it.
- **No Body field.** A `Body` field is an offset and a count in the body region of a record output ([module_outputs.md](module_outputs.md), "A large body"). Only the record of a record output or of a record input takes it: the tool refuses it in a log fact, as in the record of an export. A log fact has no body region, and its values are whole in its record. The type does not exist yet: the check of the fields of a fact type is a whole switch on the type of a field, so the first build with a type `Body` fails to compile until that switch refuses it.
- **At most 144 bytes** of fixed fields (`op.LOG_FACT_VALUE_CAPACITY`): the record of a fact type fits in the first log record of its fact. A text of no small bound is a text view of 16 bytes, whose bytes past 12 go in the out-of-line area after the record, which the records after the first carry: see "Text views" and "A fact of several records".

### The fact key: why the typeid

The code needs the key of a fact type at its compile, from the type alone, and the tool needs the same number from the source. Three ways were read.

**(a) `typeid_of(T)`, chosen.** The facts, from the sources of the compiler of the flake (the fork of `dev-2026-11a`, `src/name_canonicalization.cpp`, `src/check_builtin.cpp`, `src/llvm_backend_type.cpp`) and from builds:

- **It is a constant in the code.** The checker gives `typeid_of` a value of the type, `exact_value_typeid(t)`, and the back end writes it as `LLVMConstInt` (`lb_typeid`). A build for `freestanding_amd64_sysv` with `-o:speed` and `-reloc-mode:pic`, the flags of a module, writes `store i64 1239833465674507115, ptr @sink` for `typeid_of(T)` in a polymorphic procedure: an immediate, with no address and no table of type information (0 lines with `type_info` in that IR).
- **It is the hash of a name, not of a layout.** `type_hash_canonical_type` is SipHash-2-4 with a fixed key (`k0 = 0xa6592ea25e04ac3c`, `k1 = 0xba3cba04ed28a9ae`) over the canonical name of the type. For a named record type of the package scope, the canonical name is `<package name>::<type name>`: `storage::Bad_Block`. No address, time, path or order of the build enters it.
- **It is the same in each build and in each module.** Two builds gave `18017458693634389201` for `storage.Bad_Block`. The value depends on the two names only, so each module that compiles the package gets the same key.
- **It is unique in a module.** The compiler refuses two packages with one name in one build ("A package name must be unique"), so two fact types of one module have two canonical names.
- **The tool computes it.** SipHash-2-4 with the same key, over `storage::Bad_Block`, gave `18017458693634389201`, the value of the compiler. The tool has its own SipHash (`build.siphash_2_4`), checked against the vectors of its paper. It was written when `core:crypto/siphash` brought a package whose name the copy of the cryptography of Odin in the library also had, which the compiler refuses in one build. The copy now has its own package names ([../infrastructure/cryptography_package_names.md](../infrastructure/cryptography_package_names.md)), and `ROADMAP.md` holds the change to `core:crypto/siphash`.

The contract states the key as bytes: "SipHash-2-4, with the key of 16 bytes above, over `<package name>::<type name>` in UTF-8". A writer in another language computes it, so the contract does not depend on Odin (property 19). In Odin, `typeid_of` computes it.

The costs:

- **The key depends on the compiler.** A new compiler with another canonical name or another seed changes every key. So the tool checks it at each build: for each fact type, it searches the LLVM IR of the module, which the build writes before `llc`, for the immediate of the key that it computed. A fact type whose key the IR does not hold, at a call, fails the build. A host test of the tool compiles one fact type and compares the two values, so a change of the compiler fails before a module is built.
- **RTTI stays on.** `typeid_of` is refused with `-no-rtti`. The modules are built with RTTI today; the IR of `console` holds no table of type information, and the IR of `cryptography` and `root` holds one. Measure 5 shows whether a fact type adds bytes of type information to a module file.
- **A rename is a new key.** A fact type keeps its key while its fields change; the module hash then names the new description. A new name of the type or of its package is a new fact type, which a test that names it sees at its check.
- **The key has 8 bytes**, so the record holds 144 bytes of values, not 152.

**(b) A key that the tool generates, refused.** The tool parses each package before the compile and writes a generated file with one constant for each fact type, which the code reads. A generated file is allowed when nobody edits it: its source changes, and the tool writes it again. The cost: one more step before each compile, a build key that holds the parse, a generated file in each package that writes facts, and a stale file to detect. An index that it generates also names a fact type inside one package, not inside the module: a fact type of a support package needs its package in the key too. The typeid gives the same with no file.

**(c) The other ways read, refused.** The FNV hash of the template with `#hash` (the form before): a string beside the type. The tag of a union of the fact types of a package: two packages of one module give the same tags. The place of a declaration in a link section: an address, and a rule of the linker. No intrinsic of the compiler gives the name of a type as a constant string.

### The fact table of the module file

The tool reads each type with the attribute `log_fact` that a call of `system.log_fact` names, in each package that the module compiles in, and writes the table `Facts` of the module file. One row for each fact type, sorted by fact key:

| Field | Meaning |
|---|---|
| `key` | The fact key, never 0. |
| `record` | The index of the record description in the table `Records`. |
| `template_offset`, `template_count` | The fact template, in the string table. |
| `package_offset`, `package_count` | The name of the package that declares the record type, in the string table. |

A type with the attribute that no call of the module names gets no row. A call that the code of the module does not reach gets no row either: a support package does not add the fact types that a module does not write. The tool knows the calls that the code reaches by the IR, which holds the key of a fact type only where a call is compiled: the module `drawing` compiles the package `interface` and never writes an element line, so its IR holds no key of `interface` and its table has no row of it. The compile step writes the keys that it found (`reached_facts.list`, an output of the step), and the conversion keeps the fact types of that list, so the two steps name one set even when the compile step is kept.

The tool refuses at the build:

- two fact types of one module with the same fact key or the same key tag (the first 3 bytes of the key, which the serial line writes: see "The serial port"), a fact key of 0, and a key of a fact type of the package of the module itself that the IR of the module does not hold as an immediate `i64` (the compile step reads `<name>.ll` after the compiler wrote it, and before `llc`). The fact types of the package of a module are its own calls, which its code reaches; the check of the key against the compiler holds for them. The fact types of a support package have no such refusal, by the rule above, and the host test of the key keeps the check of the compiler for them;
- a fact template that breaks a rule of the template language (below);
- a field that the fact template does not name, and a name in braces that names no field;
- the attribute on a declaration that is not a record type, on a declaration inside a procedure or a `when`, or on a type private to its file: each of them has another canonical name, so the key is not the typeid of `<package>::<type>`;
- a record of a fact type whose name the module describes another way: one module describes a record name one way, whichever declaration names it.

The extraction reads the sources that the compiler read for the module (its list of dependencies), and parses only a file that holds the word `log_fact`. The checks of the template language are one pure procedure of the contract, `module.fact_template_check`, which each reader that renders a fact calls too: the tool and a reader cannot disagree on a template.

The tool describes each record type once in `Records`, whichever declaration names it: an export, a log fact, a record output or a record input. A record type that an export takes and a log fact writes has one row, and both name it by its index. Nothing in a record description says which declaration named it. The refusals of a fact type above are the refusals of the declaration, not of the record description.

The package name gives the fact name that a reader and a test write: `storage.Bad_Block`, the package name and the name of the record type, the two names of the key. A fact type of a support package keeps one name in each module that compiles it in: `interface.Element_Placed` is the same name in each window.

A fact template changes the hash of the module, as each byte of the metadata does. So the pair of a module hash and a fact key names one description, and the record needs no version number.

### The fact template

The language is the least that writes today's sentences:

- UTF-8 text, with no control character ([text_encoding.md](../data/text_encoding.md)).
- `{name}` writes the field `name` by its kind: an Integer in decimal, signed or unsigned by its description; a Size or a Time with its unit; a hexadecimal Integer with `0x`; a status by the words of its member, which are its name but for a stop cause and a stop outcome ([console_value_colors.md](console_value_colors.md), "The words of a member in a sentence"); a Text up to its first zero byte; a hash in hexadecimal; and each kind of "Field kinds" in its own form.
- `{{` and `}}` write one brace.
- At most 512 bytes (`module.FACT_TEMPLATE_BYTES_MOST`). The longest lines of the modules have about 380 bytes: the faults of the open of the disk and of the erase of versions, the measure of the passes of the network service. The template is in the string table of the module file, once for each fact type; a record carries no byte of it. So the limit costs bytes of the module file only, for the fact types that use them, and nothing in the log, in an own log ring, on the serial port or in the budget of each second. The buffer of a reader, `FACT_SENTENCE_BYTES_MOST` (1024 bytes), holds a template of 512 bytes with values of 144 bytes in most cases, and refuses a longer sentence, which the reader shows raw.

It refuses: a name that names no field, a field that it does not name, a field named twice (one value once in a line), an unclosed brace, a name that is not an identifier, a format inside the braces (a width, a precision, a base), and anything more: no condition, no plural, no expression, no field of a field. The kind in the description decides the form of a value, so the template never says it. A fact type that needs another sentence for another case is two fact types.

### Field kinds

Each kind writes the form that a line wrote before the facts, so a template keeps the sentence of today and each wait of a machine test passes unchanged. The form comes from the kind in the description, never from the template.

| Field kind | Type of the source | Field | Form | Value kind |
|---|---|---|---|---|
| `Hexadecimal` | `value_kinds.Hexadecimal_8` to `Hexadecimal_64` | unsigned Integer of 1 to 8 bytes | `0x` and two digits for each byte | Number |
| `Status` | a contract enum (`operation.Status`, `errors.Kind`), or its word type (`operation.Status_Word`, `errors.Kind_Word`, `errors.Unit_Word`) | unsigned Integer of the size of the type | the words of the member; a word that names no member, its number | Status |
| `Module_Name` | `value_kinds.Module_Name_Field` | Text | the text | Module |
| `Hash` | `value_kinds.Hash_Field`, `value_kinds.Hash_Sixteen_Bytes_Field` | Bytes of 1 to 32 bytes | two digits for each byte | Version |
| `Hexadecimal_Sixteen_Digits` | `value_kinds.Hexadecimal_Sixteen_Digits` | unsigned Integer of 8 bytes | 16 digits with no `0x`, as `system.Hex` writes an address or a response code | Number |
| `Hash_Head` | `value_kinds.Hash_Head_Field` | Bytes of 32 bytes | the digits of the first 4 bytes, then `…`, as the root service names a start policy | Version |
| `Hundredths` | `value_kinds.Hundredths` | Integer | n / 100 with two decimals: `1.05`, `-0.50`, `0.00` | Number |
| `Nanoseconds_As_Microseconds` | `value_kinds.Nanoseconds_As_Microseconds` | unsigned Integer | microseconds with one decimal, cut and not rounded, then ` us`: 812 499 ns is `812.4 us` | Time |
| `Tenths` | `value_kinds.Tenths` | Integer | n / 10 with one decimal: `12.3`, `-0.5`, `0.0` | Number |
| `Hexadecimal_No_Leading_Zero` | `value_kinds.Hexadecimal_No_Leading_Zero` | unsigned Integer of 8 bytes | `0x` and the digits with no zero before the first, as `write_number` of the support package `sentence` writes an address: `0x1a2b`, `0x0` | Number |
| `Time_Of_Day` | `value_kinds.Time_Of_Day` | unsigned Integer | the seconds of a day as hours and minutes of two digits at least: `07:04`; a value past the day writes its hours, `24:00` | Time |
| `Text_View` | `value_kinds.Text_View` | Bytes of 16 bytes | its text, whole, from the view and the out-of-line area of the fact ("Text views") | None |

The time of day writes the sentence of the appearance in force ("light from 07:00 to 19:00 of the local time; the local time is 01:04 ..."): the step `Appearance_Auto` of the tool reads the rendered line, which is the line of before, so its parse does not change.

The choices, each with its reason:

- **The head of a hash holds the whole hash.** A reader that filters or compares a start policy needs each byte; the render shows the head. The field costs 32 bytes of the 144, and its zeros after the hash cost nothing on the serial line, as each value.
- **Two heads of a hash, by two forms.** The root service writes 4 bytes then `…`; `cryptography_vectors` writes 16 bytes then `...`. One kind with the length of its head in the description has no place: `detail` of a Bytes field is its size, and the bytes of `module.Field` that are left are reserved and zero. The head of 16 bytes is a Hash field of 16 bytes, which the kind `Hash` writes whole, and its template writes `...`: no new kind. The head of 4 bytes keeps the whole hash, so it is a kind.
- **One writer of each form.** `module.field_kind_text` writes the four forms of the kinds that the kind alone decides. The render of a sentence, a column of the console and the tool call it, so a sentence and a cell of one field never differ.
- **A tenth is cut, not rounded.** The lines of the measures wrote `n / 1000` and `n / 100 % 10`; the kind keeps that form, and `quality_lines_check` reads it.
- **A hundredth has a sign.** The network service writes a ratio that is never negative; the kind takes an Integer with a sign so a writer of a difference uses it too. The sign comes before the whole part, so -50 is `-0.50`, not `0.-50`.

**Enums of the contract as fields.** A field of a contract enum is a field of the kind Status of one member of `value_kinds.Contract_Enum`: `operation.Status`, `Log_Level`, `Log_Record_Form`, `Stop_Cause`, `Stop_Outcome`, `Object_Kind`; `errors.Kind` and `errors.Unit`; `module.Load_Stage`, `module.Error` and `module.Difference`; `block.Status`; `storage_status.Status`; `call_status.Call_Status`; `pointer_pictures.Part`, `Field` and `Problem_Kind`. The list is closed: each reader compiles the contract in, and writes the name of a member with `module.contract_enum_member_name`; a new enum is a new member, with its names in the package of the enum. An enum of a contract that is not in the list (`tpm_service.Status`, `remote.Status`) is a member to add when a line needs it.

- **The dispatch is in `module`.** It renders a fact, and it can import each contract package that declares a contract enum: `module.Load_Stage` is one, and `operation`, which held the dispatch before, cannot import `module`, which imports it. A contract package that imports `module` (`isolated`) cannot declare a contract enum.
- **An enum that a fact holds is a contract.** A fact crosses to a reader in another process, which writes the names of the members: the names are in a contract that each reader compiles in. `storage.Status` and `system.Call_Status` were enums of support packages, which a reader of the log does not compile in: they moved to two contract packages of their own, `storage_status` and `call_status`, with explicit values. `storage.Status` had no explicit value and the size of an `int`: it is `u8` now. `isolated`, the contract of a call, imports `module`, so `Call_Status` has its own package.
- **The names of the members are beside the enum.** `errors.KIND_NAMES` (the console had its own copy, which left), `errors.UNIT_MEMBER_NAMES`, `operation.OBJECT_KIND_MEMBER_NAMES`, `block.STATUS_NAMES`, `module.LOAD_STAGE_NAMES`, `ERROR_NAMES`, `DIFFERENCE_NAMES`, `pointer_pictures.PART_MEMBER_NAMES`, `FIELD_MEMBER_NAMES`, `PROBLEM_KIND_NAMES`. A table of the words of a sentence (`errors.UNIT_NAMES`, `pointer_pictures.PART_NAMES`) stays apart: a condition names a member by its name.

**A status that a line wrote as its number becomes the name of its member.** A line wrote `status 5`; its fact writes `status No_Right`. The sentence changes, and the group that converts the line changes each wait that reads the number, in the same commit. A word that names no member stays its number, never the name of another member, so a status of a newer kernel reads as the number that it is.

**A word type.** An enum whose words come from another party (the kind and the unit of an error record), or that a record holds beside fields of 8 bytes (a `Status` of 4 bytes after a `u64` leaves 4 bytes of padding, which the build refuses), has a word type of 8 bytes in its contract package: `operation.Status_Word`, `Stop_Cause_Word`, `Stop_Outcome_Word`, `Log_Record_Form_Word`, `Object_Kind_Word`; `errors.Kind_Word`, `Unit_Word`; `module.Load_Stage_Word`, `Error_Word`, `Difference_Word`; `block.Status_Word`; `storage_status.Status_Word`; `call_status.Call_Status_Word`; `pointer_pictures.Part_Word`, `Field_Word`, `Problem_Kind_Word`. Each contract enum but `Log_Level` has one. The table `value_kinds.CONTRACT_ENUM_TYPES` names it beside the enum, and `module.CONTRACT_ENUM_WORD_SIZES` gives its size. A field of it is the same Status of the same enum, at the size of the word type. The writer copies a word with no cast to the enum (`op.Status_Word(status)`), so a word that names no member is carried as it is, and the reader, which is the border, writes its number. The refused forms: a reserved field that pads the record, which the template must name, so the sentence would show it; a status kind of 8 bytes for each enum, which is a second kind of one concept.

### The error record as fields

A line that wrote the sentence of an error record becomes a fact of the seven values of the record. The shape is `errors.Error_Record_Fact_Fields`: the kind and the unit as their word types, which a reader writes by the names of their members, then `operation`, `argument`, `value`, `limit` and `found` as Integers with a sign. A module declares its fact type as a distinct type of it, with its own template, and writes it with `errors.error_record_fact_fields`, which copies each word as it is:

```odin
@(log_fact = "storage: the block service refused a request: kind {kind}, unit {unit}, operation {operation}, argument {argument}, value {value}, limit {limit}, found {found}")
Block_Request_Refused :: distinct errors.Error_Record_Fact_Fields

system.log_fact(.Warning, Block_Request_Refused(errors.error_record_fact_fields(record)))
```

The template of such a fact type ends with `errors.ERROR_RECORD_FACT_TEMPLATE_END`, the words above after the words of the module, and the tool refuses one that does not, so each fact of an error record reads the same and a reader learns one form. `where(kind = Too_Long)` and `where(unit = Bytes)` read it by the names of the members.

**The sentence changes.** The console writes a different sentence for each kind of an error record ("the argument name has 300 bytes; it can have at most 255"), with the name of the operation and of the argument, which the record does not hold. A template has no condition (see "The fact template"), so no template writes that sentence: the line "storage: the block service refused a request: storage.write: the argument name has 300 bytes; …" becomes "storage: the block service refused a request: kind Too_Long, unit Bytes, operation 3, argument 2, value 300, limit 255, found 0". The group that converts such a line changes each wait that reads its words in the same commit. The refused forms:

- **A field kind `Error_Record` whose render writes the sentence of the console.** The one render is in the contract (`module.fact_sentence_write`), and the sentence of an error record is in the support package `sentence`, with the names of operations, of rights, of objects and of grants; the contract would hold that whole writer. The sentence also needs the name of the operation and of the argument, which the record does not hold: a field kind cannot write them. And a record in one Bytes field has no field that `where` reads: a fact of a field of a field is the form that the template language refuses.
- **The text of the sentence in a Text field.** It is a free sentence of the writer, the form that this design removes, and no reader filters it.

### Text views

A text of no small bound (a path, a line of the console, the target or the title of a link, a place of the debugger) is a field of the type `value_kinds.Text_View`: a German string, the string of Umbra and CedarDB, which DuckDB and the string view of Arrow also use.

- **The 16 bytes.** A length of 4 bytes, then the first 4 bytes of the text (its prefix), then 8 bytes: the rest of a text of at most 12 bytes, or else the offset of the whole text in the out-of-line area of the fact, a `u64`. The bytes past a short text are zero, so an empty text is 16 zero bytes and a record keeps ZII. No address crosses the log: the offset names bytes of the same fact.
- **The out-of-line area** follows the fixed record in the values of the fact, and continues in the records after the first ("A fact of several records"). It holds the long texts of the fact one after the other, whole: the prefix is in the view and in the area, so a reader reads one slice. A fact may have several views; only its long texts use the area, and its fixed record stays small.
- **The write.** The views are the last fields of the fact type, and the call gives one string for each, in their order: `system.log_fact(.Info, Request_Served{status = status}, path)`. The field of the literal stays zero; `system.log_fact` finds the views at the end of the record by their count, copies each text into its view or into the area, and gives the record and the area to `Log`. The string need not live after the call. The build refuses a field after a view, and a call with another count of texts, a named text or a spread. At the run, the write refuses, and writes no fact, more texts than the record holds views, or a place of a view that is not 16 zero bytes, as the literal leaves each view: it has no count of the views of the type without the type tables of the runtime, which a module does not link, so a fixed field of zeros at the place of a view is the build's to refuse.
- **The bound.** The area of one fact has at most `op.LOG_FACT_TEXT_AREA_BYTES_MOST` (1024) bytes: the longest texts are a load error and a target of the manual of 256 bytes, a path of 200. A text that the area has no room for is cut on a whole character and ends with the cut mark of the contract (`cut_mark`), so its view says its own length and never reads as a whole text; a text that finds no room at all keeps its start and as much of the mark as its 16 bytes hold. The write cuts and does not refuse: a writer of the log learns no result, and a cut text that says it is cut is worth more than a lost fact. The kernel refuses a fact past the bound, with its error record (`Too_Long`, `Bytes`, the length and `op.LOG_FACT_CALL_BYTES_MOST`).
- **The read.** `value_kinds.text_view_read` gives the text of a view from the view and the area, and refuses a byte past a short text that is not zero, a long text past the area, and a prefix that is not the start of its bytes. The render refuses a fact with a view that it refuses (`Text_View`), and shows it raw: it never writes a sentence with a part of a text.
- **A condition reads the head first.** `value_kinds.text_view_compare_head` compares the length and the prefix, and a short text whole, from the fixed record alone; only a long text with the length and the prefix of the condition reads its area (`console_condition.text_view_condition_holds`). The step `Fact` of the tool has the area of the line, and decides each text. A table of the console holds the fixed record of each fact, not its area: `where` decides each view from its 16 bytes and fails the line, never guesses, when a long text has the length and the prefix of the condition. The count of the reads of the area that the head did not spare is a measure to print, never a condition; it is not printed yet.
- **The paths are not limited by the log.** A path takes its bytes in the area, up to the bound of the area. `PATH_LIMIT` of `module_files` (200 bytes) is a limit of its export, not of the log, and is a question of its own.
- **Fixed Text fields stay** for short texts with a small bound: a name of a module of 32 bytes, the digits of a key. A view of such a text takes the area for each name past 12 bytes; a fixed field costs its bytes and no area, and a condition reads it in the row. A view is the form for a text with no small bound.

### A fact of several records

A fact whose values pass one record takes the records that follow each other in the log of its process: the fixed record and the start of the area in the first record, the rest of the area in the next ones, `op.LOG_FACT_VALUE_CAPACITY` bytes each. The bound is `op.LOG_FACT_RECORDS_MOST` records, 9: the fixed record of 144 bytes and an area of 1024. `more` is the byte that a long text already used: 1 on each record of a fact but the last.

- **The kernel writes them in a row.** `Log` of the form `Fact` takes `op.Log_Fact_Call`, from `op.LOG_FACT_HEAD_BYTES` to `op.LOG_FACT_CALL_BYTES_MOST` bytes, and refuses a longer one with `Bad_Address` and its error record. It writes one record for each part, each with the module hash and the key of the fact, under one log lock, so no record of another process comes between them in the whole log, and each takes the next own number of its process. It writes in each the count of its value bytes, `part` (from 0) and `part_count`, over what the process gave: the process writes neither. A fact costs one record of the budget of each second for each part.
- **The join.** `op.log_fact_join_take` takes the records of a reader in the order of their numbers (`op.Log_Fact_Part`: the number, the writer, the hash, the key, the part, the count of the parts, the values) and gives a whole fact in `op.Log_Fact_Join`. It refuses, with the fault of `op.Log_Fact_Join_Fault`: a record after the first with no fact open (`Part_Without_First`); a number that is not the next one, or a part that is not the next part (`Missing_Part`); the next record of another process (`Other_Process`); another hash, key or count of parts (`Other_Fact`); a count of parts of 0, past the bound, or a part past it (`Part_Count`); a record before the last that is not full (`Value_Count`). A record that is not a fact, of the same process or the next of another, breaks an open fact (`log_fact_join_other_record`). A record after a fault is taken again as the start of a fact. The join holds the bound of a fact too: a record that would pass `op.LOG_FACT_VALUES_MOST` value bytes is refused (`Value_Count`), so the last record of a fact of nine records holds at most 16 bytes, and no reader slices past its values; the largest number has no next one.
- **The end of a read.** A fact still open when a read ends lost its next record, unless the read stopped at its page (the records after it are past what the reader asked for): `op.log_fact_join_end` closes it with `Missing_Part`, and the reader shows its records raw after the mark, never nothing. The console stops at its page when a fact row passes the last row that it draws or when it used its count of answers; the step `Record` when its answer did not reach the last record of the scope, and its next read then starts at the first record of the open fact, so that the fact joins whole.
- **One numbering.** The console and the tool read rows of `log.fact_records`, which name no process, and give the join the writer 0: the records of one fact follow each other in one numbering, the whole log or the own records of one process, and the kernel writes them under one lock, so a number with no gap says that no record of another process came between them. The window `log`, which reads whole records, gives the writer.
- **A broken fact is raw, with a mark.** A reader shows each record of a fact that does not join after `op.LOG_FACT_JOIN_BROKEN_MARK`, then the raw line of its part, never a sentence of the values of two facts or of a fact with a hole.
- **The readers.** The window `log` joins the records that it takes, writes the sentence in the place of the last record, and nothing in the places before, so the group of the records, which `more` joins, reads the sentence; its groups take up to `op.LOG_FACT_RECORDS_MOST` records. The console joins the rows of `log.fact_records` of the records of a line. `facts()` reads the first record of each fact, which holds its fixed record. The step `Record` of the tool joins the rows that it reads. A row of `log.fact_records` gives `part` and `part_count` in the place of the reserved bytes. A row of `log.records` and of `log.process_records` gives `continues`, the byte `more`, for a fact as for a text: a reader that groups the rows by it, and only while each next row has the next number, the same form and the same slot, reads the records of one fact as one group (an answer can miss a record that the kernel wrote over during the read), and the step `Record` of the tool reads the sentence of the group at the number of its last record.
- **The serial line.** A fact of several records is one line: its first record writes "*" and the digit of the count of its records after the key tag, `#1a2b3c4d:fa0adf*2 0ch23`, and each next record, which continues the line, writes "/" and its values, `/0d`. Each record cuts its own last zeros: a reader knows that each record before the last holds 144 bytes. The last zeros can be the last bytes of a text of the area, so the tool reads the line of a record with text views as the record and the whole area, with zeros after the bytes of the line. A record after the first that starts a line, because the drain lost the record before it, writes its head and "/" with no count; the tool refuses that line and shows it raw. A first record while a line is open ends that line first. With no memory of the log, the kernel writes the same line from the copy of the fact. Measure 4 counts the bytes of the whole line, and measure 3 one record for each part.

### The load error as facts

`module.Load_Error` holds four names with their hashes, an export and two descriptions: far past one record, and its sentence (`system.load_error_text`) has a form for each stage. Each stage names a part of it only, so each stage has one shape in the contract `module`, beside `Load_Error`, with the fields that its sentence names: `Load_Find_Fields`, `Load_Read_Fields`, `Load_Cycle_Fields`, `Load_Check_Fields`, `Load_Bind_Fields`, `Load_Memory_Fields` (Map and Unmap) and `Load_Room_Fields`. A name is a Text field of `module.LOAD_NAME_FIELD_BYTES` (40) bytes, a hash a `Hash_Head_Field`, and what failed a contract enum: `module.Error` for Read, `module.Difference` for Check, `operation.Status_Word` for Map and Unmap. Each shape fits one record. A module declares its fact type of a stage as a distinct type of the shape, with its own template, and writes it with the procedure of the shape (`module.load_find_fact_fields` and the others), in a switch on the stage:

```odin
@(log_fact = "host: the load of {module_name} ({module_hash}) found no file of its import {imported_name} ({imported_hash})")
Load_Find_Failed :: distinct module.Load_Find_Fields

switch error.stage {
case .Find:
	system.log_fact(.Warning, Load_Find_Failed(module.load_find_fact_fields(&error)))
case .Read:
	...
}
```

The sentence changes to the form of the fields: a module names each field once, and no condition chooses between a name and a hash. The two descriptions of Check are not in its fact: the fact says the difference and the number of the parameter, and the module files hold the descriptions; they would pass one record. The shapes are in the contract `module`, not in the support package `system`: a reader of the fields reads the types of the contract, and the tool reads a field of a shape through the imports of its own package.

### The record

**The size.** A log record has 256 bytes today (`#assert(size_of(Log_Record) == 256)` in `src/library/contract/operation/operation.odin`), 16 records in a page, and a text line of up to 168 bytes takes one record. A fact takes one record of the same 256 bytes, so it costs no more memory in the whole log, in an own log ring or in the budget of each second than a text line of one record. A text line longer than one record costs more records than the fact of the same line. The size stays 256 until a measure shows that a smaller record pays (measure 8).

The record keeps its head: the number, the time, the process slot, the process serial, the own number, the thread, the level, `more` and the name of the process, which the kernel sets. A byte of the head that is reserved today becomes the record form (`op.Log_Record_Form`, an enum with explicit values): `Text = 0` and `Fact = 1`. A zero record is a text record, as before.

The body after the head has 192 bytes. Today a record is a text record: the value runs, then 168 bytes of text, since the channel left. With the form byte:

| Form | Body |
|---|---|
| `Text` | The value runs (24 bytes), then the text (168 bytes). A long text continues in the next records (`more`). |
| `Fact` | The module hash (32 bytes), the fact key (8), the count of the value bytes of this record (2), the part (1), the count of the parts (1), 4 reserved bytes, then the values (144). A fact of more value bytes is several records in a row, each with `more` but the last ("A fact of several records"). |

Text records and fact records follow each other in the whole log and in each own log ring, with one number sequence. The records of each second of a budget count a fact as one record.

**The version rule.** The record changes in place. Each reader takes the byte of the form through one border, which refuses a byte that names no member: the reader shows "a record of an unknown form" with its head, and no body. The service `log` gives no row of `log.records` for such a record, nor for a record whose level byte names no member of `Log_Level`, and counts it in `lost`, as a torn record: the fields `form` and `level` of a row are enums, and an enum field never holds a word that names no member. Both bytes pass their borders at one place (`record_borders`). Such a record leaves the result too, which counts the rows of the scope, so a result of 0 is true. When the call gives no row at all, `lost` has no row to be in: the contract of `records` says that a reader with no row learns no count ([log_reader_scope.md](log_reader_scope.md), "A reader whose own records are all gone"), and this keeps that form. The gap record of `log.follow` is the form that will say a loss with no row (see "The frequent tasks"). A new form is a new member. The fact record itself has no version: its module hash pins its description.

**The module hash.** A module file cannot hold its own hash, and the kernel does not know which code of a process called `Log`. So the module file names an own-hash place in its writable data, and the loader writes the hash of the module there when it binds the module. `system.log_fact` copies those 32 bytes. The kernel writes the place of the root service when it starts it, because the root service has no loader for imports. A place of zero is no module: a reader shows the fact raw.

The place is a variable of the support package `system`, exported under the symbol `modus_own_hash`: an exported variable has bytes that the compiler cannot take as the zeros of the file, and the version script of the link keeps the symbol local to the module. The conversion finds the symbol in the symbol table of the linked file, checks that it is 32 bytes in a segment that the loader writes, and writes its offset as record 1 of the table `Own_Hash`. A module whose code never reads the place has no table: the link drops the variable. `validate` refuses a place that is not 32 bytes in one segment with Write and no Execute, so no file makes a loader write into its code. Each loader writes the place where it rebases and binds, for the range of the segments that it prepares (`module.own_hash_write`): the loader of `system`, the kernel for the root service, the loader of the tool on the host. The place took the version of the module format to 3: a loader of version 2 would leave it zero.

The refused forms of the place: a field of the header, which has 4 bytes free and needs 8, and makes each file pay for a place that most modules do not have; a table that the loader finds by the name of a symbol at the load, which puts a symbol table in each module file.

### The writer path and its cost

`system.log_fact(level, value)` builds the body on the stack: the module hash, the key, `size_of(value)` and the value bytes. It gives the body to the kernel with one `Log` operation of the form `Fact`. It formats nothing, and the call site holds a composite literal and one call. With the note of the refused lines and the count of a refusal, it never waits for the kernel log, as `system.log` ([log_side_channels.md](log_side_channels.md)). When the record output `log` is wired, it also writes that record output first, and waits there (see "The record output `log`").

The `Log` operation takes the form after the runs: `(log, address, length, level, runs, form)`. This changed from a form before the runs: in the last place, a zero form is `Text`, so each writer of text keeps its call of five values, and a call of five values cannot have its count of runs read as a form. The kernel converts the word to `Log_Record_Form` at its border, and refuses a word that names no member with `Bad_Operation`. For the form `Fact` it refuses runs with `Bad_Operation`, and a length below the head of a fact (48 bytes: the hash, the key, the count and the reserved bytes) or above the 192 bytes with `Bad_Address`. It copies the bytes into one record with no UTF-8 filter, because the body is not text, writes the count of the value bytes from the length and zeros the reserved bytes. It reads no other field of the body. The kernel interface keeps its count of operations. The kernel part of this is two procedures of `src/kernel/serial.odin` (`log_fact_operation`, `log_fact_record`), the border of the form in `Log`, the line of a fact in the serial writer, and the error records of the refusals.

The cost to measure, and the claim that the measures must prove (see "The measures that decide it"): one kernel entry dominates both paths. A fact saves the formatting in the process, the UTF-8 filter and the cut of the runs in the kernel, and the records of a text longer than one record.

`system.log` stays for a throwaway line and a debugging line, as text, with a level: `system.log(.Warning, "storage: the block ", block, " has a wrong check")`. The level is the first argument, as in `system.log_fact`, so one form names the level at each call.

### The record output `log`

**What it carries.** One record of the contract record `output.Log_Output_Record` for each record that the process gives the kernel log: the time of the system clock that the writer reads in its time page, the count of the bytes of the text, the level, the form, `more`, the count of the value runs, and the body. The body is the bytes of a log record from its value runs to its end, 192 bytes, as one field of the field kind `Log_Body`: the runs and the text of a text record, or the module hash, the fact key, the part and the values of one part of a fact. A reader takes it through the border of its form (`output.log_output_text`, `output.log_output_fact`), as each reader of the log does. The record has 208 bytes, so a fact part is one record and a long text is several records with `more`, cut where the kernel cuts them. It has no process slot, no process serial, no own number and no name: the reader knows the writer by the wiring that it holds, and the serial of each record of a record output numbers it. The record is in `Records` of no module file: the contract writes its description file (`output.log_output_file_write`), which the root service takes as the module file of the writer, so the type check of the wiring compares the description of the contract with the record input of the reader.

**One body, not a union.** A record description has no union, so the text and the fact cannot be two fields that share their bytes. Refused: the 256 bytes of a log record, whose name, slot and serials no writer of its own log fills and every reader would skip; and a text field beside a fact field, 360 bytes for each record of which one half is always zero. The field kind `Log_Body` says what the bytes are, and a reader with no border writes them as hexadecimal digits.

**Who can wire it, and when.** The starter of a process, in the wiring list of its `Start` command, and only there ([module_outputs.md](module_outputs.md), "The wiring list of a start"). The root service applies the whole list before the first instruction of the process, so the audit holds each record from the first one, after a joined record of 0. The authority is the check of the root service that the asker asked for the start of that process: no process handle with Control and no other grant ([module_outputs.md](module_outputs.md), "The wiring and its rights"). No wiring of `log` comes while the process runs.

**One reader.** `log` takes one wiring. The border of the list (`output.wiring_list_check`) refuses a second row that names `log` with `Bad_Value` on the field `Writer_Stream`, and the whole list with it. It refuses too a row of `log` whose writer is not the child of the Start, which names the log of a process that the asker does not start, and a row of `log` with a writer index. A second reader of the same log reads it from the first one, as the collector forwards ([module_outputs.md](module_outputs.md), "The record output `log`").

**No condition, and a pace that holds.** The root service refuses a row of `log` with a condition, and a row with the pace `Never_Holds_Writer`, with `Unsupported` on the field that names it. A condition needs a page for the writer, so a third place in the context; the reader of `log` is an audit, which keeps each record, and a reader that wants a part filters what it read. The writer of `log` waits for room whatever the row says: `Writer_Chooses` and `Always_Holds_Writer` both describe it, and `Never_Holds_Writer` would say a pace that no writer of `log` keeps.

**Not the log of a service.** The root service refuses a row of `log` whose child has a role that exports a service (the grant `Serve`), with `No_Right`, before the child exists. The reader holds the writer, and the starter takes that cost for its child: a held service would make each of its callers wait for the reader of the starter too, and they did not choose it.

The wiring gives the starter no new fact: a starter already reads the records of its child by lending the process handle to `log.process_records` ([log_reader_scope.md](log_reader_scope.md)). The difference is the guarantee, not the scope. The records that another process writes about this one (the line of the root service at its start, the report of the kernel at a fault) are not its own records, and are not in its `log`.

**The writer path when `log` is wired.** `system.log`, `system.log_fact` and `system.log_text` meet in one call of the library, which writes each record twice, in this order:

1. To the kernel log, with `Log`, as before. The call never waits. A refusal of the budget of each second drops the line in the kernel log only. The note that says how many lines the budget refused is a record about the kernel log, so it goes to the kernel log only.
2. To the record output `log`, when the kernel took the call or refused it for its budget alone, with no deadline: the writer waits while the ring of its reader is full. No record is lost, so a reader that does not read stops the writer. A thread with a deadline (a frame loop, the path of a key) waits too: the starter that wires `log` takes that cost for the child. The library builds the records of a text from the bytes that it gave `Log`, after the same filter of the UTF-8 and with the same cut and the same value runs as the kernel, and the parts of a fact as the kernel cuts them.

The kernel first, because its border is the one border of a log call: a call that it refuses for another cause (a level or a form that names no member, a size past its bound, a fact that its module does not describe) is no log record, and the ring never holds it. The first design wrote the ring first, and so kept such a call in the ring. One check of the kernel comes after its budget: the value runs of a text; a text with bad runs that the budget refuses reaches the ring. The library builds every run itself, inside its text, so no call of the library gives one.

**The end of `log` is not an end of the table of the stream ends.** Every thread of a process writes its log, and that table serves one thread at a time. The end of `log` has its own state and its own lock, which a thread holds for the records of one call, so the parts of a long text and of a fact of several parts stay in a row in the ring. A second thread that logs meanwhile waits for the lock. Refused: the table of the stream ends with a lock, which would make each write of each record output pay for the log.

When the reader stops or closes its end, its end word ends the wait, the library removes the ring, and the process goes on with the kernel log only. The same holds when the reader refuses a compartment, or writes a count of its reads that no honest reader writes. The reader knows the serial of the last record that it read, so the end of the audit is known, not silent. When the writer stops, the reader gets the end word `Writer_Stopped` with its stop cause and its stop outcome ([../api/process_stop.md](../api/process_stop.md)).

**How the end reaches the process: two handle slots of the context.** The context of a process has two handle slots for the end of `log`, beside the wiring ring (`docs/MODULE_CONTRACT.md`, "6. The context"): the handle 17 (`op.CONTEXT_LOG_OUTPUT`) holds the output ring, with Read and Write, and the handle 18 (`op.CONTEXT_LOG_OUTPUT_END`) holds the end page, with Read only. The root service gives both before the first instruction (`system.Start_Wiring`, `log_ring` and `log_end_words`), only when the wiring list of the start wires `log`, and never one without the other: a ring with no end page would hold a writer that never learns that its reader ended. `system.process_start` refuses a grant of a starter at either slot, as at the slot of the wiring ring. The library maps both at the first write of the log. The end of `log` never goes through the wiring ring, so a process whose only wiring is `log` gets no wiring ring. The design first named one slot: the end words of each wiring live in their own page, which the root service alone writes, so the end of `log` needs that second handle as each other end does.

**A process with no wiring pays one load.** Its slot 17 holds 0. Each write of its log reads that one word of the context page, which the log path already reads for the log handle (slot 14, in the line of 64 bytes before it), and goes on to `Log`, as before: no ring, no page, no lock, no wiring ring. Measure 9 of [module_outputs.md](module_outputs.md) prints the cost of a log call with and without the wiring.

### The serial port

The serial writer writes the line of a fact record from its bytes, with no template: `[storage] #1a2b3c4d:fa0adf 0cm1a23h1a2b`, for `block = 12`, `check = 0x231a` and `expected = 0x2b1a`. After `#` comes the module tag, the first 4 bytes of the module hash; after `:` the key tag, the first 3 bytes of the fact key, from its high byte; then the value bytes in the order of memory (an integer is little-endian), up to their last byte that is not zero. A value byte that is not zero is two hexadecimal digits. A run of zero bytes is one letter: `g` for one byte up to `z` for 20, and a longer run is `z` until the rest fits one letter. `m` above is the 7 zero bytes of the block 12 in a field of 8 bytes, `h` the 2 high zero bytes of the check. It is a filter of bytes, as the line of a text record is (`op.log_fact_line`): the kernel reads no field, and writes no byte of the writer as text.

The tool renders the line on the host: it holds each module file that it built, finds the module by its module tag, the fact type by its key tag, and writes the fact template with the values. The tool refuses a build where two module files share their module tag, and a module where two fact types share their key tag.

**Why this form: the measure.** The first form wrote the first 8 bytes of the hash, the whole key and each value byte as two digits. Measure 4 showed it took about 1.9 times the bytes of the same lines as text. Each form below was counted on the lines of three logs of one full check, the head `[name] ` and the end of each line included, as measure 4 counts them; the last column is the 1686 lines of facts of every log of that check.

| Form of the line | `quic`, 18 lines | `tcp`, 21 lines | `remote_display`, 22 lines | Every log |
|---|---|---|---|---|
| The same lines as text | 827 | 1017 | 1051 | |
| Hash 8 bytes, key 8 bytes, hexadecimal (the first form) | 1574 | 1930 | 2014 | 155 820 |
| Hash 8, key 8, base64 | 1319 | 1601 | 1672 | 129 134 |
| Hash 8, key 8, base85 | 1289 | 1562 | 1631 | 125 937 |
| Hash 8, key 8, runs of zeros as letters | 1128 | 1332 | 1429 | 110 061 |
| Hash 4, key 2, hexadecimal | 1214 | 1510 | 1574 | 122 100 |
| Hash 4, key 2, base64 | 959 | 1181 | 1232 | 95 414 |
| Hash 4, key 4, runs of zeros as letters | 840 | 996 | 1077 | 83 085 |
| **Hash 4, key 3, runs of zeros as letters (chosen)** | **804** | **954** | **1033** | **79 713** |
| Hash 4, key 2, runs of zeros as letters | 768 | 912 | 989 | 76 341 |

The tags were 34 of the bytes of each line: the larger part of the cost. The rest is zeros: most values are small integers in fields of 8 bytes, and a Text field holds a short name in 32 or more bytes. The cut of the last zeros removed the zeros of the last Text field only, not those between two fields. So:

- **The runs of zeros, not base64 or base85.** Base64 writes 4 bytes for 3, zeros or not, and needs a decoder in each reader. A run is one byte for up to 20 zero bytes, and a byte that is not zero stays two digits that a person reads: `0c` is 12. The letters `g` to `z` are no hexadecimal digit, so no line has two readings.
- **A tag of 4 bytes for the module.** It names one module among the module files of a build, about 106: two of them share a tag about once in 770 000 builds, and the tool refuses that build. 8 bytes made the clash impossible in practice at 8 more bytes on each line.
- **A tag of 3 bytes for the key.** It names one fact type inside one module: the root service has 31. Two of them share a tag about once in 36 000 such modules, and the tool refuses that module; its writer renames a type. No two of the 145 fact types of the system share their first 3 bytes. A tag of 2 bytes saves 2 bytes on a line and makes the clash about once in 140 modules of 31 types: the cost of a rename is not worth it. A tag of 4 bytes passes the bytes of the text on `tcp` and `remote_display`.
- **A varint of each field, refused.** The kernel reads no field: it has no description, and the constraint of a filter of bytes holds. The writer cannot encode either: the record keeps the values whole for each reader of `log.fact_records`.

The chosen form writes fewer bytes than the text on each of the three logs: 0.97, 0.94 and 0.98 times. Measure 4 prints both forms after each machine.

**One line, one fact.** The reader of the tool refuses each text that the kernel never writes: a zero byte as two digits, a run that ends the values, a letter after a letter that is not `z`, a space with no value after it. So a line has one reading, and a reading has one line. Each step of a machine test reads the rendered line, and the raw line when no module file has that hash. The machine keeps the rendered log and the length of the file that it covers, and each read of the log renders only the whole lines after it: the same lines give the same text, so a place in the log is the same place in each read. A Text value takes the filter of the kernel for a text in the render, because the kernel filters no byte of a fact. The file of the machine log, which QEMU writes, keeps the raw lines; a copy of it with the rendered lines is left. A person who reads the serial port with no tool reads the raw form.

### The reader path

A reader copies a record, then reads its form through the border. For a fact record:

1. It checks that the count of the value bytes of the record is at most 144, and joins the records of a fact of several records ("A fact of several records").
2. It finds the module file by its hash in its catalog: the boot image that it was granted, and the store `module_files` through the module file service. It keeps the last modules that it found, so a log of one writer costs one search.
3. It reads the table `Facts` through the information functions, which check the table as they check each table of a module file. A module file is hostile input: a template that breaks a rule gives the raw form, not a fault.
4. It finds the row by the fact key, with a search in the sorted table.
5. It checks that the count of the value bytes is the size of the record description, or for a record with text views at least the size and at most the size and the out-of-line area, and that each view reads, else it shows the raw form.
6. It writes the template, each field in the color of its value kind. A Text field is copied, then checked as UTF-8, and a bad sequence is the replacement character.

**The raw form.** With no module file, the reader has no field name: the names are in the module file only. It shows the line of the serial port: the fact name as `#1a2b3c4d:fa0adf`, the module tag and the key tag, and the value bytes in hexadecimal with each run of zero bytes as a letter. The proposal said that a reader with no module file shows the field names; that cannot hold, because the record carries no name.

**One render.** Steps 3 to 6 are one pure procedure of the contract, `module.fact_sentence_write`: the file, the key and the value bytes in, the sentence and one value run for each value out, or a refusal (no fact type of the key, a count of the value bytes that is not the size of the record, a template that breaks a rule, a sentence longer than the buffer of the reader). It copies the values before it filters a Text field, so the bytes of the caller do not change. The console, the window `log` and the tool call it, so two readers never write two sentences for one fact. The tool wrote its own loop before; it had no unit after a Size or a Time.

**The catalog of each reader.** The console reads the boot image that it holds. The window `log` gets the grant `image`, the boot image read-only: the catalog is a grant of its own, and the image holds no secret of a process. A disk process names a module of the store `module_files`, which neither reader reaches yet: its facts show raw. The console checks each module file of the image that has a fact table once, at its start, when it reads the fact names, and keeps those files: the fact names, `facts` and the render read only files that the checks took, and a refused file gives no name. The window keeps the last 8 modules that it found and the last 8 hashes that no module of the image has, so a log of one writer costs one search of the image, and a fact of a disk process too. A reader does not hash a module file again: the boot program hashed each file of the image against the signed system description before the kernel ran (`system_description.image_check`, which `trust_check` of the boot program calls), and the image is granted read-only.

**The window and the service share one thread.** The process `log` is the window and the service: one thread takes each new record, draws, and serves `records`. It now checks a module file (`module.validate`) and writes the sentence of a fact when it takes the record, never in a frame: a frame copies the sentence that `take` kept with its row. This is accepted because the checks run once for each module and each hash with no module, which the two caches keep, and a fact costs one render. A call of `records` waits at most for the checks of the modules that the new records name for the first time. If a measure shows that a check holds a call too long, the check moves to a second thread.

**The rows of the log service.** A row of `log.records(after)` keeps its text for a text record, and `log.value_runs` stays for text records. The row gives the level as a status of the contract enum `Log_Level`, and the record form as a status of the contract enum `Log_Record_Form`: a reader knows a fact from its row, and `where(level = Warning)` compares a member, not a text. The text of a fact row is empty. A row of `records` has 256 bytes, the limit of a record description, so the fields of a fact come in a second table joined on `number`, as the value runs do: `log.fact_records(after)` gives, for each fact of the log scope, the record form, `more`, the fact key, the module hash, the count of the value bytes, the reserved bytes and the 144 value bytes. The values are one Bytes field of the field kind `Fact_Values`: the bytes of the record of the fact type that the hash and the key of the same row name, which a reader with no description writes in hexadecimal, as the raw form. A Bytes field was a hash only ([console_value_colors.md](console_value_colors.md)): a field of any content stays refused, and this kind names its content. The first form gave the first 8 value bytes only, and no reader could render. The log service renders nothing: it holds no catalog, and a rendered text loses the fields that a reader filters on.

**The readers that render.** The console writes the sentence of each fact in the records of a line, each value in the color of its kind; it asks `log.fact_records` for the facts of an answer of `records` that holds a row of the form `Fact`. The window `log` reads the records from the memory of the log, with the values whole, and draws the sentence in the place of the text. The service `remote` reads no log record: the tool reads the rows of the log through it, and renders on the host with its own catalog of the build.

### The log channel left

The channel of a log record was the name of 16 bytes that the writer gave at each call (`system.log_in`). A typo made a new stream, any process wrote any name, and most texts already repeated it ("kernel: boot: ..."). The fact type and its module group the records better: a reader chooses its rows by fact type, by process and by level. So the channel left the record, the `Log` operation, `system.log_in`, the serial line (`[name] text`) and each reader, in the first step of the migration, before any fact type exists. No grouping replaces it for `system.log`: a line that a reader groups is worth a fact type. A free name that any writer types is the form that this design removes, by any word.

The glossary entry "Channel" (`docs/glossary/running_code.md`) left with the field, and "Log record" says that a record carries no name that its writer chooses. The word has no meaning in the system: the glossary entry "Ring" lists it under "Do not use", "Log record" lists "log channel", and a record output does not take it.

**One writer of text, with its level.** `system.log(level, ...)` is the one writer of a text line of a process: no second procedure without a level, so each call says its level. The kernel keeps its own two writers, `log` at the level Info and `log_with_level`: they are kernel code, not the library, and most lines of the kernel are of the level Info.

### Filters of a reader: one form

The console filters log rows with its one command `where` on a column, and gets the columns of a fact type with `facts`. No name of a fact type, of a field or of a level is a free string:

```
> log.records(0) |> facts(storage.Bad_Block) |> where(block = 12)
> log.records(0) |> where(level = Warning) |> where(process = "storage")
```

- **The fact type is a typed name.** `storage.Bad_Block` is a name of the command line, as `server.requests` is ([module_outputs.md](module_outputs.md), "The console form"). The console completes it from the fact tables of the module files of its catalog: each pair of a package name and a record type that a fact table holds. It refuses, before the call, a name that no fact table holds, with the sentence of a name that names nothing and the close names that it has. `facts` keeps the rows of that fact type and gives a table: the columns of the head of a row (number, time, process, level), then the fields of `Bad_Block`. The console resolves the name to the pairs of a module hash and a fact key, and builds the description of the table from the record description.
- **Each field is checked.** Inside `where`, a name is a field of the record of the table, never a variable. The console checks each field against the description of the table that comes in: after `facts(storage.Bad_Block)` the fields are the head and `block`, `check`, `expected`. A name that is not a field, and a value of another kind than its field, are refused before the call, with the fields that the table has. Completion offers those fields.
- **The level is an enum.** The column `level` is a field of the contract enum `Log_Level`, with the kind of a status of a contract enum. The console completes its members, `Info`, `Debug`, `Warning` and `Error`, and refuses a word that names no member. It takes `=` and `!=` only: the order of the numbers of the members is not an order of weight (Debug is 1, Warning is 2), so `>=` on it has no meaning, and the console refuses it.
- **The process is a value.** `process = "storage"` compares the Text field of the name of a process. A process name is a value of the row, not a name that the console resolves: no process has an identity by its name ([log_reader_scope.md](log_reader_scope.md), "Refused forms").

So `where` stays a command of every table, and only `facts` knows the log. The operator `|>` and the comparison form of `where` are those of [module_outputs.md](module_outputs.md), "The console form". The comparison form came with the readers of the facts, and the old form `where(t, "block", 12)` left in the same change, for every table: the console keeps one form.

**How the console reads a condition.** The argument of `where` after the table is a condition: a field name, an operator (`=`, `!=`, `<`, `<=`, `>`, `>=`) and a value. The parser reads it as a condition, never as an expression, so a field name is not a variable. A Status field takes the name of a member of its contract enum, and the console turns it into its number at that one place; a word that names no member is refused with the members. An Integer field takes an Integer and each operator. A Text field takes a Text, and a Status field a member, with `=` and `!=` only. A Bytes field (a hash, the values of a fact) has no value that the console compares, and is refused. An unsigned field takes no negative value, and a field takes no value past its bytes; an unsigned field compares as unsigned, so `key > 0` keeps a key of 2^63. A text or a number after the operator of a status is refused: a member is a name. When the console knows the record of the table on the left before the run (a stage `facts(...)`, or the result of an export), it checks the condition before any call: the field, the operator, the member of a status, and the kind and the range of a value that is one literal; a value that is another expression is checked when it runs. Else the whole condition is checked when `where` runs, before it reads a row. The reading, the checks, the comparison of the values and the sentences are one private package with host tests, `console_condition`; the parser of Lex reads the head and the value of the condition, and the console evaluates the value of a field that is no status ([declarations.md](declarations.md), "The parser package").

**What `facts` does.** `facts(table, storage.Bad_Block)` takes a table of the rows of `log.records` (it checks the fields `number`, `time`, `process`, `level` and `form`). It finds each module of its catalog whose table `Facts` has a row of the package `storage` and the record `Bad_Block`. The description of the first one is the description of the table. It reads `log.fact_records` from the least number of the table, and keeps each row of the form `Fact` whose fact key and module hash are of one of those modules and whose description is equal. The rows of another description are left out. Each row of the result is the number, the time, the process and the level of the log row, then the values of the fact, in the order of its fields.

**The typed name.** The argument of `facts` after the table is a fact name, which the parser reads as a name with one dot, never as an expression. The console refuses, before any call, a name that no fact table of its catalog holds, with the fact names whose package is the same, or every fact name when none is. The completion offers the fact names inside `facts(`, and the fields of the record on the left inside `where(` when the console knows it.

### Which reader sees which fields

The log scope does not change. A reader receives whole records of its scope: the whole log for a caller that acts for the principal, else its own records and the records of a process whose handle it lends ([log_reader_scope.md](log_reader_scope.md)). A fact record holds no value that the text of that record did not hold: the writer chose each value, as it chose each byte of its text. The module hash names a module that the writer chose to name. A reader of a lent child learns the hash of a library that the child loaded only if the child writes it.

**A fact type is no border.** The pair of the module hash and the fact key is a claim of the writer, as the channel was: the kernel reads no field of the body, so any process can write any hash and any key. The process slot and the process serial, which the kernel sets, name the writer; the fact type names a description. So a grant "every record of the fact type `storage.Bad_Block`" is the grant "every record of the channel `devices`" again, which [log_reader_scope.md](log_reader_scope.md) refuses: it shows the reader each process that writes that type. That refusal holds for a fact type, by the same reason. A check by the kernel against the module records of the writer changes nothing: a module record is what the loader of the process asserts (`docs/glossary/code.md`, "Module record").

A reader that renders needs the module file in its catalog. The catalog is a grant of its own (`docs/glossary/code.md`, "Catalog"), and the template is in a file that the reader holds: rendering gives it nothing past its scope.

### The machine tests

- **A wait on the serial port keeps its text.** The tool renders a fact before it matches, and a fact template that writes the sentence of today keeps each wait as it is.
- **A wait for a fact.** The step `Fact` names the fact type as a text (`fact = "storage.Bad_Block"`), the process, and one condition on a field (`condition = "block = 12"`). The tool cannot name the record type of a module in its own code: it does not compile the module packages. So the name is a text that the check before the run reads, as the console reads its typed name. A step has one condition: a second condition is a second step, or the field `condition` grows into a list when a test needs it.
- **One reader of a condition.** The condition has the form of the condition of `where`, and the tool reads and checks it with the package of the console, `console_condition`: the field, the operator, the member of a status, the kind and the range of the value, with the same sentences. A second parser of the same form in the tool is the refused form: two readers would drift.
- **The step reads the raw line.** The render keeps, for each line of a fact that it rendered, its place in the rendered log, the name of its head and the bytes of the line (`build.Fact_Line_Place`). The step matches the process, the module tag and the key tag of the fact type in a module of the build, and the values against the condition, from the place of the last `Wait`. It reads no sentence, so two fact types with the same sentence are two facts for it. The serial port can lose a line in a flood, as for a `Wait`: the step reads what the serial port got. A test that must not lose the fact reads it through `log.fact_records`.
- **The check before the run.** The tool reads each step `Fact` of a scenario against the fact tables of the module files of the build before the machine of the scenario starts, beside the check of the key of `remote`, and stops with one line for each fault. A step with no process, a fact name that no module has, a field that its fact type lacks, an operator that the field does not take, and a value of another kind than its field fail there. A changed sentence of a `Wait` still fails at the end of a bound, in the machine. The check runs for each machine, not once for the whole test: the scenarios of some parts are built at the run (`measure_process_steps`), so no list holds every scenario before the run.
- **A step `Record` reads a fact by its sentence.** The step reads `log.records` through `remote`, and the row of a fact has no text. So when a row of its read has the form `Fact`, the tool reads `log.fact_records` from the same number and writes the sentence of each fact with the template of the module file of the build, with `module.fact_sentence_write`, as for a line of the serial port. A step `Record` on a line that became a fact passes unchanged, and keeps its place in the order of the whole log. The tool finds the module by the whole hash of the row, not by its module tag. A fact past the last record that the answer of `fact_records` reached is read again from its number, as a text that goes on; a fact that the answer reached and whose module the build does not hold has no sentence. A row of `fact_records` is not larger than a row of `records`, which an `#assert` of the log service holds, so one answer of each from one number covers the same facts. The refused form: each such step turned into a step `Fact`, which reads the serial port and loses the check of the order of `log.records`.
- **Each reader of the log of the tool reads the rendered lines.** QEMU writes the raw line of a fact, so each reader of a log file by its text renders the lines of facts first, with the module files of the build: the steps of a scenario (`log_read`), a check after a run (`log_file_rendered`), the measure record (`measure_log_rendered`), `quality_lines_check`, and the fuzzer of the kernel operations, which keeps one catalog for its run and counts its place in the file in raw bytes, since a rendered line has another length than its raw line. A line becomes a fact with no change of the reader that reads its sentence.
- **The measures.** A measure that the tool reads from the log ([measure_history.md](measure_history.md)) keeps its sentence as its identity, because the template renders the same sentence. Once its writer writes a fact, the tool reads its numbers from the fields, with no parse of digits. No line that the root service, the compositor, the storage service, the device services, the network service, `remote` or `remote_display` converted is a measured line (the measured lines of the disk are those of the demonstration `disk`, which stay text; the line of the budget of the root service at "the machine is usable" stays text, and so do the measures of the compositor, of the network service, of the sound service, of `remote` and of `remote_display`: see "The facts of the compositor and of the windows" and "The facts of the device services and of the network"), so the measure record reads text; the first writer of a measured line changes its measure in the same commit.
- **The value runs of the main test.** The check `log.value_runs({record})` of the record "log: the memory of the log" ([log_window_losses.md](log_window_losses.md)) becomes a check of the kinds of the fields of its fact.
- **A fact through the console.** The main test reads the fact of `log_reader` with `log.records({record}) |> facts(log_reader.Fact_Probe) |> where(value = 42)`, from the last record of the storm of `log_reader`: the rows of `log.records(0)` of a full log do not fit in the call region of the console. A field of a fact type with the name of a column of the head of `facts` (`number`, `time`, `process`, `level`) is refused by `facts`, so `Fact_Probe` names its third field `probe_number`.

- **The template is the sentence of today, word for word.** So each wait of a machine test passes unchanged. This costs a reader several fact types for one event: `facts(root.Process_Stopped)` gives the stops of a process by itself, and `facts(root.Process_Stopped_Without_Outcome)` the others.
- **The stop keeps its two facts apart.** `Process_Stopped` holds the cause, always `Itself`, beside the outcome, so `where(cause = Itself)` and `where(outcome = Done)` both read it, as [../api/process_stop.md](../api/process_stop.md) names them. The words of the sentence are the words of a reader (`itself, done`), not the names of the members.
- **The name of a grant is a Text field.** `Root_Grant` is an enum of a support package: a field of it is a plain Integer, which writes a number where the sentence writes a name (open question 4). The Text field `grant` holds the name that `root_grant_names` gives, and `where(grant = "store")` reads it.
- **The head of a client key is a Text field.** `key_head_text` writes the first 8 bytes of the key as 16 hexadecimal digits, and the field `client_key` holds those digits. The field has 24 bytes, not 17: the `u64` after it then starts on 8 bytes, and the record has no padding, which the compiler and the tool refuse.
- **Each start and each stop is a fact**, so `facts()` answers "which processes started" and "which processes stopped": the starts of a test with their budget, the chosen start policy, and the run of `unlock` with no window, whose sentence stays apart from the stop of the `unlock` of the start list. The stop of the start policy is a fact of the stop as for each process; the three lines that follow it say what the root service does then.
- **A line stays text** when its sentence holds a part that no field kind writes as the line does:
  - a refusal with a free sentence of its cause ("cannot start X: <the cause>", "refused X from the disk: <the cause>");
  - a status that the line writes as a number, which a status field writes by its name ("cannot start X: status 5");
  - "root: started tpm for the TPM at <address>": `system.Hex` writes 16 hexadecimal digits with no "0x" (`src/library/support/sentence/writer.odin`, `write_part`), and a hexadecimal field writes "0x" before its digits;
  - the three lines of the start policy after its stop ("the start policy <hash>… stopped before the machine was usable: ...", "the rescue start policy <hash>… stopped ...", "... stopped: ..., after the machine was usable"): the hash is its first 4 bytes in 8 digits, then "…" (`start_policy_hash_text`), which no field kind wrote at this step. The field kind `Hash_Head` of step 10 writes it: 6 fact types, with the cause and the outcome. They also follow the fact of the stop itself, so a reader of the stops does not need them.

  A line stays text also when no reader groups it: the lines of the trust, the entropy at the start, the principals, the start policy and the disk grant table, each written once or a few times in a run. The entropy lines that say a refused read are facts: see "The facts of the device services and of the network".

### The facts of the compositor and of the windows

The compositor and the package `interface` are the second writers that convert: the lines of the windows and the element lines are the lines that a reader groups by window, and that the tool reads to press an element. The fact types of the compositor are in `src/modules/system/compositor/facts.odin`; those of a window are in `src/library/support/interface/element_places.odin`, beside their writer.

| Line | Fact types | Fields |
|---|---|---|
| A surface made, the first one or the one after a resize | `compositor.Surface_Made` | `window`, `width`, `height`, `x`, `y` |
| A window shown, its first picture on the screen | `compositor.Window_Shown` | `window` |
| A window in front, by the menu of the windows or the palette | `compositor.Window_In_Front` | `window` |
| A window closed with a count of what it lost or what was refused | `compositor.Window_Closed_After_Refused_Commands`, `compositor.Window_Closed_After_Refused_Clipboard_Records`, `compositor.Window_Closed_With_Lost_Events` | `window`, and the counts |
| A window that does not read its events, and reads them again | `compositor.Window_Events_Lost`, `compositor.Window_Events_Read_Again` | `window`, and the counts |
| A refused word: of a window, of the control ring, of the input ring; a control command that only goes the other way; a pointer shape that names no shape | `compositor.Window_Word_Refused`, `compositor.Control_Word_Refused`, `compositor.Control_Command_Not_Taken`, `compositor.Input_Word_Refused`, `compositor.Pointer_Shape_Refused` | `word`, or `window` and `shape` |
| An element line of a window | `interface.Element_Placed`, `interface.Element_Gone` | `window`, `element`, `x`, `y`, `width`, `height` |
| An element line of the palette | `compositor.Palette_Element_Placed`, `compositor.Palette_Element_Gone` | `element`, `x`, `y`, `width`, `height` |

The rules that decided each line, past those of the root service:

- **The title of a window has two sizes.** The compositor holds a title as a `system.Name`, 31 bytes and a zero byte, so its field is a `Module_Name_Field`. The window layer holds the title that its process gave, up to 32 bytes (`display.Window.title`), so the field `window` of an element line has 40 bytes, as the field `element` for a name of up to 32 bytes: the zero byte, and a record that ends on 8 bytes with no padding. The tool reads the length of a Text field as a literal, so the record writes `[40]u8`, and an `#assert` ties it to `ELEMENT_FACT_TEXT_BYTES`.
- **A Text field comes last.** The serial line of a fact stops at the last value byte that is not zero. With the Integer fields first and the name last, the zeros after a short name cost no byte of the serial port: an element line is many lines in a run, and a flood of the serial port loses lines that a step reads. The order of the fields is free, because a template names its fields by name.
- **The palette has its own fact types.** Its sentence names the owner "the palette" where a window line names a title, and a template has no condition. So the compositor writes `Palette_Element_Placed` with no field `window`, with the procedures of `interface` that compare a set (`element_place_changed`, `element_places_find`, `element_places_keep`). Each fact type lives in the package of its writer, and the process of the line of the palette is `compositor`: the tool reads a line of the palette from that process only.
- **Each module that writes an element line has the fact table.** The writer is `element_places_publish`, which the window layer calls after each frame that it draws, in the process of the window. A module that compiles `interface` and draws no window (the compositor, the library modules `drawing` and `interface_module`) does not reach it, and its table has no row of it ("The fact table of the module file"). A process that draws its window through the library modules writes the facts with its own hash, because the window layer runs in its own code.
- **A refused word keeps its number.** The word of a ring is any `u32` that another party wrote: the field is an Integer, as the line wrote it, and the condition `word = 7` reads it.
- **The tool reads the element lines from their fields** (`tools/modustool/build/element_facts.odin`): the fields `window` and `element` equal to the step, then `x`, `y`, `width` and `height`. It never parses the sentence.
- **A line stays text** when its sentence holds a part that no field kind writes as the line does, or that a reader does not group:
  - the measures of the standard of quality ("the time of a frame ...: least 812.4 us, median ...", "the time of a key to the screen ...", "the start of the window ...: 2104.7 us"): a time with one decimal, which no field kind writes; two Integer fields, the whole and the tenth, would write the sentence, but a condition on one half of a time is no measure. The measure record and `quality_lines_check` read them as text;
  - the other measures of the compositor (a full frame, the move of a window, the title bar, the pointer, the bar): each written once or a few times in a run, read by the measure record as its sentence;
  - a refusal with a free sentence of its cause: the capture face ("refused a command of the capture face: <the cause>"), the pointer theme, the table of the palette provider, a resize with limits that a window cannot have;
  - the lines of the palette, the clipboard, the bar and the settings: each says a step of an act that a scenario waits for by its words, and no reader groups them by a field;
  - the place of a press ("a press of the left button at x,y") and the move of a window ("window X moved to x,y"): the tool reads them as text with the line of `Surface_Made`; a reader of fields for the place of a window is left (see "State");
  - the lines of the window layer past the element lines (a frame in an appearance, the focus, a refused draw of the drawing module): each written once, or with a free cause.

### The facts of the storage service and of the disk

The storage service and the block service are the third writers that convert: the lines of the disk, of the commits, of the open of the disk, of the stores and of the erase are the lines that a reader groups by store or by object, and filters on a fault of the disk. The fact types are in `src/modules/system/storage/facts.odin` and `src/modules/system/block/facts.odin`. The package of the storage service is `storage_service`, and the package of the block service is `block_service`, so their fact names are `storage_service.Disk_Silent` and `block_service.Device_Silent`.

| Line | Fact types | Fields |
|---|---|---|
| The disk does not answer | `storage_service.Disk_Silent` | `cause` |
| The block service stops on a fault of the device | `block_service.Device_Silent`, `block_service.Device_Needs_Reset` | `bound`, `in_flight` |
| The read back of a commit: blocks or the root that the disk did not keep, a read that failed | `Commit_Block_Dropped`, `Commit_Blocks_Dropped`, `Commit_Read_Back_Failed`, `Commit_Root_Dropped` | `generation`, `blocks`, `generation_before` |
| A root that can be on the disk or not, and a place of the root that drops each write | `Root_Write_Failed`, `Root_Read_Back_Failed`, `Root_Place_Drops_Writes` | `generation`, `commits` |
| A check that fails in a commit | `Tree_Node_Damaged`, `Commit_Count_Below_Zero`, `Versions_Dropped_At_Commit` | `store`, `generation`, `dropped` |
| The open: a new disk, a cut root, damaged blocks and versions, counts that differ, the open done, trees to free | `New_Disk_Formatted`, `Cut_Root_Skipped`, `Blocks_Damaged`, `Versions_Damaged`, `Store_Counts_Differ`, `Disk_Opened`, `Trees_Wait_To_Be_Freed` | the counts of the open, `in_use` in blocks, `elapsed` in milliseconds |
| A share made or ended | `Share_Made`, `Read_Only_Share_Made`, `Share_Ended` | `share`, `store` |
| A store at its limit | `Store_At_Limit_Thinned_One_Version`, `Store_At_Limit_Thinned_Versions` | `store`, `limit`, `generation`, `thinned` |
| The erase of the versions of an object | `Versions_Erased_One_Version`, `Versions_Erased`, `Erase_Damaged_Left` | `store`, `object`, and the counts |
| The removal of a tree that stops | `Tree_Removal_No_First_Tree`, `Tree_Removal_Step_Refused`, `Tree_Removal_Commit_Failed` | `store` |
| The commit of the range writes of an object | `Ranges_Committed` | `object`, the counts, `held` in blocks, `elapsed` in milliseconds |

The rules that decided each line, past those of the root service and of the compositor:

- **A name is the last field, and holds the longest name.** A store name has at most 32 bytes and an object name at most 64: the fields `store` and `object` have 40 and 72 bytes, the name, a zero byte, and a record that ends on 8 bytes. A fact with both names puts `object` last.
- **A closed set of causes in the code, and one fact type for each sentence.** The stop of the removal of a tree and the failure of a root had their cause as a free text at the call; they take an enum of the module now (`Removal_Stop`, `Root_Failure`), and each member writes its own fact type.
- **The cause of a silent disk is a Text field.** `Disk_Silence` is an enum of the module, whose members a field cannot name (see "Open questions", the fields of an enum of a module), and the sentence of one of its members holds the bound of the wait. One fact type keeps the one event, so `facts(storage_service.Disk_Silent)` gives each silence; the field holds the words of the cause, as the field `grant` of the root service holds the name of a grant.
- **No line names one bad block.** The open counts the blocks with a wrong check and writes one line with the counts: `storage_service.Blocks_Damaged`. The fact type `storage.Bad_Block` of this design is an example: a fact for each wrong block, with its number and its two checks, is a new line, and a flood of the serial port when a disk has many; it waits for a reader that needs the number of a block.
- **A check of the tool after the run reads the rendered log.** The file that QEMU writes keeps the raw lines. A check that counts lines in it after the machine, as the silent disk and the erase with a dropped zero do, reads the text of the file with the line of each fact rendered by the module files of the build (`log_file_rendered`).
- **A line stays text** when no field kind and no template writes it as the line does, or when no reader groups it:
  - a line with no value: the refusals of the start of the service ("storage: no service ring", "no block ring", "no data region", ...), "no valid root on the disk", the first root that a stop cut, the newest root that the open refuses. At this step a fact type needed a field; step 10 takes a fact type with none;
  - a sentence longer than the 256 bytes that a template had at this step (512 since step 10): the fault of the engine that the open finds (287 bytes), and the four faults of the erase of versions at the second root and at the zeros (273 to 361 bytes);
  - a refusal with a free sentence of its cause: "storage: the block service refused a request: <the sentence of the error record>", and the stop of the block service at its start ("block: <the cause>");
  - the line of the block service at its start, "block: ok, ...": written once, and no reader groups it;
  - each line of the demonstration `disk`: its cases end with "as it must" or "WRONG", which a scenario waits for by its words, and its measured lines are read as text by the measure record.

The fact types are in a file `facts.odin` of each module: `src/modules/system/{remote,remote_display,network,frame,entropy,input,sound,tpm}/facts.odin`. The entropy lines of the root service that say a refused read are in `src/modules/system/root/facts.odin`.

A field of the kind Hash holds a hash of a module, and its color says so: a key of Ed25519 is not one.
- **One field name is one concept, in each module of the group.** A name never holds two sizes or two meanings, so a condition `where(name = …)` means one thing in each fact type: `bound` is a bound of time in milliseconds in each module; a port is `listen_port`, `local_port` or `remote_port`; a count says what it counts (`bytes_received`, `datagrams_received`).
- **The address of a host is a Text field.** `address_text` writes "10.0.2.2 port 7100", and no field kind writes an address. The field `peer` has 32 bytes: the longest address and port have 26.
- **A cause from a closed set of sentences is a Text field.** The cause of a refused record of a viewer comes from `RECORD_PROBLEM_SENTENCES` of the protocol or from three sentences of the service; the step that a viewer did not do comes from `VIEWER_BOUND_SENTENCES`, an enum of the module; the step of the interface of the TPM comes from `Device_Step`, an enum of a contract that is not in the closed list of the contract enums ([console_value_colors.md](console_value_colors.md)); the name of an error code of the protocol is no member that a field can name. One fact type keeps each event, as `storage_service.Disk_Silent` does.
- **A word of another party keeps its number.** The word of the compositor that names no event and the status that the frame service gives for a read region are any `u32`: the field is an Integer, as the line wrote it.
- **The verdict that cannot differ is not a case.** `remote` resets a request or an answer only when the time of the machine since its start reached its bound, so "the bound of a request held" is the one sentence: `Request_Timeout` and `Answer_Timeout` are one fact type each. The idle end can differ, and keeps two fact types. A fact type that no call reaches would leave the table `Facts`, and the check of the keys of the package of a module refuses its key in the IR.
- **A count of seconds that the line writes as "N seconds" is an Integer.** A Time field in seconds writes " s": `root.Entropy_Reads_Late` has `deadline_seconds`.
- **A line stays text** when no field kind writes it as the line does, or when no reader groups it:
  - each refusal of the TPM with its response code ("(response code 0000000000000922)"): `system.Hex` writes 16 hexadecimal digits with no "0x", and a hexadecimal field writes "0x"; so the refusals of TPM2_Shutdown, of the creation ticket, of the unseal by the PCR values, by a wrong authorization value and by the lockout, of the extend and its read back, of TPM2_GetCapability and of a lockout authorization value stay text, and so does "tpm: ok, the CRB interface at ...". The field kind `Hexadecimal_Sixteen_Digits` of step 10 writes `system.Hex`, and makes them facts;
  - the end of a connection of `remote` ("... ended (the idle timeout, the code 0000000000000000 of the application): ..."): `system.Hex` again, and a cause and a part "of the application" that differ by the case;
  - a refusal with a free sentence of its cause: "remote: refused a request: <the sentence of the error record>", "root: the entropy service refused a read: <the sentence of the error record>", and the stop of each service at its start (`fail` of each module);
  - a status of the kernel that the line writes as a number ("the map of the queue gave the status 3"), as for the root service;
  - a line with no value: "input: no PS/2 controller: no keyboard and no mouse", "input: ok, the mouse has a wheel", the full input ring and its room, "network: the frame ring is full", the first hold and the first underrun of the sound service, the unseal done, the states of the lockout hierarchy, a weak seed of `remote`. At this step a fact type needed a field; step 10 takes a fact type with none;
  - the measures, each written once or a few times in a run and read by the measure record as its sentence: the passes of the network service over the bytes and its check ("... as it must"), the headers of IPv4 and Ethernet in nanoseconds, the start of the sound stream, the draw of the window of `remote`, the viewer frames of `remote_display`;
  - the lines written once at a start, which no reader groups: the public key and the listen port of `remote` and of `remote_display`, the capture face of `remote_display`, "network: ok, the address ...", the read region of the frame service, the count limits of the TPM, and the lines of the root service of the entropy device at the start ("the entropy device gave 64 bytes in 2 reads ...", the configuration, the first fresh bytes).
- **No log line of the network service is a refused frame.** The network service counts each frame that it refuses in the problem rows of an endpoint and of the machine (`datagram.Problem_Row`), which a process reads by a call: they are no log line, and need no fact.
- **No line of the entropy service is a refused read.** The service answers a refused read in its completion, with its error record; the root service writes the line, and its facts are those of `root`.

### The facts of the other system modules

The other modules of `src/modules/system` convert with the groups of the demonstrations: the debugger and its window, the start policy, the module file service, the date service, the windows `boot`, `pages`, `inspect` and `manual`, the call host `host`, the assembler `assemble` and the C compiler `c_compiler`, and the lines that the services of the devices and of the network, `remote` and `remote_display`, kept as text in their group. Each module has a file `facts.odin`; the debugger has the most fact types, 49.

The rules that decided each line, past those of the groups before:

- **A text with no small bound is a text view** ("Text views"): a path of the module file service (`path`, `request_path`), the target, the title and the label of a link of the manual, a debug place of the debugger window and of `inspect`. A name of a process or of a store keeps a fixed Text field.
- **A load error is one fact for each stage.** The call host declares its fact types as distinct types of the shapes of the contract (`host.Load_Find_Failed :: distinct module.Load_Find_Fields`, and one for each stage, `Load_Map_Failed` and `Load_Unmap_Failed` of one shape), and a fact type with no field for an error with no stage ("The load error as facts").
- **A stop of a row of the start policy has the fields of the stop of the root service:** `cause`, and `outcome` when the row stopped itself, so `where(outcome = Done)` reads both writers.
- **A refusal that crosses no border as a typed value is its word or its name.** The assembler gives its refusal by the place and the byte of the source, and the writer of module files gives its refusal as a number in an error record: neither is a contract enum. A refusal of the assembler is an Integer of 4 bytes beside the words of `assembler.refusal_sentence`; a refusal of the writer is the name of its member, a Text field that the module writes from `WRITER_REFUSAL_NAMES`. The word of the C entry that names no result keeps its number, as a word of another party does.
- **A cause from a closed set of sentences is a Text field**, as the cause of a silent disk: the cause of a read of a debug object that stopped, the fault of a start list, the failure that stops the module file service.
- **A date and a time zone are Text fields.** The date service writes a date in the form of ISO 8601 and a zone such as "+08:00", which no field kind writes.
- **A count of pages that the line writes as "N pages" is a Size in pages.** The guard pages and the pages that can be written and executed of `pages` are plain counts, because the line writes other words after their number.

### The facts of the demonstrations

The demonstrations are the fifth writers that convert, and the last of `src/modules`: each of the 50 modules of `src/modules/demonstrations` has a file `facts.odin` with its fact types, 708 in all. Their lines are the cases that a scenario waits for, the measures that the measure record reads, and the failures that stop a demonstration. No table lists them: each `facts.odin` says what its module converted.

The rules that decided each line, past those of the groups before:

- **The template is the sentence of before.** A wait of a machine test, the measure record and each check of the tool after the run (`processor_frame_lines_check`, the generation that a test of `notes` reads) read the sentence unchanged. A field never has the name of a column of the head of `facts()`: `number`, `time`, `process`, `level`.
- **A verdict is a Text field of a closed set of words.** "as it must" or "WRONG", "passed" or "FAILED", and the mark `wrong_mark`, " (WRONG)" or nothing: one fact type keeps each case, and `where(verdict = "WRONG")` finds the cases that did not hold. Where the sentence of a case leaves no room for a field of the verdict, the case is the type: `debugged.Breakpoints_Removed`.
- **A part that is there or not is a Text field with its comma.** ", held" or nothing in `heron`; a word that depends on a count is a Text field too, "block" or "blocks" in `disk`, so that the sentence never says "1 blocks".
- **A closed set of words of a module is a Text field.** The direction of a run of `disk`, the queue of `crowd`, the wait of `flow`, the name of a case of `fault_ring`: the enums of a module or of a support package are no contract enum, as for the grant of the root service. A status of another party that is no contract enum (`timed_stream.Status` in `tone`) stays its number.
- **A status of the kernel writes its name.** Its field is the contract enum, or `operation.Status_Word` beside fields of 8 bytes. The status that a case of `counters` gives back on a failure keeps its number, as its line wrote it; the status that the case expected writes its name.
- **An address is `Hexadecimal_Sixteen_Digits`.** It writes 16 digits with no "0x", as `system.Hex` did: the details of `debugged`, `fault_ring`, `guest_demo` and `return_fault`, and the hash of a body of `server`.
- **A decimal of a number that is not a time is in hundredths.** The shares of `scheduler`, the rates of `fetch` and `randomness`, the times of a part of `extended_state` and of a call of `imports`: the lines wrote one decimal, and the facts write two. The kind `Tenths` writes one decimal, and came after these groups.
- **A line that a loop wrote is one fact for each item.** The lock waits and the frame caches of `locks`, the weights of `scheduler`, the parts of a save of `extended_state`, the cost of the rules of `kernel_events`, whose 20 values passed one record. The sentence of each fact is the head of the line and the part of its item.
- **A sentence that differs by a case is one fact type for each case.** A template has no condition: the stops of `tone`, the cases of `net` whose answer is an error record and its wrong answer, the stop of a child of `fault_ring` by its cause.
- **An error record and a load error are fields.** A refusal of a service writes the seven fields of its record ("The error record as fields"): `fetch`, `net`, `notes`, `tables`. A start that fails at its load writes a fact of its status and its budgets, then a fact of the stage of its load error ("The load error as facts"): `kernel_events`, `scheduler`, `tables`.
- **A value that the line wrote twice is two fields.** A template names each field once.
- **A line with no value is a fact type with no field**, whose sentence is its template: the most frequent fact type of the small demonstrations (`fault`, `life`, `paint`, `twin`).
- **A Text field comes last, and holds its longest text and a zero byte.** Each file says the longest text of each field beside its size.
- **A line stays text** when it is the subject of its module: the demonstration `errors` writes the sentences of an error record, of a load error and of a stack, and a line longer than one log record, and its main test checks each writer of them by its words and the join of the long line.

### The kernel and the boot path

The kernel and the boot program keep text records. The reason is not the store: the module file of the kernel is in the boot image, which a reader of the whole log holds. The reasons are two. The lines of the kernel are read on the serial port by a person at a fault of the start, with no tool: the boot stages, a stop on a fault, the report of a fault. And the kernel has no own-hash place and no `system` package: a writer of facts in the kernel is a kernel part of its own. The open question below keeps this choice open.

### The frequent tasks

Property 22 ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "22. General mechanisms, and a plain expression for each frequent task") asks each design for its frequent tasks and the expression of each.

| Task | Expression |
|---|---|
| Find the bad blocks of a disk | `log.records(0) \|> facts(storage.Bad_Block)` |
| Find one bad block | `log.records(0) \|> facts(storage.Bad_Block) \|> where(block = 12)` |
| Follow the warnings of one process, as they come | `log.follow \|> where(process = "storage") \|> where(level = Warning)` |
| Wait in a machine test for a fact with one field | the step `{kind = .Fact, process = "storage", fact = "storage.Bad_Block", condition = "block = 12"}`, which the tool checks against the fact tables before the machine starts |
| Keep the whole log of a child, for an audit | in the console, `start(server, wire(server.log, collector.sources))`; in a starter, the same row in the wiring list of its `Start`, then `system.input_read(&audit, deadline)` on its record input |
| Write a fact | `system.log_fact(.Warning, Bad_Block{block = number, check = found, expected = wanted})` |

**`log.follow`** is the one expression that this list adds to the log service: a record output of the service with the rows of the whole log, from the next record on, which the console reads as a Stream ([module_outputs.md](module_outputs.md), "The console form"). Its row, `log.Follow_Row`, is the row of `records()` with no byte that no field names: the number, the time, the slot and the name of the process, the level, the form, `continues`, the count of the value runs and the text; a fact has no text there, as in `records()`, and `fact_records()` gives its values.

- **The scope is the whole log.** A reader wires `log.follow` with the end `Connected`, which the root service gives only to an asker that acts for the principal ([module_outputs.md](module_outputs.md), "The wiring and its rights"). So each follower has the scope of the whole log, and one record output serves each of them: the service never needs to know which ring is which connection. The design first said "the log scope of the connection"; with that rule of the root service, that scope is always the whole log. A scope for each connection would need a record output for each scope, which no reader asks for.
- **The loss is a gap record.** The kernel log stays lossy below it. When the kernel wrote over records before the service wrote them into `follow`, the service writes one gap record of their count in each ring, in their place (`system.output_gap`, with the pure rule `output.gap_after_lost_records`). A record that is torn during its copy, or whose form or level names no member, is lost too. The losses of one pass add up in one count, which the service says as one gap right before the next row: a torn copy reads the head of the log again, as the kernel can have written over the records after it, and adds them to the same gap. So the serials of `follow` count the records of the whole log one for one from the join, and the number of the next row says the same as the gap. On a ring with no condition, a gap that waits always ends at the next serial; lost records that do not follow it are a fault of the writer, and close that end (`Not_Contiguous`). A follower that joins before the first pass of the service joins at the head of the log, never at its first record.
- **The service never waits for a follower.** It serves every caller, so it writes each row with no wait. A full ring of the pace `Writer_Chooses` refuses the row with `Full`; the service keeps its place and writes the same row at its next pass, so a slow follower holds the rows of each follower, never the service. While it waits, the kernel can write over the records after its place: each follower then reads one gap. A ring of the pace `Never_Holds_Writer` refuses the row for its own reader, who reads its own gap.
- **What wakes the service.** Its loop waits on the log, on its wiring ring (a new follower joins at once), and on the room and the end word of each full ring of `follow` (`system.wait_output_room`): the read of a follower that the service refused wakes it, as a read wakes a writer that a full ring holds. The wait decides with the read that the refused write loaded, and waits on that value, so a follower that drained between the write and the wait ends it at once. A follower that falls behind and then reads gets its gap record with no new record of the log, and with no wait of a time.
- **The bound of the wait.** A wait holds 64 words, and a list that overflows ends at once, which would turn the loop with no wait. The other parts of the wait of the service take 26 words, each full ring 3, so the wait covers 12 full rings (`FOLLOW_RINGS_WAITED_MOST`, checked at compile time). A thirteenth full ring gets its row at the next wake of the service for another cause, at the latest the next record of the log. The root service gives a process 16 ends at most.

**The check.** No expression names a record form, a fact key, a module hash, a byte offset or a number of a level. The fact type, its fields, the members of `Log_Level` and the process are names that the console or the tool completes and checks. The raw form `#<hash>:<key>` appears only for a record whose module file the reader does not have, and no task uses it. A filter on the form and the key in place of `facts` is the incantation that property 22 refuses.

## The forms refused

- **Keep the formatting in the writer.** The writer pays the formatting at each call, the code of each call site holds it inlined, the record holds a text that a reader cannot filter by field, and a test compares sentences that a change of words breaks.
- **A format string interned by its address.** An address is not an identity: it changes with the base of each load and with each build. A library module cannot hold it in a read-only segment. And a reader needs the memory of the writer, or a table of addresses in the module, to find the string.
- **JSON, or text of `key=value` pairs.** It is text between processes, which property 19 refuses: each reader needs a parser, and the writer still formats. The names repeat in each record, so a line takes more records and more of the budget of each second, and no tool checks a name before the run.
- **The runtime type information of the language as the description.** Its tables describe the types of Odin, which ties a contract to one language (property 19), and they hold addresses that the loader rebases. Nothing checks a template against the fields at the build. The fact key uses the typeid only, an immediate in the code, which the contract defines as bytes.
- **An index of the fact type that the tool assigns.** The code needs the identity at its compile, and the tool reads the module after it. An index needs a generated source before the compile, or a value written into the code after the link. See "The fact key: why the typeid", (b).
- **The template as a string at the call or in a constant beside the type.** Two calls of one fact type repeat a string at the call, and a typo makes a second fact type. A constant beside the type, `#hash` of the template, is a second declaration that names the type by nothing. The attribute is on the type.
- **The name of the fact type in the record.** It is not an identity (two modules have a `Bad_Block`), it takes bytes of the values, and a typo makes a new name.
- **The module hash set by the kernel.** The kernel does not know which code of the process called `Log`, and a module record is what the loader asserts: the kernel then reads the module records at each `Log`, and gains no trust.
- **The kernel renders the template.** It is a text formatter and a reader of module files in the kernel.
- **The log service renders the records to text.** The service then needs the catalog of each writer, and the reader loses the fields that it filters on.
- **A grant to read a fact type of every process.** The reason is in "Which reader sees which fields".
- **A free grouping name kept for `system.log` (a log topic).** It is the channel again under another word: a typo makes a new stream, any process writes any name. A line that a reader groups is worth a fact type.
- **The kernel log as a data path.** The kernel log is never a data path: a record there is lost when a ring evicts, when a budget refuses, when the serial port drops it, and its order with the work is not promised. Its reader needs the log scope, not a handle with a right. The work of a module goes through its record outputs ([module_outputs.md](module_outputs.md)). The one reliable way to keep the log of a process is its record output `log`, wired in the wiring list of its start.
- **A reader that takes the kernel log as the data of its work.** The same reasons. A test that reads a fact checks the work. A process whose work needs the records of another process reads them through a record input that a wiring gives it; an audit reads the record output `log`.
- **The kernel writes the record output `log`.** The kernel is off the data path (property 5), and a write to a ring of another process from the kernel waits on a reader in the kernel. The library of the writer writes it, as each record output.
- **A wiring of `log` while the process runs.** The audit needs the first record, and a wiring after the start gives a joined record of N in its place. A reader that wants the records of now reads `log.follow`.
- **The authority of a process handle with Control.** A process handle goes to other processes with Give, so it names a holder, not the one who asked for the start. The check that the asker asked for the start of the process is the rule of `Stop`, which the root service already keeps.
- **Several readers of `log`.** The writer then copies each record to each reader and waits for the slowest one, for a log that most readers read only to forward. One wiring; a second reader reads from the first one.
- **The end of `log` through a wiring ring.** Every process then pays a wiring ring and its pages for a wiring that most never get. The end comes in one handle slot of the context.
- **A wired `log` that drops a record when its reader is slow.** It is then the kernel log again, with one more copy. An audit that loses records is no audit.
- **A version number in each fact record.** The module hash pins the description already.
- **A fact of any size in several records.** A fact of more than one record was refused while 144 bytes held each line. The lines of a path, a line of the console, a target of a link and a load error do not fit: a fact now takes up to `op.LOG_FACT_RECORDS_MOST` records, for the out-of-line area of its text views only, and a reader joins them with one procedure that refuses a hole ("A fact of several records"). The fixed record stays in one record.
- **One tail text after the fixed fields.** It allows one variable text only, and a reader of a field has no head of it in the fixed record: a condition then reads the whole tail. Text views allow several texts, each with its length and its prefix in the record.
- **Fixed Text fields of any size.** A path of 200 bytes as `[208]u8` takes 208 bytes of each fact, mostly zeros, and passes the 144 bytes of one record; a longer path is cut at the size of its field. A view takes 16 bytes and the bytes of its text.
- **An address in a text view.** No address crosses the log: a reader in another process has no memory of the writer. The write copies the bytes, and the view holds an offset in its fact.

## Subtle points

- **The template is a literal of the attribute.** The tool reads it from the syntax tree and refuses another form, so the template cannot come from a constant or a concatenation. The compiler ignores the attribute, so no template byte reaches the code.
- **The key names the type, not its fields.** A fact type whose fields change keeps its key, and its module hash names the new description. A reader that holds an older module file for that hash does not exist: the hash is the file.
- **A type declared inside a procedure, or private to its file,** has another canonical name (the procedure or the file enters it). The tool refuses the attribute there, so the key is always `<package name>::<type name>`.
- **A collision of fact keys** inside one module fails the build. Two modules can have the same key, as two modules that compile one package do: a key is read with its module hash.
- **The value at the call is a composite literal.** The tool reads the named type there to find the attribute. A value from a variable has a type that the tool cannot read with no type checker, so the tool refuses it, and the writer names the literal at the call.
- **The rendered sentence is not the record.** Two fact types can render the same text. A test that waits on text matches both; a test that waits for a fact matches one.
- **A support package and the module hash.** A fact type of `interface` is written with the hash of the module that compiled `interface` in: the record names the description in that file. The fact name is the same in each module, so a filter by name finds every window.
- **A fact name in two modules with two descriptions.** A new version of a module can change the fields of a fact type that keeps its name. `facts` takes the description of the first matching module of its catalog and leaves out each row whose description is not equal. A sentence that says how many it left out is still to build: a result of the console has no place for a note yet.
- **A replacement module** writes its own hash: its facts render with its own template.
- **A Text field from a writer** is UTF-8 that nobody checked. The kernel no longer filters it, so the reader checks it at its border, with the rule of [text_encoding.md](../data/text_encoding.md).
- **The serial line is shorter when the values hold zeros.** A byte that is not zero takes two digits, and a run of up to 20 zero bytes one letter. A fact of 144 bytes with no zero takes 288 digits, more than most texts: a Text field of a long name costs twice its bytes. A Text field comes last, so the zeros after its name cost nothing.
- **A tag names, a hash identifies.** The module tag and the key tag are enough for the tool, which knows each module of its build and refuses a clash. A reader of the system finds the module by the whole hash of the record, never by the tag of the line.
- **The own-hash place of a disk process** is written by the root service, which loads it from the store `module_files`; the loader of a library writes the place of that library in each process that loads it.
- **The value bytes are a copy of the record of the source.** The compiler and the tool refuse padding, so the bytes are the fields only. A record of the source and its description agree because the tool computes the offsets from the source and compares them with the compiled layout, as for an export record.

## The measures that decide it

Each measure is printed, never asserted ([`docs/TOOLS.md`](../../../docs/TOOLS.md), "The bounds of the tests"). Each one runs on the test machine under KVM, with the same line written both ways.

Each measure has its printer. The tool prints measures 4 and 7 after each machine, and measures 3, 5 and 8 after the main machine, which it also writes to `build/log_measures.txt`; the measure record keeps the lines of measures 3 and 5. The process `log_reader` prints measures 1, 2 and 6 in its measure run, which `modustool screenshots` runs with the other measure runs of the record, and `modustool measure log_reader` alone. Measures 3 and 5 compare two builds: `modustool measure-compare` reads the measure record of the full check before a change and the record after it, and prints each line and the ratio of each number ([`docs/TOOLS.md`](../../../docs/TOOLS.md), "The comparison of two measure records"). The lines are in [`docs/TOOLS.md`](../../../docs/TOOLS.md), "The measures of the log facts".

1. **The write cost.** `system.log` against `system.log_fact` for the same line, in nanoseconds from the call to the return, the least and the median of 200 calls: the line of a bad block, and the line "connected <module> to the service <module>, for principal <n>", each as a fact type of `log_reader` with the template of the line. A series starts in a second of its own and writes 200 records, under the 1000 of the log limit of the process: a line that the limit refuses returns early, and would measure the refusal. The text of the bad block writes its checks in 16 digits, as `system.Hex` does: the support library has no part of 8 digits. It must show the share of the kernel entry (measure 2), and the gain of the fact in the process. A fact that costs more than the text stops the conversion of the writers until its cause is known.
2. **The kernel time of `Log`.** The operation `Log` called by the process, from the call to the return, the least and the median of 200 calls, for the text of the bad block formatted before the series, for its fact built before the series, and for a call that the kernel refuses at the border of the form. The refused call is the kernel entry, the border and the error record: the two others less that cost are the work of each form in the kernel. The kernel event of each operation was the first way: it needs a reader of the kernel events in the process, for a number that the refused call gives. It must show that the copy of a fact costs no more than the filter of the same text.
3. **The record count.** The records that the main machine test writes up to the line of the kernel "kernel: ok" and up to the line of the root service "root: the machine is usable", not the line of the start policy with the same words a few records before it. The tool counts them on the serial log: the lines with a head `[name] ` and the lines of the kernel, which have no head; one for each fact, one for each 168 bytes of a text. The lines of the firmware and of the boot program come before the log, and count nothing. A log that lacks one of the two lines fails the machine, and no count is written. Compared before and after a conversion, it must show that no line takes more records, so the budget of each second holds the same lines.
4. **The serial bytes.** The bytes of the serial lines of the facts of a machine, and of the same lines as text. Under KVM a byte costs about 22 µs ([log_side_channels.md](log_side_channels.md)), so more bytes mean more lost lines in a flood. It changed the serial form: see "The serial port".
5. **The code bytes.** The bytes of the module files of the root service and of the compositor, and of their segments of code. Compared before and after a conversion, it must show the formatting that the call sites no longer inline, and whether a fact type adds bytes of type information to a module file through `typeid_of`.
6. **The reader cost.** The time of the one render, `module.fact_sentence_write`, which the console and the window `log` call, for 2047 renders of two fact types of `log_reader`, the least and the median, and 30 rows at the median. The module file is found and checked once, as each reader keeps the last modules that it found: the measure is the render of a row with its module at hand. The draw of a row is the frame of the window, which the compositor measures. It must show that the window renders its 30 rows in less than one frame of 8.3 ms. If it does not, a reader renders only the rows that it shows.
7. **The render of the tool.** The time of the tool to render the serial log of each machine on the host. It must show that a machine test waits no longer for a line.
8. **A smaller record.** The lines of the main machine test sorted by the bytes of their body: the text, or the head of a fact and its values up to the last byte that is not zero. The serial line carries no value run, so a text with runs uses up to 24 bytes more than the measure says. For each shape, 256 bytes with the head of 64 bytes of today, 128 bytes with the same head, and 128 bytes with a head of 32 bytes and no name of the process, it gives the records that the whole log of 128 pages keeps (2047 today), the records that the lines take, and the facts that one record cannot hold. The cost of a copy in `Log` and in `Log_Read` with a smaller record needs a kernel built with it, and is not measured. The size stays 256 until this measure shows a gain that pays for the change of each reader.

## Open questions

1. **The term.** The proposal says "event". The system has `system.Event` (a count that threads wait on), the kernel event, the event record, the event table, the event rule, the event ring and the event word. A "log event" is one more meaning of the word beside them, and an "event table" of the module file is a second event table. Recommendation: "log fact", as this file writes it, and `system.log_fact`.
2. **No grouping name for `system.log`.** Recommendation: none, as above. The other way is a "log topic" that the writer types; it keeps the fault of the channel.
3. **Facts of the kernel.** Recommendation: the kernel keeps text, for the reasons above, until a reader needs to filter the lines of the kernel by field (a stop on a fault by its address). Then a kernel part writes the facts of the kernel, with the hash of the kernel from the boot record.
4. **The fields of an enum of a module.** A status of a contract enum gets its name, because each reader compiles the contract in. An enum of the module itself (a state of a key) has no description of its members in the module file. Recommendation: an Integer field until a fact needs the names; then a table of enum descriptions, which an export also uses.
