# The floor of a module and the size of its budget

Status: Accepted, built in part: the peak of a budget and its check, the counted floor, the floors of a start list first, the default size, the rows of the plan (`root_plan_values`), `pages = unbounded` rows and start option, `Budget_Grow` on the root ring, the test image's own plan file (`test_plan_values`, excluded from release images, replacing the fallback exception tables in `root`), and the floor cleanup across all modules with counted start objects, start budgets and wiring pages (all `Measure pending` entries removed; only eight modules with large post-ready allocations keep `working_memory_pages`). The study, its prior art and its measures are in [`docs/research/budgets_as_policy_study.md`](../../../docs/research/budgets_as_policy_study.md), the critique in [`docs/research/budgets_as_policy_critique.md`](../../../docs/research/budgets_as_policy_critique.md), and the decisions in the study, section 10. The frames that a process gets for its pages are a separate design: [frames_of_a_process.md](frames_of_a_process.md).

## Purpose

A process runs inside a budget: pages of memory, processes, threads, processor time and log records. Its starter pays that budget from its own. This file records which part of a budget is a fact of the module, which part is a policy of the machine, how a starter divides its pages, and how a process gets more than its size.

The guide of the budgets is [`docs/ARCHITECTURE.md`](../../../docs/ARCHITECTURE.md), "K1. Handle table". The rules are [`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "14. Memory is supplied by the caller", and "20. No ambient access", lines 16 and 17.

## Constraints

- **A process never grants itself anything.** A value in the file of a module is a fact, never a grant.
- **The size of a budget is a reservation.** Each page of the size is held from the start: no fault fails for memory, and no process sees the pressure of another inside its size.
- **A module of another project runs.** No table of the code of the root service names it.
- **A number that a developer guesses is wrong on some day.** The working memory of today mixes fixed tables, tables sized from the machine and data that grows.
- **The size spends a resource of the machine.** The principal who owns the machine decides it, not the file of a module.
- **No bare constant.** Each amount follows from a measured or stated fact, or is a plan value with a default and its reason (the list is in the study, section 10.3).
- **The kernel reads no module file.** It has `Budget_Create` and `Budget_Read`, and no operation adds pages to a budget that lives.

## The chosen form

**Two records with two owners.**

- **The floor** is the table `Floor` of the module file: what the process needs to reach its first state of work. The module and the tool own it; the hash of the module names it. A file with no table `Floor` is refused: before 1.0 nothing is kept for an older tool.
- **The budget policy** is a row of the plan. The plan of principal 0 owns the rows of the machine and of the modules of the image; the plan of a principal owns the row of its class of disk processes. A row of a module of the image is keyed by its name, which the signed image fixes; a row of a disk process is keyed by its hash or by its class, never by its name. The signed image holds the default plan. The image of the tests carries its own plan file, which the default image does not have.

**The floor is counted whole.** The hand writes names and counts of slots, never pages. The tool counts:

- the module pages: the module and each import, with their zero part;
- the thread pages, from the stack that each thread states (`op.STACK_PAGES` for the first, `op.THREAD_STACK_PAGES` by default, or the constant that the source passes to `system.thread_start`), its thread area, the context page and the own log ring;
- the window pages: two pictures of the stated window at the largest scale;
- the load pages: the frame lists, the page tables of the mappings and the private copy of the writable data, priced by the cost functions of the contract (`op.memory_cost`, one table for each 2 MiB of a mapping);
- the start objects: a list of named constants in the package of the module (`MODULE_START_OBJECTS :: [?]system.Start_Object{RING_PAGES, LENT_PAGES}`) and in each package compiled into it (`PACKAGE_START_OBJECTS`). Each name is a constant whose value is one integer literal, which the code passes to `memory_create`. The tool prices each object as the kernel charges it: `op.memory_cost` and `op.mapping_table_pages_most`. The list is an array of inferred length, so it has no bound; the type of its elements, `system.Start_Object`, lets the compiler check each name;
- the floors of the children: the modules that the process starts before its first state of work. The module table of the tool names them (`children`), beside the imports: the build converts a child before its parent, as it converts an import first, and the floor of the child is an input of the conversion of the parent. A name in the source as well would be a second copy of the same list. A child that the parent starts with a fixed amount, not with its floor, is listed in the source instead (`MODULE_START_BUDGETS :: [?]system.Start_Budget{NODE_PAGES}`, each element the constant that the code passes to `budget_create`), and the tool counts each at its pages, as the parent carves them;
- the wiring budget: the root service carves it from the budget of an asker at its first wiring, which can come before its first state of work. The floor holds the pages that the source states (`wiring_pages`), or, for a module whose start grants send `Wire` from its root ring, whose own package syntax tree names `root_ring.Root_Command.Wire`, a step of `root_ring.Wire_Step` (`List_Page` or `Apply`), or passes `.Wire` to a package procedure taking `root_ring.Root_Command`, and that states none, half of the floor, the carve of the root service: as many pages as the rest of the floor, written in the table as its `wiring_pages`, so the root service carves that amount. The start policy, whose list prices its wirings, gets them in the floor of its start. The tool reads the start grants from the table of the root service, an input of the conversion. A holder of the grant whose package never wires gets no wiring part: its floor would double for a carve that never comes.

The load pages are a worst case that the contract prices: the top table and the tables of the time page; for each module, the larger of the frame list of one copy of the module and the frame lists of its segments, and the tables of its mapping at any address; the frame list and the tables of each stack, of the context page and of each picture of the window. Two mappings that share a table cost less, never more.

A module with an entry has a table `Floor` even when its source states nothing: its counted parts, one process and one thread. A library module has none.

A fixed table that every start uses is a variable of the package, so the module pages count it. A table that only some importers use stays an object made at its first use, and is a start object of its package. The source still states `processes`, `threads`, the window size and `screen_pictures`.

**The floor of a start.** The starter adds to the floor of the file what it computes from the plan and the machine: the screen pictures at the screen of the machine, the wiring budget of the rows of the plan, the audit pages of the collector. `system.budget_size` takes that sum, not the number of the file.

**The sum first.** A starter reserves the floors of its whole start list, then divides what is left. A process of the start list is never refused for a size that another process took. The tool adds the floors of the default start list and compares the sum with the least machine of the system (1 GiB, the reference screen); the build fails when the image cannot start there.

The rule of the division (`system.start_list_sizes`) runs once, before the first row starts. The floors come first. Of the pages left, the starter keeps the floors of the starts that are no row and that can come before the list is done: the start policy once, each part of the system that it starts in its own way and that does not run yet (the largest renderer of the console alone), and the budget of the disk processes when it is not made yet (`start_list_kept_pages`). It never keeps less than one largest budget, for a start that a process asks. One largest budget alone would let many starts before `Machine_Usable` draw past it, into the rows. What remains goes to the growth of each row, its default size less its floor: each gets its whole growth when the sum fits, else the same part of its growth as each other, rounded down to 512 pages and never below its floor. The order of the rows then changes no size. Until a row starts, the starter keeps its divided size from every other start, of the list or not (`system.Start_List_Reserves`): a start outside the list between two rows draws from the share that the division kept, never from a later row. The budget of the disk processes and a growth of the budgets of a screen take no reserved page either: each is refused while the free pages less the reserves do not hold it, and a disk process refused before `Machine_Usable` names the start-list reserves as the cause. The reserve of a row ends when its start succeeds; a start that fails keeps it. Every reserve ends when the list is done: at `Machine_Usable`, which the start policy sends after it walked each row, also the rows that it skipped or that the machine lacks, when no start policy runs, and when a start policy from the disk runs with its own order. The sum that the tool proves holds every start of the root service on the least machine: its own floor, the floor of the start policy, the floor of each part of the system that the image holds (the largest renderer of the console alone, as one runs at a time), the floor of each row, the budget of the disk processes, and what the kept share of the least machine (`module.TEST_MACHINE_LARGEST_BUDGET_PAGES`) holds past the floors of the starts that are no row.

**The size, part by part.**

- **Pages.** A row gives `pages` (a count) or `share` (a fraction of the pages of the starter at its start), never both. With no row, the size is `2 × floor`. The reason: a process can double its start memory before it needs a growth or a row, and its default follows its real need, not a fixed count. The factor is a value of the plan of principal 0, `default_growth_factor`, with 2 as its default. The size is rounded up to a multiple of `LIST_ENTRIES` pages (512): an arena pays one page of frame list for each 512 pages, so a size of another count leaves a last step that never fits.
- **A row below the floor** gives the floor and one log fact with both numbers. **A floor that the starter cannot pay** refuses the start, with one line that names both amounts; no page moves.
- **Processes and threads** are slots: the floor is the amount. A class row bounds them; no row of a disk process raises them.
- **Processor time** is one processor for each thread, a fact: a thread runs on one processor at a time. A row can lower it.
- **Log records** are the records of the machine divided by its process slots and the root service (`LOG_RECORDS_OF_A_PROCESS`), so the sum fits. A row can lower it.

**The ceiling** bounds a growth only, and comes with the growth. It is a share of the machine, a value of the plan of principal 0, with a quarter as its default: the largest process leaves three quarters to the others. The border of the share refuses a share whose ceiling is below the largest floor of the start list. Until the growth exists, the share stays what it is on the branch of integration: the most that a start gets.

**An unbounded row.** A principal often starts a module whose need nobody knows: a program of another project, a tool that reads a file of any size. A row can then say `pages = unbounded` in place of a count or a share:

- the start reserves the floor and the default size, as with no row, so the sum of the start list is unchanged;
- the row is a growth row: each growth past the size is allowed with no size of its own, up to the safety ceiling;
- the safety ceiling is the ceiling of the machine (the share of the plan of principal 0, a quarter by default). A row can lower it for this module; nothing raises it past the share;
- the growth pages are not reserved, as for every growth: a refused growth is `Budget_Or_Capacity_Exhausted`, which the process reads as a value (property 14), never a stop of the process.

"Unbounded" means "no size stated", never "no ceiling": a module that grows with no end meets the safety ceiling, and the rest of the machine keeps its three quarters. The console and the desktop offer it as the start option for a module of unknown need.

**The peak of a budget.** A budget keeps the least count of its free pages since its creation; the kernel writes it where it subtracts pages, under the frame lock that it holds there (`budget_pages_spend`), and `Process_Report` gives it (`budget_least_pages`). At the first state of work of a process, the root service reads it. A process that passed its floor fails the machine test. The difference between the floor and the peak is a measure of each build, followed over the releases, never a test.

**The first state of work** is an act of the process: `system.ready` says it once, when its start is done and it waits for its work. The library says it for each process at the first present of a window (`display.present_rectangle`) and at the first wait of a service for its calls (`system.service_wait`); a process with neither calls it before its main loop. It travels on the ready ring: each process that the root service starts with a floor gets one, at the handle 19 of its context (`op.CONTEXT_READY_RING`). The ring has the smallest capacity, the budget of the process pays it, and its floor counts it. It carries one record, `Root_Command.Ready`, and one completion that the root service sends after it read the peak. The process takes the handle out of its context with one atomic exchange, so a process that carries two copies of `system` (its own and the one of the drawing module) says it once. At that record the root service reads the peak, writes the fact `Budget_Peak_At_Ready` with the peak and the floor of the start in pages, and closes the ring; a peak past the floor writes `Budget_Floor_Passed`, and the machine test fails on that line. Another record ends the ring with one line and no peak, and so do counters that say more records than the ring holds (`ring.counters_refused`): no record can be read from it, and a wait on it ends at once, so the root service would loop with no wait. A count that moved with no record to read, as a wake with no record, ends the ready ring too (`root_ring.ready_ring_step`): an honest process moves the count once, with its one record, so the bound of such wakes is one. Each end writes one line, and no later pass reads the ring. The root ring of a process with such counters ends too, with one line; its handle stays until the release of the process, so that a later give through it still names the process, never the root service. Each other ring that the root service reads goes through `root_receive`: on a false count it drops what the ring counts (`ring.false_count_refuse`, which moves the counter of the reader alone), writes one line once per ring that names the writer, and its next wait waits. A process that runs once and stops never waits for work: all its life is its start. `system.stop` says it for such a process when it was never said, and waits for the completion, at most the answer bound of a ready ring (`root_ring.READY_ANSWER_BOUND_MILLISECONDS`, the hang bound of an answer of a process), so that the root service reads the peak while the budget lives; a process that said it before does not wait. The root ring refuses `Ready` at its sender, so there is one way to say it.

**The working memory that waits for its measure.** A number of the working memory with no fact behind it is marked `Measure pending` in its comment, which names the run that replaces it: the first machine pass with the check of the floors. `modustool floors measured <log> ...` reads the facts `Budget_Peak_At_Ready` of the logs and prints, for each module, its peak, its floor and the working memory that makes the floor the peak (the stated working memory, plus the peak, less the floor, never below 0). A module that is marked and has no peak is named: it says no first state of work.

**The growth is a second budget.** A process of the root service with a growth row asks with `Budget_Grow` on the root ring. The answer is a new budget handle, made from the free pages of the root service, up to the ceiling, or a refusal with no amount. The process makes on it the objects of one purpose (the arena of one document); when the purpose ends, it closes them and the budget, and the pages return. A growth never extends an object that exists. A process with no row is refused at the border, before any read of the pages of the starter. `Screen_Budget` is the pair form of this command for the compositor and the remote display, with its replacement rule.

**The growth is not reserved, and says so.** The pages between the size and the ceiling come from one pool, first come, first served. Three rules reduce what a refusal tells: it carries no amount; each process gets at most one decision in each period, a value of the plan of principal 0 whose default is one second, which bounds the channel to about one bit in a second; each growth and each refusal is a log fact that the principal sees. A row can give a growth reserve, pages that the starter holds for that row alone, with 0 as its default: a growth inside its reserve reads no pool and tells nothing.

**The class of the disk processes.** Its row gives its pages, its slots and its processor time. The defaults: the pages of two disk processes at the least ceiling of the machine; 8 processes (up to 4 disk processes with 1 isolated child each) and 16 threads (up to 4 threads each), so the processes of the image keep the other slots; the default share of the processors, a quarter. Its pages return to the root service never; a row that lowers the class takes effect when the class holds no process.

## The refused forms

- **The working memory in the source, or a sum `start_objects_pages`.** One number that the hand writes and that nothing ties to the code.
- **A size in the module file, or a hint of the usual size.** It spends the machine; the plan decides it.
- **A default size of a fixed page count** (`floor + max(floor, 2048)`). It gives a small module eight times its need and a large one nothing more.
- **A floor measured on a run.** The peak checks the floor; it never writes it.
- **A count of the memory objects that the code creates, by the tool.** A second evaluator of Odin.
- **A clamp of one process with no sum.** The start order then decides who runs.
- **A row keyed by the name of a disk process.** A file chooses its name.
- **A table of exceptions in the code of the root service, or rows of tests in the default plan.**
- **A kernel operation that adds pages to a budget that lives.** One more operation, and a growth with no return.
- **A refusal that gives the amount held.** A channel at the rate of a ring command.
- **A file with no table `Floor` that gets a least budget.**
- **The first state of work guessed by the kernel or by the root service** (the first wait of a thread, a process seen idle). A wait is no state of work: a process waits for its disk during its start. The process alone knows when its start is done.
- **A root ring for every process, to carry `Ready`.** Each process would hold a command channel to the root service for its life, a disk process too, and the root service a ring, a handle and a mapping for each process; its handle table is a known limit. The ready ring carries one record and lives until it.
- **A flag of the library that says `Ready` was sent.** A process with two copies of `system` has two flags; the second copy would open a handle number that the first one closed and the kernel may give again.
- **The peak read after the stop of a process.** The kernel ends the budget of a process at its stop, so the report then names another budget. The process says it in its stop path and waits instead.
- **The least free pages kept by the kernel after the stop.** A second word in the kernel for what the stop path gives with none.
- **A check of the peak at the stop of a process.** The peak of a whole life holds the growth past the floor, which the size allows.
- **A list of start objects with a fixed capacity** (`[N]Start_Object`). A bound that no fact gives; the array of inferred length has none.
- **The children named in the source and in the module table.** Two copies of one list; the build needs the table for its order.
- **An unbounded reservation.** A start that reserves all the free memory starves every later start and breaks the sum first. Unbounded is a growth, not a reservation.
- **An unbounded row with no ceiling.** One runaway module then takes the machine.

## Subtle points

- **A table sized from the machine is a floor on that machine.** The root service, the compositor and the collector need it before their first state of work. The floor in the file is the floor on the least machine; the floor of a start adds the rest.
- **A parent pays the floors of the children that it starts before its first state of work.** The source names their modules, and the tool adds their floors.
- **The channel of the growth** stays, about one bit in a second between two processes that both hold a growth row: line 17 of property 20, reduced, not solved.
- **A disk process holds no growth row by default.** Its class row can give one.

## State

Built: the least count of free pages of a budget, kept by the kernel part `budget_peak`, through which each change of the pages of a budget goes (its creation, its spends, its returns; a test parses the sources of the kernel and refuses any other assignment to the pages of a budget), and its read in `Process_Report`; the ready ring of each process that the root service starts with a floor, `system.ready`, said by the library at the first present of a window and the first wait of a service, by the services, the drivers, the terminals and the loops of the other modules before their main loop, and by `system.stop` for a process that never said it; the facts of the peak and the stop of the machine test on a passed floor; the table `Floor` for each module with an entry, counted whole (module, load, threads, window, start objects, children) with the working memory that is left; the refusal of a file with no floor; the floor of a start (screen pictures, audits, wirings); `system.budget_size` with `default_growth_factor`; the reserve of the floors of the start list and its division before the first row; the proof at the build that the floors of each list fit in the least machine; the refusal of a floor that the starter cannot pay, with one line that names both amounts; the plan rows in `root_plan_values` (`default_growth_factor`, `budget_growth_period_ms`, the disk processes class fields on `root`, and per-owner `budget_pages` as a count or `.unbounded` via `Budget_Size_Kind`, `budget_share_parts`, `budget_ceiling_pages`, `budget_growth_reserve_pages`, `budget_processor`, `budget_log_records`, `budget_screen_pages`, wired through `plan_value_description`, `plan_reader`, `root/plan_values.odin` and `root/budgets.odin`, with a log fact when a plan row sits below the floor); `pages = unbounded` rows and the unbounded start option (`root_plan_values.effective_growth_of` reserving floor and default size at start and capping every growth ceiling at the machine share while allowing a lower row ceiling, `root_ring.Start_Budget_Option` on `Root_Command.Start` and `display.Control.Start`, `start(name, "unbounded")` in `console`, and Shift+Enter in the desktop start menu); and `Root_Command.Budget_Grow` (`Grow` and `Release`, pure decision and extra-budget table in `internal:root/budget_growth`, rate-limited per process, optional growth reserve, drained on release and closed at stop, refused with no amount). Each module with an entry that stated no budget states the 2048 pages of the least budget in which it ran, marked `Measure pending`, and `modustool floors measured` gives the number that replaces it.

Left: the last eight modules that allocate large post-ready memory past twice their floor (`debugger`, `recipes`, `linux`, `guest_builder`, `doom`, `browser`, `paint`, and `clock`) keep `working_memory_pages` until their post-ready memory moves onto plan rows or growth budgets. All other modules in `src/modules/` state `working_memory_pages = 0` (omitted), using counted module/load/thread/window/screen parts, `MODULE_START_OBJECTS`, `MODULE_START_BUDGETS`, and `wiring_pages`; all `Measure pending` entries are gone, `powerbox` reserves its picker store arenas lazily in `stores_grow` after ready, and `replay_probe` calls `system.ready()` before `test_run()`. The test boot images carry the signed plan resource `test_plan_values` (carrying the budget rows for `limits` and `log_flood`), excluded from the release boot image (`release_boot_image_of`), which `root` loads after `trust_check` as defaults beneath principal 0's live plan, removing the hardcoded fallback exception tables from `src/modules/system/root/budgets.odin`. The console starts its sandboxes at a command, after its first state of work, so their budgets are no part of its floor. The processes that say no first state of work: those that another starter starts (no ready ring), `shortage` and `operation_fuzzing` (fixed amounts, no floor), and `debug_target`, whose debugger test reads breakpoints by its line numbers; `guest_builder` runs in a call host, which says it.
