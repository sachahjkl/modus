# The client keys of remote

## Purpose

A call from another machine acts for a principal that allowed its client, and for no other. Before this design, the process `remote` admitted the host by its address alone: each program of the host that reached the address of the gateway called as the principal of the session of `remote`, and the system could not tell one client from another.

## Constraints

- [`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "20. No ambient access: the other holes to close": a grant is recorded, visible, and can be revoked; the principal is the only source of a new grant.
- [`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "21. Principals: who acts, without users": a remote caller is a process tree that received handles from a principal; identity across machines is a public key.
- The root service is the one holder of the grants. A service learns the principal of a caller from the grant of its connection, never from the caller.
- No stream of a client is read before the client is known: a call must not run, even in part, for a key that no principal allowed.
- The QUIC library of the project is its own code: what it supports is what it implements, and its handshake reads only raw public keys.

## The chosen form

**The proof: mutual TLS 1.3 with raw public keys.** The server of `remote` sends a CertificateRequest; the client answers with its Ed25519 key as a raw public key (RFC 7250, `client_certificate_type`), a CertificateVerify signed with the context string of a client, then its Finished. The library verifies the signature first, then gives the proven key to a procedure of its caller (`Tls_Configuration.client_key_check`). A refusal fails the handshake with access_denied. The transport of a server opens no 1-RTT packet before the handshake is connected (RFC 9001, section 5.7), so no stream of a refused client is ever read. The form is the standard one: the signature covers the transcript, so it binds the key to this connection and to the key of the server, with no format of the project.

**The grant: a row of the client table, in the root service.** A principal allows a key with `remote_allow(key)` from a console that acts for it (`Root_Command.Remote_Client`). The root service writes the row: the key, the principal of the caller, a serial, and the state of the session of that principal (a row of a locked principal holds no grant until the unlock). One principal holds 32 of the 64 rows at most (`remote.CLIENT_ROWS_OF_ONE_PRINCIPAL`), so a principal that allows many keys leaves rows to the others: a person with a laptop, a phone, several agents and the key of a build fits with room. The table is a memory object of two pages (`remote.CLIENT_TABLE_PAGES`) that the root service writes and that `remote` maps with the right Read only, by its start grant `Remote_Clients`: `remote` reads each grant and gives none. The form is the form of the replacement table, which loaders read the same way.

**The grant across a restart: a client key of the disk grant table.** The root service also writes each allowed key into the disk grant table of its principal ([processes_from_a_disk.md](processes_from_a_disk.md), "The grants of a disk process"), beside the rows of its disk processes, and takes it out at the revocation. The table keeps 32 keys (`disk_process.CLIENT_KEY_CAPACITY`, the bound of one principal in the client table), under the tag of the table. So the key lasts as long as the other grants of the principal do: across a restart for a named principal and for principal 0 with a machine key, until the machine stops for principal 0 with no machine key, and until the machine stops when the global setting of the table is to forget (`disk_persistence("", "forget")`). When the read of a table takes it, each of its keys gets a row of the client table again, with a new serial; a row of the principal whose key the table does not hold ends, as each change made before the key of the table came. The client table stays the form of the grants while the machine runs: `remote` reads it, and never the disk.

**A key that two principals allowed: contested.** The root service cannot see a table that is not read yet, so another principal can allow a key of that table in this run (a public key is not secret). When the read finds such a key, the key acts for neither principal: the row of the holder gets a new serial and the mark `contested` with the other principal (`remote.Client.contested`), its connections end, and `client_grant_holds` refuses it. `remote` refuses the key in the handshake with a line that names both principals, and the root service refuses a `Connect` for such a row. `remote_clients()` shows the key as `contested` to both principals, and one line of the log names both. The first revocation by either principal ends the contest: the key holds again for the other one, with a new serial. The decision for each key of a table is one procedure of the contract, `remote.client_restore_decision`, which the host tests run. A device enrolled for two principals, or an attack, then needs a principal to decide: no call acts for a principal that the device was not given to.

**A revocation that the disk does not take.** A revocation is never refused, and it does what each state of the table allows (`persisted_table_revocation`). In the state Unwritten it starts the writes again: the table in memory holds each change since the last good write. Before a read of this run (the states Reading, Awaited, Unread), the root service keeps the key as revoked, and the read takes it out of the table that it gives, then writes the table. When the disk can still give the key back at the next start (the states Refused, Record_Unreadable, Awaited and Unread), the completion says it (`REMOTE_CLIENT_KEY_CAN_COME_BACK`), and `remote_disallow` says it in its sentence.

**The principal of a call: a connection to a service for one row.** `remote` binds each QUIC connection to the row of the proven key, and sends `Connect` with the row and its serial. The root service checks that the row holds that serial and that the session of its principal is not locked, and gives the connection the principal of the row, with the flag to act for it. So the principal is decided by the root service from its own table, not by `remote`. Each rule of the root service that compares a principal with the caller of a connection reads it through `connection_principal`: the debug access of a client is the debug access of the principal of its row.

**The end of a grant: a serial.** A revocation frees the row; a lock of the session of its principal, and the unlock after it, give the row a new serial. The root service ends each connection to a service that it made for the row, then wakes the version word of the table. `remote` waits on that word with its other waits, reads the table at each pass, and ends the QUIC connection of each client whose row no longer holds its serial, with the application code `Revoked`. At each pass it also frees each of its connections to services whose row no longer holds its serial, whether a client of that row is connected or not; the root service ended the other side already, so `remote` tells it nothing. Without that, a grant that ends while no client is connected (a lock and an unlock, a revocation after the client left) would keep its slots, and a few lock cycles would fill its slots. A key whose grant ended is refused in its next handshake.

**What an unknown client gets.** The alert access_denied in its handshake, before any stream, and one line on the log of `remote` with the key, while the log has room in that second (the bound of 50 lines of connections). The client of the tool reads the alert as the outcome `Client_Refused`, with a reason that says to allow the key.

## Refused forms

- **A signature over the handshake in the first stream.** The stream exists before the proof, so `remote` would hold streams of a client that nobody allowed, and the binding of the signature to the connection would be a format of the project. The handshake already has the transcript and the rule of no 1-RTT before the end.
- **The keys in a store of the principal.** `remote` would read the stores of each principal, which the storage service refuses to a caller that acts for one principal, and the grants would have a second holder beside the root service.
- **A table that `remote` writes, or the principal that `remote` names in its Connect.** `remote` would choose for whom it acts. The root service gives the principal from its own row.
- **The check of the key at the Certificate of the client, before its signature.** A peer that does not hold the private key would learn which keys are allowed.
- **One key for several principals.** A call would not say for whom it acts; `Remote_Client` refuses a key that another principal allowed (`Exists`).
- **The end of a grant at the root service alone.** The connections to the services end, but the open QUIC connection would stay until its idle timeout, and its next call would make new connections. `remote` ends it at once.
- **A wait for the next deadline of QUIC before the end.** A quiet connection has no near deadline: the revocation would wait for the idle timeout. The root service wakes `remote` on the version of the table.
- **A start grant `Remote_Clients` that a revocation ends.** The table gives nothing by itself: each row is a grant of a principal, which that principal revokes. The end of the handle would unmap a page that `remote` reads at each pass.
- **The address alone.** The listen grant still admits the address of the host only, as a second fence, but it names no principal.
- **A file of client keys of its own on the disk.** It needs a second object, a second tag, a second read and a second set of states, for a grant that has the same principal, the same key of the tag and the same life as a grant of a disk process.
- **A client key as a row of a disk process.** A row binds a nickname to the hash of a file; a key has neither, and it would take one of the 16 rows.
- **The client table on the disk, with its serials.** A serial names a grant of one run: `remote` binds a connection to it. A key read from the disk gets a new serial, so no connection of an earlier run can name it.
- **An exception of persistence for each key.** It adds a field and a command for a case that a revocation covers: a key that must not last is revoked. The keys follow the global setting of the table.
- **A revocation refused while the table takes no change.** A revocation ends a grant at once; a refusal would keep a client that the principal wants out. The grant ends in memory, the next read of the run takes the key out, and the completion says when the disk can still give it back.
- **A list of revoked keys in memory as the defence across a restart.** It is lost with the run, where the risk is. It serves only until the next read of the same run; the writes that start again, and the sentence of `remote_disallow`, cover the rest.
- **The read gives the key to its table when another principal holds it.** It would take a grant from a principal that allowed the key since the start.
- **The key waits, and the holder keeps it.** This was the first form. The client of the waiting principal then passes the handshake, and each of its calls acts silently for the other principal: persistence would turn a visible refusal into a redirect. A contested key acts for no one.
- **The row of the holder locked (`session_locked`) in place of a mark of its own.** The lock of a session gives the row a new state at each unlock, which would end the contest with no revocation, and the lines of `remote` would name a lock that did not happen.

## Subtle points

- An allow is refused, with the line of `persisted_table_refusal`, while the disk grant table of the principal takes no change: the machine passphrase is not typed, the read runs, or the table is refused, unread or unwritten. A key taken then would be lost at the read, or would not reach the disk.
- A contested key keeps one row, the row of the principal that allowed it in this run; the key of the other table has no row of its own. A revocation by the holder frees the row, and the other principal takes it at once; a revocation by the other principal takes the key out of its table, and the row holds again for the holder. Each principal has 32 keys at most and the client table has 64 rows for the 2 principals of a machine (an assertion in the root service), so a key of a table always gets a row or a contest.
- A contested key still counts against the bound of 4 of each principal: the allow counts the keys of the table too.
- A table of the format 1, 2 or 3 (1008, 1136 or 1168 bytes: no client keys, keys with no uses, or 4 keys) is refused as an older format that this system does not read, and the refusal of a change does not ask for a restore: no version of it verifies under this format. The disks of the builds before the format 4 lose their tables; no migration is built.
- The key of a principal 0 with a machine key comes with the read of its table: until the machine passphrase is typed, or the TPM unseals the machine key, a client of principal 0 is refused in its handshake.
- The tag keeps a reader of the disk with no key from adding a key. A restored older version of the table verifies, so a revoked key can come back, as a grant of a disk process can; a counter of the TPM that only grows ends it, and it is not built.
- The client is connected in TLS before the server checks its key: it sends its Finished right after its proof. A refusal then ends a connection that the client counted as made. The peer of the tool fails each call of that connection at once and makes no new one for them.
- The row can end between the check of the handshake and the first pass of `remote` (`client_bind`): `remote` reads the table again before it binds, and ends such a connection with `Revoked`.
- The end of a grant is enforced by the end of the connections to services, not by a check of each call. The order: the root service writes the row, ends each connection of the row (a Disconnect on the service ring of each service), then wakes `remote`. A service reads its service ring before its call rings in each pass (`service_run`), so a call that waits in the ring of an ended connection is dropped. Two calls can still run after the revocation completes: a call that the service took in its pass before the Disconnect came, and a call that `remote` sends in the same pass in which the row ended, after its copy of the table (`serve_next` checks the copy of the start of the pass). Each one runs as the grant stood a moment before; the window does not grow with time. A call that waits for its turn at the next pass is not made: `serve_next` resets its stream with `Revoked`.
- The debug access of a client is recorded against the process and the row (`Started.debug_for_row`, `Debug_Store.report_for_row`): the clients of two principals are the one caller `remote`, so the end of a connection of one row ends the debuggings of that row only, and a client of one row cannot end or take the debugging of another.
- `Remote_Client` refuses a key that another principal allowed with `Exists`. So a caller learns that some other principal allowed that key, and not which one. The key is public, and one key for several principals is refused for a stronger reason: a call would not say for whom it acts.
- A lock ends the grants of the principal without a revocation: its rows stay, locked, and the unlock gives them a new serial, so a connection to a service made before the lock never serves again.
- The connections of `remote` to one service are one for each row: the root service keys a connection by the caller, the service, and the row.
- `remote` is trusted with the rows: a fault of `remote` could use each row whose grant holds. It cannot act for a principal with no row, and the root service checks each serial.
- The peer of a machine test has a fixed key, which protects nothing but the test; the peer of `modustool run` draws a key at each run from the generator of the host, so no key that the source fixes is ever allowed outside a test.
