# A missing or silent part of the machine

The system keeps running when a part of the machine is absent, or stops to answer: a device, a timer, a table of the firmware, a screen, a disk. It writes one line that names the part and what the system does without it, and the rest of the system works. A stop of the whole machine is kept for a refusal of security and for a broken invariant of the kernel.

## The constraints

- **The fixed machine.** The system targets one fixed machine at a time ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "7. No drivers in the kernel, and fixed hardware first"). A part that the first machine always has can still be absent: a firmware that gates the PIT off, a machine with no screen, a disk that a host stops to serve. The second machine is a real one, where such absences are usual.
- **A device service is a process.** A fault of the code that drives a device stops that process, not the machine. A client that waits for that process with no bound undoes this: the fault then stops every client, and the machine looks stopped.
- **Security refusals stay stops.** A refused signature or a refused version stops the boot program, with its message on the boot display ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "17. Trusted boot: UEFI program, Secure Boot, TPM"). An IOMMU unit that does not finish an invalidation after the start stops the machine, because a page that a device can still reach must never become free ([iommu.md](../infrastructure/iommu.md)). These are not absences.

## The chosen form

Each absence has the same three parts:

1. **A bounded wait.** No wait for a device, a register or a process has no bound. A register poll is bounded by the cycle counter; a wait for a record of a ring is bounded by a deadline, or ends when the process that writes the ring stops: the waiter holds the handle of that process with the right `.Read`, so its stop ends the wait.
2. **One line.** The line names the part and what the system does without it: `input: no PS/2 controller: no keyboard and no mouse`. A line is written once, at the place where the absence is found, by the process that found it.
3. **A smaller system.** The capability is absent and the rest runs:
   - a service that cannot serve stops with its code; its clients get `Gone`;
   - the start policy does not start a process that needs the absent part, and starts the others ([start_policy.md](start_policy.md));
   - a kernel part that is absent at the start is off, with its line, when a safe form without it exists. With no time base, the kernel stops with `Start_Failed` and the line.

The places, by the risk for a user:

| Part | Today | The form |
|---|---|---|
| A disk that stops to answer | Built | A deadline for each block request: past it, the block service completes each request in flight with `Device_Error` and the record `No_Answer` of the device, writes its line and stops; it does the same, with the same record, when the device sets its needs-reset bit, as such a device answers none of them. The storage service holds the handle of the block service with `.Read`, and bounds each wait for a completion by a stall of the hang bound. A record `No_Answer`, the stop of the block service or its own bound make the disk silent: the storage service writes its line once, and from then on refuses each read and each change at once, with no request to the block service |
| No PIT | The first processor hangs before its first line | Built. The calibration wait is bounded by the cycle counter; an output of the 8254 that is high before its count starts is no 8254. The frequency of the cycle counter that CPUID leaf 0x15 or 0x16 of a processor of Intel states is then the time base, and the timer is measured against the cycle counter; with none, the line and `Start_Failed`. The start of the other processors waits with the cycle counter, never with the 8254 |
| No screen | The root service stops to serve its ring | Built. The root service and the compositor make one test of the framebuffer (`modus:support/screen_presence`). With no screen before the first start, the root service writes its line, starts no input service, no compositor and no console, and starts the other services of the boot and no process in place of the console; `unlock` that needs typing writes one line and stops, and is not started again. A compositor that stops later gives one line and starts nothing. In both cases a later start gives no window and refuses the grant `Terminal` |
| No PS/2 controller | The input service spins on one processor for ever | Built. A status of all ones, or a drain that reaches `CONTROLLER_POLLS` bytes: the input service writes its line and stops with the code 1. The root service does not track the input service, so the stop adds no line. A refusal of a device of the controller by the kernel is a refusal of rights or of a slot, never an absence: it stays a failure of the start |

| An xsave area that the processor does not read back | `Start_Failed` | Built. The sentence of the failed proof names the cause; then one more proof with the form `fxsave`, x87 and SSE only, with its line; `Start_Failed` when that proof fails too |

## The stop of the boot program

The boot program cannot run a smaller system: with no memory for the kernel, or no map of the memory, no kernel starts. Its stop is needed; the fault was its silence. The code is `stop` and `boot_stop` in `src/boot/main.odin`, and the arithmetic of the map in `src/library/private/boot_program/firmware_memory_map`, which the host tests run.

- **One stop for each failure.** A refusal of trust and a stop for memory, for the map or for the kernel module take the same path: the line on the log, the failure in red on the boot display with its step, the watchdog off, then a wait. With no screen, or before the boot record has its pages, the line stays on the console of the firmware, and a second line says so. A power off is refused: it removes the message before anyone reads it, and a machine whose firmware restarts it would run the same failure again.
- **A stop after a failed exit.** Once the boot program has called ExitBootServices, the specification allows only the services of the memory, also when the call fails. From that call on, each line goes to the serial port only, a stop draws on the screen (memory that the boot program writes itself) but calls no watchdog, and with no screen its second line says that the failure is on the serial port only.
- **The steps in their order.** The steps of the boot display follow the boot program: the boot image (its copy, its system description and the hash of each file), then the kernel module (its hash, then its load), then the memory map. The hash of the kernel is checked after the files of the image, so a failure of the kernel shows the boot image as done, which it is.
- **The buffer of the map.** The first read of the map asks its size with a buffer of no byte. The buffer then gets that size and a margin of 8 descriptors, because its own allocation, and the free of a smaller buffer, split ranges of the map. Each read that is too small again gets a larger buffer, up to 4 reads; then the boot program stops. A size past 4 MiB and a size of 0 stop it too.
- **The walk of the map.** A read that succeeds must give a size that fits its buffer, and a step between descriptors from the 40 bytes of the specification to one page, and not larger than the map. The walk goes by index, up to the size divided by the step: each descriptor that it reads ends inside the map. A walk by offset with a step near the largest u64 wraps, and reads descriptors before the buffer.
- **A usable range that the kernel can hold.** A `Free` or `Boot` range starts on a page and ends at or below 2^52, the physical addresses of the processor; else the boot program stops with its address. The kernel computes the end of each range (`device_range`, the size of the direct map): an end that wraps would make a range at the top cover the low addresses.
- **The room of the boot record.** The kernel receives at most 1024 ranges. It reads an address that no range lists as an address that a device can hold (`device_range`): a usable range left out could then be given to a device service, the pages of the kernel too. So each `Free` and `Boot` range is kept, and only `Reserved` ranges are left out, which the kernel reads as it reads an address of no range. A range that follows the last one, with the same kind, joins it, so a map has far fewer ranges than descriptors. The boot program counts the usable ranges first; when they alone pass the room, it stops. The reserved ranges left out give one line, on the serial port, after the end of the firmware services: `boot program: the memory map has more ranges than the 1024 of the boot record: <count> reserved ranges of <pages> pages are left out, and the kernel reads them as reserved`.
- **Refused: drop the ranges past the room in the order of the map.** That form was silent, and a usable range at the end of the map was lost: with the rule of `device_range`, that is a breach, not a smaller system.
- **Refused: a fixed buffer of more pages.** Any fixed size is a bet on the firmware; the firmware states the size it needs.

## The tests

Each absence has a machine test that removes the part from QEMU, and checks its line and a later step that still works. The hang bound is the only time in it:

- no PS/2: `-machine q35,i8042=off`, then the desktop with its console;
- no PIT: `-machine q35,pit=off`, with a processor whose highest leaf of CPUID is 0x14 (`-cpu max,level=0x14`, the part `no_pit`). The machine stops on every host, and the reason in its line is the vendor (a host of AMD, or TCG, whose processor `max` is not of Intel) or the missing leaf (a host of Intel under KVM): the test waits for the text before and after the reason. A machine where the fallback succeeds is not built: QEMU fills no leaf 0x15, `tsc-frequency` does not fill it, and the processor of TCG is not of Intel, so no machine gives a stated frequency on every host. The path of a stated frequency, the bounds of the waits, the counts of the tick, the absence of a table of the APIC and the second proof of the extended state reach no QEMU machine: the host tests of the kernel parts `time_base`, `delivery_count` and `acpi_processors` hold their decisions;
- no screen: `-vga none`, then the steps that the root service takes after the place of the console: the boot pass of `settings` through the storage service of the data disk, then `unlock`, then the line of the end of the start, with no call and no picture;
- an entropy read that never completes: the entropy device with the source `rng-egd` over a socket that no process connects to, so the device takes each read and never ends it, then a process that shows the refused reads;
- no network device, no data disk: the machine leaves the device out;
- a disk that stops to answer: the NBD server of the tool reads each request from the first write of a block that starts with a marker, and answers none. A marker and not a count of requests: QEMU joins and splits requests, and the start writes a count that changes with each release, so a count would cut the boot. The scenario writes that block with the console, waits for the line of the block service and of the storage service, then runs a command that needs no store. Before its end the tool closes the connection, so QEMU fails the request that waits and can stop. The data disk of this machine has no ioevent file: with one, QEMU drains the requests of the disk when the root service turns the bus master off, and the request that never ends would stop every processor;
- a frame service that stops: QEMU has no form of a network device that the root service starts and the frame service then refuses after it maps its ring. The machine with no network device is the test: the root service writes its line, refuses `net`, and the console runs on. The wait of the network service for a frame service that stops has host tests of its decision only.
- a stop of the boot program: a test volume of `test trusted_boot` whose kernel states 1 TiB more memory, signed as it is, so each check passes and the firmware gives no pages; the test waits for `boot program: the firmware gives no memory for ` and `boot program: the boot display shows the failure`, then the tool ends the machine, which waits. No firmware of the tests gives a map past 1024 ranges or a map that grows at each read: the host tests of `firmware_memory_map` cover those, with 0 ranges, exactly 1024, and 1025.

## The refused forms

- **A silent fallback.** A part that is absent with no line is a fault that nobody can find: one processor with no word of the missing table, a screen of another size with no word of the mode. The line is part of the form.
- **A stop of the machine for an absence.** A stop hides the cause when the message is on a console that nobody sees, and it removes each capability that did not need the part.
- **A retry for ever.** A loop that tries again with no bound is a hang with more work.
- **A part that the system pretends to have.** A service that answers `ok` with no device gives wrong data to its clients. An absent capability is refused, never simulated.
- **No screen: a wait for the stop of the compositor.** The compositor finds no framebuffer and stops, but a wait for that stop has no end when it runs. The root service makes the same test on its own context before it starts anything, and keeps the stop of a compositor as the second sign, at the start of the console and at the reap.
- **No screen: a terminal with no window.** Its process would write into a ring that no process reads, and wait when it is full. A start of a process with the grant `Terminal` is refused; a process with no window gets no surface and runs.
- **No screen: the input service with no compositor.** Its records would fill a ring that no process reads. It does not start.
- **No PS/2: a drain with no bound only.** A bound alone spins 100 000 reads of a port before the line; the status of all ones names the absence at the first read, as the i8042 driver of Linux reads it, and the bound stays for a controller that gives bytes with no end.
- **An entropy read past its deadline: a second read.** The entropy service serves one read at a time, so a second read waits behind the first for ever. The service stops; a late answer of the device is not counted.

## The subtle points

- **The wait of a client is the hazard, not the fault of the device.** The device service already stops on a fault; the hang comes from the processes that wait for it. Each wait for another process holds its handle or has a deadline.
- **The deadline of a device request** comes from the hang bound of the system, not from a measure of the speed of a device, so that a slow disk is not called absent.
- **A request past its deadline is never given back to the device.** The device can still write the data region of that request. The block service therefore does not take a new request after a deadline: it completes each request in flight and stops, and the root service turns the bus master off. A service that went on would give the same place of the region to a new request that the late answer can overwrite.
- **The storage service and the block service have the same bound, and either can end first.** The block service counts from the moment that it gives the request to the device; the storage service counts a stall from its last completion. Both ends give the same line of the storage service: the record `No_Answer`, the stop of the block service and the bound of the storage service each make the disk silent. Once silent, the storage service never reads the block ring again, so a late completion cannot be taken for the answer of a later request.
- **The storage service does not stop on a silent disk, also before its open.** A stop makes the root service start it again for the next process with a store: a new block service, a reset of a device that still holds a request (which QEMU drains, and the machine freezes), a new wait and new lines. The device can also still write the data region, which a stop frees. So the service serves on with no store known, and refuses each call that names a store with `Device`.
- **A silent disk refuses reads too.** A read would wait for the same device. The storage service answers each call that needs a block with `Device` at once, and a call that needs no block is still served.
- **The root service refuses the network once.** After the network service stops or cannot start, each start of a process with an endpoint is refused with no new start of the frame service and no new line: a frame service that stops at each start would cost a start and a line for each process that asks.
- **At the start, before a device service holds memory, the IOMMU can go off.** After it, it cannot: the reason of the stop is a page that a device can still reach.
- **The no-screen line is written once.** The start, a console that does not start and the reap of the compositor can each find the absence; the first writes the line, and each refusal after it adds none. The line of the start says that the other services start; the line of a compositor that stopped says only that windows and terminals are refused, because nothing starts then.
- **The processes that start with no screen.** This service starts no process in place of the console, `remote` included: which services start with no screen is a decision of the start policy ([start_policy.md](start_policy.md)), and not a policy in the code.
- **`unlock` with no screen.** The root service cannot know before `unlock` reads its store whether a key must be typed: a machine key sealed by the TPM alone needs no typing. So `unlock` starts at the boot; when it reaches the point where a key must be typed and has no window, it writes one line that names what cannot be typed (`unlock: no screen: ...`) and stops with the code 0, and the root service does not start it again while the screen is absent.
- **A restart of the entropy service.** Nothing starts the entropy service again after the stop at its deadline. If a later form does, the device holds the read that it never ended: the root service must reset the device before it turns the bus master on again, so that no old descriptor of the queue writes into memory that the new service received.
- **A bound before the kernel knows the frequency.** The 8254 and the serial port are waited for before the calibration, when the frequency of the cycle counter is 0. The bound then takes the highest frequency that the kernel accepts, 10 GHz: on a slower processor the wait is longer, never shorter, so a working part is not called absent. The wait of the 8254 is one second at that frequency, a hundred times the count of the calibration, so a host that stops the machine for a while does not end it.
- **The leaves of the frequency are of Intel.** AMD documents the leaves 0x15 and 0x16 as reserved, and Linux reads the leaf 0x15 on Intel only, so the kernel reads them only when leaf 0 names Intel. In a guest, a hypervisor can pass the leaf 0x15 of the host, whose crystal is not the clock of the guest. Its cycle counter runs at the frequency of the host unless the hypervisor scales it; with a scaled counter the stated frequency is wrong, and the time of the machine runs fast or slow by that ratio. The kernel has no way to tell, and takes the leaf as it is: a hypervisor that scales the counter and passes the leaf is a fault of the hypervisor. The 8254, when it is there, always wins.
- **A high output before the count.** A port with no device reads with each bit set, so the output of channel 2 reads high at once and a wait would end at once, with a time base of 0. The write of the mode makes the output low until the end of the count; a high output there is no 8254. A real 8254 does not count while its gate is low, but an emulation that ignores the gate in this mode, as QEMU and the 8254 of KVM do, counts from the write of the count: a host that stops the machine between that write and the read gives the same high output, so the start tries three times. Each try starts the timer and the cycle counter of the measure again, so the time of a stopped try is in no measure.
- **A silent serial port is a state.** Without it, each byte of a dead port would wait the whole bound, and a start that drains each line at once would take minutes. The first read that finds the register empty ends the state.
- **A count that a locked path cannot write.** A writer of the serial port and a sender of an interrupt can hold any lock, and the log lock comes before the run lock. So they count, and the tick, which holds none, writes the count each time it reaches a new power of two (the kernel part `delivery_count`): a part that stays broken writes about one line for each doubling. A lost interrupt of synchronization makes its sender spin until the next tick of its target, and the line says so. The line is a record of the log: the serial port shows it when it takes bytes again, and the log shows it when the port never does.
- **A reset that was not sent.** A processor that did not start is reset before its record and its stacks are freed. When the controller does not send the reset, the processor can still run from that memory: it stays taken, with the page table of the start, and the next processor would take the same index, so no other processor starts.
- **A machine check or an NMI** still stops the machine. To read the error and stop only the process whose memory it touches is planned work.
