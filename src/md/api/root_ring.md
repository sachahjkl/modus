# The root ring and the context of a process that the root service starts

The root ring is the border between the root service and each process that asks it for a start, a connection, a revocation or a command of the principals. The context is the border between the root service and each process that it starts. Both carry authority, so a word of either must never become a right that its writer was not given.

## Purpose

- A process sends a command on its root ring only when its role gives it that command. The role is the set of start grants and the terms that the root service gave the process at its start.
- A word of a record becomes a command or a member of an enumeration at one place, which refuses a word that names no member.
- Each refused command gets one error record, written by one known party.
- Each handle that a start gives takes its own context slot, and each value its own index: no role loses a handle or a value in silence because two of its parts have one number. This holds for each starter of the root service, the fixed starters too.
- The whole role of a process is in one place, and a new module of the boot image cannot start with a role that nobody wrote.

## Constraints

- The kind of a record and each word in it come from another process, which can be hostile ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "No ambient access: the other holes to close").
- A disk process has a nickname that its principal chose. A name gives no authority ([`docs/MODULE_CONTRACT.md`](../../../docs/MODULE_CONTRACT.md), "A process from a disk").
- A module is not built for a host test: each decision that a test must break lives in a package.
- A contract package imports no support package. The site reads the table of the context slots and the recorded grants from `src/library/support/system/grants.odin`, and the role of each process from the table `process_roles` of `src/modules/system/root/roles.odin`.
- A module is no package: the tool, the site and a host test read the source of the table, not the compiled table.

## The chosen form

**The contract** is the package `modus:contract/root_ring`: `Root_Command`, the enumerations of its words, the border procedures, the table of the senders, the table of the writers of the error records, the decision of the dispatch and the name tables. The root service, the console and the processes that send a command agree on it. It holds no kernel operation, so it is a contract and not a part of `system`.

**Three steps for each record**, in this order. The first two are one pure procedure of the contract, `dispatch_decide`, which a host test and the fuzz target `root_ring` call with any word and any role; the root service (`src/modules/system/root/root_ring.odin`) runs the third only when the decision says `Command`:

1. **The border.** `command_of_word` reads the kind. A word that names no command, and `None`, get `Unsupported` with the word, and nothing runs.
2. **The sender.** `sender_allowed` reads the table `ROOT_COMMAND_SENDERS` with the start grants of the sender, never its name. A process receives a root ring only with a start grant of `ROOT_RING_GRANTS` (Root_Ring, Connect, Principals, Debugger). A refusal gets `No_Grant` before any other check, so a process learns nothing of a command that it cannot send. For `Connect` with the grant Connect and not Root_Ring, the decision also needs the fact that the list of the services of the role names the service; the root service computes it from the role (`role_may_connect`) and passes it.
3. **The command.** One case of a whole switch runs it. The table `ROOT_COMMAND_REFUSAL_WRITERS` of the contract says who writes the error record of a refusal: the dispatch, from the name of `values[0..4]` and the word of `values[4]`, or the procedure of the command, whose values hold a hash, a nickname or a key, or whose cause only it knows.

**The role of a process** is one row of the table `process_roles` (`src/modules/system/root/roles.odin`): the name of the process, its start grants, and the other terms of its role (the services that it can connect to, the blocks of its private store, the log with Give, the size of its terminal, a start on demand), with the reason of each in the comment above the row. Each module of the boot image with an entry has one row, the parts of the system that the root service starts itself too (the grant System_Part), and a process with no grant has a row with no grant. The tool keeps the table whole: before each build, and before the site, it reads the rows with the parser of Odin and refuses a module of the boot image with an entry and no row, a row that names no module of the boot image (a disk process, the root service, a name of no module), a module with two rows and a grant that is no start grant (`tools/modustool/process_roles_check.odin`). It also reads the list `system_part_names` beside the table, and refuses the grant System_Part on a row that the list does not name, a name of the list with no row, and a part of the system whose row is not System_Part alone (with Serve for the compositor) with no term: the debug access refuses a part of the system by that grant, and the starter of a part gives no handle of another grant. The role is read one time, at the start (`role_of`), and kept in `Started.role`. Each rule after the start reads `Started.role`: the sender of a command, the grant of a connection, the debug access, a replacement. A disk process has the role of the row of its nickname in the disk grant table: the grant Store at most, so no root ring. What changed: the grants were a switch `grants_of` and the terms a second table beside it, so a reader of a role read two places, and a module that no case named had the zero role in silence.

**The context slots** are one table: the `GRANT_` constants of `src/library/support/system/grants.odin`, for the handles 0 to 13 and the values that the root service and its process agree on. Two roles share a context slot only when no process holds both. Each starter of the root service writes each handle with `system.grant_put`, and each value with `system.value_put`, `system.values_put` (a value of several words, written whole or not at all) or `system.range_mapped_put` (the bit of a fixed range). Each one refuses a place that is taken already and writes nothing there; `grant_put` also refuses the slot of the budget, which the loader writes, and `value_put` the indexes of the seed, of its strength and of the fixed ranges, which `random.values_with_seed` and `range_mapped_put` write. The first refusal is kept in the record that the starter builds (`Context_Refusal`), and the starter reads it once, before the start (`context_refused`): a refused write stops the start with one line that names the slot or the index. This holds for the start of a process by its name, a disk process, a terminal, and the fixed starters: the input service, the compositor, the device services, the TPM service, the font service and `shortage`, each with its own layout (`pci.GRANT_`, `tpm_service.SERVICE_`, `INPUT_GRANT_`, `COMPOSITOR_GRANT_`). A support package that reads a slot names the constant of the table (`terminal.GRANT_RING :: system.GRANT_TERMINAL_RING`). A contract package keeps its number, and the root service checks it against the table with `#assert`, so the build stops when the two differ.

**The `unlock` of the root service** is one record, `Unlock_Run`, with one stage: Stopped, Starting, Running, Stop_Asked. The stage says when `start` takes the name `unlock`, whether a stop counts toward the bound of its restarts, and whether a reader of the records sees a principal that is created.

## The refused forms

- **A cast of the kind, then a `#partial switch`.** A word past the last member became a member that does not exist, and a new command with no case compiled and answered `Bad_Operation`.
- **The role read again from the name at each command.** The nickname of a disk process is a name that the principal chose: a rule by name is a rule that a name can meet. The rule had to rely on a refusal of the nickname at its start.
- **One boolean expression for the sender.** It named each exception in one line, and the reader could not see which grant sends which command.
- **A chain of `command != ...` for the record that the command wrote itself.** A new command that writes its record and is missing from the chain had its record written over.
- **The table of the context slots in `src/library/contract/root_ring`.** The contract packages of the readers would import it, but the site reads the table of `system`, and `system` already names the slots for the support packages.
- **A table of the roles indexed by an enumeration of the modules.** The compiler would then refuse a missing row, but the enumeration would be a second list of the modules beside `module_builds`, which the tool would have to generate or check; the check of the tool against `module_builds` is the one list.
- **A default row for each other module.** It is the form that the table replaced: a new module got the zero role with no line that said so.
- **The grants in the source of each module.** A module would state its own authority; the root service is the one that decides it, and a reader finds every role in one file.
- **A return value of each giver of a page in place of the refusal record.** Each giver (the date page, the glyph caches, the debug image) would need a result, and each caller a check; one record that the starter reads once covers them all, and no write can be forgotten.
- **The dispatch tested only in a machine.** The decision of the border and the sender reads no state; in the module, a host test and a fuzz target cannot call it.

## Subtle points

- **The order of the steps is a rule.** The border comes first, then the sender, then the command. A refusal of the sender never says whether the name exists.
- **A disk process has no root ring.** The test that breaks the design first is a disk process whose nickname is the name of a privileged process (`console`, `unlock`, `remote`), which sends each command: `root_ring_test.odin` tries each start grant outside `ROOT_RING_GRANTS`, alone and together, and each command is refused.
- **The terminal text is the handle 4.** It was the handle 7, which is the call ring of the private store: a role with the grants Terminal and Store would have lost its store. The log service, the one holder of Log_Records, has a window.
- **The error record of `Machine_Seal` with Secure Boot off** is `Refused` with the unit Principals: the general rule of `No_Right` no longer comes before it. `Machine_Passphrase` never reads Secure Boot, and its records did not change.
- **The records of a refused `Replace`** that the state explains (`by` past the entries, a name of no module, a module that replaces itself, a full table, no grant Replace) are the pure procedure `root_ring.replace_refusal`, which a host test calls; a refusal of a signed row is written by `replace` itself.
- **One mapping from a role to its handles.** `root_ring.role_handles` gives the handles of a role, and `system.ROLE_HANDLE_SLOTS` the context slot of each. The start writes a handle by that mapping only, and refuses a handle that the mapping does not give, so the test of the tool that reads each row of `process_roles` checks what the start does.
- **The compositor writes its framebuffer slot once.** It held the framebuffer of the firmware, then the screen pages over it; a checked write takes one handle, so the start chooses first and writes once.
- **The terms of a row hold no comment.** The site shows the terms as the source writes them, on one line; a comment inside them would show as code, so the reader refuses it, and the reason goes above the row.
- **A row with no grant reserves no nickname.** A disk process does not take a nickname that `process_roles` gives a grant or a term (`role_names_the_process`), as the name would carry an authority that its principal did not give. A row with no grant and no term carries none: a nickname of a module of the boot image is still refused for that module, and a nickname of a module that this image does not hold (`shortage` on a normal image) stays free, as before the one table.
- **The layout of a device service before the device.** The start of a device service tries each slot that its layout can take (`pci.service_context_trial`, with the ring of its contract) before it arms the device: a refusal leaves the device with no bus master and no message interrupt. Each real start takes a part of those slots.
- **The context of a terminal in its package.** `terminal.context_of` writes the context of a terminal, so a host test reads the layout that the root service starts it with; the decision of each starter, `system.context_refusal_of`, has its host test too. The other starters (the input service, the compositor, the TPM service, the font service, `shortage`) write a few slots of their own layouts in the module, which no host test builds.
- **The name before the border.** The dispatch unpacks the name of `values[0..4]` before the decision, as `Connect` needs it for the list of the role. The unpack reads no state and the decision reads only whether the list names it, so a refused record still learns nothing.
- **A nested start never takes the place of a start that runs.** `start_place_take` marks the place that it takes (`Started.reserved`) before any step that can start another process, such as a service that starts on demand at the connection to the private store; each search of a free place skips a marked place, and `release` clears it.

## State

Built: the package `root_ring` with its host tests, the dispatch in three steps with the pure decision `dispatch_decide` and the fuzz target `root_ring` ([../infrastructure/fuzzing.md](../infrastructure/fuzzing.md)), the role in `Started.role`, the one table `process_roles` with its check before each build and its reader of the site, the table of the context slots with the checked writes of the handles and the values for each starter and their host tests, the stage of `unlock`.
