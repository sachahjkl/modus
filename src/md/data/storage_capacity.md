# The capacity of the data disk: its size, its stores, its names and its trees

The storage service uses each block of its device, holds thousands of stores on one disk, takes names of 255 bytes, freezes folders of any size, commits a change of any size in one commit, and opens a disk larger than its memory. The guide is [`docs/STORAGE.md`](../../../docs/STORAGE.md), "3. The format on the disk".

## Purpose

The format `STORAGE4` had four fixed caps that a person meets on the first day: the service used the first 1 GiB of any disk, a disk held 60 stores (each process has one), a name had 64 bytes, and a content tree held 512 entries (a whole-store snapshot 128 objects, a history 64 snapshots). Each was a constant of the code, not a budget. This file records how each cap became the device, a budget, or a bound that real use does not meet.

## Constraints

- **A loss of power leaves the state of one commit** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "9. A storage engine with one private store per process"). Each new block follows the rule of copy on write, and the tool checks each image that a loss can leave.
- **Memory is supplied by the caller** ([`docs/PROPERTIES.md`](../../../docs/PROPERTIES.md), "14. Memory is supplied by the caller"). A table whose size follows the disk is memory of a budget, never a static array sized for the largest disk.
- **No backward compatibility.** The format changes in place: `STORAGE7`, `MODTREE2`. An older disk is not read, and the open refuses it whole: it never takes it for a new disk to format.
- **A store is named by a number in the tables of the service** (its owner of each block, its counts, its damage). That number must be stable while the service runs.

## The chosen form

**The disk is the device.** The service reads the count of blocks of its device and binds the tables of the open to memory of that size (`storage_mount.state_layout`, `state_bind`): for each block a count of names (4 bytes), an owner (2 bytes) and three bits (in use, wrong, damaged under). A disk of 64 GiB costs 102 MiB of these tables. The service creates that memory from its budget; a budget that pays less gives the tables of half as many blocks, then half again, and the service uses the first blocks of the disk and writes `Disk_Larger_Than_Tables`. A root that names more blocks than the tables hold is refused whole (`Mount.larger_than_capacity`): a root is never opened in part. The search of a free block passes 64 blocks at a time over a word of the bitmap with each bit set.

**The stores are a paged table.** The root holds the pointers of up to 251 pages of the store table; a page holds 63 cells of 64 bytes, each one store: 15 813 stores on a disk. A store keeps its cell for the life of the disk, so its number (page and cell) is stable: the owner of each block, the counts and the flags of the open and of the service are indexed by it. A commit changes one store, so it writes one page again to a free block, after the last change of the cell's count, and the root names the new page. A page is named by the root only, not by a store: its block is outside the counts of the stores (`STORE_TABLE_OWNER`), so a limit of a store never pays for it. A page with a wrong check damages its 63 stores only; the service makes no new store in it.

**A name has 1 to 255 bytes**, as in the other file systems, in a key of 256 bytes so that each record of a node stays aligned on 8 bytes. A leaf holds 11 entries and a branch 14 children; the B+ tree holds 10 levels. A log fact names an object with a text view, whose long text goes in the out-of-line area of the fact.

**A content tree has entries of variable length** (`MODTREE2`): the kind, the length of the name, the name, the hash. A node holds up to 4096 entries, about 1.2 MB with names of 255 bytes, a sixth of that with short names. A lookup walks the entries in their order and stops past the name: its check already walks them.

**Pending changes are a pool of each connection.** A connection that writes a range takes, at its first change, a pool of its own: arenas of the memory of the service, the first of 2 MiB of reservation, each next one twice the one before up to one memory object, so a pool past 1 GiB takes several. A pool holds at most the limit of blocks of its store in pending blocks: a change past it could never commit (`Over_Limit`, unit `Pending`). The blocks of a pool are found by an index of their object and place, which doubles at half use. One connection that writes a large range takes no room of another: each pool has its own memory, and a pool ends, with its memory, at its commit, at `drop_pending` of its last object, or at the end of its connection.

**A commit is sized to its changes.** The fixed tables of a plan (4096 writes, 262 144 counts, 1536 object nodes) hold a commit of one call region and the work of the trees. The commit of pending changes adds, in the memory of its pool, tables of the room of its changes (`plan_room_of_changes`): the object nodes that its changed blocks can copy, at most one for each changed block on each level and never more than the nodes of the level (`block_tree.slots_needed`), their writes, and the counts of the blocks that they name and release. The nodes come in pages of 64, so no table of a large commit is one piece of memory. The tables go back to the pool after the commit (`pool_rewind`), and the plan takes its fixed tables again before the pool can end. The counts of a commit are one table of one memory object: 2^26 places, about 64 GiB of changed blocks in one commit.

**A version reads in pieces.** `version` takes an offset and gives the bytes from it up to the end of the state or of the call region; the client reads a version larger than the call region piece by piece. A generation names one state that no commit changes, so the pieces are of one state.

**A large state is released in steps.** The release of the last name of a state walks the nodes that lose their last name, and counts each block that it frees: a state of 1 TiB would pass any table of one commit. The commit first counts, with no change, the names that the release changes (`storage_release.release_names`): the root, each child of a node that loses its last name, and the children under it; inside one state a node has one name from its parent, so the count is the count of the release. A version that shares most of its nodes with the state that stays changes a few names, whatever its size, and goes in its commit. When the names pass the room left in the counts of the commit, or half of its staging less the leaves that it touches (counted in a set of the plan), the state goes to the removal queue. The commit gathers such states in release lists of 127 (`Release_List`), one block each, chained (a list names the next one), under one entry of the kind `Release` for the commit: a commit that releases any count of large states makes one put in the queue. A wrong list drops its entry, at a step and at the open: the open of the form Tables counts none of its states, and the commit of the step that drops it starts a recount of the count tree (below), so their blocks are free in both forms. Each step of the queue is one commit (`internal:storage/storage_release`), which frees the states of the first list in their order, several in one step, and writes the list again with what is left; it frees blocks in the order of the blocks of data, at most 65 536 names and at most a quarter of its staging in leaves, a block counted as one leaf, a subtree that goes whole as one leaf for each of its blocks; it keeps a cursor in the entry: the first block of data that no step has freed. A node that another state names too is one name to drop, whatever its size; a node whose blocks fit the room of the step goes whole; a node that holds the cursor is walked again by the next step, and the room of its own name is taken when the step enters it, so its name goes with its last child. The open counts a queued state from its cursor: no name for a child whose blocks are all before it.

**A folder of more than 4096 entries is a tree of several nodes.** Its entries, in their order, are cut into nodes of exactly 4096 entries, the last one with the rest. Each node is a `Part` of a node above it: the first name under it and its tree hash. The parts are cut the same way into nodes of exactly 64 parts, up to one root of 2 to 64 parts; four levels of parts hold 2^36 entries. The cut depends on the count only, so one folder has one form and one hash, and a folder of at most 4096 entries keeps its one node and its hash. The freeze writes each node of entries when one more entry comes, and keeps the parts of each level on a stack: the levels of one tree are in order on the stack, the higher deeper, and a level is on top each time a part comes to it. A lookup goes down the parts and checks the form: a node before the last of its level is whole, and starts with the name of its part.

**The counts of names live on the disk.** Format `STORAGE7` (`STORAGE6` had no record of the leaves to recount). The root names a count tree (`Root.counts`): leaves of 512 blocks, each with its count of names (4 bytes) and its owner (2 bytes), under directories of 128 children; a child holds the block, the check and the count of free blocks under it (8 bytes each), and a missing child is a part of the disk where each count is 0. Each block of the count tree has the count 1 and the owner `COUNT_TREE_OWNER`. A commit, when its plan is final, makes the new version of each leaf that its counts change, then of their directories, each to a new block; the new blocks and the blocks that they replace change the counts of other leaves, which the commit adds, until no leaf is added (a new block is taken first under a leaf that the commit writes already). The new leaves and directories are written before the root, as each block of the commit, and the root names the new tree: a loss of power leaves the counts of one commit.

The open has two forms. When the tables of the memory hold the disk, it walks each store as before, which checks each block, and compares the leaves of the count tree with its counts: a leaf that differs is written by the next commit, with a fact on the log. When they do not hold it and the root names a complete count tree, the open does not walk the block trees: the counts come from the leaves, through a cache of up to 4096 pages in the memory of the service, halved down to a page of each level while the budget refuses; the hash index comes from a walk of the trees of the stores, which reads entries, not blocks of objects, each node once (a set of the visited nodes of 128 places for each page of the cache, then a bound of one read for each block of the disk), so a disk whose trees name one node again and again ends its open, with its store faulty; the counts of each store are those of its cell and its store block; a wrong block is found at its read and kept in a set of 16 places for each page of the cache (32 768 blocks with the largest cache), past which the service stops its changes (`Damage_Set_Full`). A leaf with a wrong check is kept as wrong (16 at most; more stop the changes): the search of a free block passes it, and a commit that changes one of its counts is refused (for the read: the store stays trusted). The service then enters the repair state.

**The repair state.** Reads are served; each change is refused with `Busy` (-14), unit `Count_Repair`, whose record gives the stores that the walk ended and the stores in all. The client of the storage service (`modus:storage`, `call`) makes such a call again every 100 ms, up to `REPAIR_WAIT_BOUND_MILLISECONDS` (60 s), so a program sees its change pass after the repair; past the bound it gets the refusal, whose sentence gives the progress. No commit runs, and no step of a removal. The repair counts the names of the blocks of the wrong leaves again, in memory, by a walk of each store from the roots of the last commit (the store blocks and the pages of the store table that the service holds, never the root that the open read). A run counts at most 128 leaves: the leaves of a wrong directory come whole and first, then the other wrong leaves; the others wait for the next run. The walk runs in steps of at most 4096 reads and writes (nodes, versions, lists and pages of the scratch), one step after each round of calls, so a service that is never idle still ends its repair. Since nothing changes between two steps, the walk resumes by its path in the trees, its place in the entry (the current state, a version, a state of a release list), and the first block of data of the state that it did not count yet. In a tree, the walk keeps the path from the root to the node of its last entry: each node is read once, and the entries of one leaf share its read (a folder of 500 000 entries in 48 954 nodes: 48 954 reads and writes, in 12 steps; the host model, one run); a tree inside it reads its path again once, when the walk comes back to it. Each node that it walks, of a tree or of an object, it records in a scratch: pages of one bit for each block, under directories. A node of several names is counted at each name and walked at the first only, whatever leaf of the count tree it is in, so a store whose trees name one tree again and again ends its walk, and no set of visited nodes bounds it. When each page of the scratch fits in its 32 frames (a disk of up to about a million blocks), the scratch stays in memory; else its pages go to free blocks that the count tree gives (never in a wrong leaf), taken in their order, written in place with no flush. Each page carries a header with the run and a random word drawn at the start of the service: a page that the device did not keep reads with another header, and the run fails as on a failed read. The root never names the scratch: a loss of power loses it, and the next open that reads the wrong leaf starts the repair again. A wrong node of a tree of a store ends the walk of that store: its blocks under the node are not counted, as at an open, the store takes no change (`Count_Repair_Store_Damaged`), and the walk goes on with the next store. A failed read or write of the device ends the run; the next run starts after the next call (`Count_Repair_Device`, once). A disk with no free block for the scratch ends the run too: the service takes changes again, and the next run starts after the next commit (`Count_Repair_No_Room`). After the last store the repair counts the pages of the store table and of the count tree; then one commit, which changes no store, writes the counted leaves, and the service leaves the repair state (`Count_Leaves_Repaired`). The free search of that commit reads the repaired leaves from the memory of the repair, so a disk whose only free blocks are in them still takes the pages of the commit. Leaves found wrong during the run wait for the next run.

**A wrong directory of level 1 is made again.** Its pointers to its leaves are lost, so each leaf under it is wrong: the repair counts all of them in one run, and the commit of the repair makes the directory again from them, with no read of the wrong page, and refuses if one leaf under it is missing. The old leaves, which no page names now, keep their names where a trusted leaf holds them: lost blocks, never a block named twice. A wrong directory above level 1 has more leaves than a run holds: its damage is not known whole, and the service stops its changes (`Damage_Set_Full`).

**A recount frees the blocks that a release could not read.** A release that meets a wrong block leaves names that no state holds (dead names): a wrong list drops its entry with the states in it and in the lists after it, a wrong node of a state of a release loses its name with the blocks under it, a commit that releases a version with a wrong block under its root releases nothing under that block, and a version index or leaf with a wrong check is dropped with the states under it. No step reads those blocks again, and only a count of their leaves finds them. Which leaves they are in is not known: a list with a wrong check gives no root that can be trusted, and the blocks of a state lie anywhere on the disk. So the commit that leaves dead names (`plan.release_damaged`, `plan.dropped_versions`) writes in the top directory of the count tree the leaves to recount (`Count_Directory.leaves_to_recount`): each leaf of the disk, as the count of the last leaves, so that a recount goes from the first leaf to the last. The record and the dead names are in one commit: a loss of power leaves both or neither. The log says the blocks that the commit keeps by dead names, at least: the blocks under a wrong node, as its parent counts them; a wrong list or a dropped index gives no count.

**A recount starts when the space is needed, or on a request.** A dead name is a count too large, never too small: its block stays in use, the safe side, and a commit changes such a count as any count. So nothing starts at once. A recount starts when the free blocks of the disk, as the top directory counts them, fall under a sixteenth of the disk (`RECOUNT_FREE_SHARE`, a plan value: under it the disk nears the refusal `Full`, and a walk of each store is worth the space; above it the walk costs and gives nothing that a change needs), or when a process with the start grant `Recount` (the console) calls the export `recount`: a recount refuses the changes of every caller, so acting for a principal is not enough, as for the erase of versions. It starts when no call and no removal waits; the open of the form Count_Tree says the leaves that wait (`Count_Recount_Waits`). It starts only when the disk has a free block for each page of its tally and of its scratch that leaves the memory: a page for each leaf in use from the first leaf to recount, which the top directory bounds by the blocks in use under each child. With less room it does not start (`Count_Recount_No_Room`), and the changes go on; a walk that finds no room for a page, or a commit of the write that finds no block, stops the recount (`Count_Recount_Stopped_For_Room`), with the record on the disk right and the changes back. After either, no recount starts until the free blocks grow: a person who removes files on a full disk never gets `Busy` for a walk that cannot end. A request ends with a failure of its recount, so a walk that fails on the device does not start again for it. A walk that meets a wrong block when the set of damage of the form Count_Tree holds no more stops (`Count_Recount_Damage_Full`): the set does not fill, so the changes go on, and no recount starts until the next start of the service.

**A recount is one walk.** It is a run of the repair whose walk counts every name of the blocks of the leaves to recount, not 128 leaves: each name adds one to its block in a tally, a scratch of one page for each leaf (the counts and the owners of 512 blocks, the form of a leaf), under directories, on free blocks of the disk as the scratch of the walked nodes, which the root never names. Its pages stay in memory on a small disk. On a large one, a name to a page that left the memory costs a read and a write: on an aged disk of the host model, whose blocks lie at random, the tally costs 1.02 reads and writes for each name with its 32 pages over 64 leaves, and 1.86 with 4 pages, as on a disk of 8 times more leaves. So the walk keeps the names of a step, up to 16 384 (`TALLY_NAMES_MOST`, an inline capacity), sorts them by leaf, and in their order inside a leaf so that the last name of a block gives its owner, then adds them: each page is touched once for a sort, 0.02 reads and writes for each name on that disk. A full buffer is sorted inside the step, and counted (`Count_Recount_Sorts_Full`). One walk then costs much less than the runs of 128 leaves, one whole walk for each 65 536 blocks of the disk. During the walk the service serves reads and refuses each change with `Busy`, unit `Count_Recount`, whose record gives the stores walked and the stores in all; the client makes the call again as for a repair, and past its bound gives the refusal, whose sentence names the recount and its progress. Then the run compares, one directory of level 1 at a time, each leaf of the tree with its tally: a leaf that no directory names and that no name reached is passed with no read, and no free count is trusted. The leaves of one directory that differ go in one commit, with the leaves still to recount after that directory; a directory where no leaf differs makes no commit. The changes stay refused until the last directory: a commit of a change between two of them would make a tally stale. The pages that each commit of the run takes and frees change the tallies of the leaves after its directory, as they change the leaves of the tree. When no commit of the run wrote the last record, the next commit of any kind writes 0; a loss of power before it makes the next recount walk again for nothing, never free a block in use. A loss of power during a run loses its scratch, not the record: the next recount goes on from the first leaf that no commit wrote. The walk records each wrong node that it meets as a wrong block, so a later step of a release never trusts it. The open of the form Tables counts by its walk, so its tables hold no dead name: once each leaf that differs is written, its next commit writes 0, unless a commit of its own left dead names since its open.

A commit writes at most 1024 pages of the count tree; a commit of pending changes takes from its pool a staging of the room of its changes. A step of a release stops when it has changed a quarter of the staging of its commit in leaves.

The open tries the tables first, of the size of the disk, halved while the budget refuses. When they do not hold the root, or a new disk, it binds the form Count_Tree: the new memory is made and bound before the memory before ends, so a refusal keeps the binding before; a budget that cannot hold both ends the tables first, as their open refused and they hold nothing of use; a budget that pays neither refuses the open whole. A root that a form refuses and that is the newest valid root refuses the disk whole: an older root would lose the commits after it. The levels of the count tree follow the blocks that the root names, not the device, so a device that grew keeps the tree of its root. The blocks outside the stores (the pages of the store table and of the count tree) change the counts outside the count of a store, with their own owner, and the erase of versions writes no zeros over them.

**A snapshot history is memory of its caller**: a table of records and one pool of objects that the snapshots share. The count of snapshots and of objects is the memory that the caller gives; a full table or pool is a refusal with no change. A diff is read in pages from a count.

## Refused forms

- **A B+ tree of the stores.** It has no bound at all, but a store then has no stable number: each change of the tree moves the cells, and the owner of each block, the counts and the flags would need a key by name. The paged table keeps one number for each store at the cost of a bound of 15 813 stores, past any real use of one disk. Refused for now; a disk past that bound would need it.
- **Static tables sized for the largest disk.** A static array for 1 TiB is gigabytes of the module of the service on every machine. Refused: the tables follow the device.
- **Counts in a fixed region of the disk, written in place in two copies.** No tree and no recursion of the counts of the counts. Refused: a copy written by a commit whose root the disk did not keep has the generation of the next commit, so the open cannot tell it from a valid copy without a record that the root names; the copy on write of a count tree needs no such record.
- **An incremental repair beside the writers** (counted leaves only, a walk that resumes while commits run, renames and removes of trees refused during it). Refused: its rules of consistency kept leaking. A commit between two steps can move the name of a root by the hash index or by a clone, so the walk counts nothing under it or counts it twice; and its counts come from a view of the store that commits change under it. The recount with the changes paused has one rule: nothing changes while it walks.
- **A repair that passes the stores that the open found faulty.** A hostile store would then cost nothing. Refused: a faulty store takes no change but serves its reads, and its blocks in a wrong leaf would get the count 0 and go to another object under it. The record of each node of a tree in the scratch ends the walk of a hostile store as well.
- **A recount of the leaves that the states of a wrong list touch, and of no other leaf.** A run of the repair would count only those leaves. Refused: they are not known. The bytes of a list with a wrong check are not a list; a root read from them that has a valid check still gives the leaves only by a walk of its whole tree, and a state of a terabyte touches most leaves of the disk anyway. A leaf that such a guess misses keeps its blocks for ever.
- **Blocks that a wrong release keeps, in use until an open of the form Tables.** No work, the safe side. Refused: a disk larger than the memory never opens in the form Tables, so the blocks are lost for the life of the disk.
- **The record of the recount in the root.** Refused: the root has no free byte, and a field there costs a page of the store table, 63 stores. The top directory has 1000 bytes of padding and is written by each commit that changes a count.
- **A recount in runs of 128 leaves, each run a walk of each store.** The repair of a wrong leaf, with no new scratch. Refused: on a disk of 32 GiB it is 128 walks of each store, with the changes refused for hours. The 128 stays only for the repair of a wrong directory, whose 128 leaves come whole: a format property.
- **A tally page touched at each name, with no sort.** No buffer, no sort. Refused: on a disk with many more leaves than pages in memory, each name costs nearly a read and a write (the measure above).
- **A recount that starts with the room that it finds.** No estimate. Refused: on a full disk its walk refuses the changes, then ends with no room, again and again, while a person removes files.
- **A recount that starts at once.** The dead names go soon. Refused: they only keep blocks in use, the safe side, and a walk of each store refuses the changes; the space is worth that walk only when the disk needs it, or when a person asks.
- **The changes taken between two commits of the write of a recount.** Refused: a commit of a change frees and takes blocks in leaves that the run did not write, and their tallies would not see it. The commits of the run itself are the only ones, and each of them changes the tallies of the pages that it takes and frees.
- **A repair of wrong leaves that counts every block into a count tree of its own on the disk.** (The recount takes a tally of every block, outside the tree, and writes only the leaves that differ.) It would make a whole new count tree, but each name changes a leaf of that tree, in the random order of the walk, and the commit writes the whole tree. Refused: the counts of the wrong leaves fit in memory (16 leaves of 512 blocks), and the scratch needs one bit for each block, not six bytes.
- **A walk at each open with the counts in a swap region of the disk.** The format stays, but the walk names each block in a random order: on a disk of terabytes it reads and writes the swap region once for each name. Refused: the open of a large disk must not walk.
- **One shared pool of pending changes** (1024 blocks and 16 objects for all connections). Refused: one connection that writes a large range took the room of each other one.
- **A fixed stride of 289 bytes for each entry of a content tree.** Binary search with no walk, but a folder of short names costs six times its bytes on the disk and on the wire. Refused.
- **Cuts of a folder by its content** (a boundary where the hash of a name says so). One new entry changes one node, not each node after it, but the form depends on the hash of each name and a node has no bound of size. Refused: a freeze writes each node of the folder anyway, and the cut by count is one rule with a bound.
- **The removal of a large object in one commit with a larger table of counts.** One rule, no queue, but the table follows the object: 16 GiB of memory for an object of 4 TiB. Refused: the steps bound the memory of a commit.
- **A history with its tables inside its record.** The record of 64 snapshots of 128 objects was 2.4 MB with names of 255 bytes, whatever the use. Refused: the caller gives the memory.

## Subtle points

- **The walk of a run names the block of a wrong list, and none of its states**, as the open of the form Tables. A run before the step that drops the list leaves it one name, which the drop takes; a run after it finds no name. Either order gives the counts of the commit after the drop.
- **The commits of the write of a recount take no block under the scratch.** The two scratches take free blocks in their order; a commit of the write takes none before the first block that they did not take, as a page of the tally there is still read.
- **The tally takes the changes of a commit after it.** After the install and the end of its repaired leaves: before, the free search reads those leaves from the memory of the run, and a new page of the tally could take a block of the commit.
- **The write of a recount trusts no free count.** A directory can name a free count that its leaves do not hold; the run compares each leaf that a directory names or that a name reached, and passes only a leaf that neither holds.
- **The 128 leaves of a run of the repair are the leaves of one directory of level 1** (a format property): a wrong directory comes whole, and the write of a recount commits one directory at a time.
- **The page of a commit is written after the count of its cell is final.** `plan_commit` changes `used`, then writes the page with its check: a page written earlier would carry a stale count under a valid check.
- **The block of the page before is freed after the root**, as each block that a commit stops naming, but outside the change of the reference counts: the erase of versions writes no zeros over it, as it holds names and counts, no byte of an object.
- **The open counts a page of the store table as a block of one name.** A page named two times is a fault of the engine, as a store block named two times.
- **The hash index is sized by roots**, not by blocks ([hash_index.md](hash_index.md)).
- **A dying node gains no name.** A node that a release cuts has one name, from its parent: only a root of a current entry can gain a name (by the hash index), and such a root has the name of its entry. So a step finds a node that no other state names whole or in part, never shared after a step cut it.
- **The tables of a commit go back before its pool ends.** The commit takes the fixed tables again (`plan_tables_fixed`) before `pool_rewind`; a later `plan_reset` clears the counts through the tables that it holds, and the memory of a pool is gone after its end.
- **A part has the first name under it**, not the last: a lookup takes the last part whose name is at most the name, so a name before the first part is absent with no read.
- **A node of parts stays small**: 64 parts of 289 bytes. A reader keeps one for each level and one node of entries.
- **The size of the nodes is a parameter of the freeze and of the lookup** (`immutable_tree.Folder_Shape`): the service passes the bounds of the format (`FOLDER_SHAPE`, 4096 and 64); the host tests pass nodes of 8 entries and of 8 or 2 parts, so that folders of a few dozen entries take each path of the cut and the bound of the levels in milliseconds. The test at the size of the format is opt-in (`-define:FULL_SIZE_FOLDERS=true`): its B+ tree of 262 145 entries takes minutes.
- **The shape of the scratch is a parameter of the repair** (`Scratch_Shape`): the service takes the size of the format (32 512 bits of a page, 508 children of a directory, 32 pages in memory); the host tests take pages of 8 or 64 bits, directories of 2 or 4 children and 1 or 2 pages in memory, so that a disk of a thousand blocks has several levels of directories and its pages leave the memory.
- **The lists of the releases of one commit have a bound that no commit reaches.** A commit releases the versions of the leaves of version indexes that it holds (300 leaves of 85 versions) and the current states of its entries: `RELEASE_LISTS_MOST` lists of 127 hold them all, so a count of large states never refuses a commit.
- **The guest disk image has its own bound of a path**: a path of a file of the image holds one name of the store whole (255 bytes); a mount path keeps its 124 bytes, which the wire of a mount holds.
