# The intent of modus

This folder follows <https://srcmd.org>. It records why each part of the system has its form: the purpose, the constraints, the chosen form, each refused form with its reason, and the subtle points. It is written for a developer or an agent who starts work on a part.

Read this file first. Then read the file of the part that you change. Change that file before you change the code.

## What this folder is not

- It is not the documentation. A guide of `docs/` says what the system does and how to use it, and the site publishes it. An intent file links to a guide; it does not repeat it.
- It is not a record of who decided what, and when. Git keeps that.
- It is not a log of the work. A review, a log and a measure of one run do not go in the repository.
- It is not a plan. The planned work is in `ROADMAP.md`; a plan in progress goes in a folder `tmp/` that git ignores.

## The system on one page

`modus` is an operating system for x86-64, written in Odin, that runs on one fixed machine: QEMU with virtio devices, UEFI firmware and a TPM. Its kernel is `modulus`, and its language and runtime is `lex`. The 25 properties of [`docs/PROPERTIES.md`](../../docs/PROPERTIES.md) are its rules. Each proposal is compared with them before any work.

**The kernel, `modulus`** (`src/modulus/`), is small, and its kernel operations are counted (the count is in [`docs/PROPERTIES.md`](../../docs/PROPERTIES.md), "1. Small kernel with a small, counted interface"). A process asks for an operation with a command record in a ring of shared memory, one ring for each thread. The one kernel entry runs the records of the ring, then waits. The kernel holds the handle tables, the memory objects, the page tables, the threads, the scheduler with a closed set of strategies, the budgets, the fault ring, the control of a thread, and the entry of a guest processor, whose nested page table is the page table of a process ([features/guest.md](features/guest.md)). It holds no driver, no file system, no network code, no loader for imports and no text parser. Its check of a line of the log is a filter of bytes, not a text parser: it writes `?` for each byte of an invalid sequence of UTF-8, keeps no state and builds no structure, as the check of a process name does ([data/text_encoding.md](data/text_encoding.md)). It imports the contract packages and its kernel parts only: the pure packages in the folders under `src/modulus` (`iommu`, `acpi_processors`, `debug_exception`, `extended_switch`, `processor_counters`, `stolen_time`, `time_base`, `delivery_count`, `replay_filter`, `guest_rules`, `page_attributes`), with host tests, which the source library `modulus` names (`modulus:iommu`) and which no module can import.

**The contracts** (`src/library/modus/contract/`) are the records, the constants and the pure procedures that two bodies of code compile in so that they agree: the kernel operations, the module format, the ring, the draw and block and frame records, the system description. A contract package holds no kernel operation call and imports no support package. A format that only the kernel reads is not a contract, even when the hardware writes it: it is a kernel part. **The support packages** (`src/library/modus/`) are the code that two modules or more compile in, or that a program outside needs: `system` (the kernel entry, the rings, the loader), `interface` and `graphics`, `tcp`, `quic`, `storage`, `sentence`, `cryptography_primitives`. Together with `src/library/modus/contract/`, they form the public library `modus`, the one part of the sources that ships in the SDK ([infrastructure/sdk.md](infrastructure/sdk.md)). Count the owners of a package, the bodies of code whose chain of imports reaches it, not the files that import it: the tool refuses a support package with fewer than two owners unless its one owner is a module of the group `libraries`. **The internal parts** (`src/library/internal/<module>/`, `internal:storage/storage_tree`) are what one module alone compiles in, with its host tests: the storage service, the console, the compositor, the manual and other modules have them. The compiler refuses `internal:` in the kernel and in an outside module, and the tool refuses an internal part that another module imports. The design: [infrastructure/repository_layout.md](infrastructure/repository_layout.md).

**One code module** is the one format of compiled code. The same file runs as a process, serves as a service, loads as a library and runs sandboxed inside another process. A module describes each export in flat tables: the parameters, their types, their rights. From that description the console completes and checks a call, the manual shows a page, a call host isolates a call, and the loader checks a replacement. A module is named by the BLAKE3 hash of its file. An import names the hash of the imported file.

**The start.** The boot program (`src/boot/`, a UEFI application) checks the signed system description, measures into the TPM, loads the boot image and jumps to the kernel. The kernel starts one process, the root service (`src/modules/system/root`). The root service holds every grant at the start, and holds no order of the start: it starts one start policy, which reads a start list and asks for each other start, and a rescue start policy when that one fails ([features/start_policy.md](features/start_policy.md)). It starts each other process with the grants of its start grant set, serves the root ring (start, stop, connect, revoke, replace, debug), and keeps the table of the replacements.

**The modules** (`src/modules/`) are in four module groups: `system`, `libraries` (the modules with no entry that other modules import, as `drawing` and `cryptography`), `demonstrations` and `tests` (the test modules, which only a machine test starts). The group is the folder of a source, not a kind of file ([infrastructure/repository_layout.md](infrastructure/repository_layout.md)). **The processes** are each one module in its own address space, with only the handles that it was given:

- Device services: `block`, `frame` (the network device), `input`, `entropy` (the entropy device: bytes that the root service mixes into its generator), `tpm` (the TPM after the start: it seals the machine key, and the keys of a named principal with its passphrase, to the measure). The code of a device is a process.
- Shared services: `storage` (one private store for each process, versions, no save action), `network` (the multiplexer of one network device), `settings`, `log`, `manual`, `debugger`, `remote` (calls from another machine over QUIC, each for the principal that allowed the key of its client), `remote_display` (the screen for a viewer on another machine, and its keys), `processes` (a module file from the network into the store `module_files`).
- The desktop: `compositor` (the surfaces, the input, the bar, the palette), `terminal` (the window of a process that writes text), `console` (Lex in mode `console`: a command is a function, a result has a kind and a drawer).
- About fifty processes that each show one property: `rights`, `origin`, `budget`, `scheduler`, `fault_ring`, `tally`.

**Communication** between two processes is shared memory: a ring of records and, for bytes, a region. A call of a service is a record in a call ring with its arguments in a call region. No process parses the text of another.

**The tool** (`tools/modustool`) is the only automation: the build (incremental, in two steps for a module, reproducible), the machine tests under QEMU with a peer for the network, the checks of the sources, the site, the changelog, the news, the films. `nix flake check` and `modustool screenshots` are the full check: the machine test runs once, in the check of the flake, and `screenshots` takes its pictures and its logs from the store ([infrastructure/full_check.md](infrastructure/full_check.md)).

## The subtle points

These are the points that an agent gets wrong most often.

1. **Compare first, then build.** A proposal that contradicts a property or the design of an intent file is named as such before any work. Propose the nearest form that keeps the property. A property changes in the documents first, then in the code.
2. **The described export is the only border between two modules.** There is no second kind of import. A parameter that a description cannot carry (a slice by value, a record that holds an address, a procedure value) means that the border is in the wrong place. The count of the parameters is not such a sign: an export takes up to 12 arguments, past the six registers on the stack. See [api/library_modules.md](api/library_modules.md) and [api/call_form_arguments.md](api/call_form_arguments.md).
3. **A new right for a process is the last answer.** First look for the process that already holds the grant, and give it a new face. The palette gives no process a new authority: see [features/palette.md](features/palette.md).
4. **The policy is outside the kernel, the mechanism inside.** No code of a process runs on the path of the scheduler. A write that a process chooses the moment and the direction of must change no history that a strategy keeps. See [features/scheduling_policy.md](features/scheduling_policy.md).
5. **A count, an offset or a length from another party is copied, then checked.** A value is never checked once and read again from memory that the other party can change. This holds for a table of another process, a file and a packet.
6. **No queue drops a record in silence.** A full queue stops its writer, or it has a stated capacity and counts each refusal on the log. See [features/key_path.md](features/key_path.md).
7. **A test checks a condition. A time in a test only ends a hang.** Never assert a speed, a duration or a rate: print it as a measure. Never wait a fixed delay for a state: wait for the state. See [`docs/TOOLS.md`](../../docs/TOOLS.md), "The bounds of the tests".
8. **The hash of a module is its identity, and many things change it.** A change of an import changes the hash of each importer. A path of a source file is in a debug object, not in a module. Debug information must not change the code. See [infrastructure/debug_information_and_code.md](infrastructure/debug_information_and_code.md).
9. **The kernel never imports a support package or an internal part.** The compiler refuses `internal:` in the kernel, and the tool refuses a support package before each build. A kernel part (`modulus:iommu`) is the opposite border: only the kernel gets its source library `modulus`, so the compiler refuses it in a module, and the tool refuses it in each other file of `src/`. The kernel is freestanding: `"contextless"`, no allocator, no `fmt`. The build uses `-vet`: no shadowed local, no unused import. See [infrastructure/repository_layout.md](infrastructure/repository_layout.md).
10. **One term for one concept.** Define a term in `docs/glossary/`, in the file of its group, before its first use, and never use a word of its "Do not use" list. A name in the code is long and of complete words.
11. **A document that says what the code no longer does is a fault.** A change of the code changes, in the same commit, the guide, the glossary, the README and the intent file that describe it.
12. **A comment in a source gives the reason in words.** It names no number of a property, a choice, a step or a review finding, no identifier of a decision, and no date. A pointer to a guide names a heading that exists.
13. **No text over another text, and no cut text, in any picture or page.** A text has a box. Compute its width from the font before you place it.
14. **No backward compatibility.** Change a format in place and remove the old path.
15. **A client depends on a role contract, never on the module of its holder.** No code, test or step names the module that holds a role, compiles in its private part, or waits for a fact that only it writes, unless it tests that one holder. See [features/roles_and_contracts.md](features/roles_and_contracts.md).

## The rules of this folder

- **One file for one part.** `features/` holds a capability that a principal or a process sees. `data/` holds a format or a table. `api/` holds a border between two bodies of code. `infrastructure/` holds the build, the tests, the site and the layout of the repository. A folder exists only when it holds a file.
- **A file exists only when a design exists.** Do not write a file for a part that has no design to record.
- **Each file has a title of level 1**, then its purpose, its constraints, the chosen form with its reasons, the refused forms, the subtle points and the hazards, and a short state: what is built and what is left.
- **High signal.** Omit what the code shows. Keep a measured number only when it decided a choice. Do not keep a plan of work, a list of files to change, or the steps of an agent.
- **The form of today.** When a design changes, the file states the new form, with one line on what changed. It is not a history.
- **No name of a person, no role of the project and no date.** Git keeps who decided and when.
- **No number of a decision, a choice, a step or a review finding.** An intent file states the reason itself.
- **A pointer to a guide** is a link with the path of the guide from the root as its text, then the heading in quotes: [`docs/CONSOLE.md`](../../docs/CONSOLE.md), "8. The palette provider". The tool checks that the heading exists.
- **A link between two intent files** is a relative link. The tool checks that the file exists.
- **The name of a file** has lower case letters, digits and `_`, and ends with `.md`.
- **Simplified Technical English**, with the terms of the glossary.
- `modustool check` runs the check `intent_index_check`: the file index below lists each other file of this folder exactly once, and names no file that does not exist.
