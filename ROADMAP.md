# Roadmap

This file holds the planned work of modus. **Now** is the work that is in progress. **Next** is the work that is decided and comes after. **Later** is the work that is wanted and has no order. **Maybe** is what may be done one day and is not decided: each entry says the ways open and what each waits for. An entry leaves this file in the commit that ends its work.

## Now

## Next

- **The test image carries its own plan file.** The image of the tests ships a plan file carrying the budget rows for `limits` and `log_flood`, removing the fallback exception tables from the root service. [Design](src/md/features/module_budget_request.md)
- **Reclaiming orphaned encrypted store blocks after principal removal.** Deliberate principal removal cryptographically destroys the principal's key material, leaving its encrypted stores permanently unreadable; a later pass reclaims those unreachable store blocks on disk so repeated principal creation and removal never leaks disk capacity. [Design](src/md/features/several_principals.md)
- **The working memory leaves each module.** With the peak of each module read at its first state of work, its working memory becomes counted parts, start objects and children, so no floor holds a number that the hand writes. [Design](src/md/features/module_budget_request.md)
- **The script font set from an object cache.** A machine takes the set that its plan names from an object cache by its hash, as a large object, so a machine draws Hebrew, Arabic, the emoji and the ideographs with no disk that the tool wrote. [Design](src/md/features/script_fonts.md)
- **A machine case of a start refused as busy during the read of the script fonts.** A change of the root service then shows that a start that comes during the read is refused, and not lost. The case waits for a way to hold the read open from the test: with no such way, the start would have to fall inside the read, and the time of the read depends on the speed of the host. [Design](src/md/features/script_fonts.md)
- **The cache signing key authorised, and the first publication to the cache.** The deployment of `cache.modus.systems` names `resources/keys/cache_signing_key.public` in `--authorized-key`, and the next release fills the public object cache, which `cache-get cache.modus.systems:5010 test-recipe` then proves; until then the job `cache` of a release fails and the release is published. [Design](src/md/infrastructure/cache_publication.md)
- **Each wait for another process ends at its stop or at the hang bound.** A slow machine never turns a correct answer into a failure: each wait for another process ends when that process stops, or at the hang bound of an answer, never at a time tuned to a fast host. Left after the connection path and the service call/picker/load/roles bounds: the other root commands of the console (the default of `request_record`), `WIRE_ANSWER_LIMIT` and the limit of the palette provider; the waits of `debugger`; the mesh bounds of `remote`; `DISK_LOAD_CANCEL_BOUND_MILLISECONDS` of the root service; the wait of the GPU scanout of `compositor`; `quic_server.INFO_WAIT_MILLISECONDS`. [Design](src/md/api/call_ring_ready.md)
- **The deployed object cache upgraded before the next release.** The `cache-serve` of `cache.modus.systems` runs a build that knows the release pointers and serves the browser, so the next release puts its pointer and a reader browses what it put. [Design](src/md/infrastructure/cache_browser.md)
- **A machine test of the exact release boot image.** The machine of Secure Boot with the test keys boots the release boot image, with no test module, so the image that a release ships is the image that a machine test ran. [Design](src/md/infrastructure/release_image.md)
- **The service `recipes`.** A recipe names how each output is made, and `recipes.build` takes its realisation from the cache or builds it in a sandbox. [Design](src/md/features/recipes.md)
- **The roles of the plan of principal 0 measured at the start.** The set of the role holders that the plan of principal 0 gives before the start policy is measured, so an attestation sees which holders of the signed image ran. [Design](src/md/features/declarations.md)
- **Projects, `pins.lex` and the service `projects`.** A developer shares a project as a tree with `project.lex`, `pins.lex` and its sources, moves its inputs with `projects.update(kernel)`, reviews each moved input as one line of `pins.lex`, and builds one output with `recipes.build(kernel.tools)`. [Design](src/md/features/declarations.md)
- **A local realisation signed with the key of the principal.** A realisation that a build of the machine gives carries the signature of the principal that asked, so another machine that trusts that key takes it from a cache. [Design](src/md/features/recipes.md)
- **The collatz project built, cached and pulled on two machines.** A machine test builds `src/outside/projects/collatz` with `recipes.build`, starts its module from the store, publishes the realisation to an object cache, and a second machine takes it with `Cache_Only` and runs it with no build: the path that each next program copies. [Design](src/md/features/application_projects.md)
- **The stages of the C compiler run on modus, each a recipe.** The chain that `modustool c-self-host` proves on the host runs on modus: the module `c_compiler` takes a program of several sources, the assembler a workspace for the 295 KiB of code of `chibicc`, and each stage is a recipe whose output the next stage takes by its hash. A reader then knows that modus builds its own C compiler with no host. [Design](src/md/features/bootstrap.md)
- **The bootstrap from the seed, through the guest.** The chain of live-bootstrap runs in the guest builder from hex0 to the Odin fork, each stage a recipe, and its outputs are compared with the build of the host. A reader then trusts the compiler from a seed of about 500 bytes, not from a binary. [Design](src/md/features/bootstrap.md)
- **SQLite, Lua and zstd built by the C compiler of modus.** The modules of the three programs pass their tests today, built by the clang of the host from their pinned recipes; a machine of modus then builds each recipe with its own C compiler and runs its tests, so a database, a scripting language and the compression of the cache come with no host compiler. [Design](src/md/features/c_compiler.md)
- **A release image with no test module.** The release image holds no module of `src/modules/tests` and no row of the start grant sets of such a module, so a release never ships a test asker or the grants that it holds; today only the modules of one test image are kept out. [Design](src/md/infrastructure/releases.md)
- **A machine test of the end of a wide grant by a lock.** A lock ends a grant on a machine with its record in the collector, so that end runs once on a machine as the revocation, the time and a second connection do. It needs a principal other than principal 0, whose lock stops the console that drives the scenario. [Design](src/md/features/wide_grants.md)
- **The proof of a wide grant with no person.** A signature of a key of the principal on the host proves a wide grant on a machine with no one at its keyboard. [Design](src/md/features/wide_grants.md)
- **The native viewer of the remote display.** A principal sees and drives the desktop of a machine from a program of its own on Linux, macOS and Windows that uses gui_toolkit, with the key that it allowed, in place of the peer of the tool. [Design](src/md/features/remote_display.md)
- **The console image answers in Node on COM2.** `modustool browser-machine console` gets a boot run in Node that types a line on COM2 and reads the answer of the console there, so the console page is proved end to end as the desktop page is. [Design](src/md/features/console_renderers.md)
- **The console image on QEMU.** A boot volume of a console image and `modustool run --console` start the console in the terminal of the developer on COM2, with the log of the kernel from COM1 in a file, so a developer uses modus with no window. [Design](src/md/features/console_renderers.md)
- **The console line that never ran under a loaded host.** Once, in a full check on a loaded host, the console of the part `debugger` took the keys of a line and never ran it, while the machine stayed idle with a line of the serial port waiting; the part passes alone each time. The cause is found from the whole log of the next such failure, so a line that a principal types always runs.
- **The record of the console and of a window process on a test machine.** A machine test records the console and a window process, which map their rings and their surface after their start, and replays each alone to its end with no divergence. A developer then knows that a failure of the console or of a window runs again with the same inputs. [Design](src/md/features/record_and_replay.md)
- **A planted `rdrand` and the measures of a record.** A machine test records a module that runs `rdrand` without asking `cpuid`, and its replay finds the divergence; the measures of "The size and the cost" decide the size of a history, the bound of the first layer and the rate of the checkpoints. [Design](src/md/features/record_and_replay.md)
- **The whole machine test on a second holder of the display.** The main scenario and the network scenario wait for the facts of the display contract, not for the lines, the start menu and `compositor.windows()` of our compositor, and the tool takes the place of a window from the contract. A second holder of the display then runs the whole machine test. [Design](src/md/features/roles_and_contracts.md)
- **The rules of the principals in their service.** The rules of the disk grants, the client table of `remote` and the choice of a start policy move to `principals`, which gives the root service each change of a table through `Disk_Rows_Set`, so a fault in those rules is a fault of `principals`, not of the root. [Design](src/md/api/root_service_split.md)
- **Bounded resumable zeroing for 1 GiB frame runs.** Prefaulting a 1 GiB run zeroes in interruptible steps across yields so no kernel section holds interrupts off across 1 GiB, checked by a 4 GiB machine test with `pdpe1gb`, and `Large_Pages` leaves once its callers move to runs. [Design](src/md/features/frames_of_a_process.md)

## Later

- **A plan longer than one line.** A principal applies a plan of a declaration file, whose evaluation process gives its record, so a plan is no longer bound by a line of the console (200 bytes, 4096 with the line editor of `work/limits_text_and_clipboard`) and can name a holder by a name of the catalog. [Design](src/md/features/declarations.md)
- **The other scripts of the Universal Shaping Engine.** Sinhala, Lao and the other scripts that HarfBuzz shapes by USE each take a row, a font of the set and words compared with HarfBuzz, with the topographical features of USE for a font that has them, so a principal reads them in place of the box. [Design](src/md/features/written_shaping.md)
- **No clock in a builder.** The time page is not mapped in the call host of a builder, and a read of the cycle counter traps, so a builder cannot write the time of its build in its output (property 20). [Design](src/md/features/recipes.md)
- **A limit of blocks for each share.** A share that can change gets a limit of its own, so a builder fills its store "out" and not the store of `recipes`, whose oldest versions a full store frees. [Design](src/md/features/recipes.md)
- **The collection of the objects of `recipes`.** An output that no realisation names leaves the place `objects`, so the store of `recipes` does not grow with each build forever. [Design](src/md/features/recipes.md)
- **The pointer through the cursor of the virtual GPU.** On a machine with a VirtIO-GPU, the pointer moves with no frame of the compositor: the device draws it from its cursor queue, so a move costs the host no redraw of the screen. The pointer is a part of each frame today, and of the capture of the screen of `remote_display`. [Design](src/md/infrastructure/whole_frame.md)
- **Builds across paired machines, on the machine.** The root service connects `recipes` to the outbound links of `remote` and gives `remote` the listen grant of each address, so `recipes.build` gives the recipes of a graph to the builders and the caches that a principal paired, and a machine test runs it on two machines. [Design](src/md/features/recipes.md)

- **The elements and the other windows on the layout tree.** The elements of the interface package and the windows other than `monitor` and `settings` take their rectangles from `modus:layout`, so a text that grows, a scale factor or a resize moves each element with no place computed by hand. [Design](src/md/features/box_layout.md)
- **A principal resizes `monitor`.** The window lays out each frame at its size now, but stays fixed: it becomes resizable when its stated budget holds a second surface at its largest size, so a larger `monitor` shows more rows of processes and wider graphs. [Design](src/md/features/box_layout.md)
- **Stored data that survives each change of its type, from 1.0.** Each object of records in a store carries the description of its records, and a module that changes a stored type declares how the data of the release before takes the new form and goes back, so an update keeps the data of a principal. It starts at the preparation of 1.0; before it, a change breaks the old data. [Design](src/md/features/data_evolution.md)
- **A rollback that takes the data back, and the upgrade test.** `plans.rollback()` runs the backward migration of each newer module before the older module starts, and a machine test boots the image of the release before, writes each store, then boots the new image and reads them. It starts at the preparation of 1.0. [Design](src/md/features/data_evolution.md)
- **The log of a module kept by the collector, and its machine test.** `collector` gets its record input `sources`, so `start("server", wire(server.log, collector.sources))` in the console keeps each record of `server`, and a machine test types that line and `log.follow |> where(level = Warning)` and checks that the console never draws its own rows. [Design](src/md/features/log_facts.md)
- **The glyph memory counted in each budget.** The tool counts the glyph memory of each copy of the text rendering that a module carries and that draws, its own and the one of the drawing module, in place of a sum written by hand in each stated budget. Every window then has the pages of its glyphs, a window with no stated budget too, not only the room of the least budget. [Design](src/md/features/text_rendering.md)
- **The ring of counter sets of the counted kernel.** The tool writes several operation sequences ahead, and each counted runner counts into its own set of counters, so the machine waits less for the tool. It comes only if the measure of the loop and of the counted kernel shows that these waits cost more than the sequences. [Design](src/md/infrastructure/kernel_fuzzing.md)
- **Two processors in the kernel fuzzing.** Operation sequences with several threads run on two processors, so the fuzzing reaches the lock order and the wakes between processors. [Design](src/md/infrastructure/kernel_fuzzing.md)
- **The kernel procedures that a fuzzing run reached.** A run of `fuzz operations` names the procedures of the kernel that its kept inputs reached first, from the listing of the counted kernel, so a developer sees which code of the kernel the fuzzing reaches and which it never reaches. [Design](src/md/infrastructure/kernel_fuzzing.md)
- **The bound by memory for `nix flake check`.** A developer who runs `nix flake check` with no `--max-jobs` gets the count of part derivations that the configuration of Nix gives, which can be far above what the memory of the host holds; the check then gets the same bound as `modustool screenshots`, so a swapped machine never fails a step. [Design](src/md/infrastructure/full_check.md)
- **No defence against a cut int1 once the hosts run Linux 7.3.** The kernel stops reading the bytes of a process at a debug exception with no status, when every host of the test machines runs Linux 7.3 or later, whose KVM no longer gives a cut `int1` again. A debug exception then costs no read of the process, and the kernel keeps no rule for one bug of one hypervisor.
- **A machine test of write-combining device memory.** A test part maps device memory with `Write_Combining`, checks each refusal (normal memory, a screen, `Execute`, a live mapping with no cache over the same frames) with its status, its error record and no change of the mappings, checks that a map that fails after its claim of the cache type gives the count back, and reads the flag `Write_Combining` in the report of the mappings; host tests check the rules today. [Design](src/md/features/gpu_access.md)
- **A guest that runs a whole system.** A guest gets several guest processors, an interrupt that its process injects, long mode, memory at the guest address 0, and memory that it writes and then executes. A process can then run a kernel of another system in it. [Design](src/md/features/guest.md)
- **No memory object writable and executable at once.** The kernel refuses a mapping with Write of a memory object that another mapping executes, and the reverse, in one process or across processes and guests, so property 11 holds for each object and not only for each page table entry. [Design](src/md/features/guest.md)
- **Linux in a guest with its disks and its network.** The shell of `linux` gets a disk that keeps its files and a network that goes through the grants of the process, so a principal runs the programs of Linux on its own data. [Design](src/md/features/linux_shell.md)
- **Several guest processors for Linux.** The machine of a Linux guest gets a local APIC and the table that Linux reads to find it, so a guest runs on more than one processor, as many as the threads of the budget of its process. [Design](src/md/features/linux_shell.md)
- **A guest image in the store of a principal.** A principal puts a kernel and an initial archive in the store of `linux` from the network or from a recipe, so the shell starts on any machine, not only on the disk that the test writes. [Design](src/md/features/linux_shell.md)
- **Processes of NT.** A process of NT runs through Wine inside the Linux guest, with no work of its own in the system. [Design](src/md/features/foreign_systems.md)
- **Acceleration by the virtual GPU of the test machine.** A back end of the drawing module draws the draw table through the WebGPU subset of the system, over Vulkan to the host through Venus. The GPU then draws the windows and the pictures, and not the processor. [Design](src/md/features/gpu_access.md)
- **The answers of the Vulkan of the host through Venus.** The system reads the replies of the Vulkan of the host and streams its commands through the shared ring of the virtual GPU of the test machine, checked by an opt-in machine test under QEMU with Venus. [Design](src/md/features/gpu_access.md)
- **Several principals on one machine.** More than one named principal uses a machine, each with its own session, its own stores and its own keys, and none reads the data of another. The capacity grows only after each shared place of the system has a scope. [Design](src/md/features/several_principals.md)
- **One identity for each machine.** The machine identity key comes from the machine key, so the TPM roots it, and `remote` and `remote_display` present it in place of a key for each start. A client then pins one key for the life of the machine. [Design](src/md/features/several_machines.md)
- **Two machines paired by a code.** A principal shows a pairing code on one machine and types it on the other, and each machine then accepts the other by its identity key, with no discovery on the network. [Design](src/md/features/several_machines.md)
- **Several frames of an object in flight.** The client of an object cache sends the requests of several frames before it reads their answers, so a round trip of 50 ms no longer bounds one connection to 20 MiB/s. [Design](src/md/features/recipes.md)
- **A put to an object cache that resumes.** An upload that ends halfway resumes at its last frame, with a proof of each frame from an outboard that the client writes, so a release disk does not start again from its first byte. [Design](src/md/features/recipes.md)
- **Blobs past 16 MiB in a browser machine.** The page of a browser machine fetches a blob in object frames with their proofs, so a blob past the 16 MiB that one fetch holds in memory reaches the machine. [Design](src/md/features/browser_machine.md)
- **Objects by hash from a paired machine.** A machine takes the modules, the trees and the realisations of a plan from a paired machine, as from an object cache, so a second machine of a principal builds nothing that the first one built. [Design](src/md/features/several_machines.md)
- **One principal on several machines.** A principal joins a second machine with keys made and sealed there by the TPM, and a machine list that its root key signs, kept offline, makes each of its machines know the others; a lost machine is removed from all of them at once, with no change of the identity of the principal. [Design](src/md/features/several_machines.md)
- **A role held on another machine.** The plan of a principal gives a role, such as the storage, to a paired machine, and a client sees the same contract, with a stated outcome when the link breaks. [Design](src/md/features/several_machines.md)
- **One store on two machines.** A principal writes one store on two machines with no link, and the machines merge their versions when they meet, with each conflict kept in the store until the principal resolves it once. [Design](src/md/features/several_machines.md)
- **A grant signed for a principal of another machine.** A principal shares an object or a role with another principal by a grant that its signing key signs, with a life of at most one day or a revocation list, and the receiver connects to it from its own machine with no account on the machine of the giver. [Design](src/md/features/several_machines.md)
- **A relay for machines behind a NAT.** Two paired machines that each sit behind a NAT reach each other through a relay that carries their encrypted datagrams, so a principal needs no forwarded port. [Design](src/md/features/several_machines.md)
- **Every window uses the interface package.** The windows of the processes that still draw by themselves are built from the elements of the interface package. Each window then has the same look, the same keys and the same damage rules, and its text is drawn at the size of the screen at each scale, not as the pixels of a hand picture. [Design](src/md/features/desktop_to_browser.md)
- **LLVM 22.** The build uses LLVM 22, with a measure of the speed of the code before and after. LLVM 22 has the fix of the order of dead store elimination, so the flake then builds no LLVM of its own. [Design](src/md/infrastructure/llvm_of_the_build.md)
- **A machine test of the pins of the TPM.** A machine with a software TPM and Secure Boot whose record of the machine key is replaced, removed or rolled back, and whose file of a principal is put back to the file of before a change of the passphrase, between two starts, shows each refusal on a real TPM; today host tests prove the rules and the commands. [Design](src/md/features/tpm_sealed_machine_key.md)
- **The TPM floors kept against code with the TPM.** The storage hierarchy of the TPM gets a random authorization value, sealed in the record of the machine key under a storage key that the TPM keeps, so another system on the machine can no longer remove a floor and start an older signed system that then keeps its own numbers as the floors, nor remove the pin of a record and put back an older one. It comes before the signed seal, and leaves open a compromise of the code that holds that value, the kernel or the TPM service, and a change of PCR 7. [Design](src/md/features/tpm_sealed_machine_key.md)
- **An update of the system that keeps the seal of the machine key.** The machine key is sealed to a policy that an ECDSA P-256 key of the publisher signs and the TPM verifies, with the version floor of the TPM, so a new system opens it with no recovery key and an older system still opens nothing. It waits for the authorization value of the storage hierarchy. [Design](src/md/features/tpm_sealed_machine_key.md)
- **The TPM floors kept across a change of PCR 7.** The policy of a floor names a key of the publisher (`TPM2_PolicyAuthorize`) in place of the value of PCR 7, so an update of `dbx` or of the firmware no longer lets one older signed system start and make its numbers the floors. [Design](src/md/features/rollback_floors.md)
- **The network libraries become modules.** TCP, QUIC and the cryptography are loaded one time and imported, as the drawing module is. One correction then reaches every process that uses the network. [Design](src/md/api/library_modules.md)
- **A processor time that the other processes do not set.** The processor time of a process is an amount that its budget holds and divides among its children, as its log records are. A thread then cannot learn from its own share that a sibling ran. [Design](src/md/features/log_side_channels.md)
- **A resolution and a scale that the principal chooses.** The principal sets the mode of the display and a scale of the interface, and every window draws at that scale. [Design](src/md/features/desktop_to_browser.md)
- **The rest of the HTML algorithm of the WHATWG.** A process reads into the tree that the WHATWG defines the parts of a page that the parser does not read yet: SVG and MathML, `template`, `select`, `frameset`, the quirks mode, the escaped data of a script and the whole table of named references. [Design](src/md/features/desktop_to_browser.md)
- **A light web browser, one process for each origin.** A principal reads pages of documents, follows links, goes back and sends forms, and a page of one origin reads nothing of another. [Design](src/md/features/desktop_to_browser.md)
- **3D on the processor, through the WebGPU subset.** A process draws 3D with no GPU through the same buffers, pipelines and draw calls as on a GPU, with a fixed set of shaders in Odin with SIMD, so only the back end changes when a GPU comes. [Design](src/md/features/desktop_to_browser.md)
- **The configuration space of one device, by its own page.** The core maps the memory of the configuration space (ECAM) and gives each device service a handle of the page of its own function only, so a device service reads its own registers with no access to the ports that the core keeps. [Design](src/md/api/root_service_split.md)
- **grid_terminal draws through the draw table.** The grid of the console draws its characters and its fills through the draw table of the drawing module, as each window does, once a measure shows its cost against the direct path, so a grid on a GPU costs no work of the processor. [Design](src/md/features/console_renderers.md)
- **Device services for the devices of a real machine.** The root service starts the device service of each device by its identity, and a principal grants a device service from the disk for one device. [Design](src/md/features/device_services.md)
- **Odin modules of other projects on the system.** A module written for the core library of Odin runs on the system, with its files in its private store. [Design](src/md/features/desktop_to_browser.md)
- **gui_toolkit, the toolkit of rich modules.** Each application of the toolkit runs in a window of the system as an outside module, and a developer writes a rich module with it. [Design](src/md/features/desktop_to_browser.md)
- **The browser wren whole in a Linux guest.** A principal runs wren, with no port, in a Linux guest that shows it in a window of the system. [Design](src/md/features/desktop_to_browser.md)
- **Language tags read at the check of the line and against CLDR.** A line with a wrong literal tag in `language(...)` fails before any call runs, and the border checks each subtag and each alias against the validity data of the pinned CLDR. [Design](src/md/features/interface_language.md)
- **Interface messages in English.** Each sentence of a window, of the console and of a log fact is an interface message of its package, compiled at the build with its typed variables from a message resource in the pinned form of the W3C draft, so English writes "1 block" and "2 blocks" and no process parses a template. [Design](src/md/features/interface_language.md)
- **Language packs and fonts from the cache.** A machine fetches the language packs and the fonts that the plan of a principal names, by hash, so it holds only the languages and the scripts of its principals. [Design](src/md/features/interface_language.md)
- **The assistive role.** A screen reader, a magnifier or a switch input reads the semantic tree of each window through the compositor, moves the focus and acts on an element only by an action that the element declares, with a mark in the bar while it reads. Any module that passes the conformance suite can fill it. [Design](src/md/features/accessibility.md)
- **The semantic tree to a remote viewer.** The native viewer of the remote display gives the trees of the machine to the screen reader of the machine where it runs, so a principal who does not see hears a remote desktop with its own reader. [Design](src/md/features/accessibility.md)
- **A step back in the debugger.** The debugger replays a history from checkpoints, steps back one instruction or one line, and finds the last write of a variable, from the console and from its window. [Design](src/md/features/record_and_replay.md)
- **The replay of a failed part of the full check.** A machine test records the processes that its start list marks, and `modustool replay <part> <process>` replays the failure of a part on the host, so a fault that came once under a loaded host is read to its cause. [Design](src/md/features/record_and_replay.md)
- **Interrupts placed by the branch count.** An interrupt becomes an input point, placed by the count of the retired conditional branches, so a recorded thread that runs long with no kernel entry keeps its history and several threads switch at any instruction. [Design](src/md/features/record_and_replay.md)
- **The restart group and the ranks of the start.** The root service starts a holder again with the processes that hold one of its rings in their context, and the tool refuses a role table where a holder depends on a holder of a later rank. [Design](src/md/features/supervision.md)
- **The time of a service charged to its client.** A service runs the calls of each client on a work thread paid by the budget of that client, and runs only the bounded shared step on its own thread in the order of the step debt, so a client that spends its time delays only its own calls. [Design](src/md/features/work_accounting.md)
- **The numbers of the work of services in the report of a process.** `work(process)` shows, for each connection of any process, the pages and the processor time that the service spent for it and its step debt, from the work budget that the root service reads and the snapshot that the service writes. [Design](src/md/features/work_accounting.md)
- **The class protocol of the display.** A display device service serves a scanout, its modes and a change of the mode, so the compositor runs on any display with no change, and a browser machine follows each resize of its page. [Design](src/md/features/device_services.md)
- **The software processor on the host.** A part of the kernel runs the x86-64 code of the modules through the page tables of the kernel, with host tests and a fuzz target that compares it with the processor of the host, and the tool checks that each instruction of each module of the image is one that it runs. It is the processor of the browser machine. [Design](src/md/features/browser_machine.md)
- **modus in a web page, on one processor.** The kernel built for WebAssembly starts the boot image of the release in a page, from a signed description, to "the machine is usable", and a machine test part runs on it through a headless browser. A reader then runs the system with nothing to install. [Design](src/md/features/browser_machine.md)
- **The desktop in a web page.** The screen of a browser machine is a canvas at the pixels and the scale of the display, that changes its mode at each resize of the page, with the keys and an absolute pointer, and the pictures of a scenario equal those of QEMU. A reader then uses the desktop and the console in the page. [Design](src/md/features/browser_machine.md)
- **The browser machine on the site.** Each release has a page that starts it, and a guide embeds a console of modus beside its text, so a reader tries what the guide explains. [Design](src/md/features/browser_machine.md)
- **The holders of the boot image read only checked files on a page.** On a browser machine the root service hashes each file at its first load or give, but a process with the grant `Image` (the console, the log service, the manual) reads the tables of modules that nothing checked yet; each read of such a holder then waits for the hash of its file, as a load does. [Design](src/md/features/browser_machine.md)
- **The compiled tier of the software processor.** A page starts the console and the desktop in a fraction of the time of today: the decoded blocks that run often become modules of WebAssembly. With the decoded blocks, the emulated vector forms are about 40 % of the start of the console image in Node, and the step of each instruction and the decode of its ModRM byte most of the rest. [Design](src/md/features/browser_machine.md)
- **Several processors in a browser machine.** The processors of a browser machine are workers on one shared memory, so the threads of a page run in parallel. [Design](src/md/features/browser_machine.md)
- **The object cache device of a browser machine.** A process of a browser machine asks the page for a blob or a realisation by its hash, and a service checks the bytes and gives them to `recipes` and to the loader, so a page takes a module or an output from an HTTPS object cache with no relay. [Design](src/md/features/browser_machine.md)
- **A service connection through the powerbox.** A process asks for a connection to a service of a table of requestable services, which shows the caller its own data only, and the principal keeps or refuses it in the grant dialog. [Design](src/md/features/powerbox.md)
- **Grants of the powerbox kept for a module.** "Always for this module" keeps the items that the principal kept in the disk grant table, bound to the hash of the module, and "never ask again" keeps a refusal, so a disk process asks once across restarts. [Design](src/md/features/powerbox.md)
- **The difference of a plan on the trusted display.** `plans.apply` shows the difference of its grants on the trusted path as one screen, which the principal accepts whole, so a console that an agent drives cannot accept a grant. [Design](src/md/features/powerbox.md)
- **The console asks before a call.** A line that calls an export with a Handle parameter and no value for it asks the powerbox, with the console as the asker, and lends the handle that the principal chose for that call only. [Design](src/md/features/powerbox.md)
- **The agent console, the processes, the log and the stores of a wide grant.** An agent runs lines in a console whose start grant set holds only the scopes that the principal kept, starts and stops the processes picked, reads the log, and reads or changes the stores picked. [Design](src/md/features/wide_grants.md)
- **Acts of an agent that ask each time.** A scope set to ask each time makes each act of the agent wait for the principal in a grant dialog, as the stop of a process or the change of a store. [Design](src/md/features/wide_grants.md)
- **The screen, the keys and the pointer in the lines of an agent.** An agent sees a frame of the screen, types and points in the windows that the principal picked, and waits for the next frame of a window, each as a line of a step. [Design](src/md/features/agent_code_mode.md)
- **An agent edits, builds and runs a project.** An agent reads a source of a project, replaces a text in it, builds an output, runs it and reads its log, in a loop of steps, within the stores and the processes that the principal picked. [Design](src/md/features/agent_code_mode.md)

## Maybe

- **Builds of other callers while one build runs.** The service `recipes` serves one call at a time, so a call waits for the build that runs, up to its bound. Two ways are open: a thread of the service for each build, which waits for a budget of threads, or builds queued with an answer at their end, which waits for an answer that comes after the call.
- **Guest memory that switches between Write and Execute by the page.** Code and data of a guest in one region then switch no more at each change of access. Two ways are open: smaller regions, which the 128 mappings of a process bound, or a switch of each page by the kernel at its nested fault; each waits for a measure of the switches of a Linux boot in the guest builder. [Design](src/md/features/foreign_systems.md)
- **Console lines kept and run again, as scripts.** A principal keeps lines in the store and runs them again in a console, which reads them as its own input, as it reads the keys of the principal and an agent console reads the lines of an agent, and calls the functions with typed values: no export evaluates a line for another process. Two ways are open: a kept line that the console of its principal runs again, which waits for a user who repeats lines; and a console with no terminal that a starter runs on a list of lines, which waits for a task that needs no person at the keys.
- **An environment and arguments built for a ported module.** A ported module reads `HOME`, `LANG` or `argv` from a layer that builds them from its start record, in place of a change of its code. Two ways are open: each port adapts its code to the handles, the settings and the values of the context, which is the rule today; or one layer for ported modules only, which waits for the first ports and what they read. [Design](src/md/features/desktop_to_browser.md)
- **An auto_cast to a type that is no enum, past the check of the casts.** The check of the casts refuses each `auto_cast`, because the syntax tree does not hold its target, and it would accept one whose target is no enum. Two ways are open: the types that the compiler infers, which wait for an output of `odin check` that names the type of each expression, or a type checker in the tool, which waits for a need of the system that a written conversion does not meet. [Design](src/md/infrastructure/choice_constants.md)
- **A machine case for the refused ring words of the frame and palette rings.** The frame service and the palette provider of the console show on a machine that they answer the refused words as their host-tested borders decided. Their one writer is the network service or the compositor, so two ways are open: a test module that holds their ring, which waits for a choice to give a test module the grant `Network_Device` or the place of the compositor; or a test build of the writer that sends the words, which waits for a choice to put test code in a module of the system. [Design](src/md/infrastructure/choice_constants.md)
- **A handle table larger than 128 for the root service.** The root service names more processes at once than its table of 128 handles allows, past the prepared modules, which now give their handles back before each start. Two ways are open, a table of the size of a role, named at the start and paid by the budget, or a table that grows with the budget up to a bound of the kernel, and both wait for a run whose measure of the root tables shows the handles of the processes alone near 128, and for the measure of the kernel memory of a larger table. [Design](src/md/features/module_outputs.md)

- **A guest on a machine with an Intel processor.** A process runs a guest on a machine with an Intel processor too, with the same operation and the same exit records as on AMD. One way is open, and it waits for a host with an Intel processor: QEMU emulates no VMX, so only such a host runs the machine test of it. [Design](src/md/features/guest.md)
- **The release image started on a real machine.** The image starts from a USB key on the UEFI firmware of a real machine, with the certificate of the publisher enrolled, Secure Boot on and the machine key sealed by its TPM. One way is open, and it waits for a real machine with a TPM and a USB key: today the image starts in the machine test only, on the firmware of QEMU. [Design](src/md/infrastructure/release_image.md)
- **A whole frame on the display of a real machine.** The compositor flips its screen pages on a real display too, writes the page that the display showed only after its next vertical blank, and writes the pixels through the write-combining entry of the page attribute table of the kernel, which `Display_Memory` and the framebuffer of the firmware then use, and not through the memory type that the firmware chose. One way is open, and it waits for a real machine whose display offers a page flip: today the flip uses the display registers of the standard VGA of QEMU, whose flip takes effect when its write returns. [Design](src/md/infrastructure/whole_frame.md)
- **Acceleration by a real GPU.** The draw table is drawn through WebGPU on a real GPU through a driver domain, so the GPU draws the windows and the pictures of a real machine. One way is open, and it waits for a real machine with a GPU and an IOMMU: QEMU gives a virtual GPU only. [Design](src/md/features/gpu_access.md)
- **A remapping unit that the firmware left with its queue of invalidations on.** The kernel takes over the queue of such a unit, so the unit runs with the IOMMU on, where today it leaves the IOMMU off. Two ways are open, a real machine whose firmware leaves the queue on or a firmware for the test machine that turns it on, and each waits for that machine or that firmware: QEMU has no option for it. [Design](src/md/infrastructure/iommu.md)
- **A thread stopped at the limit of its budget, not at the next tick.** A thread that reaches the limit of its budget stops at that moment, not up to one tick later. One way is open, a timer of each processor in the TSC deadline mode set to the earlier of the next tick and the time left in the budgets of the thread, and it waits for a need: the next period already takes back what a budget used past its part. [Design](src/md/features/stolen_time.md)
